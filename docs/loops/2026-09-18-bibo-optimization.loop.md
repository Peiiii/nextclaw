- 文档类型：`.loop.md` 试用合同；创建于 2026-09-18，中文正文、日期前缀、英文 kebab 主题与 `.loop.md` 后缀。
- 范围：Bibo 官网的视觉、角色表达、信息理解与交互体验。
- 文档性质：可重复执行的设计合同；只在目标、规则或边界改变时修订，不承载运行状态。
- 关联：[产品愿景](../VISION.md)、[产品设计](../designs/2026-09-18-bibo-public-surface.design.md)、[部署与候选版本](../../apps/bibo-camera-site/README.md)。
- 运行日志：[首批 Pilot](../logs/v0.56.2-bibo-loop-pilot/README.md)。每个新执行批次按既有迭代日志规范建立独立记录；设计与日志相互引用。

## 1. 目标与适用边界

核心产品表达：Bibo以用户这个人为持续关注对象，理解任务、项目、未成形想法、讨论、调研、设计、近期日程、学习、资讯与长期方向之间的联系。具体执行只是参与方式之一；帮助想清楚、提出相关问题、更新理解和尊重节奏也是结果。不能再把“收到任务→完成交付”的故事当成整个产品，也不能用堆功能清单替代整体理解。

每批至少证明同一人的两个不同上下文之间为何有关联，并保留一个尚未变成任务的想法或讨论；选择少数真实可理解的关联，不要求每帧塞入所有领域。“全局”指关注范围，不意味着全量数据访问或无边界行动。晋升前检查：遮掉任务执行后，还能否看出这是长期个人搭档？若不能，返回选题，不仅换任务皮肤。

宣传目标：在有限注意力内，让尽可能多的潜在用户理解与自己有关、真实可信的Bibo价值，产生继续了解的意愿。方法复用[产品叙事Skill的有效吸引门](../../.agents/skills/nextclaw-product-blog-storytelling/SKILL.md#宣传内容的有效吸引门)。视觉与故事完整性是基础，不能代替有效吸引。

每轮选题先记录“共同处境→核心价值→具体证据→继续动作”，同时说明可能覆盖/遗漏哪些用户（假设，不编比例）。场景只负责证明，不限制产品定位；允许推翻题材，不能只把普通内容越包装越完整。验证分为AI能证明的内容/交互事实与需要真实访客判断的兴趣，不以自评声称吸引更多人。

让 Bibo 官网在整体设计、品牌记忆与互动叙事上产生明显跃迁，让访客感到这是一个能干、机灵、值得一起做事的 AI 搭档。每轮产出一个可体验、前后差异显著的整体设计实验；用户不需要逐轮催促。局部可用性修复只是实验的质量底线，不能代替这一目标。

### 内容与交互协同门

- 每轮先写清“访客应理解的一个价值 → 故事中的具体证据 → 访客动作 → 角色回应/结果”。文案、场景、动效和操作共同验证这个命题，不能分别润色后拼接。
- 从访客处境选题：他为什么需要搭档、交代了什么、哪些个人背景影响判断、搭档替他推进了什么、结果如何帮助下一步。具体内容必须支撑品牌主张；不把“懂你”“持续做事”仅当口号。
- 每輪必须同时改变信息表达与承载该信息的交互或场景结构；文字量、动画数量、视觉冲击不是收益证据。交互应揭示原因、体现协作或交付结果，避免仅为好玩增加操作。
- 验证首屏身份与用途、完整故事因果、动作与反馈含义、结果价值和能力真实性。预设数据、模拟天气/路线、未上线能力必须清晰标注；无用户研究时只报告 AI 内容审查结论，不声称理解率提升。
- 单轮记录与批次概览同时说明内容变化、交互变化以及二者如何相互证明；只换文案或装饰性动画不计一轮。已有视觉收益须保留，内容升级不增加长篇功能墙。
- 角色动效与内容反馈一同验收：观察起势、接触、跟随与收势是否协调，避免匀速平移和互不关联的机械晃动；动作服务当前故事含义。保留减少动态效果与输入可达性，不用增加动画数量证明自然。

### 整体设计要求

- 选题先审视整页构图、角色与界面的关系、故事推进和情绪节奏；不得因为键盘、间距、字号等问题更容易证明就优先拿它们凑轮次。
- 一个假设可以覆盖整页和多处协同改动，例如“让整个页面成为角色操控的故事相机”；最小范围指验证该整体命题所需的完整范围，不等于最小 diff。
- 每轮至少在整体构图、视觉语言、叙事结构、核心交互中的一项形成实质变化，并说明其它层如何配合；单独换文案、补手势或修按钮不算设计轮次。
- 用同视口前后截图与真实交互对照回答：第一眼变化在哪里、品牌是否更独特、搭档价值是否更清楚、趣味是否来自角色参与。功能通过不能代替设计判断，也不虚构审美得分。
- 允许为视觉假设提出原型、尝试更大改动；紫色平面角色、双手搭相机和单一搭档定位保留，页面布局、比例、配色关系、场景图形及过渡可重做。不得退回写实硬件、长篇功能墙或多候选切换官网。
- 每批交付逐轮概览、同尺寸前后图、可恢复候选和体验入口。明确指定三轮时跑三轮设计实验，失败轮如实放弃；预算或真实阻塞可中止，不能把三个维护修复称为完成三轮设计。

本文件不预先安排具体优化方案。每轮改什么由观察和比较产生。运行本 loop 不以改动数量、轮数、动画数量或自评分上涨作为成功标准。

品牌目标沿用用户已表达的方向：一个能干、机灵、有辨识度的个人 AI 搭档；非写实；整体体验有趣、协调；少量文字传递关键价值，避免文档或 PPT 式平铺。不向访客突出底层 NextClaw 品牌，不把概念演示包装成已可使用的真实 AI 能力。

当前受众假设按用户反馈优先关注二十至四十岁人群，选题仍须说明具体需求，不能由年龄推断所有人偏好。已否定的“妈妈走不远/看海”故事不再用于新候选。主快门保持末帧回首帧的连续循环；结果详情仅在相机画面内部按需展示，展开时外部主控仍可操作，不用全局模态结果窗打断体验。

用户已认可的紫色形象与相机方向作为起点。它们是需要保护的已有收益，不永久冻结每一个细节；改变核心方向时先交用户判断。七版独立源码保留，不增加候选切换器。

## 2. 启动条件与权限

文档落盘或用户 Review 不等于启动。用户明确要求按本 loop 执行时，才建立执行批次。

启动时记录：批次编号、活动 worktree 与分支、源码基准、线上部署标识、基准截图、预览入口、预算模式与起点、上限、最大轮数、现有发布授权范围。沿用本会话仍适用的授权，不重复索要；有冲突时以用户最新限定为准。授权不因上下文压缩而丢失。

参数缺省时采用“单轮校准批次”：最多一个假设、一次返工，不委派、不生图、不部署实验候选。该模式只限制工作量，不宣称具备 Token 硬上限。需要严格 Token 上限而环境不能提供对应计量与中止时，先说明能力缺口，不以轮数冒充 Token 限制。

连续优化指当前获准执行批次内持续推进；不隐含定时任务、无人值守无限运行或未来自动唤醒。

### 首批 Pilot 建议

首次运行同时验证这套 Loop 是否提高质量和 Token 效率。用户明确采用本 Pilot 时使用下表；只授权运行而未指定模式时使用上文单轮校准。实际选定值写入批次日志：

| 参数 | 建议值 |
| --- | --- |
| 最大轮数 | 3；每轮一个假设、一个候选、最多返工一次 |
| 停止规则 | 连续两轮无可保留改善时提前停止 |
| Agent | 单 Agent，不委派 |
| 生图 | 默认关闭；现有 HTML/CSS/SVG 无法验证假设时才评估 |
| 实验发布 | 只进入隔离本地预览，不逐轮覆盖生产站 |
| 预算 | 周额度使用率最多增加 5 个百分点的软上限；开始时重新读取起点 |
| 预算分配 | 约 4 个百分点用于探索，至少 1 个百分点留给验证、恢复和交付 |

周额度统计可能延迟，也可能包含同一账户上的其它任务，因此它只能作为保守停止信号，不能证明本批的精确 Token 消耗。并发时不能将差额归因于本批，但仍保留账户软停止阈值与轮数上限；统计失效或跨重置窗口则停止探索并记录缺口，不能自动重置预算。

收到执行授权后，由 Agent 自主在批次 README 建立基准、记录参数并将批次状态置为 `active`，再开始候选实现，不另加激活审批。只读基准观察属于初始化；合同本身不切换运行状态。

## 3. 最小循环

```text
读取目标 + 最佳版本 + 上轮结论 + 剩余预算
  → 观察真实页面
  → 更新问题队列，选择一个最高价值问题
  → 写出假设、成功/失败条件与最小实验范围
  → 检查预算，决定是否进入实现
  → 在隔离预览制作一个候选
  → 定向验证 + 与最佳版本对照
  → 保留 / 返工一次 / 放弃
  → 更新简短记录
  → 检查继续条件；继续或交付最佳结果
```

每轮围绕一个整体体验假设。实现可协同重做必要的构图、角色动作、场景、文案和交互；可用性修复随候选完成，不单独计作设计轮次。

同一个 Agent 依次承担观察、实现、验收视角。不得把这些视角包装成独立评委或真实用户反馈。

## 4. 各阶段的进入与退出条件

| 阶段 | 必须得到的结果 | 不满足时 |
| --- | --- | --- |
| 观察 | 具体画面或操作路径、可定位的问题证据 | 不凭“还不够高级”启动开发 |
| 选题 | 说明整体感知的缺口，达到设计跃迁门；说明预期体验与验证成本 | 重选整体命题，不用小修小补替代 |
| 假设 | 价值→内容证据→动作→回应的整体因果判断，完整范围与内容/交互成功失败条件 | 不写代码；最多一次补充分析 |
| 实现 | 一个可运行候选和明确差异 | 超预算或持续扩大范围则保存状态并停止实验 |
| 验证 | 行为证据、前后对照、回归检查、主观判断及其不确定性 | 不晋升最佳版本 |
| 决策 | 保留、返工或放弃，附理由 | 无明确改善默认保留旧最佳版本 |

候选晋升必须同时满足：目标问题得到具体改善；没有损害已认可的优点；关键行为正常；新增复杂度与收益相称。不能靠提高自评分或降低原验收标准晋升。

主观审美由 Agent 给出有依据的暂定判断，最终偏好由用户 Review；功能、状态与资源正确性由 Agent 自验。无真实访客证据时，不声称转化率、理解率或用户喜爱程度提升。

## 5. Token 与成本约束

### 预算模式

1. 有可用硬预算执行器：使用其支持的计量单位与中止机制，并记录统计口径；不得承诺比工具能力更强的上限。
2. 仅有消耗统计：采用软预算，明确统计范围、延迟与可能超额；到检查点主动停止。
3. 无可靠计量：使用单轮校准或用户指定的轮数/时间边界，报告 Token 不可测，不估造精确账单。

账户周额度百分比不能直接换算成固定 Token。模型用量、缓存输入、输出及工具成本可能使用不同口径；额度、Token 和费用不得混称。

有绝对 Token 总预算 B 时，默认仅用 80% 探索，20% 留给验证、恢复和交付。普通轮次初始上限为 B 的 20%；这只是软分配策略，不能覆盖全局硬上限。任何候选开始前都要预留完成验证与安全恢复的余量，不能先耗尽预算再要求追加。

只在批次开始、进入候选实现前、轮末检查消耗；统计有明显延迟时保守处理。计量成本也计入预算，不为省 Token 建立高频统计流程。生图等独立费用在使用前另做价值判断，默认关闭，确有必要才使用。

### 抑制浪费的默认动作

- 单 Agent，不创建并行审查组。只有用户明确允许且预期总成本净节省时才考虑一个有边界的子 Agent；多 Agent 成本计入同一总预算，不能另开预算池。
- 已读且未变的规则、代码和材料不重复全文读取；按路径和差异定向搜索，限制输出大小。
- 每轮最多实现一个候选。路径明确时不机械生成多套方案。
- DOM/状态用于行为检查，截图用于视觉判断；按受影响布局选择代表性尺寸，稳定后统一检查必要回归。
- 优先本地预览，失败候选不反复云端发布；不引入与本轮无关的依赖、框架或基础设施。
- 使用事件或有界等待，禁止无变化的密集轮询；进度只说新发现和下一步。
- 同一假设最多返工一次。失败理由入记录，后续无新证据不得换个名称重试相同方案。
- 记录几行结论即可；不生成长篇自评、逐轮演示文稿或多份重复日志。

## 6. 状态与记忆

设计与日志分开，复用 `docs/logs/v<semver>-<slug>/` 的版本规则；明确执行本合同即需要可追踪批次，不在 `docs/loops` 下另建运行目录。

| 载体 | 唯一职责 |
| --- | --- |
| 本 `.loop.md` | 目标、边界、循环与预算规则、验收和停止条件 |
| 批次 `README.md` | 所用合同链接与版本、授权、活动 worktree、批次状态、预算起点与实耗、当前最佳、问题队列、轮次索引和下一步 |
| `work/YYYY-MM-DD-bibo-round-NNN.md` | 一轮的问题、预设判定、尝试/返工、证据和决策；日期为轮次开始日，返工不另开轮次 |
| 批次 `evidence/` | 命名带日期/轮次的必要截图、对照或快照，通过相对链接引用 |

批次沿用现有迭代 README 六个章节；进行中的批次明确标注未完成。合同版本使用 commit；未提交修订保存只读快照或补丁，运行中修订不得悄悄覆盖旧轮次依据。每轮开始实现前先记录假设与判定，完成后补结果；已结束轮次的纠错追加说明，失败记录同样保留。事后补录标明证据来源和未知，不伪造执行时间或先验判断。

基准同时记录源码 commit 与 Cloudflare 部署标识；无法查询标识或验证映射时，记录未知与实际线上证据，不凭 HEAD 推断生产内容。批次 README 记录活动 worktree 与分支；结果落盘不等于提交或远端持久化。

单轮记录模板：

```text
轮次 / 基准：
问题证据与假设：
内容信息 / 交互动作 / 两者的因果联系：
成功 / 失败条件：
最小改动与预览：
验证证据 / 主观判断：
决策：保留 | 返工一次 | 放弃
已用预算 / 剩余预算 / 计量限制：
下一步或停止原因：
```

“最佳版本”不等于“最近一次修改”。候选通过前，必须有明确可恢复的基准；恢复仅触达本任务文件，不覆盖其它任务改动，不使用破坏性 Git 操作清理共享工作区。

中断或压缩后，先读本合同、批次 README 与最近相关轮次，核对实际文件、版本和预览状态，不默认加载全部历史。不能把未验证候选当最佳版本，也不能重置已耗预算或重复已完成检查。

## 7. 继续、停止与交付

仅当存在有证据的高价值问题、存在未被否定的新假设、预算足够闭合一轮时继续。

出现任一条件即停止探索：用户叫停；达到约定上限；剩余预算不足以完成下一轮及验收；连续两轮无可保留改善；找不到值得验证的问题；遇到无法独立解决的外部阻塞；需要改变用户已认可的核心方向。

停止探索后，使用预留预算恢复稳定状态并交付。不得为了达到轮数制造改动，不以“永远还能更好”为理由持续运行。停止原因是预算或阻塞时，不宣称质量目标已经完成。

交付一次给齐：最佳版本入口、保留的关键差异、放弃的尝试与原因、实际验证范围、未解决问题、实测成本或计量缺口、停止原因。没有改善时直接交还原最佳版本。

实验验证与正式发布分开。达到交付条件后按本会话有效授权及仓库交付流程执行；不得把每轮实验直接覆盖线上。是否需要提交、部署、changeset 或产品文档由实际候选和有效授权判断，不因 Loop 文档类型跳过交付合同。

## 8. 对 Loop 机制的复盘

首批 Pilot 同时验证网站结果和 Loop 方法。批次结束时只回答以下问题，不另写长篇报告：

| 观察项 | 判定证据 |
| --- | --- |
| 质量收益 | 至少一个候选解决了预先记录的问题，并通过前后对照晋升；没有改善也如实成立 |
| 选择效率 | 实际实现的候选都来自有证据的问题，没有为凑轮数制造方案 |
| 成本控制 | 在约定检查点记录用量或计量缺口，没有因反复读取、重复验证或多 Agent 明显浪费 |
| 连续性 | 中断后能由合同与批次日志恢复基准、已耗预算、最近决策与下一步，没有重复实验 |
| 判断可信度 | 主观审美、功能事实和真实用户证据明确分开，没有把 Agent 偏好包装成用户结论 |
| 治理负担 | 记录足以恢复任务，但维护成本没有超过实验本身；若超过，下一版应删减字段或频率 |

复盘只允许基于本批真实记录调整全局 `.loop.md` 规则。单次感觉、未发生的风险或为了显得完备而增加的字段，不上升为通用机制。

## 9. 对 Loop 本身的验收

| 场景 | 预期行为 |
| --- | --- |
| 用户要求文档化但未启动 | 只产出待 Review 文档，不修改官网 |
| 候选视觉更花哨但遮挡操作 | 不晋升；返工一次或恢复最佳版本 |
| 无明显改善，但尚有预算 | 可以停止；预算剩余不构成继续理由 |
| 连续两轮失败 | 交付最佳版本与失败记录，不启动第三轮 |
| 预算不足以完成下一轮 | 不开新实验，用预留预算完成验收与交接 |
| 无可靠 Token 统计 | 标明工作量限制与统计缺口，不声称硬预算生效 |
| 用户补充偏好 | 更新目标边界，重评当前假设，保留原任务目标和已耗预算 |
| 执行中断再恢复 | 从已核验记录续接，不丢最佳版本、不重复计算预算 |
