# Bibo 收件箱阅读布局

## 目标与依据

用户要求优化截图中的收件箱页面。截图是布局现状参考，正文内容不构成指令。遵循产品愿景：让用户方便地浏览送达内容并完成处理。当前 `Inbox` 消费 space store 的条目和选择，Markdown 使用共享阅读组件；列表与详情各占接近一半，外部标题与正文首标题重复，操作位于长文之后。

范围为收件箱展示，standard / L2；交付沿用本任务已授权的部署及合入主干。无存储、接口或共享 Markdown 合同变更。design-document: required；plan: not-required，单批闭环。

## 用户链路与方案

用户从收件箱筛选待处理／未读／全部，点击消息，看到日期、状态、标题和正文；阅读时可随时标记已读、处理或查看来源，然后选择下一条。手机保留列表／详情切换和返回入口。失败提示与重试由既有 store 和 source 路径承载。

- 桌面列表采用 300–360px 的受限宽度，详情使用剩余空间；正文居中并限制到 760px。相比比例分栏，宽屏不会把空白浪费在列表；牺牲超长标题的横向空间，以现有两行省略与完整详情补足。
- 列表标题、摘要、状态与日期分层，日期不与标题争抢同一行。筛选固定在列表顶部。
- 详情上方固定操作栏，正文单独滚动；手机允许按钮换行且触控高度不少于 44px，返回操作一直可达。
- 详情标题是单一主标题。仅当正文第一个非空行是与条目标题完全一致的 ATX 一级／二级标题时，阅读副本移除该行（允许标准尾部井号）。不同标题、正文段落及后续章节原样保留；不猜测格式化标题、不改变持久化原文。纯展示转换归 inbox-content utils。
- 删除 Inbox 对所有正文 h2 的字号覆盖，章节字号继续由共享 Markdown density 控制。布局样式归 space 样式 owner，控件状态继续用共享 primitives。

不采用新增拖拽分栏或可折叠列表：本次问题可由响应式尺寸解决，新增布局状态和入口没有必要。

## 验收

- INBOX-01：1440／2048 桌面选择长消息，列表宽 300–360px；正文不超过 760px；单一标题，不同正文标题保留；日期、两行长标题和摘要没有相互挤压。
- INBOX-02：阅读长文至末尾，操作栏仍在首屏且可操作；切换另一条消息从正文顶部开始。筛选、标记已读和处理仍走既有动作，来源错误保留消息。
- INBOX-03：1100／390／320 单栏下选择消息、阅读、返回列表和切换筛选；无页面横向溢出，按钮不少于 44px，正文内表格／代码继续独立滚动。
- INBOX-04：匹配范围 tsc、既有 Markdown 冒烟及布局浏览器验证通过，远程主干与生产资产一致。
- INBOX-05：前端部署不构建、推送或 rollout 容器，部署前后容器镜像身份保持一致。

浏览器使用代表性消息验证布局和操作，线上真实账号只读验证入口与资产；不需要模型生成或修改真实用户消息。截图由 AI 确认正常渲染，视觉偏好由用户判断。

## 方案 Review

mode=design：核对截图目标、既有 store 动作、来源错误路径、移动返回和 Markdown 保留边界。无新增状态 owner、平行解析器或公共抽象；标题转换采用保守精确匹配，验收包含不同标题反例。design-review: passed，适用于上述范围。

## 发布链路纠偏

用户补充询问“更新前端还要构建镜像吗？”。Worker 对非 API 请求调用 ASSETS.fetch，容器运行独立 runner；原 deploy 入口全量构建并因 image 指向 Dockerfile 触发容器发布。本次仅前端变化，采用 deploy:client（build:client + Wrangler 4.138.0 deploy --containers-rollout none），完整后端部署仍使用原 deploy。已核对固定版本 CLI 与源码：none 分支跳过 prepareDurableObjectContainerApplications，并恢复线上容器 metadata；元数据无法恢复时在 Worker 上传前失败。方案 Review：保留唯一 Wrangler 配置与现有发布 owner，不生成第二套配置或固定镜像副本；新增 INBOX-05 验证线上容器身份。design-review: passed。
