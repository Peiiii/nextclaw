# Bibo 聊天与个人空间读取并发修复

## 现象与证据

用户打开两小时多前已完成的会话，发送消息后收到“正在处理上一条消息”。生产诊断显示该会话上次运行已保存并结束；本次请求在 2026-09-28 14:30:47 UTC 被 `RUN_BUSY` 拒绝。同一用户容器当时正在处理页面触发的 `/space` 读取，其中一项从约 14:30:42 开始，耗时约 7 秒。之后同一容器又成功接受并保存聊天，说明不是持久化的“上一条消息”状态。

当前 `BiboUserContainer.space()` 在解析动作前就占用用户级 `inFlight`，读列表和概览也与聊天互斥。聊天页加载历史消息时，React effect 把任意 `messages` 变化当作聊天完成，调用 `refreshAfterChat()`，额外读取概览、文件和工作区。容器闲置后的唤醒放大了读取占锁时间。

## 用户验收

1. 打开一条已结束的旧会话，马上发送消息；即使页面正在读取概览或个人空间，消息仍被接受并给出回复，不出现“上一条消息”误报。
2. 聊天真正运行时，同一用户的写入操作仍不得与运行交叉破坏状态；运行结束后可正常写入。
3. 打开或切换旧会话只加载聊天必需的数据；聊天成功保存后，当前可见的空间内容保持可刷新。

生产验证记录发送到首字及最终保存，同时检查拒绝诊断和容器健康。用户只需在原会话重发已保留的输入，判断交互是否顺畅；AI 负责先完成技术验证。

## 活跃验收契约

- `contract-id`: `bibo-chat-space-read-2026-09-28`
- `parent-goal`: 旧会话长时间未发送消息后，用户能立即正常发起新聊天，页面读取不制造虚假的“上一条消息”忙碌状态。
- `scope-revision`: 1；来源为用户提供的线上会话、截图和“一个小时内没有发消息”的说明；已获得同一 Bibo 延迟修复任务的合入及部署授权。

| ID | Required | Status | 可观察判定 |
| --- | --- | --- | --- |
| BCSR-1 | true | not-run | 旧会话加载同时发送，聊天被接受并产生回复，不返回 `RUN_BUSY`。 |
| BCSR-2 | true | not-run | 空间只读不占聊天锁，空间写入与聊天仍互斥，已保存状态不丢失。 |
| BCSR-3 | true | not-run | 历史加载不触发全空间刷新；聊天提交后可见空间内容可刷新。 |
| BCSR-4 | true | not-run | 修复部署到生产，旧会话真实链路复验且无新的异常拒绝或保存失败。 |

单阶段完成；当前证据为本文件的事件顺序与源码调用链，修后证据待补。必须不发生：为避免拒绝而允许空间写入覆盖聊天、丢失历史或仅把错误改成等待。当前没有范围删减提议。

## 方案与取舍

- **只改文案**：用户仍无法发送，放弃。
- **只取消历史消息触发的空间刷新**：减少本次触发，但空间面板读取与聊天仍会误互斥，放弃作为唯一修复。
- **按操作语义占锁，让聊天优先于容器读取，并移除无关自动刷新**：采用。仅修改空间或快照的操作占用 `inFlight`；纯 Durable Object 的只读动作可与聊天并行。容器 runner 有自身的单请求 `busy` 约束，因此聊天只等待已经进入容器的那一次只读操作完成；之后先进入容器，排队中的只读操作等待聊天结束。若用户级清空或其它写入正在执行，只读仍服从写入互斥。空间动作仍保留原有队列和写入保护。

前端在聊天历史加载时不触发 `refreshAfterChat()`。只有真正收到 `committed` 事件或从错误恢复发现运行已保存时才刷新可见空间；处于普通聊天页且没有打开工作区时无需预取概览，导航到概览时再读取。

## 边界与验证矩阵

只读闭集为 `overview.get` 和已支持领域的 `.list`、`.get`；`inbox.read`、`inbox.resolve` 及所有创建、更新、移动、删除仍占锁。未知动作沿用保守写入路径。结构化只读直接读 Durable Object 状态；容器只读从进入到退出占用一个可等待的读取完成信号。聊天接单后等待当前容器读取的完成信号，排队中的后续读取等聊天完成信号，保证 runner 单请求约束。读到运行开始前的已保存状态可以接受，运行最终提交后再刷新。

定向并发测试覆盖：慢的 `overview.get` 正在容器内时聊天被接受并等待本次读取，后续读取不能抢在聊天前；慢的结构化列表与聊天并行；写入在聊天期间被拒且运行完成后成功；聊天失败、取消和读失败时锁能释放。前端测试覆盖加载历史不刷新空间，真正提交才刷新。生产只在冻结的主线版本上发布，并在原有旧会话和新会话复验。

本修复不改变模型、额度、会话历史格式、空间写入语义或容器闲置时间。闲置后首字延迟仍单独以真实数据判断。

## 2026-09-29 方案复核与精简

这是整体合同 BE-03 的独立止血切片，不替代零容器架构。源头是页面读取占用用户级 `inFlight`，而不是上一条聊天仍在处理。沿真实入口审查后确认：结构化只读直接取 DO；容器只读需要一条完成信号，以便已接受的聊天在进入 runner 前等待当前读取；聊天一旦接受，后续容器只读等待其终态。`spaceQueue` 已经序列化空间请求，因此无需另设 `spaceReadActive` 布尔状态；现有 `containerReadDone` 信号足以保护 reset/写入与运行的先后。保留 `activeRun.finished` 作为等待点，但必须在异常和取消后始终完成。

首份实现补丁的 maintainability guard 报 3 个 `max-statements` 错误，说明把解析、读取、写入、快照和锁都堆在同一函数不可交付。返工时将请求解析与容器执行分别归入单职责函数，并把运行前的空间同步归入单职责步骤；不以压缩语句或删除测试绕过检查。设计审查结论：**方案可实施，首份实现不通过；按本节精简后重新验证和 Review。**
