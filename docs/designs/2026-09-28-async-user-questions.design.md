## Codex 实际机制

`request_user_input_async` 接受一个或多个 `{title, options?}` 问题。handler 校验非空后生成一条 `AgentMessage`：`delivery=async`、`questions` 保存结构化题目、`content` 保存可读文本兜底；它发布 item started/completed，向模型立即返回 `{ "accepted": true }`。这里的 `accepted` 仅表示问题已发出，**不是用户已经回答或批准**。同步版 `request_user_input` 则有等待答复的请求与响应合同。

TUI 将每道题作为带 ID 的待回答项，提交时把题目 ID 和答案组织为用户输入；已经回答的 ID 用于清掉待回答项。当前轮次能继续执行，与问答直接解耦；答案到来后按普通用户输入路由到正在运行的轮次或后续轮次。它不会让依赖答案的步骤自动获得尚未发生的回答。UI 到期/结束时的具体清理策略不是内核不变量。

上游有可借鉴的边界问题：[桌面端问题卡在 final 后消失](https://github.com/openai/codex/issues/43803)及 [TUI 多题回答只清掉一题](https://github.com/openai/codex/issues/47535)。这些是对应客户端的公开问题报告，不推断所有 Codex 客户端都存在同样行为。NextClaw 应以持久问题事实、逐题 ID 和明确的回答/撤回状态避免同类问题。

## NextClaw 当前能力与断点

| 链路 | 已确认事实 | 对方案的含义 |
| --- | --- | --- |
| 用户运行中输入 | `SessionRun` 拥有 next-run/next-step；`AgentRunRequestManager.sendOnce` 按 `prefer-steer` 选择当前 run 或排队；Native runtime 声明 `nextStepInput` | 回答可复用同一输入入口；其受理回执必须说明 `steered` 或 `queued` |
| 持久会话 | `SessionEventIngestionService` 顺序写 journal；`SessionRun` 投影消息；NCP `MessageSent/MessageCompleted` 进入会话状态 | 问题必须成为可恢复的会话事实，不能只放 React 状态或工具返回文本 |
| 内容协议与 UI | `NcpMessage` 有文本、`extension` part 和 metadata；Chat 消息链可渲染自定义 part | 第一版可用带文本兜底的 `nextclaw.user-question` extension part，无需立即增加公开 NCP 闭集 variant |
| Codex 外部 runtime | `codex-app-server-ncp-agent-runtime.service.ts` 的 `handleAgentMessageItem` 当前只处理文本 | 已知相邻缺口；本次按用户明确范围不改此 adapter |

已确认的缺口是“提问事实 + 回答关联 + 可恢复状态”。`SessionRun` 现有待输入状态是进程内状态，因此不能拿它作为问题的唯一持久 owner。

## 推荐用户链路

用户在现有会话发起一个较长任务。Agent 遇到偏好缺口时调用 `request_user_input_async`，会话回答时间线在发问位置显示紧凑的可点击问题标签；首次收到新问题时，输入区上方自动浮出临时答题面板。用户可关闭面板继续阅读和输入，再点标签或输入区旁的待答入口重新打开。面板将建议答案列为 A/B/C/D 式单选项，点击预设项即提交，不再要求二次点“发送回答”；最后一项直接是带选项编号的自定义输入框，按回车或点行内发送按钮提交。无建议选项时仍显示带 A 编号的输入框。跳过仍是独立操作。主运行保持 `running` 并继续独立步骤。回答后浮层关闭，标签在原位置显示简短的已回答状态，答案以一条带 `questionId` 关联的用户消息进入同一会话；输入区不保留已回答卡。若当前 Native run 还接受 next-step，答案在下一安全步骤生效；否则进入下一 run。若用户暂不回答，标签与待答入口保持可找回，Agent 对依赖答案的部分保持待定，可完成其余工作。刷新、切换会话再回来仍能看到问题与状态。

## 主链路与唯一 owner

1. **Kernel 会话 owner** 接受发问意图，一次工具调用可产生 1–3 题；每题有稳定 `questionId`，一条 assistant 消息承载本次全部题目与可读文本。消息经现有 session event ingestion 写入 journal，成功后工具立即返回“已发出”的 receipt；如果 journal 写入失败，工具报错。发问工具只面向当前会话，不能以消息工具向任意聊天发送并假装可回流。
2. **标准会话消息** 承载题目：assistant 消息含可读文本和 `extensionType: "nextclaw.user-question"` 的结构化 part。题目记录本身是不可变事实；用户回答生成标准 user message，并在 metadata 中关联 `questionId`。待回答状态从题目及回答/撤回事实派生，不能另存一份互相竞争的前端状态。若采用单独关闭事件，它只表达撤回/过期，不能伪造用户答案。
3. **Kernel 回答操作** 接受 `{sessionId, questionId, answer | dismiss}`，核对题目存在、会话属于原生 runtime、答案非空；选项是建议值，自由文本同样有效。固定用户消息 ID 和 ingress 幂等键由 question ID 派生，metadata 记录关联与结算动作，经现有 `AgentRunRequestManager` 进入 `prefer-steer` 或 next-run，并返回实际 delivery。结算状态由 journal 中的关联用户消息、当前 `SessionRun` 消息与待输入队列共同投影；进程中重复提交原值返回先前结果，冲突值拒绝，不产生第二条消息。现有待输入队列在进程重启时丢失，重启后未落 journal 的回答重新呈现为待答，与当前输入队列合同一致。
4. **UI presenter** 经独立的会话问题读取接口取得全量问题投影，避免早于最近 40 条的待答问题被分页隐藏；会话回答时间线将 `extension` part 渲染为每题一个紧凑按钮，结构化渲染时隐藏同一消息的可读文本兜底，避免重复。输入区只显示待答数量的轻入口；打开时在输入区上方浮出有关闭按钮的答题面板，不占用固定聊天高度。新题第一次被当前浏览器页看到时自动打开最新一题，关闭后不因投影刷新而反复弹出。时间线按钮和待答入口均可重新打开；回答或跳过后面板收起且入口数更新，历史标签保留终态。浮层回调调用同一个回答操作。问题不随当前 run final、组件卸载或 Tab 切换而删除。输入框草稿与问题草稿分开；回答不会覆盖用户正在编辑的普通消息。刷新与会话事件触发问题投影重读。
5. **范围边界**：本次工具仅暴露给 Web 会话中的原生 Agent。渠道消息由 channel adapter 负责收发，当前没有结构化问题 ID 的回流合同；向渠道暴露工具会形成用户看不到或答不回的问题，因此渠道会话不暴露该工具。Codex app-server 适配器保持现状，不将其文本处理误报为结构化提问支持。

不建立新的问答 run、独立问题数据库、第二套 input queue 或泛化审批系统。提问不能代表高风险操作授权；需要明确授权的动作仍等待用户明确决定。

## 真实取舍

### 2026-09-28 交互修订

用户指出原实现把待答和最近已答卡片固定在输入区上方，随着会话增长无法形成闭环；并明确希望回答中的轻量标签、可关闭可重开的面板，以及可选的自动弹出。Codex 公开的 PR 与 TUI 源码只证明异步消息与问题状态合同，桌面客户端的具体视觉没有完整公开；桌面标签形态以用户观察为需求输入，不冒充开源源码结论。[上游 PR](https://github.com/openai/codex/pull/42178)、[TUI 状态源码](https://github.com/openai/codex/blob/44fe510ce3ee61c8ef623adcbf89b901c73ddd61/codex-rs/tui/src/bottom_pane/async_questions/state.rs)。

在“点击标签后弹窗”和“输入区上方临时面板”之间选择后者：同一入口既能自动出现，也能从历史标签或待答数重新打开；面板临时覆盖而非占据正文高度，且和当前普通输入保持邻近。大屏宽度不超过聊天正文，窄屏不越界；关闭、Escape、回答或跳过均收起，焦点返回触发入口。多道待答题在面板顶部有逐题切换，保证较早的问题即使不在当前聊天分页内也可从待答入口打开。已答标签只表达历史状态，已答内容由相邻用户消息留存。待答数只在仍有待答时出现，作为分页后找回入口。问题选项适合已有少量明确候选时优先提供，自定义回答始终可用；未来密码或敏感输入必须另建受保护的输入/传输合同，不能把普通回答框标成密码框。

本修订不改 Kernel 问题事实或回答 owner，只替换 UI 投影和展示生命周期。Golden path：新题在时间线出现标签并自动浮出面板 → 用户关闭仍能点击标签重开 → 单击建议项立即提交，或选择最后的“自己填写”再输入提交 → 回答进入同会话 → 面板与待答入口消失、历史标签显示已回答；第二条路径从超过最近 40 条的待答问题，经输入区待答入口完成同样操作。AI 验证事件、状态、刷新、键盘/触控与真实浏览器渲染；用户再评审主观交互感受。

后续交互纠偏将最后一项从“先点自己填写，再展开输入框”改为直接显示的带编号输入行；按回车或点行内发送按钮提交。前述 Golden path 的自定义输入分支以此为准。

### 2026-09-28 回答引用修订

用户进一步要求回答消息呈现为“引用先前问题 → 给出答案”，并要求 Agent 在很久以后收到答案时仍理解来源。当前 Kernel 已在回答消息 metadata 持久保存 questionId，文本是“↳ 题目 / 答案”；模型转换器只读取用户消息的 text part，不读取 metadata，因此模型虽然能从题目猜到关联，界面却只是普通文本。本次保持 Kernel 的问题事实和回答入口为唯一 owner：回答消息 metadata 增加原问题的 messageId 与题目快照，作为可恢复的引用合同；模型可见文本明确写“回答先前问题 / 问题 / 答案”，不依赖旧问题仍位于上下文窗口。UI 根据该 metadata 在用户消息内显示带引用线、题目与答案的引用样式，旧的“↳ 题目 / 答案”记录仍可回退展示。用户普通消息、会话回复和问题结算不新增第二条发送主链路，也不把 UI 引用标签误当成模型可见内容。

黄金验收补充：先产生一题 → 插入大量其它消息或刷新 → 从待答入口回答 → 用户气泡显示原题引用与本次答案 → 同一会话下一 run 的模型输入包含明确的问题和答案，Agent 回答能指认所答的是该旧题。验证从 journal metadata、模型转换器输出和真实会话三处取证；只看 UI 标签或模型口头确认均不单独算通过。

### 2026-09-28 引用视觉修订

用户提供的实际截图显示，引用块被画成嵌套卡片，还在原题上方重复写“回答了这个问题”，导致气泡显得笨重。公开搜索没有找到足以复刻这一具体 ChatGPT 控件的可靠截图，因此以用户截图及明确反馈为准：引用只占一行，左侧细线与引用图标表达关系，正文只显示原问题标题，超长标题单行省略；悬停或辅助技术可读取“引用问题：完整标题”。下方是答案，不在引用内重复答案、状态或解释性文案。持久 metadata 与模型输入合同不变。

### 2026-09-28 Codex 面板对照修订

用户后续提供了 Codex 实际问题面板截图，并指出自定义项应始终是带编号的输入行，输入聚焦不能出现额外外框，输入一行文字不能使面板跳高。面板采用截图的内容层级：顶部问题标识与关闭、独立题干、轻量编号的推荐选项、底部常显的自定义输入以及跳过/发送。仍保留此前确定的预设选项点选即提交，不因为截图中的发送按钮而增加二次操作。Agent 可选传 `recommendedOption`，必须与某个建议选项精确匹配；只有明确推荐时才高亮，不默认推荐第一项。自定义输入与按钮位于固定高度的同一行，聚焦不改变外层边框、背景、阴影或 ring，输入前后尺寸不变。截图中的输入麦克风涉及独立语音输入合同，本次不加无功能图标。

用户再次指出面板过大、选项与输入行不齐、待答入口造成底部空隙，以及面板和输入框宽度、表面层级不一致。根因是面板使用独立 `max-w-3xl` 浮层，输入框却走聊天 composer 轨道；浮层还锚在待答入口上方。修订为面板与输入框使用同一布局宽度，直接排在输入框上方，间距保持 8px；面板使用输入框相同的卡片表面、边框、圆角和阴影。打开时隐藏待答计数入口，关闭后恢复；选项与自定义项共享编号左边距，标题和行高收紧。推荐项只在 Agent 显式给出 `recommendedOption` 时呈现，不能把第一项暗示为推荐。

随后采纳选项说明与推荐提示的建议：`optionDescriptions` 是以选项原文为 key 的可选结构化字段，只有非空解释才渲染独立问号；悬停、键盘聚焦、点按都能显示 tooltip，点问号不提交选项。提问工具的 description 作为 Agent 专项指引：提供建议项时通常给一个合理推荐，确实无法推荐则省略；不在选项原文拼接“（推荐）”。这样 UI 状态和实际提交答案仍使用干净的选项原文，旧问题可继续投影。

| 候选 | 结果 |
| --- | --- |
| 普通文本提问 + 用户手动回复 | 可立即用，但没有稳定关联、已答状态、多题结算和刷新恢复；只作为不支持结构化控件的渠道兜底 |
| 工具返回一个等待用户的 Promise | 会卡住模型轮次与工具调用；无法实现题后继续工作 |
| Kernel 持久会话问题 + 现有输入投递（推荐） | 复用 session、journal 和 steer owner；需补会话问题协议、回答操作与 UI 投影，是完整闭环的最小边界 |

## 状态与失败合同

- `asked → answered | dismissed`。回答与撤回是同一问题的终态；重复点击、双客户端竞争、迟到回答必须幂等。普通聊天回复不能仅凭文本相似度隐式关题。
- 工具返回前若 journal 写入失败，报告失败，不能在 UI 显示一个实际上不存在的问题。重连从 journal 重建；消息事件与 UI 投影保持同一 ID。
- 当前 run 停止或自然结束不清除未答问题。回答到来时重新判断运行窗口；Native 可 steer 则 steer，窗口关闭则排队。
- 问题消息有可读文本兜底，供会话时间线与无自定义 part 的读取者查看；没有可关联回答入口的渠道暂不暴露此工具，普通自由文本回复不被擅自认定为某道题的授权。

## 黄金验收与最小验证

1. 原生 Native 长任务中提问后继续执行独立步骤；用户在当前 run 回答，问题只出现一次，答案在下一安全步骤进入同一 run。
2. 问题发出后结束 run、刷新/重启会话入口再回答；卡片仍在，答案进入下一 run，状态正确更新。问题早于最近 40 条时仍可操作。
3. 两道题分别回答或撤回、重复提交第一题、另一客户端同时回答第二题；每题仅一条有效结算，不能清掉未答题。
4. 非原生 Agent 不暴露本工具；其现有文本消息行为不受影响。

实现覆盖消息投影、journal 重放、server/SDK 操作和 UI 控件；改动 TypeScript 与运行链路后已运行相应 `tsc`、定向测试、构建及真实链路验收。NCP 使用现有 `extension` part，不改变公开闭集 variant。
