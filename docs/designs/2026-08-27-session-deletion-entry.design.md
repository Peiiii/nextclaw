# 会话删除入口设计

## 问题与目标

用户从聊天侧边栏浏览历史会话时，不能直接删除目标会话；现有删除入口只出现在已打开会话的标题菜单中。用户任务是：在会话列表定位不再需要的会话，明确确认后删除，并立即看到列表更新，而不意外离开当前正在查看的另一段会话。

当前删除的唯一数据 owner 已经是 kernel `sessionManager`，服务端的 `DELETE /api/ncp/sessions/:sessionId` 会停止该会话运行状态并删除会话；UI 已有同一 API、缓存失效与当前会话删除后的回退逻辑。CLI 则只支持重命名和项目绑定，未暴露删除操作。

## 功能闭环

| 场景 | 用户看到/操作 | 结果与 owner |
| --- | --- | --- |
| 浏览侧边栏 | 每项已有更多菜单 | 菜单新增危险态“删除会话” |
| 确认 | 复用现有 destructive 确认对话框 | 取消不改变状态；确认才调用既有会话删除 API |
| 删除当前会话 | 会话和本地详情状态消失 | 删除缓存后回到会话根页 |
| 删除未选中会话 | 当前会话保持打开 | 仅移除目标的列表/消息缓存，保留路由与详情状态 |
| 失败 | 确认流程结束 | 不清除 UI/缓存，保留可重试入口 |
| CLI | `nextclaw sessions delete <session-id>` | 通过现有 kernel 会话删除 contract 执行，提供非交互 JSON 输出 |

进行中的会话不新增不同语义：服务端当前 contract 已先移除 run 状态再删除会话。删除是不可逆的用户数据操作，所有 UI 路径都必须确认；CLI 采用现有 CLI 的显式子命令而不另设替代 API。

## 方案选择

选择“侧边栏更多菜单 + 现有 `ChatThreadManager` 扩展为可接收目标 session key”的单一路径。

- 相比先切换到目标会话再删除，它减少一次导航，且不会干扰用户正在阅读的会话。
- 相比为列表项建立第二套 mutation/state owner，它复用现有确认、API、缓存删除与详情清理逻辑。
- 相比新增归档/回收站，本次不改变已存在的永久删除服务合同；恢复能力是独立的持久化产品设计，不应作为本入口的隐式 fallback。

`ChatThreadManager` 是 UI 侧删除编排 owner：根据目标是否当前选中，唯一地决定详情状态和路由是否清理。kernel/server 继续是删除语义的 owner；CLI 复用同一 kernel-owned command contract，不复制删除逻辑。

## 范围与验证

本次只增加 UI 侧边栏和 CLI 的可发现入口；不修改存储模型、删除 API、权限模型或恢复机制。验证至少覆盖：取消不调用删除、删除当前会话清理并返回根页、删除非当前会话保留当前路由和详情、侧边栏菜单触发目标 key、CLI 注册/调用正确，以及相关 TypeScript 检查。
