# 会话内定时任务卡片统一管理设计

## 设计状态

- design-document: required
- plan: not-required（实现限定在现有定时任务前端投影和测试；不改变 Cron 的领域合同、持久化或服务端 API）
- 当前阶段：Design Ready，尚未进入实现

## 1. 用户任务

用户在一段用于绘画或其它工作的会话中打开“定时任务”，为了暂停、恢复、手动执行、检查结果或清理该会话创建的自动化，能够直接看到与全局定时任务页语义一致的状态和操作；成功后卡片立即反映真实任务状态，而不必跳转、猜测或删除后重建。

这里的“绘画类定时任务”不是独立领域对象。它是 `payload.sessionId` 指向当前会话的普通 `CronJob`，因此不应为图像生成增加专属卡片、字段、接口或状态机。

## 2. 当前事实与问题

已确认的端到端链路：

```text
CronService（任务状态 owner）
  -> CronRoutesController
  -> /api/cron、/api/cron/:id/enable、/api/cron/:id/run、/api/cron/:id
  -> client SDK / React Query mutation hooks
  -> 全局“定时任务”页 CronJobRow / CronJobDetailDialog
  -> 会话工作区 SessionCronJobContent
```

- `CronService` 已拥有 `enabled`、执行、下次/最近运行、错误和删除的完整生命周期；`CronRoutesController` 已把暂停/恢复、立即执行和删除暴露为稳定 API。
- 全局 [定时任务页面](../../packages/nextclaw-ui/src/features/cron/components/cron-config.tsx) 已提供状态、暂停/恢复、立即执行、详情、最近错误、执行会话入口和删除确认。
- 会话工作区通过 `useCronJobs({ all: true })` 后按 `payload.sessionId` 投影同一批任务；这正是用户在绘画会话中看到的卡片来源。
- 但 [SessionCronJobContent](../../packages/nextclaw-ui/src/features/chat/features/workspace/components/session-cron-job-content.tsx) 只调用 `useDeleteCronJob`。它没有展示可读的启用状态，也没有接入已存在的暂停/恢复、立即执行或详情能力。

因此根因是**会话投影绕过了定时任务的管理控制面**，不是 Cron 后端能力不足。

## 3. 功能地图

| 场景 | 用户看到什么 | 可执行动作 | 状态 / 数据 owner | 失败或返回路径 | 验证证据 |
| --- | --- | --- | --- | --- | --- |
| 首次进入 | 与当前会话绑定的任务卡片；名称、计划、运行/已暂停/需关注、下次运行 | 展开或查看详情 | `CronService`，通过 cron query 投影 | 加载时不误显示为空；请求失败显示可重试错误 | workspace 组件测试 + 真实页面操作 |
| 任务运行中 | “运行中”及下次运行时间 | 切换为“暂停”；更多操作中“立即执行” | 同上 | 变更 pending 时仅锁定该任务的重复操作；失败保留旧状态并显示错误反馈 | mutation 请求与失效缓存断言 |
| 任务已暂停 | “已暂停”，明确说明不会按计划运行 | 切换为“恢复”；“立即执行”需二次确认 | 同上 | 用户取消确认则不请求；恢复失败不伪造运行中 | 确认与 `force: true` 断言 |
| 立即执行 | 操作进行中的可见反馈 | 打开详情、等待执行完成、进入执行会话（可用时） | `runJob` 返回的真实任务快照 | 请求失败显示错误；执行结果刷新卡片状态 | 运行 mutation + 状态刷新断言 |
| 查看详情 | 任务内容、计划、Agent、会话、最近运行和错误 | 暂停/恢复、立即执行、删除、打开执行会话 | 同上 | 关闭详情回到原卡片；任务已删除则关闭详情并从列表消失 | Sheet 与导航测试 |
| 删除 | 危险操作确认，明确任务名 / ID | 确认删除或取消 | `CronService.removeJob` | 取消不请求；成功从会话列表移除；失败保留卡片 | 删除确认与列表更新断言 |
| 空、加载、错误 | 区分“没有本会话任务”“正在读取”“暂时无法读取” | 错误态重试 | query owner | 刷新后重新投影真实数据 | 三态组件测试 |

当前会话范围不是全局任务目录；本次不为少量会话绑定任务新建客户端伪分页。若产品允许单会话持续积累到超过一个可读页面，应由服务端为现有 `CronListQuery` 增加会话过滤和分页，再替换当前全量投影，不能在浏览器先取全量后分页。

## 4. 候选方案

| 方案 | 用户理解 | owner / 耦合 | 取舍 |
| --- | --- | --- | --- |
| A. 在现有会话卡片上临时增加开关和按钮 | 表面上更完整 | 在 chat feature 复制确认、强制执行和 mutation 编排 | 改动小，但下一次新增 Cron 操作仍会再次漂移；不采用 |
| B. 点击卡片一律跳转全局定时任务页 | 语义一致 | 不复制操作 | 用户离开当前会话，且无法快速治理当前自动化；只作为“查看全部任务”的辅助入口，不采用为主路径 |
| C. 会话卡片复用 Cron feature 的操作合同和详情面板，以紧凑卡片呈现 | 当前会话内可直接完成管理，语义与全局页一致 | Cron feature 继续拥有操作编排；chat feature 仅提供会话范围和展示位置 | 需整理现有前端 action 复用点；采用 |

## 5. 推荐设计

### 5.1 一份任务，一份管理语义

`CronService` 继续是唯一领域状态 owner；服务端路由、SDK 和既有 `useDeleteCronJob`、`useToggleCronJob`、`useRunCronJob` 继续是唯一 mutation 链路。不得为会话或绘画任务新建 API、store、状态字段、镜像任务或专属 service。

前端将“删除确认、暂停/恢复、已暂停任务的强制立即执行确认、pending / 成功 / 失败反馈、cron query 失效”收敛为 Cron feature 内可复用的**任务操作控制器**（可实现为单个 hook 与其确认对话框）。它只编排已有 mutation，不创造新的领域 owner。

全局页面保留分页、筛选和选中任务等页面状态；会话工作区只把任务和必要的成功后本地 UI 清理回调交给该控制器。两处不得分别重写 `force` 判断、确认文案或缓存失效规则。

这符合 `single-complete-owner`、`equivalence-by-construction` 和 `simple-structure-first`：同一 `CronJob` 的状态迁移只从一个控制器进入，且不为两个实际 consumer 提前引入 registry、capability DSL、第二个 manager 或后端适配层。

### 5.2 会话卡片的信息与操作层级

会话工作区的每张卡片使用适合窄面板的紧凑布局，但功能合同与全局行一致：

```text
任务名称                         [运行中 / 已暂停 / 需关注] [开关]
计划 · 下次执行（或“暂停后不会自动执行”）                 [更多]
任务摘要（默认最多两行）                                  [查看详情]

更多：查看任务详情 | 立即执行 | 删除
```

- **开关是主要、可发现的非破坏性操作**：运行中的任务切换为“暂停”，暂停任务切换为“恢复”。开关的可访问名称随状态变化；任务进行中的重复操作被禁用并有状态反馈。
- **“立即执行”是二级操作**：正常任务直接发起；已暂停任务先明确说明“该任务已暂停，仍要立即执行吗？”，确认后以 `force: true` 调用现有 API。它不改变任务的启用状态。
- **“查看任务详情”是稳定的详情入口**：复用现有 `CronJobDetailDialog`，包含任务内容、计划、执行 Agent、会话链接、最近结果/错误，并在其中提供同一组管理操作。会话存在时使用真实导航链接；独立执行会话首次运行前维持不可进入状态和说明。
- **内容默认渐进披露**：会话面板首先服务“识别与管理任务”，不服务阅读整段 prompt。默认只显示两行摘要，长任务内容只在“查看任务详情”中完整呈现；不以不断增高的卡片挤掉同一会话中的其它任务。这采用 ChatGPT 卡片常见的低噪摘要、用户触发后再阅读完整上下文的交互取向，而非复制其视觉品牌。
- **删除始终位于更多菜单和详情页的危险区**：二次确认后才调用删除；不能用“关闭”或“暂停”冒充删除。
- 卡片标题 / 展开区域与行内开关、更多菜单保持独立焦点和事件边界；图标操作有可访问名称、tooltip，窄面板不依赖 hover 才能发现管理入口。

全局“定时任务”页当前把详情入口称为“查看与编辑任务”，但不存在编辑计划或任务内容的 `PATCH` 合同。本次统一时应改为“查看任务详情”，避免把只读查看误称为编辑；需要改动任务内容或计划仍回到其来源会话说明意图。这是产品语义澄清，不是放弃编辑能力。

### 5.3 状态与刷新不变量

1. 任一入口对同一任务执行暂停、恢复、运行或删除后，所有 `['cron', ...]` 查询失效并从 `CronService` 重新投影；不在 chat state 中维护第二份 `enabled`、运行结果或错误。
2. 操作失败时，界面不能提前把状态显示为成功；保留服务端最后已知快照并显示可理解的错误反馈。
3. 已删除的任务不会留在详情 Sheet 或会话列表中；一次性任务自然执行后同样按下一次刷新消失。
4. `enabled === false` 的含义固定为“不会按计划自动执行”；它不禁止经明确确认的强制立即执行，也不等同于删除。
5. 会话工作区的空态只能在 query 已成功完成且当前会话没有匹配任务时出现；加载和失败必须与空态区分。

### 5.4 实现边界与建议落点

- `packages/nextclaw-ui/src/features/cron/hooks/`：承接共享的 UI action 编排；继续调用既有 API hooks。
- `packages/nextclaw-ui/src/features/cron/components/`：保留 `CronJobRow` 和 `CronJobDetailDialog` 作为标准任务展示 / 详情 surface，并让它们消费同一 action 合同。
- `packages/nextclaw-ui/src/features/chat/features/workspace/components/session-cron-job-content.tsx`：只负责当前会话的紧凑投影、详情打开状态及渲染，不直接拥有 Cron mutation 规则。
- `packages/nextclaw-ui/src/features/chat/features/workspace/hooks/use-chat-conversation-workspace-state.ts`：保留 query 的加载 / 错误事实并传给 workspace，不再把未加载误折叠为空列表。

不新增后端路由、Cron 类型字段、数据库迁移、绘画专用类型或跨 feature 的通用卡片框架。当前两个 consumer 已足以证明需要共享“操作编排”，不足以证明需要通用卡片注册机制。

## 6. 验收标准

1. 在绘画会话及任意普通绑定会话中，任务卡片能显示运行、暂停和最近失败三种状态，以及计划、下次 / 最近执行事实。
2. 用户可在不离开会话工作区的前提下暂停、恢复、立即执行和删除；每个动作调用既有 Cron API 的正确语义。
3. 已暂停任务的立即执行必须确认且携带 `force: true`；取消不会产生请求，立即执行不会偷偷恢复定时执行。
4. 删除必须确认；成功后卡片和已打开详情都消失，失败后保留真实状态并提示错误。
5. 会话卡片与全局页对同一任务操作后都会刷新到同一服务端状态；不存在 chat-local 影子状态。
6. 键盘可聚焦开关、更多菜单和详情入口；图标操作具备可访问名称与 tooltip；行内操作不会误触发展开。
7. 覆盖 workspace 的加载、空、错误、运行中、暂停、失败、确认取消和 mutation 成功 / 失败测试；同时保留全局 Cron 页面相同行为的回归测试。

## 7. 非目标与后续入口

- 本次不新增直接编辑任务名称、任务内容或计划。该能力需要专门的 `CronJob` 更新合同，并需厘清“会话里的原始意图”与“任务快照”谁是编辑 owner；不能把现有详情 Sheet 伪装成表单。
- 本次不把所有未绑定会话的独立 Cron 任务塞入当前会话工作区。
- 本次不新增绘画 / 图像生成任务分类、筛选或视觉专属管理面。
- 若后续需要单会话管理大量任务，再单独设计服务端会话过滤、分页和稳定排序；届时会改变 API 合同，应形成新的设计。
