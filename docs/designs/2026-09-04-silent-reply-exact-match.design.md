# 静默回复严格匹配设计

## 背景

会话 `ncp-mtln3ih3-426zjbv2` 的一条完整 assistant 回复被消息列表隐藏，但消息事实源和会话概览仍能读取。该回复只是在正常方案说明中引用了 `<noreply/>`，现有共享判定却把正文任意位置出现该标记都解释为整条静默回复。

## 目标与不变量

- 后端持久化消息继续作为会话事实源，前端按原始顺序投影可见消息。
- 只有 assistant 消息的全部用户可见文本合并并去除首尾空白后，整体匹配 `<noreply/>`，才判为静默回复；标记前后的历史转义空白 `\\n`、`\\r`、`\\t` 继续按空白处理，以免旧会话重新露出控制标记。
- 标记匹配继续兼容大小写与标记内部空白，但不得吞掉引用、说明、Markdown 或代码中的正常内容。
- UI 消息投影、reply policy 和继续运行锚点复用同一个共享判定，不建立平行规则。

## 主链路

1. shared utility 提取 assistant 消息中的 `text` 与 `rich-text`，按顺序连接。
2. 对连接结果执行首尾空白归一化；兼容已持久化的历史转义空白，并以锚定正则判断它是否只包含静默标记。
3. UI 仅过滤严格匹配的消息；正常引用标记的回复保持可见。
4. core reply policy 与 kernel 继续运行锚点沿用相同语义。

## 选择与取舍

不继续保留“任意位置命中”的宽松兼容。系统提示已经要求模型把静默标记作为完整输出；为容忍违约输出而吞掉正常回复，会把恢复逻辑升级成数据可见性风险。也不在 UI 单独加例外，因为这会让生成期、刷新后和继续运行产生不同语义。

## 验证

- shared：精确标记、内部空白、大小写、普通文字引用、多文本 part 与 rich-text 回归。
- core：正常正文引用标记时不丢弃，精确标记仍丢弃。
- UI：真实形态的长回复引用标记时仍进入可见时间线。
- 运行时：用问题 session 的已持久化末条消息验证共享判定为 false，并确认消息接口顺序不变。

## 非目标

- 不改变消息排序、存储格式、streaming 合并或会话概览结构。
- 不重写历史消息；修复后的客户端会直接重新展示现有持久化回复。
