# Runtime 会话模型与思考强度复用设计

## 问题与目标

新建会话会按 agent runtime 复用最近使用的模型，但当前模型与思考强度由两条独立 fallback 链路选择：模型还会优先读取本地最近模型记录，思考强度则独立扫描最近会话。这会把不同会话或不同模型的偏好拼在一起，也可能在复用模型时回落到该模型默认强度。

目标是把最近会话中的模型与思考强度视为同一份偏好快照。用户在同一 runtime 新建会话时，如果最近会话的模型仍可用，就同时继承该会话为该模型保存的思考强度；思考强度仍须通过目标模型的能力校验。

## 用户链路

用户在会话输入栏中为某个 runtime 选择模型 A 和思考强度 `high`，随后新建同一 runtime 的会话。系统在输入栏中默认显示模型 A 与 `high`，用户直接发送消息时，现有发送链路使用这组偏好。若模型 A 已不可用，系统沿现有模型默认链路选择可用模型，并使用该模型自身的默认思考强度，不把旧模型的强度带过去。

成功判定：新会话继承的模型和思考强度来自同一个最近会话；跨 runtime、不可用模型和不支持的思考强度都不会被错误继承。

## Owner 与主链路

- producer：会话偏好更新继续把 `preferredModel` 与 `preferredThinking` 写入现有会话 metadata。
- owner：会话输入查询层从同一 runtime 的会话摘要中一次选出最近的完整偏好快照。
- consumer：现有会话输入偏好同步逻辑使用该快照选中模型，再按该模型能力校验思考强度。
- persistence、服务端协议和发送请求保持不变。

## 选择

采用“同一最近会话快照”而不是新增本地思考强度缓存。会话摘要已经是模型与思考强度的共同持久化 owner，复用它能保证两者来源一致，也避免浏览器缓存与服务端状态形成第二套事实源。

本地最近模型记录保留用于模型选择器的最近项展示，并只在该 runtime 尚无持久化会话偏好时作为模型 fallback。只要存在会话快照，新会话默认值就来自可恢复、可解释的持久化状态。

## 边界与失败行为

- 当前会话有显式偏好时，继续优先使用当前会话偏好。
- 只在 session type/runtime 相同的会话间复用。
- 最近会话没有有效模型时，沿现有 runtime 推荐模型、全局默认模型和首个可用模型链路回退。
- 最近思考强度为空或目标模型不支持该强度时，使用目标模型默认强度或现有安全 fallback。
- 不新增 UI、配置项、CLI、服务端字段或迁移。

## 验证矩阵

1. 同 runtime 最近会话的 `模型 A + high` 在新会话中成组恢复。
2. 更旧会话的思考强度不会覆盖最近会话模型对应的强度。
3. 不同 runtime 的偏好不串用。
4. 最近模型不可用时不继承它的思考强度，改用所选模型默认值。
5. 当前会话显式偏好与草稿物化期间的本地选择保持现有优先级。
