# 工作台视图、容器与交互统一设计

- 状态：Design Ready；2026-09-11；flow=standard，风险 L3。
- design-document: required；plan: required。
- 愿景依据：让用户在会话、资料与工具之间连续工作，降低每种内容重复学习窗口操作的成本。

## 目标与事实

会话主区、会话工作台、全局右侧栏、独立会话悬浮窗采用统一的容器协议与交互语言。内容保持自己的数据 owner，不再实现拖动、缩放、收起、最大化等外壳能力。

当前完整链路：会话列表/通知 → SessionSurfaceManager → FloatingSessionStore → FloatingSessionConversation；停靠 → DocBrowserManager → DocBrowserStore → 全局 DocBrowser → SessionConversationArea。文件/子会话入口 → ChatThreadManager → ChatThreadStore 工作台选择与历史 → ChatSessionWorkspacePanel → 内容预览/SessionConversationArea。

现状问题：三套外壳分别管理位置与生命周期；悬浮会话固定尺寸且不可拖动；全局容器停靠/浮动分支导致内容重新挂载；工作台最大化只覆盖局部；“展开”同时指恢复、弹出；右侧栏的 X 实际隐藏整个标签组，却与关闭标签同名。全局容器已有资源路由、历史、固定入口与扩展 renderer，工作台已有会话上下文、文件预览和目录联动，应保留这些业务 owner。

## 模型与归属

1. **资源**：会话 ID、文件与来源工作目录、网页 URL 或 App ID。身份不等于展示位置。
2. **视图**：资源的一种展示，如文件源代码/渲染预览；同一资源可有多处展示，业务数据不复制。
3. **视图组**：共享标签栏、活动选择和导航历史的容器。全局资料组、会话工作台组、单会话视图都是实际消费者。
4. **位置**：主会话路由、会话侧栏、全局侧栏或浮动层。每类内容有实际可行的目标位置；会话上下文不随位置迁移。
5. **容器状态**：停靠/悬浮、正常/最大化、展开/收起、浮窗矩形与层序。独立于业务资源与标签历史，由公共 WorkbenchSurfaceManager 统一转移。

公共层位于 UI shared/components/workbench，提供 typed state、manager/store、容器骨架及操作栏。业务只提供标题、内容、默认位置、宽度提交与业务动作。DocBrowserManager 继续拥有标签、URL、历史；ChatThreadManager 继续拥有会话工作台选择和归属；SessionSurfaceManager 只编排打开哪个会话以及跨业务容器的移动。公共层不理解会话/文件协议，不搬运服务端运行状态。

对比：仅换按钮皮肤不能消除重复状态机；全量替换现有导航/资源系统为任意布局树，会同时重写没有问题的业务合同。选择统一外壳与操作模型，复用已成立的资源 owner，并补齐真实跨位置入口。单个视图的移动与整个视图组的悬浮明确区分，不能用同一个模糊按钮实现两种动作。

## 操作与视觉合同

| 动作 | 明确结果 | 状态保证 |
| --- | --- | --- |
| 在悬浮窗中打开 | 从列表等入口展示资源；已有主会话保持原位 | 沿用资源身份与共享草稿 |
| 悬浮此视图组 / 停靠到侧栏 | 移动整个容器；标签组与历史不变 | 相同 React 内容实例，保留 iframe、选择与输入 |
| 移动到全局右侧栏 | 将指定会话/文件视图交给全局容器，移除原临时视图 | 文件携带来源目录与会话身份；不依赖当前主路由 |
| 最大化 / 还原大小 | 覆盖应用可用区域；还原回先前位置和尺寸 | 不改资源和停靠位置 |
| 收起 / 展开 | 暂时隐藏内容，留下带标题的恢复条 | 不销毁内容，不取消运行 |
| 关闭视图 | 关闭指定标签或独立视图 | 不删除资源、不停止会话任务 |
| 隐藏视图组 | 暂时隐藏整个侧栏，可从原入口重开 | 保留标签与导航历史 |

所有外壳使用同一高度标题栏、语义色、边框、圆角、阴影、图标尺寸、tooltip 与键盘焦点。导航动作与窗口动作分组，窗口动作固定为位置、收起、最大化、关闭/隐藏；多项业务动作保留在内容工具栏/标签菜单。固定到右边图标轨道是“固定入口”，不称为停靠窗口。

悬浮窗标题栏空白处可拖动，八边/角可调整尺寸，交互时屏蔽 iframe；双击标题空白区最大化/还原。控件点击、文本输入及标签选择不触发拖动。浮窗聚焦提升层级，始终约束在视口内；浏览器尺寸变化重新约束。调整侧栏宽度也支持键盘。窄屏自动全屏呈现并提供显式返回/关闭；不显示无实际意义的拖动缩放控件。

Escape 先还原最大化，再收起悬浮窗；不吞掉输入法或子层已消费的事件。关闭后焦点回到可用入口，收起后焦点落视图组容器，Tab 可进入恢复控件。状态变化使用短暂且尊重 reduced-motion 的反馈，不对拖动使用位置动画。

## 内容差异与跨位置

- 会话：主路由、悬浮、全局侧栏与子会话工作台共享 SessionConversationArea。关闭视图不调用 abort/delete。
- 文件：源代码/渲染预览、目录、diff 保留工作台能力；跨入全局须携带文件完整描述与来源上下文，不把相对路径放到当前另一会话解析。原有内容相关动作继续使用业务 owner。
- 全局网页、文档、Marketplace 详情、Panel App：复用现有资源路由与 renderer；共享视图组外壳。不是所有内容都要增加主路由。
- 工作台概览、定时任务、关注等绑定会话的工具：共享浮动/收起/最大化外壳，保持会话归属；不伪造脱离会话的全局业务实例。

## 生命周期、持久化与安全

### 导航与视图记忆（用户补充，必需交付）

统一范围包含路由身份、前进/后退和阅读位置恢复，不限于窗口按钮。现有 `navigation-history` 已被全局与会话工作台使用；继续作为唯一历史转移算法，统一去重、回退后分叉截断、删除失效项、容量限制。业务 owner 提供资源路由与匹配规则；容器内部后退不冒充浏览器主路由后退。

现有 `ScrollRestorationManager` 为 DOM 与 Panel App 协议共用 owner，但只有内存存储、恢复时机单次、iframe key 只到标签而不到 URL。修正为有容量和版本边界的会话级记忆；资源+视图+路由构成恢复键，移动不改键，源代码/渲染视图分开。iframe URL A→B→后退 A 保留两份位置，不能由 B 覆盖 A。跨域网页不读取其 DOM，只对支持的桥接协议恢复；不承诺浏览器安全边界外的任意网站深层状态。

恢复时等待内容尺寸允许再应用，用户主动滚动立即接管；加载过程不能用暂时的 0 覆盖已保存位置。聊天的“跟随最新”是上层策略：已有历史阅读位置优先，新会话默认底部；用户返回底部后再跟随流式更新。不会把所有内容都强制套用聊天底部规则。

容器布局记忆和内容阅读记忆分开存储。刷新恢复停靠/浮动及合理尺寸，窗口缩小重新约束；未恢复内容的容器不自行重建业务。关闭后重新打开同一资源可恢复阅读位置；显式刷新内容与删除资源由业务 owner 决定是否失效。记录只含位置、身份与必要桥接 payload，限量、校验，并容忍浏览器存储不可用。

业务数据维持原有持久化；公共容器状态不存业务凭据或内容。已有全局标签/URL 恢复合同保留。浮动位置与尺寸按视图组持久化，刷新不承诺恢复正在输入的 DOM 内部状态；会话草稿沿用原有 owner。收起、最大化、停靠转换不能因切换容器 JSX 类型而重新挂载内容。内容不存在、文件失效等继续使用原有加载/错误状态。

通用框架不提供“任意回调插件注册”或无消费者的关闭拦截 API；当前文件是预览，不伪造未保存编辑状态。需要真实编辑能力时由业务报告状态再扩展关闭协议。主页面配置表单等不在用户指出的现有视图容器范围内。

## 页面协议与左侧固定区（用户补充，必需交付）

用户进一步要求统一页面身份和完整动作，而非仅统一外壳。将现有资源描述提升为页面描述：稳定 URI、标题、可重建的目标和上下文、适用位置。位置分为内容展示位置和导航固定入口，左侧原“应用”分组改为通用“页面”，右侧快捷栏仍是另一个固定入口。

页面动作由一个 owner 生成：在主区打开、右侧打开、悬浮打开、固定/取消固定到左侧、添加到聊天、复制 URI；当前位置只影响操作的可用性或当前状态，不复制菜单实现。应用专有动作（刷新、授权、删除等）保留业务扩展，不能替代通用动作。空白页及不能形成有效引用的瞬态视图允许不可引用，但必须是能力规则而非某处漏接。文件引用保留来源路径；会话引用使用原会话 URI，不复制消息数据。

已有 Panel App 左侧固定偏好属于服务端应用偏好，不另存第二份相同事实；普通页面固定信息由页面导航存储拥有，页面列表合并两个来源并按 URI 去重。主区已有路由继续使用原路由；没有主路由但可渲染的资源必须提供稳定页面承载入口，不能点击左侧后悄悄只打开侧栏。主路由的普通页面可以固定和引用；不适合多实例展示的设置表单等通过能力声明限制额外容器，不能重建嵌套全应用。

设计重审：本补充取代早先“仅三个容器即完整范围”的结论，新增 Required WV-11/12/13。在这些结果完成前不可报告整体交付。

### Markdown 资源链接（用户补充，必需交付）

AI 会话是页面资源的一种，语音输入中的“绘画”在本任务统一按会话理解。Markdown 普通链接可以指向任何受支持资源 URI；链接身份不包含临时窗口位置。统一打开策略优先定位已打开的资源视图；无现有视图时，会话/主路由页面默认主区，资料默认全局侧栏。明确打开方式可覆盖默认位置，所有入口共用策略。链接不能绕过授权或把未知 scheme 当作可执行指令。正文嵌入不属于本轮必需，普通链接可点击、可回退和资源不存在时可解释是必需。

资源图标作为页面身份的一部分：专属图标优先，加载失败或缺失时降级类型图标，未知类型使用通用资源图标。Markdown 使用紧凑内联“图标＋文字”而非卡片，保留链接键盘和复制语义。新增动作/URI/图标共用现有 right-panel-resources 领域，不新建平行页面注册系统。上述补充的设计 Review 检查了旧偏好单 owner、URI 安全和内容重建边界，通过；实现与验收仍未完成。

## 标准名称与 AI 可感知合同

正式名称为「NextClaw 资源协议」（NextClaw Resource Protocol），文内简称「资源协议」，不引入缩写或平行注册体系。资源是具有 URI、类型、标题、图标和能力的对象；视图是资源的一次展示及其阅读/导航状态；容器是主区、全局右侧栏或悬浮等承载位置。左侧固定项是资源的导航入口，不是另一份资源或容器。会话、Panel App、文件与普通页面均沿此术语描述；页面是可打开资源的用户称呼，不与资源竞争身份 owner。

AI 必须在稳定运行上下文中知道资源协议，区分普通 Markdown 链接、内嵌展示和主动打开工具。添加到聊天沿已有 ui_resource 元数据传输并作为不可信引用资料注入模型；它不是实时 DOM 内容，也不赋予额外读取权限。模型可复用用户引用或工具返回的真实 URI，不编造资源 ID。资源 URI 标识对象而非临时容器，模型不需要预测点击位置。工具返回与 Markdown 消费须验证同一资源往返，不以只改提示词代替链路证据。

补充方案 Review：名称不改变现有 nextclaw URI 兼容；引用资料不升级为系统指令；展示位置仍由 UI 打开策略拥有。新增 WV-16（AI 感知与引用往返）及 WV-17（术语一致），均为必需验收，未完成不可交付。

### 更多操作的视觉规范

更多操作统一使用竖向三个点。左侧页面行默认隐藏操作按钮，行 hover、键盘 focus-within 或菜单打开期间显示；无 hover 的触摸设备保留可见入口。显示与隐藏只改变透明度，不改变行布局或标题宽度。此项属于共享动作呈现合同，不由各资源自行决定。

## 资源覆盖补充：系统对象与 Skill

真实验收发现 nextclaw://objects/cron-job/... 属于既有共享对象协议，却未被页面解析器接入；marketplace-detail 也已有内容 renderer，但独立 URI 未注册。两者不是非法链接，必须复用原业务 owner 纳入资源协议。Skill 区分可重建的市场详情身份与本地安装来源身份，不能只支持技能市场集合，也不能把同名不同来源 Skill 合并。

资源矩阵补全：既有 objects 类型沿 shared parse/resolve 合同加载只读快照，保留对象 URI、版本与权限边界；操作可进入原业务页面。单个 Skill 沿既有 marketplace-detail 重建内容，补齐普通链接路由、类型图标、固定与聊天引用；本地 Skill 保留 ref/path 来源。文件原生 URI 需要明确来源根和 viewer/line/column，未提供来源不能擅自按另一个会话目录解释。已有集合 URI new-tab/apps/marketplace 与普通页面路由共同验收。未知对象类型不被任意 URL 执行兜底，而由对象解析 owner 给出资源级错误。

补充设计 Review：同一对象只保留原 URI/读取 owner；UI 桥接只提供视图，不另建业务 CRUD 或私有数据副本。WV-13/14/15/16 对扩展覆盖重新开启；新增 WV-18 逐类资源覆盖矩阵，所有必需项完成后才交付。

### 对象发现的 AI 闭环补充

资源链接不能靠模型猜 ID。新增只读 `resource_list` / `resource_resolve` 工具，直接消费现有 SystemObjectReferenceManager 公共合同；列表返回真实 URI，解析返回不可变资产引用，内容读取复用已有 asset 工具。没有新配置 owner，不执行对象业务动作。已安装 Skill 使用加载器 exact ref，市场详情维持独立资源身份。新增对象类型后同一注册表自动覆盖 UI 选择器与 AI 发现，不在提示词复制对象清单。CLI 的 `resources list` / `resources resolve` 已通过本地服务 API 消费同一 kernel 合同，不启动第二套运行时。
