# Bibo 自动保存与稳定目录菜单

## 目标、来源与现状

用户在 2026-10-03 要求参考 Notion 改善手机笔记/文件编辑保存，并补充面包屑目录菜单加载高度抖动。最终结果：用户安心编辑，不必寻找保存按钮；目录菜单打开、刷新和浏览时保持稳定。

当前编辑调用 `editFile` 只更改草稿并写入已有的账号隔离 sessionStorage；`saveFile` 才调用带版本的 `file.update`。共享 FileEditor 覆盖笔记、文件和聊天工作区。手机按钮存在但只有勾号，缺少触屏上的文字含义。真实浏览器 1440px 下目录浮层加载高度约 162px，完成约 80px，原因是 LoadingState 与条目共同参与布局。

愿景对齐：减少为保存和导航承担的操作负担，明确数据是否已保存，保护连续编辑。参考 [Notion 官方离线编辑说明](https://www.notion.com/help/guides/working-offline-in-notion-everything-you-need-to-know)：修改本地保留、联网后自动同步。这里采用自动保存体验；现有网页草稿保护继续使用，不宣称具备原生应用全量离线下载或多人合并。

## 用户链路与方案

用户在手机或桌面直接打开笔记/可编辑文件，编辑正文或源码。输入立即保留草稿，停顿 1 秒后自动提交；底部固定反馈区域显示等待、保存中和已保存。只有服务器确认当前正文后才能显示已保存。用户继续输入时，正在提交的快照与新草稿隔离，前一提交完成后接着保存新内容。文字“保存”提供立即提交，快捷键复用同一入口；保存失败时显示草稿保留并提供“重试保存”。

断网时保留当前标签页草稿并明确告知联网后同步，在线事件触发待保存正文；刷新后只有已验证读取的文件才能恢复自动提交。网络失败暂停自动提交，等待明确重试、新编辑或恢复联网，不持续轮询。版本冲突保留草稿并停止自动写入，用户通过现有读取最新/确认覆盖流程处理；不可静默覆盖其它设备修改。

目录菜单沿用共享 Popover 的定位、焦点和关闭行为。标题/返回占固定槽位，列表采用限制高度的内部滚动区域；初次无内容加载替换阅读区，缓存刷新保留条目并在标题槽位反馈，不添加撑高列表的 loading 块。空目录、错误/重试、分页和返回使用同一区域。菜单宽度与高度不随 loading/error/ready 切换跳变；目录变化仍保持面板几何。

实现检查还发现，共享目录刷新会在背后的目录树插入同类 LoadingState。已有条目时不再插入加载块，保持已有导航位置；这一同 owner 的相邻修正归 BE-05。

相比保留手动保存、只加文字按钮，自动保存更符合用户委托和日常笔记编辑。相比引入新的同步服务/全文协作机制，复用已存在的版本写入、草稿和文件编辑 owner，避免第二条存储链路。

## Owner、生命周期与边界

- 输入/草稿仍归 BiboSpaceOwner，存储格式保持不变；现有 set 在草稿变更时通知 FileEditingManager。
- 自动提交的定时器、序列、在线/后台事件和销毁归现有 FileEditingManager；同一文件最多一个在途写入，账号切换销毁旧定时器与事件订阅。只提交已打开验证、非只读、非冲突的脏稿。
- 保存响应一次更新详情、草稿、现有文件/笔记列表投影，不为每次自动提交额外刷新目录集合。
- 保存中撤销到旧正文仍是待确认的修改，继续保留草稿；刷新时已验证的服务端正文与草稿完全相同则认可新版本，不再重复提交。只读截断预览不能作为这种确认。
- UI 只展示状态和连接操作，不在组件 effect 中编排保存。正文与源码、独立页面与工作区共用同一路径。
- 目录读取/分页仍归 FileDirectoryManager，菜单只安排稳定展示区域。无新后端合同或容器修改。
- 抽象审计：没有新增同步 manager、queue service 或 UI 状态机；新增状态只有账号内文件网络状态，定时器属于既有写流程 owner。
