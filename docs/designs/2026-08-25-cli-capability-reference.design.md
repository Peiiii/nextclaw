# NextClaw CLI 能力全集文档设计

## 背景与用户任务

NextClaw 已有中英文 `/guide/commands` 页面，但当前只列出少量常用命令，无法承担完整能力盘点。目标用户包括普通用户、高级用户、开发者和项目维护者：他们应能从文档站进入一个稳定页面，理解 CLI 为什么是一等入口，按能力域浏览 NextClaw 的完整命令面，并确认某项能力是否可从终端、脚本、CI 或 Agent 调用。

## 当前事实与约束

- `apps/docs/{zh,en}/guide/commands.md` 已被文档首页、侧边栏和多篇指南引用，是现有公开入口。
- Commander 注册树是 CLI 命令存在性的事实源；公开文档不应另造平行命令 catalog。
- 中英文页面需要保留面向用户的自然说明，不能直接复制英文 `--help` 输出充当中文文档。
- 命令选项和专题流程仍由 `nextclaw <command> --help`、核心命令页和各专题指南解释；本页负责完整命令路径与能力地图。

## 方案比较

### 方案 A：新增第二个 CLI 页面

可以保留旧命令索引并新增“CLI 理念与全集”，但会产生两个相邻入口、重复命令清单和链接迁移成本，不采用。

### 方案 B：构建时从 `--help` 全量生成 Markdown

命令覆盖最准确，但生成内容只有英文运行时描述，难以维持中文质量、产品分组和专题链接；文档构建还会耦合 CLI 构建产物，不采用。

### 方案 C：升级现有页面并用真实命令树校验

保留 `/guide/commands` 作为唯一公开 owner。中英文页面人工维护理念、能力分组、命令用途和专题链接；测试直接遍历 Commander 命令树，要求两个页面都精确覆盖全部叶子命令。采用此方案。

## 信息架构

页面按以下顺序组织：

1. CLI 作为一等入口的产品含义与适用边界；
2. 如何使用本页和 `--help`；
3. 按用户心智分组的能力地图；
4. 每个能力域的完整可执行命令表；
5. 机器可读输出、自动化使用和相关专题文档。

命令表第一列只放规范命令路径，不混入参数变体。参数、选项和示例放在用途说明或专题页，确保同步测试能稳定读取命令身份。

## Owner 与同步合同

- 命令存在性的 owner：`packages/nextclaw/src/cli/app` 中的 Commander 注册树。
- 公开能力说明的 owner：中英文 `/guide/commands` 页面。
- 同步不变量：每个 Commander 叶子命令必须在中英文页面各出现一次；页面不得保留已经从注册树删除的命令。
- 新增或修改 `nextclaw` CLI 命令时，开发任务必须同步更新两个页面；自动测试阻止遗漏或过期命令进入交付。
- CLI、UI 和 Agent 入口继续复用对应产品 owner 的公共 contract，本页不改变运行时语义。

## 非目标

- 不在本页复制每个 option 的完整帮助文本。
- 不替代安装、故障排查、Headless、App、MCP 等专题指南。
- 不为文档生成引入新的 registry、DSL 或运行时 catalog。
- 不承诺纯视觉或直接操控能力必须提供 CLI。

## 验证标准

- 中英文页面都能从首页和侧边栏进入，并清楚说明 CLI 产品定位。
- 自动测试从真实 Commander 树得到命令集合，并证明中英文页面与其完全一致。
- CLI 类型检查、定向测试和文档站构建通过。
- 文档新增命令与实际 `nextclaw --help` 树一致，没有未说明的平行入口。
