# NextClaw 统一能力基座与 Bibo 宿主设计

状态：**架构返工中，未达到发布门槛**。本设计以 [BIBO-EDGE-2026-09-29](../work/2026-09-29-bibo-edge-conversation/acceptance-contract.md) 的用户任务与量化验收为准；任何已上线的边缘聊天数据都不能替代完整能力验收。当前采用的 Harness 具体形状、公开 API 和升级回归门见 [Harness 双宿主组合设计](2026-09-29-nextclaw-harness-host-composition.design.md)；本文较早的“C1 边缘原型接近最终形态”及 Bibo 独立编排表述不再作为实现依据。

## 2026-09-29 架构复核：统一基座是硬约束

用户明确指出：仅复用 `DefaultNcpAgentRuntime`、模型输入和压缩算法，而在 Bibo 侧重新实现会话持久化、提示词装配和工具目录，实质上仍是第二套产品运行链路。现有 `BiboEdgeConversationService` 正是这种实现，**不得作为最终架构上线**。旧容器 Harness 与新 Edge 对话并存，也不满足单一路径。此次复核优先于下文曾把 C1 纵向原型描述为接近最终形态的表述。

冻结的目标是：NextClaw 公共基座拥有一轮 Agent 运行的会话加载/事件提交、上下文与启动提示词、能力目录、工具调用、压缩和结果投影语义；本地 Harness 与 Cloudflare 宿主消费**同一个编排核心**。宿主只提供存储、模型、授权资源和需要 OS 时的执行环境。公共基座不导入 Bibo 或 Cloudflare。`NextclawHarness` 当前会启动依赖 Node 的完整 `NextclawKernel`，因此不能仅凭把类直接导入 Worker 宣称解决；需要从本地实现抽出可移植编排，并使本地路径也实际调用它。若无法证明双宿主真实共用，应实测完整 Harness 独立宿主的延迟/成本，再重新裁决，不能悄悄保留 Bibo 专用分叉。

开发版之间不做 legacy 格式兼容或双运行时；保留用户任务和数据体验是验收目标，不意味着持续维护每个试验版本的迁移层。存储采用账号隔离的 R2 路径键为唯一文件字节真相；Worker 直接读写，需 OS 时用官方 `sandbox.mountBucket` 按前缀挂载。无 SQL 文件索引、投影同步或 Agent 显式保存步骤。Git、依赖与构建缓存留在执行器临时磁盘。

当前硬门槛：① 本地 Harness 和 Bibo 运行同一个公共编排核心的可执行证据；② 启动文件、记忆、压缩、会话连续性、工具/Skill 与主要用户任务逐项对账；③ 纯聊天不获取执行器，命令才按需获取，文件读写及挂载使用同一 R2 真相；④ 真实入口首字/冷热工具 p50、p95、p99、成本及故障恢复数字。**单元测试或代码路径存在不能替代生产实测。**

## 当前架构决策与复核条件（2026-09-29）

**已冻结的计算主链路 C**：Bibo 入口/账号 DO 内运行同一 NCP 对话与可用能力目录；普通聊天及无需进程的工具保持边缘直达。Agent 的身份、会话和决策不属于任何一个 OS；需要 OS 时，由 Agent 通过公共能力请求创建、选择、连接、挂载或释放隔离执行环境。一个任务可顺序使用不同环境；确有并行任务时可同时持有多个环境。对话循环始终只有 NCP 一条链路。NextClaw 公共层拥有会话、能力授权与调用结果语义，不导入 Bibo、Cloudflare 或宿主实现；Node 本地版继续使用本地实现。**统一语义不要求两宿主装配完全相同的工具实现或原样运行每个 Node provider。** Worker 原生能力、云服务 API 和隔离执行器可分别实现同一上层用户任务，能复用稳定代码时复用。

**2026-09-29 用户修订的实现边界**：完整本地版仍是用户任务结果的能力基线；不再把 16 类 provider、每个既有工具名和 Node 实现的无缝复用当成上线硬门槛。硬门槛是上层任务和体验：原有 Bibo 能力与数据不退化，普通聊天快且零容器，文件/网络工具直达，OS 任务按需可用；本地版可完成的其它非设备专属任务用 Bibo 宿主适合的工具达到相应结果。持续任务和用户资料按明确承诺恢复，成本/性能与迁移有实证。对本地能力逐项按**用户任务、入口、结果、必要例外**对账，不用清单数量宣称产品等价，也不为满足静态工具清单建设无实际用户入口的迁移层。

**默认临时、按需挂载原则（用户再次纠偏）**：新执行环境的文件系统默认没有用户持久目录，未挂载部分随环境回收。Agent 按任务选择需要的用户资料或结果等资源，请求挂载到明确路径并获得可见的读写范围与持久性说明；只有挂载路径内的普通文件写入会自动持久化，Worker 文件工具随后读取的是同一份逻辑资源，不需要额外 `save`/`publish` 工具。Git clone、仓库历史、`node_modules`、包管理和构建缓存默认全在容器临时磁盘，**平台不把这些内容同步进用户文件资源**；需要保留最终产物时，Agent 将产物写入选定的挂载路径。用户若另有长期仓库需求，可使用获授权的远端 Git 服务或单独讨论，不把项目工作树自动挂载/同步列为这条主链路的前提。平台必须以路径隔离、权限和真实任务验证这个模型，不只靠提示词。

**环境控制也是 Agent 能力，不是环境的所有权**：Agent 可以选择环境类型、镜像/能力配置和资源挂载，也能观察、停止及复用仍有效的环境；启动/挂载请求由宿主校验账号授权、允许的资源、最小权限、隔离、并发、预算和租期。环境 ID、挂载 ID 与调用收据属于公共能力合同；平台负责超时、撤权、崩溃及闲置后的兜底回收。未授权资源不能因模型选择而被挂载；多个环境不得通过共享凭据或默认全盘挂载意外串联。此处的“自由”是 Agent 不被固定在某个宿主或 OS 内，不是绕过用户授权和资源边界。

**调用形态要避免模型多轮空转**：普通一次命令可由 Agent 在一次工具调用中给出环境需求与待挂载的资源清单，宿主在工具内部完成校验、懒启动、挂载、执行和回收；这仍是 Agent 自己触发和选择资源。需要多步命令、后台服务或并行环境时，提供显式 `create/attach/mount/inspect/release` 能力并返回稳定环境句柄，后续命令明确指定句柄。不能强迫每个简单命令都经过“创建→挂载→执行”三次模型决策，否则 1～3 秒的容器启动收益会被额外模型往返吞没。多个环境之间没有隐式共享当前目录、进程、权限或文件；同一持久资源的并发写挂载采用排他租约或可证明的冲突处理。

公共合同中的“挂载”是**把某个已授权资源附着到某个环境**，返回该环境内可使用的位置和读写范围，不预设底层必定是 Linux bind mount、R2 FUSE 或同一台机器。POSIX 环境可以返回目录路径；其它环境可返回原生资源句柄。Agent 只依赖资源身份、能力与生命周期，不依赖 Bibo 或 Cloudflare 的物理拓扑。Node 本地宿主也通过这一语义暴露本地环境与文件，但无需人为复制本地磁盘。

**当前优先验证 C1**：将用户持久资源留在 Cloudflare DO/R2，Agent 按需启动 Cloudflare Sandbox/Container，并仅挂载此次选中的资源；未挂载的容器文件系统继续是临时的。C1 的挂载底层可以是 R2 路径挂载，或在真实任务证明必要时使用对 Agent 透明的本地缓存和自动回写；后者不能向 Agent 或用户增加保存步骤，已确认的持久写入须能从 Worker 回读。C2 是 C1 的按需挂载在实际任务中仍无法兼顾延时、可靠性和规模时的候选：另一台持久宿主拥有账号 POSIX 资源，Worker 经可信文件接口访问，按需执行器只挂载选中的账号资源。两者消费相同的 NextClaw 资源与挂载合同，不能同时在线写入。C2 的可信控制面带来跨网调用、固定费用、备份和可用性责任。

**目录挂载实现复核（2026-09-29）**：官方 Sandbox `mountBucket(binding, path, {prefix})` 已提供按 R2 前缀直接挂载目录，生产挂载是直达文件系统视图，R2 Workers binding 的读写和列举具有强一致性。当前未上线的纵向原型为适配旧 `state.files` + 随机 R2 blob，每次挂载复制选中目录到运行专属前缀，执行后扫描并回写；它能验证 NCP 工具接力，却让挂载成本随文件总量增长，100 MiB/大目录还会触发全量字符串读取，不满足 BE-13/14。**最终 C1 文件 owner 应优先用账号隔离的 R2 路径键作为可挂载的持久字节真相**，Worker 文件工具与 Sandbox 选定前缀访问同一键空间；目录索引/文件类型只是可重建的产品元数据，不能成为第二份正文真相。R2 ETag 可作为文件内容的冲突令牌，旧 Bibo 数字版本只承担界面比较所需的兼容映射，挂载行为本身不产生新版本。文件移动/删除、空目录、旧 ID/URI、R2 条件写入、OS 外部写入后索引发现和故障清理须由真实测试裁决；若直接前缀无法满足这些合同，才保留投影桥接，且不得把它称为最终可扩展实现。

现有证据：C1 的直接 R2 文件访问可行，带一个 R2 挂载文件写入并由 Worker 即刻回读的自然休眠后探针 12/12 成功，端到端 p50/p95 为 3.229/5.487 秒。R2 FUSE 写 200 小文件超过 120 秒、5,000 文件工作区全量归档在加入无关 100 MiB 后恢复约 9.694 秒，说明**不能把 Git、依赖和整个工作树写进挂载目录或每轮归档**；按用户本轮明确纠正，它们本就应留在临时磁盘，因此这些反证不构成 C1 出局理由。C2 的隔离原型 12/12 次「远程写→按需容器命令→远程读」成功，客户端整段 p50/p95 为 2.250/3.092 秒，小文件远端读取 p50/p95 为 241/264 毫秒；但还没有计入专用主机的费用、备份和故障。两者都不是生产分位。D 的每用户完整 Node 进程仅作同标准对照。

**裁决实验与硬退出条件**：先在 C1 分别跑纯聊天零环境、未挂载环境的命令、临时磁盘 Git clone/安装依赖与构建、按需挂载单个已有文件、在挂载路径写最终产物、100 MiB 用户文件、双环境顺序/并行调用和后台服务。记录挂载资源与临时磁盘各自产生的字节/文件数、冷热等待、写后即读、下次调用恢复、失败后可见结果和费用；不调用额外保存工具仍必须完成任务。**禁止把临时 Git/依赖目录的逐文件同步当作默认路径或验收负载。**先测官方挂载；只有真实挂载资源的常规读写门槛失败才考虑透明缓存/自动回写。C1 必须通过租户/密钥隔离、已确认写入恢复、同路径冲突、100 MiB 文本与二进制流、旧账号迁移、完整本地能力任务、真实冷热工具 p95/p99、纯聊天零执行器及每用户总成本。若 C1 在相同任务下仍无法达标，再正式比较 C2 的跨网读写、同目录执行、主机费/备份和故障。不能通过隐藏能力或降低验收标准收尾；当前原型不足以上线。

一致性只用于**已挂载的持久资源**：成功返回的写入不会丢、后续读取看见它、同一路径冲突不被静默覆盖、命令部分成功/失败如实显示。未挂载文件系统不是第二份长期权威，不要求其内容与持久资源实时同步；更不要求命令改动多个文件与 NCP 历史跨系统原子提交。工具结果须准确说明哪些路径会回收，但不让 Agent 执行额外保存动作；失败时不能假报挂载路径的内容已经持久。

三个黄金验收链路：① 用户在原 Bibo 会话继续纯聊天，立即看到接受/首字和完整回复；旧上下文连续，执行器启动数不变。② Agent 先通过 Worker 读取已有文件，按需取得 OS 并挂载该资源，在容器临时目录完成 Git/依赖/构建，再把最终产物写入挂载路径；不调用保存工具，Worker 文件工具和 UI 立即读到新内容，刷新及环境休眠后仍在；临时仓库与依赖在回收后消失且结果如实说明。③ 旧用户升级后从原文件入口打开、编辑并下载文件，再让 Agent 使用它；100 MiB 文本/二进制走流，不转成模型上下文里的完整字符串；模拟宿主重启与恢复后摘要一致。另验证 Agent 在同一会话里顺序使用两种环境、按授权在两个环境分别挂载资源，且持久结果一致。所有链路由 AI 在真实入口和生产灰度自验，用户只需评判主观等待感受。

## 用户结果与不可妥协边界

1. 同版本、同配置与同等授权下，以完整 NextClaw 本地版**能完成的用户任务**为能力基线；本次还必须完整保留原有 Bibo 用户能力。Node 工具名、provider 数量和源码的原样云端移植不是验收目标；缺口以用户任务和真实入口表述，若非设备专属任务无法等价须逐项解决，不能把静态注册表或工具复用率当成成败指标。
2. 普通聊天以及无需 OS 的文件/网络工具不触发用户容器；需要 OS 的调用按需启动隔离执行器，用户先看到真实已接受/等待状态，随后得到结果。首字和各阶段延迟、容器调用和每用户成本必须有生产数字。
   决策单位是**某一次工具调用**，不是整段会话、整轮消息或工具是否“高级”：读文件只用持久字节存储，`exec`/二进制/进程工具才需要 OS；若 MCP 走纯 HTTP 可直达，stdio MCP 需要执行器。
3. NextClaw 是唯一通用基座：NCP 事件、会话/运行状态语义、能力授权与工具调用结果语义由公共内核拥有。Node 产品和 Bibo 通过适用的公共合同装配各自宿主工具；公共包不导入 Bibo/Cloudflare。这里要求的是**稳定的上层语义与清晰的依赖方向**，不是所有宿主必须运行同一个 Node 进程、装配相同目录或复用每一段工具实现。
4. 用户事实只有一个持久 owner。旧用户用一次性迁移、版本校验和有限备份保护；隔离执行器中的磁盘是缓存或租约内工作副本，不能悄悄成为第二份权威。Node 本地版仍保有现有文件和运行语义。Bibo 最终在线运行包不得保留 legacy 对话分支。

**方案裁决顺序**：先逐项固定用户能做什么、完成所需等待和反馈、状态连续性、隔离与单位成本；再选择 Worker、进程、容器和存储原语。现有 Node Kernel 的装配方式、全局路径和工具实现只是迁移成本与回归风险的证据，不是要求用户接受额外网络跳、常驻内存或能力缺口的理由。C/D 使用同一 BE-01～14 门槛；如果两者都不达标，继续改变内部结构，不降低用户结果。

## 现状证据和失效机理

`ToolProviderContribution` 给完整 Node Kernel 注册 16 类 provider，涉及 Core、Session、Project、Messaging/cron、MCP、Service App、设备等；`CoreToolProvider` 单独提供文件、命令、网页和记忆工具。Bibo 的 `BiboEdgeConversationService` 虽使用同一 NCP loop、模型输入和压缩组件，却手工只装配 Bibo 空间、展示、用户提问及网页工具；因此能力缺口发生在**能力装配与状态/宿主边界**，不能用同一模型循环就声称等价。16 类 provider 是盘点入口，不是必须整体移入 Worker 的 16 个模块：每类按用户任务与资源依赖拆成 Worker 直达、独立持久服务、按需执行和确实需要设备授权的路径。旧 Bibo 容器 Harness 同样有工具白名单，不能作为新目标的上限。现在的容器 `onStart()` 会恢复整包快照，runner 每轮创建 Harness，`commitSnapshot()` 把最多 32 MiB home 压缩上传；让边缘 Agent 直接在这个旧容器里执行 `exec`，会重新引入双份文件状态、全包压缩和令牌落盘风险。

当前 `conversationMode` 按账号在 `edge`/`legacy` 间选整个对话运行路径：新账号默认 edge；有旧数据的账号迁移并校验后切 edge；管理员可用反向导入、快照再切 legacy。它**不是**某个工具调用的动态分流。既有生产盘点 4 edge、0 legacy；旧路径当前主要是迁移/回滚合同。专用账号 edge→legacy→edge 的 5 个会话摘要一致，但只证明该样本，旧路径不补足边缘能力。用户 2026-09-29 明确修订：Bibo 是新项目，最终在线产物**不保留 legacy 对话路径**。现存状态用一次性迁移、回读与有限备份处理；发布前证明可恢复，发布后从常规运行包删除模式分叉、旧 Harness 对话入口和整包压缩提交。按需执行器是工具调用资源，不能借旧 runner 充当第二套 Agent。

### 从实际 provider 反推的能力清单

下表是源码注册类别，不等同于每次运行都获授权。动态类别必须在相同配置、安装和权限下生成实际目录；“计划绑定”是设计目标，尚非实现证据。

| 本地 provider | 用户任务与状态依赖 | 计划绑定；当前缺口 |
| --- | --- | --- |
| StructuredResult | 结构化结果协议 | 公共 NCP 语义直达；Bibo 现未装配该 provider |
| Resource | 引用系统对象并解析 | 公共资源 ID/授权，宿主对象存储；Bibo 未实现 |
| ShowContent | 展示文件或内容 | Bibo 已接 `show_file`，其它展示语义需对账 |
| InboxDelivery | Agent 送达与收件箱 | 持久送达状态；Bibo 有迁移记录但边缘未装配工具 |
| Observation | 持续观察与查询 | 持久观察 owner/后台触发；Bibo 未接入 |
| Desktop | 用户本机桌面操作 | 经用户授权的配对设备；未配对是明确限制 |
| Core | 读写编辑、目录、图片、`exec`、网页、记忆、gateway | 便携文件/网络直达；OS 调用按需执行；Bibo 目前只有网页和 Bibo 专用空间 |
| Messaging | 渠道消息与 cron | 持久自动化和已安装渠道；Bibo 文档当前明确缺后台任务/通知 |
| Project | 项目与项目工作 | 项目存储/权限；Bibo 未装配 |
| Session | 会话查询、分支、请求、异步问答 | 共用会话状态语义；Bibo 仅异步问答 |
| Asset | 生成产物的保存/读取 | 版本化字节对象；Bibo 未装配 |
| ServiceAction | 已授予的外部服务动作 | 授权动作目录和调用；Bibo 未装配 |
| ServiceAppJob | 应用持久 Job 列表/观察/取消 | 后台作业状态；Bibo 未装配 |
| ServiceAppAiCapability | 应用模型/Agent slot 管理 | 安装清单和授权；Bibo 未装配 |
| AppPackageDependency | 依赖与密钥检查/绑定 | 私密配置及安装状态；Bibo 未装配 |
| MCP | 已连接 MCP 工具 | HTTP 可直达，stdio 需隔离执行器；Bibo 未装配 |

除此之外还要独立比较模型切换、Skill 加载、扩展/应用安装、配置入口和长期进程，因为它们不一定表现为上述工具，却是完整本地版能完成的用户任务。目录若随权限变化，应同时证明撤权立即生效；不能在纯聊天时为了刷新动态目录而启动容器。

## 对比与裁决

| 方案 | 能力等价 | 普通聊天延迟/成本 | 状态与风险 | 裁决 |
| --- | --- | --- | --- | --- |
| A. 继续只给 Bibo 手写少量边缘工具 | 本地能力持续分叉 | 已证实快、便宜 | 缺口隐蔽，扩展每次双实现 | 淘汰 |
| B. 全部请求进入每用户 Node 容器 | Kernel 能力易复用 | 冷启与整包恢复回到聊天主链路，平台成本随活跃用户攀升 | 旧数据形态便于沿用 | 不符合 BE-01/02/06 |
| C. Worker 对话使用公共能力目录；无需 OS 的能力直达，进程/二进制/后台能力按需由隔离执行环境实现 | 必须证明完整本地版的逐类任务等价，不能只继承现有边缘五项工具 | 普通聊天保持已测的边缘路径，OS 调用付冷启 | 需要公共能力宿主端口、单一状态 owner、动态能力同步及执行器回写 | **优先纵向验证**；完整能力与文件闭环是硬门槛 |
| D. 共享接入服务调度隔离的用户 Node Kernel 进程，OS 工具再进入隔离执行器 | 完整 Node Kernel 与普通文件系统可直接复用 | 普通聊天增加网络跳与用户进程启动，常驻主机有固定费；不启动用户容器 | 需持久主机、账号级 OS 隔离、旧数据迁移与成本验证 | 同条件对照；C 不达标或 D 实测更优时再采用 |

裁决依据已由纯聊的历史性能扩展到完整能力与文件结果：C 的纯聊切片已在线达到低延时，且独立 Cloudflare 探针没有证实容器固有十秒启动；它仍缺完整本地版的能力映射、执行器写回同一权威工作区及长任务状态。D 本机完整 Kernel 启动与 Linux 内存采样显示能力复用较直接，却会使每次纯聊增加跨主机调用和用户进程启动。**下一纵向切片优先验证 C**：公共 Kernel 能力目录和 NCP 对话语义留在 Worker，按工具依赖接入 Node/Sandbox 执行宿主，以 `read_file → exec → read_file`、完整能力代表任务、100 MiB 文件及新旧会话首字复验。不能把现有五项工具补几个名字就当成完整能力。若 C 的能力、状态或尾延迟无法在 BE 门槛内实现，再以同条件 D 纵向对照；两案都不得豁免未达标项，也不保留两套在线聊天主链路。

**启动时间复审后的第一性原理裁决**：第二批 Cloudflare 现场探针把无挂载 Sandbox 冷调用的中位数测到约 2 秒、自然休眠后挂载并读回约 3.2 秒；前一批 10 秒不能再当作平台的固定下界。既然纯聊的 Worker 路径已证明快，且用户只在需要 OS 工具时接受冷启，C 应先接受完整能力与状态闭环验证。一次 17 秒尾部样本不能排除 C；D 的本机 0.3～0.9 秒 Kernel 启动也不能代替公网首字、租户隔离和固定费用证明。纯聊零用户容器、BE-02/09/13/14 和旧数据不退化作为两案相同门槛。

**C 内部必须再比较文件 owner 的物理形态**：C1 让 Worker 直达与按需 OS 挂载同一份 Cloudflare 持久资源；R2 路径键直挂、带透明缓存的挂载以及现有 DO 版本索引都只是实现候选。当前未上线的 `BiboWorkspaceStore` 草稿把逻辑路径存在 DO SQLite、内容放在随机 R2 blob key；官方 R2 桶挂载不能据此呈现逻辑目录，不能直接接到 OS。必须先裁决唯一文件权威及路径/版本/挂载写入的关系，再保留或重做该草稿。C2 让 Worker 经最小权限文件 API 访问共享持久 POSIX 服务；OS 执行器只挂载选中的账号资源，聊天和文件直达仍不启动用户进程。两者的产品合同、工具目录、NCP 会话和按工具分流相同，因此不是两套在线聊天架构。按相同 100/1000 人、300/900/1800 条负载以及 `read_file → 挂载 → exec → read_file`、临时 Git/依赖任务仅写少量持久产物、100 MiB 用户文件裁决；不能因某项已有代码便预先排除另一项。

**D 的本机可行性采样（2026-09-29，未接模型/生产网络）**：共享 Node 进程中，每个临时用户单独创建 worker thread、独立 `NEXTCLAW_HOME`，从线程创建到完整 `NextclawKernel.start()` 的五次顺序样本为 0.580、0.352、0.336、0.887、0.367 秒；五个均存活时进程 RSS 到约 632 MiB。这个采样说明「完整 Kernel 必然让普通聊天等数秒容器启动」不是事实，也让 D 值得正式比较；它没有证明公网首字、100/1000 用户成本、持久文件、故障恢复或安全。worker thread 与其它用户共享 OS 进程和文件权限，**不能当租户安全边界**；MCP/扩展/命令等不可信执行仍须隔离。若采用 D，必须在同负载下证明多租户状态隔离、用户文件权限、闲置回收、后台任务与模型链路尾延时，且不退化 BE-02/06/07/13。当前不据此将 C 改为 D。

进一步以原有完整 `nextclaw serve`（内置扩展启用）启动五个全新临时 home，到 `/api/health` 返回 200 的本机样本为 1.478、0.464、0.420、0.453、0.414 秒，各进程就绪时 RSS 约 208～218 MiB。macOS Docker Desktop 上，已缓存的 Debian 镜像以只读根、无网络、低权限执行固定命令 20 次 p50/p95/p99 为 0.334/0.582/0.826 秒；同样约束且绑定临时工作区读 100 MiB 文件、写回产物一次为 1.656 秒。都是**本机候选下界**，不能套成 Linux VPS、Cloudflare、带模型/鉴权/用户数据的生产分位；但它们使「共享 Node + 本地持久文件 + 仅 OS 调用拉起隔离进程/容器」值得与 C 同级比较。这个方案保留完整 Node Kernel 和普通文件系统，减少为 16 类能力各自移植 Worker 的风险；代价是常驻主机、按活跃用户计的内存、可用性/备份及跨租户安全。当前共享 worker thread 本身不具备 OS 隔离，不能直接上线为 Bibo 多租户宿主。

固定费敏感性也必须纳入 BE-06：以[Hetzner 2026-06 官方价目](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/)举例，Singapore CPX22（2 vCPU/4 GB）为 $30.99/月、CPX32（4 vCPU/8 GB）为 $57.99/月，未含备份、卷、额外节点与运维；[官方规格](https://www.hetzner.com/cloud-made-in-germany/)支持该内存档。按 1,000 MAU、每人 900 条/月、每条占用宿主 10 秒的**仅供容量推演**假设，平均活跃用户约 3.5、10 倍峰值约 35；若每人完整进程 0.21 GiB，峰值用户进程约 7.4 GiB，单台 8 GB 节点没有安全余量；worker thread 单用户增量约 0.12 GiB，峰值约 4.2 GiB，但它没有安全边界。不能只拿 $30.99/$57.99 与边缘方案的 $47～107/千人历史估算直接宣称谁更便宜；须按同样 300/900/1800 条负载、真正驻留时长、OS 任务/备份/故障容量计算每人总价，并用线上可用性和首字复验。

2026-09-29 阿里云账号的只读 `swas-open list-plans` / `describe-price` 返回新加坡 `swas.s.c4m8s70b1.linux` 为 4 vCPU、8 GiB、70 GiB ESSD、标称 200 Mbps BGP，按月原价和成交价均为 **¥220/台**；两台仅实例费 **¥440/月**，尚不含备份、额外卷、带宽/流量条件、运维和模型/搜索。该账号报价比上面的公开异币种例子更适合做 D 的现场探针，但它不是已购买实例或可承载量证明。一个 8 GiB 节点在 35 并发、每个约 175 MiB PSS 的假设下用户进程约需 6 GiB，尚需给共享服务、文件缓存、执行器和故障切换留余量；两台能否达到目标取决于用户在节点间的分布与故障时的容量。

**D 的新增隔离阻断项**：`NextclawKernel` 虽有若干 `homeDir`/store path 选项，`assetStore` 等初始化仍使用 `getDataDir()` 等进程环境派生路径；`CoreToolProvider` 按默认配置直接构造本地 `ExecTool`，其它扩展和 stdio MCP 可加载/运行 Node 代码。因此不能把多个用户的完整 Kernel 直接放到同一个主线程、只换请求中的 userId 就认为状态隔离。worker thread 默认有独立环境变量副本，可承载逻辑状态隔离实验，但共享进程级文件权限，不能执行用户可影响的 Node 扩展、MCP 或命令。若 D 要成为正式方案，必须二选一并实测：将所有持久路径改为显式 per-user 宿主端口、用户可执行代码全部转隔离执行器；或用不同 OS 身份/隔离进程承载用户 Kernel，并接受其内存与冷启动成本。两者都要通过双账号交错调用、恶意路径/扩展、故障重启与密钥泄露检查。尚未解决前，D 不能因本机启动快就替换 C。

**D 的可验证收敛形态（候选，未裁决）**：一台常驻 Node 接入服务只负责鉴权后的消息路由、活跃进程管理和模型密钥代理；每位活跃用户由独立 OS 身份的短驻留 NextClaw Kernel 进程持有完整本地能力，未运行时无需用户容器。账号的持久工作区是普通本地文件系统，Node 文件工具直接访问；确需命令、二进制或独立环境的调用才启动该用户专属隔离执行器，绑定同一工作区。执行器停止后保留明确承诺的软件环境或任务状态，不用整包压缩快照；后台任务/服务按真实生命周期保活。Bibo 只提供账号、额度、界面与云端宿主适配，Kernel 仍是通用产品基座。该形态省去边缘 Worker 逐个重做 16 类 Node manager 和跨 DO/R2 的 POSIX 工作区提交协议，但需要可靠主机、文件备份、用户进程与模型密钥隔离、旧 DO 数据一次性迁移、边缘到宿主的延时/可用性与 300/900/1800 条成本实测。`ExecTool`、stdio MCP、Service App runner 和用户扩展的 OS 调用都要逐类验证隔离，不能只代理一个 `exec` 名称便宣布 BE-09/10 通过。

**部署边界澄清**：D 会改变 Bibo 的计算位置，不是在 Cloudflare Worker 内创建用户进程。现在线上的 Worker/DO 直接完成边缘对话；D 保留 Worker 作为公网入口、鉴权与额度边界，却将完整 NextClaw 对话运行转交另一台 Linux 宿主上的短驻留用户进程。每用户进程是复用现有 Node Kernel、进程级配置和普通文件系统的手段，不是产品目标，也不由“容器启动必须很慢”推出。代价是跨网络跳、主机固定费用、容量与运维；若同负载公网首字、全能力、隔离和每用户成本不优于 C 的 Worker + 按需 Cloudflare Sandbox，D 即淘汰。纯聊天的精确表述是“不启动用户容器”，而非“不启动任何用户计算进程”。

**D 的执行隔离再拆解（2026-09-29，待现场裁决）**：额外 OCI 容器是实现隔离的一种手段，不是用户任务本身。D0 先验证完整 Kernel 所在的每用户 Linux 服务能否作为安全边界：不同用户身份、仅各自可写的持久状态目录、进程/临时目录/设备隔离、无特权和 Docker socket、cgroup 资源上限、服务端按账号校验的模型/搜索代理；`exec`、stdio MCP 与其它 OS 子进程仅在实际调用时产生，并继承同一租户限额。这样纯聊天虽按需启动轻量用户进程，却没有用户 OCI 容器；文件和命令天然看到同一目录，软件安装与长任务不用从 R2 还原。若用户可执行代码能访问其他账号、平台密钥、越过资源限额或破坏 Kernel 本身且无法在同一服务内隔离，就采用 D1：工具调用时进入独立受限执行器，仍挂载同一账号目录。不能把 Linux UID 本身视为充分安全证明，也不能仅为迎合“容器”这个实现词而重复启动一层环境。

本机 Linux amd64 镜像中的早期纵向见证：以非 root UID 20001 启动完整 `NextclawKernel`，约 0.27 秒 ready；当前注册目录返回 53 个工具，`write_file → read_file → exec → read_file` 在同一个账号工作区成功。另以 UID 20002 创建私有文件，UID 20001 直接读取及通过符号链接读取均被 OS 拒绝。这里的 53 是**已注册工具名数量**，不等于 53 项用户任务可用，更不覆盖模型凭据、网络、动态扩展、持久重启、系统服务沙箱及生产并发。D0/D1 必须在真实 Linux 主机完成跨账号恶意路径、进程可见性、凭据、资源耗尽、后台生命周期和故障恢复测试后才裁决；若 D0 通过且全链路延时/费用更好，删除不必要的额外执行容器分支。

**D 的 Linux 内存补测**：复用已构建的 NextClaw/Bibo Linux amd64 镜像，在本机 Docker Desktop 的模拟环境中，以五个不同 `NEXTCLAW_HOME` 启动完整 `NextclawKernel.start()`；五个就绪时间 335/320/322/310/292 毫秒，五个同时存活的 `/proc/<pid>/smaps_rollup` PSS 为 174,908/174,816/175,679/174,265/174,875 KiB。单进程样本就绪 541 毫秒、PSS 218,834 KiB。多进程共享只读页使 PSS 低于 RSS，按 35 个峰值活跃用户、每人约 175 MiB 推演，用户进程合计约 6 GiB，8 GiB 主机理论可容纳但故障/缓存/峰值余量有限；不能把该估算当成已通过 BE-06。模拟运行、没有真实模型/网络和生产 Linux 宿主；进程安全与 8 GiB 下的 p95 必须现场测。

#### D 的单链路和状态归属

```text
Bibo 浏览器 → Cloudflare 身份/额度入口 → 共享接入服务
  → 当前用户的 NextClaw Kernel 进程 → NCP 会话/工具/长期状态
       ├─ 普通聊天、文件、HTTP 工具：用户持久目录/授权外部服务
       └─ 进程/二进制工具：宿主执行端口 → 用户专属隔离执行器
```

接入服务持有账号到进程的租约，按需启动用户进程并在无聊天、后台任务或服务租约时回收；纯聊天只启动用户进程。每个进程以独立 OS 身份、独立 `NEXTCLAW_HOME` 和持久目录运行，配置、journal、文件、应用安装状态均归此目录或同账号的持久数据库。用户进程没有 Docker socket、其它用户目录和平台模型密钥；它通过进程间调用请求模型代理和 OS 执行。共享接入服务只转发身份已核实的账户请求，临时授权绑定账号、会话、调用 ID 和过期时间；进程只接受该服务的 IPC，不开放可被公网直接调用的用户端口。节点宕机后，新的租约从同一持久状态恢复，旧进程租约失效，重复请求由 journal 幂等处理。

`exec` 的公共 `ExecTool` 已有宿主 runner 参数，本地安装沿用 Node 直接执行；云宿主通过 Kernel 选项注入 runner，执行器由拥有 Docker 权限的受控服务创建/启动，工作区只绑定该用户目录，固定镜像、资源/网络限制和安全配置，绝不把 Docker socket 或模型密钥交给用户进程/容器。文件由宿主和执行器访问**同一个持久文件系统路径**，命令写入的产物在执行结束后直接被 `read_file` 看见；工具返回前刷新文件元数据并记录结果/失败。每用户隔离执行器停止后保留明确承诺的可写层和工作区，不依靠整包压缩；删除账户和依赖环境有独立清理生命周期。此处只是 Core 工具的纵向合同：stdio MCP、用户扩展、Service App runner、后台服务和子代理直接创建子进程的入口必须继续盘点并导向相同权限/资源边界，不能把单个 `exec` 注入当完整 OS 隔离。

迁移的权威切换以账号为单位：先只读导出当前 DO 的 NCP 会话、问题、Bibo 结构化空间与 R2 文件，导入该账号的 Kernel journal、Bibo 宿主数据和工作区；对消息序列、压缩检查点、文件路径/字节哈希、任务及记忆做双向校验。短暂冻结该账号的新写入并记录源版本，再做最后增量校验和原子路由标记；只有新宿主确认可回读后才接受首条新消息。切换后 DO/R2 仅在限定恢复窗口保留只读备份，不能继续在线双写；若新宿主已经产生新事实，恢复必须以新状态为准并修复前进，不能把旧快照覆盖上去。原 Bibo 前端的会话和空间 API 由同一新宿主适配，但最终聊天事件只来自 Kernel NCP 主链路，UI 的重试/取消/预览用真实持久状态核对。

这份 D 合同仍有设计 Review 阻断：独立 OS 身份的生命周期与文件权限、执行器中软件安装状态、NCP journal 导入 API、Bibo 前端事件映射、跨节点恢复/备份和真实 100/1000 用户费用尚未纵向验证。每一项要以原本地版用户任务和旧 Bibo 行为双向对账；在发现不可满足的性能或成本前不进行生产切换。

### C 的执行器实现候选：Cloudflare Sandbox SDK

2026-09-29 核对官方文档后，优先把 [Sandbox SDK 的懒启动实例](https://developers.cloudflare.com/sandbox/api/lifecycle/)作为验证对象：取得 sandbox 句柄不启动容器，首次执行文件或命令操作才启动；[R2 绑定挂载](https://developers.cloudflare.com/sandbox/api/storage/)支持指定前缀且不向容器交付 R2 凭据。这样有机会用同一 R2 字节对象支持 Worker 文件工具和 OS 文件路径，免去现有每轮整包压缩、恢复与 32 MiB 快照上限。[后台进程](https://developers.cloudflare.com/sandbox/guides/background-processes/)和[端口/隧道](https://developers.cloudflare.com/sandbox/guides/expose-services/)提供长任务与 HTTP 服务的底层能力，用户级计划、租约、授权、计费和恢复仍由 NextClaw 公共状态合同拥有。

该 SDK **还不是裁决结果**：[R2 对象强一致](https://developers.cloudflare.com/r2/reference/consistency/)只保证单对象读写/列表；同一键并发写仍是最后完成者获胜，不能据此推断多文件操作与 NCP 会话同事务提交。Sandbox 的用户前缀挂载要实测目录逃逸、另一个账号读写、直接外网访问和撤权；命令执行器必须没有全桶或模型密钥。`wrangler dev` 的[本地 R2 挂载有周期同步窗口](https://developers.cloudflare.com/sandbox/guides/mount-buckets/)，因此本地通过不能代替生产 `read_file → exec → read_file` 的强一致见证。

现有 `BiboUserContainer` 同时是会话 DO 和容器宿主，拆开时不能另建一个空 DO 丢掉用户数据。目标是原账号 DO 只保留会话、权限、任务协调，独立 Sandbox DO 只承载按需 OS。Cloudflare 的[DO 类重命名合同](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/)允许保留原命名空间及数据；具体发布采用别名→类名迁移→移除别名的分阶段版本，并在每阶段读回账号与会话摘要。`Container` 本身[继承 DurableObject](https://developers.cloudflare.com/containers/reference/container-class/)，但改父类、删除旧容器绑定和图片也要用真实灰度验证，不能仅由类型检查推断生产数据安全。最终运行包删除旧 Harness 会话与整包 snapshot 路径，旧 R2 备份只用于限期恢复。

**R2 挂载的真实适用边界（隔离现场探针，非最终性能验收）**：同一官方 Sandbox 镜像，向 `/tmp` 连续创建 200 个小文件，命令内部约 9 毫秒；向 R2 绑定挂载目录写 200 个小文件，120 秒命令超时后 Worker 即刻列出 197 个对象。后续对挂载目录覆盖写 20 个文件，命令内部 10.608 秒、整个 Worker 请求 16.905 秒。另在 Sandbox 临时磁盘创建 200 个文件后仅把单个 215,040 字节 tar 写到挂载目录，打包写入的命令内部 389 毫秒、Worker 请求 2.042 秒；显式销毁后重新启动、挂载并解包，命令内部 277 毫秒、Worker 请求 5.796 秒，200 文件均读回。样本小、两个不同实例且 tar 未模拟大规模依赖，不能推导正式 p95；但足以否定“把 `node_modules` 等海量小文件直接安装到 R2 FUSE 挂载目录就足够快”的未经验证假设。

据此把**默认环境**与**明确挂载的用户资源**区分开：前者的文件、依赖和进程默认临时，后者的普通文件写入自动持久化，由 Worker 和下次授权挂载直接访问。若用户要求软件环境跨任务继续，需选择独立的可恢复环境能力，不能靠默认容器磁盘永久存在，也不能每次命令或聊天全量压缩。Cloudflare 官方[目录备份/恢复](https://developers.cloudflare.com/sandbox/guides/backup-restore/)以 SquashFS 只读层加可写 overlay 恢复，overlay 休眠后丢失；它只能作为显式环境检查点候选，须测真实依赖、备份/恢复时间、TTL 和重启后可执行性。此前 tar 探针否定逐文件把依赖放在 R2 FUSE，也否定每轮恢复整个项目归档；不构成要求 Agent 执行额外保存动作的理由。

纵向原型先测 100 次闲置后唤醒、热调用、无挂载命令、带 1/10/100 个文件的资源挂载、读写后立即从 Worker 回读，记录 p50/p95/p99 与失败率；再测会话取消、重复调用、并行挂载和执行器崩溃时的真实持久结果。若直接可写挂载不能给出可解释的版本/冲突语义，先验证宿主透明的写入拦截/自动回写；仍达不到普通文件写入即持久的体验，就放弃该 SDK 路径，不把额外发布步骤交给 Agent。SDK 还须与当前容器方案按相同镜像体积、实例规模和活跃时间比成本。现有旧 Bibo runner/Harness 不作为 SDK 路径的一部分。

**休眠时长的成本敏感性，尚非账单。** 使用历史 1,000 月活、每人 900 条/月的同一基线：历史纯边缘聊天估算 $30/月，旧版每条聊天依赖容器约 $172/月；假设 10% 的消息调用一次 OS 工具、每次互相隔开足以冷启动、简单命令消耗 5 秒 × 1/4 vCPU。按 Cloudflare 官方 [basic 配额](https://developers.cloudflare.com/containers/platform/limits/)（1 GiB 内存、4 GB 磁盘）及[2026-08 单价](https://developers.cloudflare.com/containers/platform/pricing/)，不含每账号共享额度和 R2/日志时，执行器增量约为：

| 每次调用后闲置保留 | 每人月执行器活跃时间 | 1,000 人执行器增量 | 连同历史纯边缘聊天估算 | 相对旧容器路径 |
| --- | ---: | ---: | ---: | ---: |
| 1 分钟 | 1.5 小时 | $17/月 | $47/月 | 约低 73% |
| 5 分钟 | 7.5 小时 | $77/月 | $107/月 | 约低 38% |

若 OS 比例为 5%，5 分钟档约 $69/月；若为 20%，约 $185/月，甚至高于旧路径。以上是独立冷事件的压力假设，不含模型、搜索、R2、SDK 自身额外操作、并发上限、失败重试或长任务；真实事件聚集会减少启动次数，真正后台服务会增加驻留。不能因为 1 分钟便宜就直接选它：必须同时达到 BE-13 的冷启 p95/p99 与任务连续性，且在生产混合负载重新计费。历史 A/B 估算详见[原成本基线](2026-09-28-bibo-personal-space-persistence-and-latency.design.md#粗略成本边界非报价)。

**当前设计 Review（mode=design）阻断项**：16 类能力中，多项依赖 Node manager 和长期状态；当前边缘 DO 只有会话/个人空间，尚无项目、应用、MCP、自动化等持久 owner 与配置入口。旧容器带入整包恢复、固定 `/data` 和令牌配置写盘；不能直接当安全执行器。当前 1 MiB 文本/32 MiB 结构限制也不具备本地文件等价。以下合同描述目标边界，但在动态目录来源、字节存储事务、执行器安全与后台生命周期有真实纵向证据前，**不得判定 design-review 通过，不得把仅有 `exec` 工具名的版本部署为完成品**。

2026-09-29 再审文件执行链路补充阻断：R2 可写挂载会绕开现有 DO 路径版本/CAS，而现有随机 blob key 的 R2 内容也不能直接形成可挂载的用户目录。不能把 `mountBucket()` 成功等同于同一权威文件系统。C 必须在设计和测试中证明挂载目录普通写入、Worker 直读、路径/版本冲突与 UI 文件元数据共同指向一个持久 owner；若只能靠 Agent 显式发布或使 BE-13/14 失效，就改测 C2，而非在线保留两套文件真相。

### 冷启动与常驻策略的决策条件

用户接受「工具调用时冷启动若真正只需 1～3 秒，就先不常驻容器」的取舍。这是体验偏好和待验证假设，**不是**当前平台实测结论。测量起点是公共 Agent 发出需要 OS 的工具调用，终点是隔离环境内第一条简单命令已执行；其中要计入容器调度、镜像准备、工作区挂载/同步、授权和网络往返，不能只量 `getSandbox()` 或启动请求返回。分别报告连续闲置 1、5、30、60 分钟后及首次新用户调用的 p50/p95/p99 和失败率，并与用户看到「已接受、正在准备执行环境」的时间分开。若端到端稳定在 1～3 秒且 BE-13 通过，初始采用按需启动、无最低常驻实例，并从短休眠档开始压测成本；若尾部超标，先定位镜像、挂载和执行链路，再依据真实成本/尾延时比较预热池或常驻，不能把 1～3 秒当平台承诺。纯聊天与无需 OS 的工具在所有档位均不得等待或启动容器。

**第一次临时线上探针，尚非 Bibo 正式链路。** 使用隔离 Worker、独立测试桶、`@cloudflare/sandbox@0.12.10` 与匹配的默认镜像、basic 实例、`sleepAfter: 1m`，鉴权后执行 `mountBucket` 和 `printf ready`。首个不挂载的真正冷调用 4.334 秒、销毁后 4.857 秒，热调用 0.129 秒；首次带 R2 前缀挂载的首命令 3.645 秒，Worker 立即读回刚写入的对象，总计 4.548 秒。进一步连续 10 次**显式 `destroy()` 后重建**，首命令 p50 11.037 秒、p95 14.479 秒，容器启动检查 p50 10.233 秒，挂载后 p50 10.936 秒；其后另一次重建首命令 3.700 秒。两次等待超过 1 分钟后的自然休眠唤醒，首命令分别为 3.424、4.196 秒，立即写入回读总计为 4.202、4.890 秒。这些数值均由 Worker 内 `performance.now()` 计时，p95 用 nearest-rank，样本小、调度波动大，尤其自然休眠只有两个样本，不能外推其 p95。热实例重复调用 `mountBucket` 报挂载点非空；执行器适配必须在每次实例启动检查挂载状态并只挂一次。**后续受控复测已推翻“显式销毁或 Sandbox 固定需要约 10 秒”的推断**；该批数据只能作为平台长尾样本，不能据此排除无常驻方案。

当前的执行器选型顺序据此调整：先比较只含必要运行时的隔离镜像与默认 Sandbox 镜像，按相同用户文件、生命周期和样本口径量首条命令；只有最终调用链路的 BE-13 尾延时与失败率过线，初始才无需最低常驻。若尾部不过线，先拆分容器调度、挂载、命令与存储回读，再比较小规模安全预留池，分别算每百条消息启动数、用户等待和实例小时；池中容器不能在未清空可见状态、撤销授权并完成跨用户隔离验证前转给下一用户。保持独立用户隔离、后台任务和软件环境恢复为门槛，不能只因为空容器启动快就放弃完整本地能力。纯聊天不得因预测性预热而偷偷产生用户容器启动。

**轻镜像对照（2026-09-29，隔离探针）。** 直接引用现有 118 MB Bibo Node 镜像，独立 Container DO 只请求固定 `/health`，没有 R2 挂载和实际 `exec`，因此这是「服务就绪」下界而非最终工具延时。首个启动 2.518 秒，热请求 13 毫秒（均为容器 DO 内计时）；连续 20 次 `stop()` 后重启的就绪 p50/p95/p99 为 5.127/6.113/6.281 秒，Worker 到 DO 的总时间 p95 为 6.131 秒。小镜像仍不能稳定证明 1～3 秒，且 `stop()` 与自然休眠需要分组；不能因为首个 2.518 秒样本就定零常驻。探针受临时鉴权保护，不接用户数据。

同一隔离探针换为真正运行 `/bin/sh -lc 'printf ready'` 的容器后，发现 `stop()` 只发送终止信号，连续请求仍可能命中未退出的热进程；20 个表面上 13～24 毫秒的样本因此作废。改用等待完成的 `destroy()` 后，连续冷重建的可核实样本包括 5.126、5.618、5.902、6.020、6.145、13.283 秒，另有一次命令入口返回 503、等待约 19.9 秒。这是固定命令、不挂载工作区的下界，尚不是完整 BE-13 抽样；但已经足以否定无预热实例稳定通过 p95≤3 秒的当前假设。轻镜像与默认 Sandbox 均保留为候选，正式路径须比较安全预热、真实工作区恢复、完整命令和费用。探针结束后 Worker、自定义域、容器应用及上传镜像均已删除，容器列表仅余生产应用。

**第二次同环境复测（2026-09-29，隔离 Worker 与 basic 实例，`sleepAfter: 30s`）。** 为避免把 SDK 句柄获取当作启动，所有服务端时间从请求进入 Worker 计到固定命令执行完成；挂载组还要求命令写入独立 R2 测试桶、Worker 立即回读 `ready`。全新实例各 12 次：Sandbox 无挂载 p50/p95 为 2.067/6.139 秒，现有 118 MB Node 镜像的普通 Container 到 `/health` 为 3.572/5.957 秒；两者镜像与终点不同，不能将差值解释为 SDK 开销。45 秒自然闲置后同 ID 再呼叫各 12 次，实例身份全部改变：Sandbox 固定命令 p50/p95 1.848/2.536 秒，普通 Container 就绪 3.031/4.223 秒。无挂载显式销毁重建各 6 次：Sandbox 1.131/2.058 秒，普通 Container 2.693/4.675 秒，均无失败。

同一 Sandbox 镜像加 R2 凭据免交付的前缀挂载、固定命令写入和 Worker 即刻回读，全新实例 12/12 成功，端到端服务端 p50/p95 为 3.443/17.036 秒；其中 1 次长尾为 17.036 秒，挂载完成前已耗 16.414 秒。自然闲置后 12/12 身份改变且回读成功，p50/p95 为 3.229/5.487 秒；显式销毁重建 6/6 成功，p50/p95 为 2.500/3.017 秒。再交替发起 12 对全新无挂载/挂载请求，分别得到 p50 2.046/3.486 秒、p95 3.900/4.496 秒；配对差的中位数为 1.348 秒。挂载有实际代价与偶发长尾，但前一批约 10 秒并非容器固有启动时间，也不能归因为 `destroy()` 本身。此探针未带 Bibo 鉴权、用户文件、模型、会话和并发负载，12 个样本的 nearest-rank p95/p99 就是最大值，仍不足以证明 BE-13；最终选择需测完整用户工具链路。探针资源将按本批次结束后删除。

若完整工具链路的尾部未过线，候选是**单次租用的预热空容器池**：后台维持极少量无用户数据的空实例，模型明确发出需要 OS 的工具调用后才原子租给某个用户；该实例整个租期只属于此用户，结束后销毁并异步补池，绝不把残留工作区交给下一用户。池耗尽时可按需新建并显示真实等待状态。它比「所有用户各自常驻」更可能满足成本，但只有挂载/首命令尾延时、租约竞争、跨用户隔离、后台任务留存和每百条实例小时均通过后才采用。纯聊天不申请租约，也不因聊天请求触发补池；预热是独立的容量维护动作。长期服务和需要保留的软件环境转为专属租约，按明确生命周期和费用处理，不能被短任务池回收。

## 单一通用基座与依赖方向

```text
                            NextClaw 公共内核
 NCP 运行/事件 ─ 会话与运行状态 ─ 能力描述与授权 ─ 工具调用 ─ 上下文/压缩
           ↑                  ↑                    ↑
  Node 宿主适配          存储/资源端口          直接或隔离执行端口
  本地 NextClaw          本地 journal+FS         本地 OS、扩展、设备
  Bibo 宿主适配          DO 会话+待裁决工作区   Worker 原生工具、按需隔离执行器
```

**公共合同的最小变化点**：

- `ConversationStore`：按用户/会话版本读取、接受运行、追加 NCP 事件、提交/取消/恢复。Bibo DO 和本地 journal 是两个宿主实现，投影、压缩、模型输入和终态判定不重写。
- `WorkspaceStore`：账号范围的文件元数据、流式正文/二进制、同路径条件写入和目录查询。Node 用本地文件，Bibo 的物理实现由 C1/C2 裁决；不让当前 1 MiB 文本和 32 MiB 快照限制成为公共能力上限。目录/路径、编码、冲突和用户隔离由统一语义合同控制，备份与物理写入由宿主处理。跨多个文件的原子发布不是公共合同。
- `CapabilityCatalog`：每项能力有稳定 ID、参数 schema、所需权限/宿主资源和可用性来源。Node 和 Bibo 对同一能力目录给出绑定：Worker 直达、隔离执行器、已授权外部服务、用户配对设备或有证据的例外。动态 MCP/App/Skill 通过已安装实例与权限生成条目，不能只靠源码工具数推断。
- `ExecutionHost`：以用户、会话、运行/调用 ID、工作区版本和一次性授权执行工具/任务，流式回报结果、产物和真实状态。Node 本地调用与云端按需隔离执行使用同一调用合同；Bibo 不把固定 `home=/data`、持久 token 文件或旧 runner 的 HTTP 细节写入公共层。
- `BackgroundHost`：按本地版实际自动化、Service App Job 与长时进程语义提供持久计划、触发、检查点、观察、取消及故障恢复。HTTP 服务若本地版可由 OS 完成，也至少提供有明示可用性和生命周期的云端路径；新建完整托管平台的额外能力不凭空列入基线。

对 16 类既有 provider 的实施重点是**共享目录生成与调用合同**，而不是在 Worker 重写 16 套 manager。纯计算/HTTP/文件能力可在 Worker 装配；运行时确需 Node、stdio、二进制或用户安装代码的能力可由按需启动的完整 Kernel 工具宿主执行，但该宿主不拥有对话循环。Worker 必须在容器未启动时仍能从持久的安装、配置和授权清单取得可调用目录；实际调用以同一工具 ID、schema、权限和 NCP 事件跨边界执行。若某项能力必须靠启动容器才能“发现”，它不满足纯聊天零容器的目标。构建时静态目录快照可用于校验，不能替代用户安装与撤权后的动态目录。

目录可见不等于每轮把全部工具完整 JSON schema 塞给模型。当前 Bibo 真模型对 Kernel `tool_schema` 的首次回归表现为 `bibo` 参数延迟披露后未正确查询，团队暂时以 `includeSchemaTool: false` 保住已有任务；直接加回 53 个本地工具也可能增加提示词成本与首字延时。正式目录需要保留少数高频直达工具，并让模型可搜索、读取已授权能力的完整参数；用 Bibo 当前模型的真实任务集合测试工具发现成功率、额外轮次、首字及费用。不能通过隐藏低频能力来虚报完整，也不能以某个模型不主动使用延迟 schema 为由永久停在五项工具。

端口不是统一大接口；只有同时被 Node 与 Bibo 使用、且切开真实宿主变化点时才落为公共 contract。保留现有 `NextclawKernel`/Harness 公共入口，由其消费新合同；不要求全部 Node manager 在一次改动中迁移。上层 Bibo 只能持有其账号、额度、UI 与具体适配，不进入下层类型、provider 或状态机。

### 文件规模与访问合同：不能停在字符串原型

旧 Bibo 的 `file.create/update/get` 是**小文本编辑 API**：一次请求传完整字符串，服务限制 100 万字符/1 MiB；个人空间把文件目录连同任务等状态整份序列化，DO 结构化状态上限 32 MiB。本次未提交的最初 R2 原型只移出了正文，`file.get`、公共 `WorkspaceFilePort.read` 和编辑工具仍整份读入字符串，目录索引仍整份重写。它不能通过 BE-14，也不能仅删掉检查后发布。Cloudflare [Workers 每 isolate 128 MiB 内存](https://developers.cloudflare.com/workers/platform/limits/)；100 MiB 正文经字符串解码与拷贝就可能耗尽内存。

冻结目标边界为：`WorkspaceStore` 的持久核心以**字节、元数据与版本**表达文件；目录项按路径/父目录独立查询和分页，不以一次整份 JSON 读写表达工作区。Bibo 的现有文本编辑 API 作为这个核心上的小文本视图继续服务旧用户；大文本的工具读取按范围/行窗口逐段扫描，二进制与上传/下载走流。模型一次返回的 50 KiB 分页是上下文保护，不是文件容量。`edit_file` 对大文本需要有界的流式替换或明确的分块修改语义，不能先把 100 MiB 载入 Worker。Node 宿主继续用本地文件字节流；Bibo 的执行器由 C1/C2 工作区宿主接入同一用户文件真相。小文本 UI、工具、执行器与下载对同一路径只承认同一份字节。

**现有 Bibo 个人空间与公共工作区必须是同一个目录 owner**：不能在 Bibo 的 `state.files` 和新宿主中各留一份可写路径清单。一次性迁移逐项复制旧文件正文、ID、类型、创建/更新时间与版本至唯一工作区 owner，回读数量/哈希后切换版本；迁移失败保持旧状态只读可恢复，切换后旧文件数组退出在线写入。Bibo 文件 UI 的 `file.list/get/create/update/move/delete` 作为同一工作区上的产品视图，额外的笔记/文档/产物类型是目录项的扩展元数据；公共 `WorkspaceByteStore` 不认识 Bibo 类型。Node 本地版使用同一文件行为合同、普通本地文件实现，避免把任何云端宿主协议带进通用逻辑。对大文件，现有 `file.get` 的小文本内容字段只给有界预览，完整正文经流式下载/范围 API；上传和编辑也走流/版本 API。不能把 100 MiB 先转成 JSON 字符串或复制进 NCP 模型上下文。

此处采用平台原语而不自造数据库/对象协议：现有 Bibo DO 已是 SQLite-backed；Cloudflare [DO SQL API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)可做独立目录索引与事务，已有 KV 状态不需要重新建账号 DO。Cloudflare [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)支持 `ReadableStream` 上传和 range 读取；[R2 multipart](https://developers.cloudflare.com/r2/api/workers/workers-multipart-usage/)用于越过单请求限制。自有代码仅负责平台跨 DO/R2 无法提供的路径授权、版本/CAS、暂存发布、失败回收及与 NCP 事件的一致性。R2 [单次上传可达 5 GiB、分段上传可达约 5 TiB](https://developers.cloudflare.com/r2/platform/limits/)，这只是平台能力，不宣称产品已支持这些大小；产品门槛是 BE-14 的 100 MiB 双类型、端到端内存/延时和故障验证。

**官方现成抽象评估**：Cloudflare 于 2026-08 发布的 [`@cloudflare/computer`](https://github.com/cloudflare/computer/blob/main/packages/computer/README.md)恰好提供 DO 内虚拟文件系统、Worker isolate 与容器 FUSE 的统一工作区及常见文件/`exec` 工具，证明需求有平台级共性，不能再声称必须从零造一整套 VFS。但其官方 README 同时明确标注「PREVIEW ONLY / NOT suitable for production」；当前工作区约 10 GB、容器侧文件系统驻内存，重 I/O 如大规模依赖安装比原生磁盘慢。用户要求不能交付 MVP/demo 或隐藏容量断崖，因此本轮**不把该预览包直接作为生产持久 owner**。在设计和原型上复用其接口/路由经验；可持续跟踪正式生产合同。正式实现优先组合已有 DO SQLite、R2 流/范围 API、官方隔离执行器，或在同负载证据表明更合适时使用共享 Node + 持久磁盘；自写层限于 NextClaw 语义、版本及跨原语发布，必须通过 BE-14 才可上线。

真实 Wrangler/Miniflare 纵向探针纠正了一个实现细节：R2 `put()` 虽接受 `ReadableStream` 类型，运行时要求流具有已知长度；直接传未知长度生成流返回 HTTP 500。小对象可先在有界内存中取得长度再单次 PUT，大对象要使用官方 multipart API，以 5 MiB 固定分段和有限缓冲上传。改造后的隔离本地探针已写入 100 MiB 并核对首尾范围字节，但尚未证明生产网络、用户文件入口或执行器状态发布。这个结果不能用来解除上述设计阻断。

**2026-09-29 生产平台隔离探针进一步界定了 C1**：同一地区 Worker 直接用 R2 binding、4 并发写 200 个 1 KiB 对象，200/200 成功，写入 14.371 秒、含 list/read 的请求 14.849 秒；单对象写入 p50/p95 为 272/405 毫秒。覆盖其中 20 个对象的第二次请求，写入 1.456 秒、含 list/read 1.852 秒。此前 Sandbox 的 R2 FUSE 挂载写 200 个小文件在 120 秒超时、只可见 197 个，覆盖 20 个文件也需 10.608 秒命令时间。两组的计时终点、容器状态和具体路径不同，不能把 14.8 秒与 120 秒直接当标准化加速比；足以说明 **R2 直接 API 可承担稀疏的用户资料/产物调用，但无论 API 还是挂载都不应逐文件承受包管理器或 Git 的高频 POSIX I/O**。早期“将整个项目/软件环境归档并在每次 OS 调用恢复”的候选现已被用户的默认临时模型取代，不再作为主链路实现或成本负担。另一候选 C2 需用真实远端 RPC 和主机故障测试证明其文件延时、成本和耐久性。两个探针均未用真实用户数据，测试 Worker、桶及令牌已清理；不计入 BE-13/14 最终分位。

Cloudflare 的 [Sandbox outbound handler](https://developers.cloudflare.com/sandbox/guides/workers-connections/)可让执行器的受控 HTTP 请求在 Worker 内访问 R2、DO 等 binding，按容器 ID 范围授权；C1 不必把 R2 S3 密钥发给执行器，也不必经 FUSE 才能取回/发布少量变更。这是平台能力，不是现成的跨文件事务或 POSIX 磁盘；变更集的版本提交、并发冲突和失败清理仍由 NextClaw 工作区合同负责。长期运行的进程与 HTTP 服务按 [Sandbox 后台进程](https://developers.cloudflare.com/sandbox/guides/background-processes/)能力评估，但进程在容器休眠时的生命周期和恢复不能由单个 PID 保证。

**同日最小跨界链路实测**：隔离 Worker 先以 R2 binding 存入 `hello`，仅在 `/run` 调用时让官方 Sandbox 从受控 outbound handler 读入文件到本地 `/tmp`，执行追加后通过同一 handler 写回 R2，再由 Worker 立即直接读回。首次请求含容器冷启、双向文件传输和命令，服务端 2.723 秒、客户端 3.341 秒；显式销毁容器后同一操作服务端 2.818 秒、客户端 3.577 秒，内容连续累加。再次销毁后只走 Worker 文件读取，客户端 0.684 秒且读到完整结果。它证明“同一权威文件可由 Worker 与按需容器接力，普通文件读取不需要容器”在平台上可行。测试仅为一个小文件、固定受控命令，没有账号 DO、版本 CAS、恶意命令隔离、生产 Bibo 对话、100 MiB、软件环境与多文件同步，不能充当 BE-01/09/10/13/14 通过证据。测试 Worker、容器应用、R2 对象/桶和令牌均已删除；复查容器列表只余生产应用。

**C2 网络代价的初步测量**：另一个独立 Worker 从 `SEA` 节点经普通公网 HTTP 请求现有新加坡主机的公开健康接口，两批各十次全部 200；各批首次为 1.213/1.096 秒，其余大多 0.189～0.383 秒，另一次 0.481 秒。该主机不是专用文件服务，且探针未运行在实际 Bibo 用户 DO、没有文件负载或 Cloudflare Tunnel；它只说明不能假定共享主机的冷连接与跨网 RPC 低于 R2 直达。现有主机磁盘接近满载且运行其它服务，绝不直接承载 Bibo 新文件真相。若 C1 多文件工作区失败，再用专用 C2 主机/隧道按同一 BE-13/14 口径实测。探针 Worker/域名及令牌已删除。

**较大工作区的现场反证及适用范围修订**：同一个隔离 Worker、官方 Sandbox 和 R2 挂载探针，把 5,000 个很小的本地文件打成约 5.13 MB 单一 tar；保存请求含挂载/命令为 3.519 秒，显式销毁后恢复并解包为 4.880 秒，5000/5000 文件可见。加入一个 100 MiB 文件后，归档约 109.99 MB，保存请求升至 11.930 秒、恢复升至 9.694 秒。各为单次冷样本，证明每轮保存/恢复整份工作区不合适；用户现已明确 Git/依赖留在临时容器，不要求同步，因此这个负载**不再用于否定 C1 的目标模型**。C1 仍须证明所选大文件的按需访问、少量持久结果的写后回读及临时任务的真实冷热延时。该探针的 Worker、容器应用、桶/对象和临时令牌均已清理。

**C2 同一目录链路的隔离对照**：在本机临时 Node 文件服务中放一份测试目录，按需 Docker 容器挂载同目录并追加内容，服务随后读到更新；第一次本机容器命令 2.170 秒。再以独立 Cloudflare Worker 经临时 Cloudflare Tunnel 请求这个服务：连续 20 次小文件读取全部成功，Worker 到文件结果 p50/p95 为 241/264 毫秒，首次 638 毫秒，服务端读盘约 0.2～1.0 毫秒。一次 `远程写 → 容器命令 → 远程读回` 客户端 3.208 秒；另外 12 次同链路全部成功，客户端整轮 p50/p95 为 2.250/3.092 秒，Worker 到命令完成阶段 p50/p95 为 751/1,137 毫秒，读回阶段 p50/p95 为 349/406 毫秒。这证明 C2 在轻量操作上没有显然不可接受的网络下界，也消除了文件同步步骤；**不证明**专用新加坡 Linux 主机、真实 Bibo DO、100 MiB 流、租户隔离、备份、长任务或生产 p95。测试文件 API 只支持小请求，不能当 BE-14 实现。临时 Worker、隧道、本机服务、数据和令牌已清理，测试安装的 `cloudflared` 也已卸载。

## 运行与状态次序

1. 请求在 Bibo 入口完成账号认证、配额预留，DO 以 `clientRequestId` 和会话版本接受运行。纯聊天创建公共 runtime 与能力目录时，不能为获取目录或 Skill 而唤醒用户容器；动态目录须从持久的安装/授权清单生成。
2. 模型调用公共 NCP loop。直达工具在 Worker 的宿主绑定执行；需要 OS 时先提交 `tool-awaiting-executor` 的真实事件，再按需取得该用户隔离执行器，以短期能力票据加载明确的工作区版本。原对话 run 保留同一会话/调用 ID，工具结果按公共事件协议回到 loop。
3. Agent 按需创建或选择环境，并为该环境选择需要的持久资源及读写权限；宿主校验后返回环境 ID、挂载 ID、路径和租期。无挂载时整个环境文件系统临时；已挂载路径普通写入自动进入唯一持久 owner。C1/C2 都须处理同路径版本冲突，不能用过时整包快照覆盖。执行失败、取消和超时只留下可解释状态与真实已发生的副作用，不伪造成功。
4. 软件安装默认属于临时环境；只有用户任务明确需要跨任务复用且 Agent 选择可恢复环境时才形成持久承诺，重启后须验证可执行。R2 逐文件 FUSE 不是软件安装目录的默认实现；C2 的持久资源须纳入备份和容量管理。后台任务和 HTTP 服务由持久任务/服务记录驱动，含启动、观察、停止、健康、路由、期限与计费；不能把聊天连接或 PID 当作状态 owner。
5. 设备能力通过用户授权的配对宿主调用；未配对只反馈具体缺失条件。外部服务按账户授予最小权限、可撤销，密钥不写进工作区、快照或通用日志。

最小端到端证明是同一轮对话里的 `read_file → 选择 OS/挂载文件资源 → exec → read_file`：第一次读只访问持久资源，容器启动计数不变；Agent 再取得隔离环境，挂载仅该资源，在挂载路径创建文件而不调用保存工具；第二次读直接读取新内容，不再触发容器。另在未挂载路径写文件并回收环境，验证它不会被误报为持久。各调用的 NCP 事件、权限、路径、会话 ID 和失败状态必须相连，且用户不需要知道物理运行位置。这个场景同时否定当前按 `conversationMode` 切整轮的旧方式。

**C1 多文件挂载的冻结前问题与试验合同**：一条命令修改多个挂载文件时，不要求比完整本地版更强的“全部文件原子提交”。门槛是已确认的内容不丢失、Worker 随后能读取、同一路径的并发 UI 编辑不会被静默覆盖、失败时明确显示哪些副作用已经发生。账号 DO 可记录资源租约和起始版本，但直接 R2 挂载写入不会经过其 CAS；因此当前 DO 索引 + 随机 blob key 草稿不能直接作为可写挂载的文件权威。先比较路径键 R2 挂载与经可信文件接口的透明挂载，验证版本冲突、路径逃逸、撤权、断线、重复调用及多环境读写。不同路径不要求全局串行，`node_modules`/Git 高频 I/O 不默认写入 R2 FUSE。若挂载或自动回写使普通任务明显不可用，C1 不通过，改测 C2 的持久 POSIX owner，不继续堆自研归档索引，也不增加 Agent 显式保存动作。

**提交与恢复边界**：账号 DO 是 SQLite-backed，官方 `transactionSync()` 可包裹 SQL，异步 `transaction()` 可将同一 DO 上的 SQL 与 KV 操作纳入一个事务；挂载文件写入与命令仍在该事务外。这里不要求命令副作用、所有文件和整轮 NCP 历史跨系统原子提交。需要的是环境/挂载/工具调用有稳定 ID 和持久收据，能区分等待、执行中、已确认写入可读、失败/冲突，以及命令失败但部分文件已写的状态。模型和界面不能把仍未确认的写入说成全部成功；重试先查收据，避免重复运行有外部副作用的命令。当前 `BiboEdgeConversationService` 只在整轮结束时保存内存中的 NCP 消息，若文件已写而模型随后失败，恢复时须把已发生的工具结果/失败补进同一会话，而不是回滚真实文件。用命令后中断、挂载写入失败、撤权和重试注入验证用户可见结果。

**重新审视 C1/C2/D 的工程代价**：C1 的一次小文件 `Worker → Sandbox → Worker` 已证明约 3 秒可行；它尚需证明真正的 Bibo 账号、持久资源挂载、动态能力及生产尾延时。Git/依赖高频 I/O 留在 Sandbox 临时盘，不以 R2 FUSE 小文件性能淘汰 C1。C2 让 Worker 保持聊天热路径、由持久 POSIX 服务承载用户资料，再按需启动隔离执行器；当少量挂载资源在 C1 仍不能满足性能、版本或安全边界时才值得承担其固定费和运维。D 则把普通聊天也交给每用户 Node Kernel，能力复用更容易，却增加用户进程内存和聊天启动路径。下一次正式裁决比较**同一组真实任务、同一用户数、同一冷热状态**下的首字、工具完成、状态恢复、平台每用户成本和达到完整能力所需改造量；C1 任一硬门槛失败，优先实测 C2，不延长自研文件同步链路。

C2 若采用**同宿主持久目录 + 按需隔离容器挂载该目录**，命令与文件工具可访问同一份字节，不需要把每次命令的整个项目解包到远端再逐文件回传；这是它对 C1 最有价值的结构优势，而非沿用 Node 源码的方便。文件服务必须是可信控制面，只提供带账号范围和版本条件的文件 API；不可信扩展、stdio MCP、命令与二进制进入账号隔离的执行器，不在共享服务进程中加载。纯聊天从 Worker 读取已持久化的能力清单，不访问或启动用户执行器。命令直接修改持久目录与普通 POSIX 命令一样，可能在执行中留下部分文件改动；不额外要求跨文件事务，但必须备份已确认内容、检测同一路径 UI 编辑冲突、在失败时说明副作用。Cloudflare [Sandbox 当前公开的存储挂载 API](https://developers.cloudflare.com/sandbox/api/storage/)是 S3 兼容桶，尚无已验证的外部 Linux POSIX 目录同机 bind mount 能力；因此这个 C2 形态先按自管隔离执行宿主估算，不能把 CF Sandbox 的 1～3 秒探针原样当作 C2 冷启动承诺。固定节点的可用性、备份、隔离和实际冷启/文件 RPC 一起计成本。若这些使它劣于 C1，则仍选 C1。

## 能力对账与验收设计

先从当前实际注册 provider、安装包和服务扫描生成基线，再用**用户任务**而非工具名验收。代表性分支：

| 类别 | 正向见证 | 失败/恢复见证 | 状态与成本指标 |
| --- | --- | --- | --- |
| 聊天/模型/上下文/Skill | 新旧会话、长上下文压缩、切模型、加载 Skill 后回复 | 断流、模型失败、刷新重试 | 首字 p50/p95/p99、模型前时长、容器启动 0 |
| 文件/命令/软件 | 读写文本与二进制、目录、图片；`exec` 安装依赖后再次调用仍可用 | 大文件、版本冲突、执行器休眠/重启 | 工作区摘要、首次/再次 OS 准备时间、对象操作 |
| 会话/项目/子任务 | 列表、检索、分支任务与状态更新 | 并发、取消、刷新后的子任务状态 | 事件顺序、跨用户隔离、任务排队 |
| MCP/应用/外部服务 | 授权连接、列工具、调用、应用 Job 观察 | 撤权、服务不可用、重启恢复 | 授权范围、调用结果、失败可见性 |
| 后台/设备 | 定时触发并通知；配对设备执行授权任务 | 到时服务休眠、设备离线 | 触发准确率、恢复时间、运行费 |

每一项在 Node 和 Bibo 相同配置/权限下比较结果。设备/平台必要例外只可逐条列出不可替代证据、替代路径及用户可见损失，未经用户确认不计通过。发布门禁校验能力目录与两宿主映射没有未解释缺口；真实场景覆盖成功、失败、重启，不能以静态快照代替。保留旧 Bibo 文件、搜索、预览、提问、旧会话及迁移的回归集合。生产灰度先核对工作区摘要和隔离；任何数据不一致停止切换并保留旧状态。

## 首次实施门槛

先以 Core 文件/`exec` 和现有 Bibo 文件工具做一个真正纵向切片：同一公共能力定义在本地 Node 与 Bibo 可调用；Bibo 纯文件/聊天容器数为零，`exec` 启动隔离执行器、写入产物、休眠后回读，并在失败/冲突时不丢状态。这个切片同时检验目录、状态和执行端口的真实必要性。通过后扩展会话/项目、Skill/MCP/App、后台与设备；每类填验收账本。所有 BE 项及量化门槛达标后，从冻结远程主干发布并现场复验。
