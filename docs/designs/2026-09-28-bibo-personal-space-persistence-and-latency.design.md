# Bibo 响应、存储与运行架构整体方案（待评审）

日期：2026-09-28
状态：整体目标与实施/上线已获用户授权；边缘技术选型仍待原型、兼容及数据迁移证据通过设计门。当前验收以 [BIBO-EDGE-2026-09-29](../work/2026-09-29-bibo-edge-conversation/acceptance-contract.md) 为准。

## 决策目标

把 NextClaw 内核重构纳入候选空间。现有 Harness、Kernel、容器和快照边界都不是约束；**NextClaw 的产品独立性、通用性、扩展能力及既有公共合同是约束**。Bibo 是一个消费者，不能反向决定 NextClaw 的产品语义或让其他宿主退化。目标是让普通对话、长会话续聊和 Bibo 文件操作尽可能快，优先验证这些路径完全不启动容器；只有真正需要独立 OS 的能力才按需启动执行器。同时使低活跃用户的基础设施成本接近按需使用，且普通聊天代码变更不因容器镜像而拖慢发布。模型与搜索的外部费用单独计量，不混进平台费用。

拟以真实用户路径验收：新会话和一小时前的旧会话发消息后开始输出；旧会话能正确继承上下文；对话中创建、读取、修改和展示文件；中断、重试及重复提交不丢失或重复写入；用户文件在运行实例休眠、重启与回滚后仍可用。暂定体验门槛是发送到首字的 p95 小于 5 秒、p99 小于 10 秒，最终门槛需用线上分位数和模型供应商基线校准。

## 已确认的现状与根因边界

当前链路是浏览器 → Worker → 用户 Durable Object → 用户容器 → 每次消息新建并启动完整 NextclawHarness/Kernel → 模型与工具；容器启动时从 R2 恢复整个 home 快照，成功对话和空间写入后再打包整个 home 为 tar/gzip，上传新对象并切换快照键。空间结构化状态另存于 Durable Object，文件正文在容器本地目录；会话界面历史和 Agent journal 分属 Durable Object 与 Kernel 本地文件/SQLite 两套状态。

已复现的旧会话“正在处理上一条消息”是 `/space` 读取占用用户级 `inFlight`，与发消息冲突；旧消息实际上已经完成。另一次成功请求首字约 15.3 秒，其中模型响应不足 1 秒，模型请求前约 14.5 秒。全量快照写入发生在生成之后，不能单独解释首字慢。上述是观测到的链路和样本，不代表所有延迟分位数；需要继续拆分鉴权、DO 唤醒、容器唤醒、快照恢复、Kernel 启动、模型首字和后处理耗时。

现有 `deploy:client` 已能只部署 Worker 与前端，涉及 runner 的完整发布仍要构建容器。发布慢和回复慢有部分共同根因，但要分别计时与解决。

补充可移植性实测：在本地 workerd 开启 `nodejs_compat` 后，现有公共入口 `@nextclaw/ncp-agent-runtime-next` 能加载并完成一次伪模型流，产生完整 NCP run 与 message 事件，约 7 毫秒。这说明早先浏览器平台 esbuild 的 Node builtin 解析失败不能直接判定 Worker 失败。**完整 Kernel 入口仍含大量 Node 文件、进程和服务能力**，不能照搬；模型、文件工具、长会话、压缩、持久化和生产资源限制尚未在 Worker 证明。优先沿现有公共 Agent runtime 的 `AgentRuntimeSessionState`、`AgentModelInputBuilder`、`NcpLLMApi` 和 `NcpTool` 合同做纵向实验，再决定是否需要改动 NextClaw；不能预设必须大范围重构。

后续实验已把真实模型流和纯内存工具轮次跑通。公共 `@nextclaw/ncp-toolkit` 的会话状态管理器也能在 Worker 运行；当前 NextClaw Kernel 自身消费同一 runtime 和状态管理器。新的关键阻塞在**工具参数校验**：现有 Ajv 对动态 JSON Schema 的运行时编译需要 Worker 禁止的字符串代码生成。NCP 已有 `NcpTool.validateArgs` 无 JIT 扩展点，实测可运行工具和第二轮模型；正式路径须从一份工具定义派生模型 Schema 和 Worker 验证器，并保持 Node 的原校验与工具体验。这个证据将设计的 NextClaw 改动范围从“预设拆 Kernel”收窄为“先复用已存在的通用 runtime/状态合同，确有缺口时才抽宿主端口”，但尚不足以宣布 Bibo 可迁移。

## 候选架构

| 候选 | 首字与扩缩容 | 平台成本 | 工程代价与主要风险 |
| --- | --- | --- | --- |
| A. 保留用户容器，改为文件增量持久化并修并发锁 | 可去掉全量快照开销，但冷启动和每次完整 Kernel 启动仍在普通消息路径 | 活跃实例计费；闲置可休眠 | 迁移较小，适合作为短期可靠性修复，长期上限受容器链路限制 |
| B. 可移植 NextClaw 对话核心运行在 Worker/DO；DO SQLite 保存会话与常用小文件，R2 保存较大文件版本；仅真正需要 OS 的工具按需用容器 | 普通消息不等容器，边缘实例按需启动；需实测模型前初始化与工具耗时 | 低流量可落在 Workers/DO/R2 共享额度内；长时间运行的 DO、存储写入和模型费用仍增长 | 要重构 Kernel 的运行与持久化边界，并验证 Workers CPU/内存/兼容性；旧状态迁移复杂 |
| C. 共享常驻 Node 对话服务，DO/R2 或数据库做持久化，OS 工具用隔离执行器 | 避开单用户容器冷启动，固定热实例可给出稳定首字 | 低流量仍付固定实例费；较高稳定负载可能比 DO 更便宜 | 最易复用现有 Node 栈；要承担多租户隔离、扩容和服务运维 |
| D. 在 Bibo 内另写一套边缘 Agent 或直接把完整 Kernel 打包到 Worker | 可能获得短期速度 | 难以预测 | 前者复制 NextClaw 语义，后者受 Node 文件/SQLite/进程能力与 Worker 资源限制；均不作为默认方案 |
| E. 共享按需 Cloudflare Container 池，可配置最低常驻实例数 | 默认最低 0 台，闲置后休眠；首条消息有冷启，繁忙时实例自然保持运行 | 运行及闲置尾时长计费；按需不保证实际费用很低 | 是 C 的托管容器部署变体；需外置每用户状态、做路由和多租户隔离，聊天核心改动仍需镜像发布 |

**目标方向为 B：纯聊天和现有 Bibo 文件工具不启动容器。** 这仍是待验证的设计目标，不等于现有 NextClaw Kernel 已可在 Worker 内运行。先做同一公共对话合同的真实纵向原型；若兼容、资源或尾延迟门槛不过，则用 E 的共享按需容器池作为托管备选，初始最低常驻数 0；C 是自行管理的常驻 Node 成本与运维对照。A 只作为可独立交付的止血措施。目标 B 的高重构成本与 E 较快复用 Node 的优势要放在同一决策门比较，不能为实现“无容器”削弱 NextClaw 独立性或实际聊天体验。流量增长后继续以实测工作负载重新比较。

### 运行路径与容器启动条件

- **A：现状方向。** 每位用户有自己的容器。普通发消息、读取需要容器参与的空间内容和某些文件操作都会触达它；休眠后首次请求须启动容器、恢复状态。增量持久化可减少恢复与保存工作，但容器仍在普通消息必经链路上。
- **B：边缘对话方向。** 普通发消息、续聊、上下文压缩、任务/日历/笔记以及 Bibo 文件的创建、读取、编辑和预览均由 Worker/DO 与持久存储完成，**不启动用户容器**。只有某个已注册工具实际需要 shell、子进程、安装软件或其他不可在边缘安全完成的 OS 能力时，才为那次工具调用启动隔离执行环境；该次请求可能因此有工具冷启延迟。如果 Bibo 不提供这类工具，线上 Bibo 可以完全没有容器。NextClaw 的 Node 产品仍独立运行，不受 Bibo 是否使用容器的决定影响。
- **C：共享 Node 方向。** Worker 做入口，消息路由到少量常驻 Node 进程；所有用户共用这些计算进程，用户会话与文件按身份隔离并持久存放，不能每条消息重新启动完整 Harness，也不需每位用户一个常热容器。共享服务可运行在虚拟机或 Docker 中；这里的“无用户容器冷启”指它不按用户创建/休眠运行实例。遇到不可信代码或需要隔离 OS 的工具，再另起受控执行器，不能直接把用户代码放进共享服务进程。
- **E：共享 Cloudflare Container 池。** 将 C 的共享 Node 进程放进 Cloudflare Containers，最低常驻实例数作为配置，初始为 **0**；首次请求启动共享实例，闲置一段时间后休眠，运行期间服务多个用户。实例达到经测量的并发上限时才启动额外实例；每位用户的会话、文件与身份都在容器外持久化和隔离。不能沿用当前 `user:${id}` 的一人一容器寻址方式。扩容尚需应用自己控制实例 ID、启动和路由，Cloudflare 当前没有可直接依赖的内置自动扩缩容与智能负载路由；突发仍可能冷启或排队。容器磁盘休眠后会清空，不能把它当成用户数据的主存储。

E 的运行策略应配置最低常驻实例数、闲置休眠时间、单实例并发上限和最大实例数，初始最低数为 0，不按用户预留。这里的“按需”指**容器池没有保底常驻**，不代表每条消息新建进程或 Harness：启动后的共享实例可处理后续用户消息，空闲时才休眠。先用真实首字分位数决定是否把最低数从 0 提高到 1 或更多；不能仅凭平台常见的 1–3 秒容器冷启动值作决定。

B、C、E 使用同一个 NextClaw 通用对话合同，区别主要是对话核心的宿主、实例生命周期和资源计费方式。B 的普通聊天没有容器冷启，C 有一跳到常驻 Node 服务，E 在共享实例休眠后的首条消息还会遇到容器冷启；三者对首字的实际影响须测，不能仅凭拓扑判断。

### 共享运行池的状态一致性与软件环境

不能把现有 runner 直接改成多个用户共用：目前 `home` 固定为 `/data`，`BiboSpaceService(home)` 在模块加载时建立，`configure()` 把请求 token 写入 `/data/config.json`，Harness 也使用这个 home；每条消息仍新建并启动 Harness。若只改请求路由，会出现用户会话、文件、配置或凭据串用的风险，且模型前初始化延时可能仍在。当前 Bibo 允许的工具是 `bibo`、`show_file`、`web_search`、`web_fetch`、`tool_schema`，并未提供用户可调用的 shell/安装软件工具；现有 run 还设有 85 秒超时。按需 OS 执行器与长时间后台任务均属于未来扩展路径，不是现有聊天已经具备的能力。

| 状态或能力 | 建议的权威归属 | 共享运行池与按需执行器如何使用 |
| --- | --- | --- |
| 会话事件、身份、长期记忆与上下文检查点 | 按用户隔离的持久会话存储；NextClaw 通用合同负责语义 | 每次运行按用户与版本读取；进程内可缓存，但缓存不是权威状态 |
| Bibo 任务、日历、笔记与文件索引 | Bibo 的每用户持久状态 owner | 两类运行环境通过受控工具合同读写，写入要有版本和幂等键 |
| 文件正文、产物与任务工作区 | 版本化持久对象；小文件是否同数据库存放由实测决定 | 容器只持有临时副本，产物提交后其他实例才能见到 |
| 任务进度、重试与取消 | 持久任务记录和事件 | 进程退出后仍可查询与恢复；不能把正在运行的 PID 当作任务状态 |
| 软件、依赖与环境设置 | 版本化基础镜像和按任务/用户保存的依赖清单、环境版本 | 通用工具预装；临时安装只在隔离执行器内生效，可用缓存或预制镜像缩短下次准备时间 |
| 访问令牌、临时文件和进程缓存 | 凭据按请求注入；其余仅为运行时临时状态 | 不进入共享 `config.json`、用户快照或跨用户可见目录；实例结束可丢弃 |

一次长任务读取明确的用户状态版本，写出的文件和状态先暂存，成功后以同一提交记录发布新版本；失败或取消不得报告“已保存”。聊天可以与长任务并行，只有写同一资源时才需冲突检测，不能锁住用户的全部聊天。已开始的对话使用自己的上下文快照；后续对话读取任务已提交的新版本。容器滚动更新时，进行中的任务继续在旧环境完成或从持久检查点恢复，新任务标记所用镜像与依赖版本，避免“同一个任务重试却换了环境”。

“安装软件”需要明确产品承诺：共享运行镜像中的通用软件由发布统一安装，所有用户可用；用户请求的临时依赖在隔离任务环境安装，必须保存依赖清单或环境版本并在下次重建，不能承诺容器休眠后软件仍躺在磁盘上。若产品要求“为这个用户安装一次，以后拥有完整、持续可变的个人 Linux 环境”，则要另设每用户持久环境或镜像/卷及其升级、备份、计费合同；这不是共享运行池天然提供的能力，也不应拖慢普通聊天。NextClaw 本地 Node 宿主的完整 OS 能力继续保留。

### 阶段性讨论结论与长期运行服务（2026-09-29）

用户明确同意沉淀当前讨论，认可“普通聊天与真正需要独立 OS 的长任务分离、用户状态独立持久保存”作为有价值的方向，并进一步提出常驻应为可控能力；若采用共享容器备选，初期最低常驻数设为 0。用户还明确询问纯聊天是否可以完全不启动容器，因此将其列为目标 B 的关键结果，而不把“按需启动共享聊天容器”混同于“只有 OS 任务才启容器”。这不等于已批准实现或部署。还需验证首字、跨用户隔离、NextClaw 可移植对话合同、长期状态与成本。项目特有的设计讨论继续维护在本文，不复制进跨项目个人知识库。

“长时间运行”至少有三种不同产品语义，不能都塞进一次聊天 run 或一次任务执行器：

| 类型 | 用户期待 | 合适的生命周期 |
| --- | --- | --- |
| 长任务、批处理 | 最终完成；中途可看进度、取消、失败后恢复 | 持久任务记录与检查点，执行器按需启动，完成后退出 |
| HTTP server、预览站点、持续运行的应用 | 稳定 URL，按承诺可访问，进程故障后恢复 | 独立服务记录声明期望状态、镜像/依赖版本、路由、健康与资源策略；运行实例可替换 |
| 定时任务、Webhook 或外部事件处理 | 到时或事件到来时执行 | 持久触发器与事件入口唤起短任务；只有确需持续连接时才保持进程 |

对用户创建的 HTTP server，建议另设**托管服务能力**，与聊天运行池和一次性任务池分开：持久记录服务所有者、启动命令/镜像、环境版本、访问策略、端口、稳定 URL、所需数据版本、期望状态（运行、按需唤醒、停止）、健康状态和日志入口。Worker 作为 HTTP 入口路由到相应服务实例；只有确认已就绪才接流量。若承诺首次请求也快，则至少一台常驻并为发布/故障留冗余；若可接受唤醒等待，则闲置休眠并在下一请求启动。独立服务按其运行时间计费，并设闲置回收或显式配额。对用户暴露的是稳定服务合同，不能承诺 PID 永远不变。

实例被部署、宿主重启或内存故障打断时，服务管理者按照期望状态重启并重新绑定路由；收到终止信号时尽量排空请求。业务数据、文件和软件环境版本在实例外持久保存，进程内内存和容器磁盘只作临时缓存。Cloudflare Containers 没有固定最长运行时长，但也不保证任一实例持续运行；磁盘在休眠后重建，端用户 HTTP 请求须经 Worker 路由。服务若必须 24 小时在线，就不能用“5 分钟闲置休眠”冒充常驻；每个 basic 实例持续运行的内存与磁盘预留约增加 $7.2/月，尚未算 CPU、网络和其它共享费用。若为每位用户默认常驻一个实例，成本会随用户数直接上升，应作为明确的产品能力而非聊天默认配置。

当前 Bibo 的容器 runner 自身是内部 HTTP 服务，但没有“用户创建并托管 HTTP server”的产品入口或服务状态合同。是否真的需要用户自建长期服务、需保证多久可访问以及能否在闲置时休眠，是后续产品决策；先不要因为可能出现这种需求，就让每位聊天用户获得常驻 Linux 环境。NextClaw 的通用能力应允许宿主声明可用服务/执行能力，Bibo 的具体服务生命周期和费用由 Bibo 宿主负责。

### 具体方案草案：普通聊天的完整纵向路径（待评审）

先把用户可感知的一次使用走通：用户在新会话或旧会话发送消息，界面立即显示已接收和真实运行状态，随后连续显示回复；刷新后能看到已提交的消息和工具结果。若生成中断，界面显示中断与重试入口，不把残留运行标记解释为“上一条消息还在处理”。用户可以在另一个会话继续聊天，文件读取不占用整个用户的发送锁。

拟采用以下单一状态路径，不沿用容器快照作为权威副本：Worker 认证并代理流；每用户 Durable Object 负责会话事件、运行记录、幂等键、Bibo 空间索引和版本仲裁，小文件是否存同一 SQLite 由测量决定；R2 保存较大文件的不可变版本。一次发送先按会话版本登记用户消息和有到期时间的运行租约，再把带短期身份与运行 ID 的请求派给对话宿主。对话宿主从权威存储读取当前状态，逐步输出；工具对状态或外部系统产生的副作用必须记录各自提交结果，不能把整轮回复假装成跨系统原子事务。助手最终消息提交后才标为完成。宿主退出、超时或网络中断时，租约到期使运行进入可检查的中断态，重试沿同一幂等键处理已提交的副作用；不能只靠进程内 `busy` 布尔值判定用户是否可发送。

对话宿主有两个真实候选，复用**同一 NextClaw 通用对话语义**和持久状态合同。先在 Worker/DO 做目标 B 的完整纵向原型：真实模型流、长会话、文件工具、压缩、取消、隔离和资源限额都过线，才能把纯聊天移出容器；它还须证明不会削弱 NextClaw Node 宿主。E 作为不达标时的托管备选，使用共享按需 Node/Container 池复用现有 Node 扩展能力，但必须把用户 home、凭据、工具上下文和缓存改为按请求隔离，并消除每条消息新建完整 Kernel；最低常驻实例数初始为 0，按并发与排队情况增减，满载时明确排队状态。E 的普通聊天仍需发布 Node 镜像，休眠后的首条纯聊天也要启动容器。Cloudflare 当前的 Container 固定池路由和扩缩容需要应用管理，不能把 `getRandom` 当成智能负载均衡或自动预热。

真正需要 OS 的工具由短任务执行器处理：聊天先持久记录已接收与任务状态，执行器按需启动、读取明确版本的用户数据、上传产物并提交结果后退出。用户创建的长期 HTTP 服务若成为真实需求，再建立独立的服务生命周期与计费入口；它不占聊天运行池，也不借一次聊天运行租约维持。定时触发优先唤起短任务。首批迁移只验证现有 Bibo 能力，不能为尚未提供的用户 shell、软件安装或服务托管提前建设通用平台。

裁决依据是同一批真实负载的完整链路：新旧会话首字与恢复、跨用户隔离、普通文件工具、每消息资源占用、峰值排队、发布耗时，以及每月 300/900/1,800 条消息下的单活跃用户总费用。分别记录 Worker/DO、持久读取、派发、Harness/Kernel、模型首字、工具和提交阶段的 p50/p95/p99；模型费与平台费分开。若边缘原型在 NextClaw 兼容性或尾延迟上不过线，采用共享 Node；若按需共享池的冷启动、发布或峰值排队达不到目标，且边缘原型通过，再采用边缘。这个裁决前不冻结运行平台或对现网迁移。

### 按需启动实际增加的延时，以及用户能否接受

Cloudflare 文档描述容器冷启**常见约 1–3 秒**，取决于镜像和入口程序，属于平台经验值而非 Bibo 的端到端保证。现有 Bibo 容器冷启还串行执行 `onStart()` 中的 R2 整包快照读取与恢复、个人空间同步；每条消息又新建并启动完整 Harness。一次生产请求模型前约 14.5 秒，但没有足够的阶段数据将这段精确归因于容器冷启、恢复或 Harness。因此不能向用户承诺“按需启动只多 1–3 秒”。若先把用户状态迁出容器并避免每条消息重启 Kernel，共享聊天实例与任务型容器的额外等待才有机会接近平台冷启时间，仍需按镜像、状态大小与地域实测 p95/p99；若聊天的空池首字仍超过体验门槛，再考虑最低常驻数 1 或改用边缘对话宿主。

产品路径按等待容忍度区分：普通聊天、长会话续聊和任务/日历/笔记/文件操作应快速开始输出，不应为容器等待；真正需要 OS 的长任务可以先持久确认已接收、立即显示阶段进度，再按需启动隔离执行器。确认事件不是虚构的回答，任务开始、排队、失败与完成都要有真实状态；任务可能在连接断开后继续并可恢复。建议把聊天发出到首字和任务发出到**已接收确认**分别量化，再单独测任务执行环境准备好所需时间，不能把异步确认当作任务已完成。

## NextClaw 独立性与兼容性硬约束

- **依赖方向**：NextClaw/NCP 公共核心不导入 Bibo、Cloudflare DO/R2、Wrangler 或 Bibo 的任务、日历、空间概念。Bibo 只能从公开 package 入口组装对话核心、注册自己的工具并提供宿主适配；NextClaw 自己继续消费同一核心。具体 DO/R2 数据布局、用户额度和产品界面属于 Bibo。
- **保留能力差异**：可移植核心只承载各宿主共同需要的会话和 Agent 语义，不把完整 NextClaw 降为 Worker 的最小能力集合。Node 宿主仍能装载现有扩展、使用本地文件与进程工具、CLI、渠道和自管理能力；边缘宿主按能力注册工具与执行器。不可用能力由宿主明确声明或路由到适合的执行器，不能静默消失。
- **真实变化点才抽象**：先识别当前代码中真正受宿主影响的持久 journal、文件/字节存储、工具执行及运行环境入口。为这些边界提供最小、可组合的公共合同；上下文投影、压缩、模型输入和工具循环保持单一语义 owner。不要为适配 Bibo 添加透传 wrapper、Cloudflare 术语或一套平行的 Agent 实现。是否新建 package 由稳定公共入口和两个真实消费者证明，而非先验决定。
- **既有合同兼容**：盘点 `@nextclaw/kernel`、NCP runtime、extension SDK、CLI 与会话格式的现有外部消费者。内部可重构，但公共 API、事件顺序、工具注册、取消语义及 Node 扩展加载不得无声改变；确需变更时提供版本化合同、兼容适配、迁移说明及退出时间。Bibo 不能通过导入 Kernel 内部路径绕开合同。
- **验收**：同一组对话合同样例同时在 NextClaw Node 宿主与 Bibo 边缘宿主运行，比较模型输入、流式事件、工具调用、取消、恢复和持久状态。Node 现有功能及扩展回归必须通过；再用一个独立消费者只依赖公开入口完成最小会话与自定义工具接入，证明抽象不是 Bibo 专用。若这一门槛不成立，不得以改善 Bibo 延迟为由替换 NextClaw 主链路。

### 目标对象与唯一状态 owner

```text
NextClaw 对话 owner：会话/运行状态迁移、NCP 事件、上下文投影和压缩、模型输入、取消与恢复
         ↑ 同一公共入口被两个真实宿主消费
Node 宿主：本地 journal/SQLite、文件与进程、扩展/渠道/CLI、完整 NextclawKernel 与 Harness
边缘宿主：Worker 请求入口、每用户 DO 会话事实、R2 文件内容、Bibo 注册的工具与模型凭据
```

对话 owner 继续属于 NextClaw Kernel 产品主干；NCP runtime 负责模型轮次和工具循环，不能再让 Bibo 复制一套会话投影、压缩或 run 状态机。完整 `NextclawKernel` 仍是 Node 宿主的产品装配，调用相同的对话 owner；边缘装配只提供所需事实与能力。这里的“拆分”是**依赖方向和启动生命周期**的拆分，不意味着把桌面、渠道、扩展或 OS 能力从 NextClaw 产品中删除。

对话 owner 所需的宿主边界限定为已经存在真实差异的三处：**版本化会话事实**（读取、按预期版本追加事件、运行 claim/取消/终态及投影重建所需数据）、**资产内容**（按身份读写字节与引用，不要求本地绝对路径）、**模型和工具能力**（每次运行注入模型连接、获授权的工具集合与请求上下文）。在本地分别由现有 journal/文件/Provider/扩展能力提供；Bibo 由 DO/R2/模型网关和 Bibo 工具提供。Bibo 用户 ID、DO/R2 术语、额度及 UI 不进入这些 NextClaw 合同。跨用户凭据不得写进共享进程的全局 config/home；每次运行的身份与能力只在其作用域内有效。

会话事实的提交规则由同一 owner 决定：每会话单调版本、重复请求幂等、活跃 run 有期限且可恢复；读操作和另一会话的写入不占用户级全局锁。流式 delta 可以先展示为暂态，但续聊只读取已提交的事实；宿主死掉后不能留永久 busy。外部工具的副作用不能假装与回答处于一个跨系统原子事务，需逐项记录执行与提交结果，重试时识别已经完成的操作。这些语义在 Node 和边缘使用同一事件、状态迁移和测试，不由两个宿主各自重写。

### 保留、迁移与延后

- **保留**：`NextclawKernel`、`NextclawHarness`、CLI、Node 扩展、渠道、MCP、项目/桌面/进程能力及现有公共入口；其内部对话实现改为消费共同 owner。当前 NCP 事件格式、工具调用、取消及会话导出行为先作为兼容基线。
- **迁移**：本地 journal 和资产存储变为对话 owner 的 Node 实现；现有 Bibo 的 DO UI 历史与 Kernel journal 收敛为一个权威会话事实；旧 R2 home 快照仅在迁移窗口作只读输入，完成后删除普通聊天的整包快照链路。
- **延后**：通用服务托管平台、所有 NextClaw 工具在 Worker 运行、任意第三方宿主的动态发现、可变的用户 Linux 环境。未来新应用可以消费稳定的对话入口和自选宿主能力，但不能凭“可能催生场景”提前加入 registry/factory 层。
- **包边界**：先在现有代码中把可移植模块及依赖图跑通；一旦 Node 产品与 Bibo Worker 成为两个真实消费者，以单独 package 根公共入口暴露稳定合同，两个宿主都通过该入口使用。名称、拆包数量和外部版本在原型后确定；不靠导入 Kernel 内部路径或大量 `exports` 子路径绕过边界。

### 重构顺序与判定门

1. 锁定现有 Node 行为样本：新旧会话、消息/工具事件顺序、模型输入、压缩前后续聊、取消/中断、资产引用和扩展工具；形成跨宿主合同样例。记录启动与首字各段耗时，明确当前延迟所在。
2. 先在 Node 内抽出对话 owner 并让完整 Kernel/Harness 改用它；移走对话核心的本地路径假设、请求级全局配置和纯计算模块的 Node API。Node 现有入口和能力回归通过前，不接入 Bibo Worker；不能并存一套长期旧会话主链路。
3. 用相同公共入口在真实 Worker/DO 环境跑一个纵向切片：新会话、旧长会话、模型流、一个 Bibo 读写工具、压缩、取消、实例中断与恢复。实际测 Worker 包加载、CPU/内存、DO 事务及首字 p95/p99；只打包成功不算通过。DO 内运行整轮还是 Worker 运行、DO 作短事务，由这组数据裁决。
4. 两端通过后迁移 Bibo 现有会话和文件，按用户灰度切换单一写入 owner，演练失败与回滚；不在旧快照与新会话事实之间永久双写。完成后删除 Bibo 普通聊天的容器/全量快照路径。若第 3 步在兼容性或体验上失败，用同一 Node 对话 owner 评估共享按需容器备选，保留已完成的 Node 解耦收益。

验收至少覆盖三条真实链路：Bibo 用户在休眠一小时的旧会话发送消息并正确续聊，纯聊天全程没有容器调用；用户通过 Bibo 工具修改文件，刷新及实例重启后看到已提交版本；本地 NextClaw 用户沿现有入口使用同一会话与 Node 专属工具，扩展、取消及恢复行为不退化。AI 负责完成合同测试与真实运行验证；用户仅需在成品交付后评审结果。当前是设计阶段，`design-document: required`，跨 runtime/存储/公共合同的实施须另有分阶段执行计划；实施与上线授权已经由 2026-09-29 用户委托明确给出，但上线仍以验收门通过为前提。

**方案自审中的开放问题**：目前只定位了代表性耦合，尚无完整传递依赖图；版本化会话事实的最小原子操作与旧事件格式兼容还需在 Node 内原型确定；Worker 与 DO 哪个运行模型循环尚未由真实尾延迟和账单裁决；NextClaw 的本地项目工作目录等能力要核对哪些是对话共性、哪些只能由 Node 宿主声明。任何一项若在验证中要求复制会话语义或削弱现有 Node 使用链路，须返回本节修改设计，不能把 Bibo 专用实现冒充通用内核。

## 候选 B 的边界

1. **NextClaw 对话核心**保留单一产品语义 owner，覆盖会话事件、上下文投影与压缩、模型输入构建、工具循环、流式输出、取消和幂等提交。现有 `ncp-agent-runtime-next` 已承载模型/工具循环；Kernel 承载模型输入、压缩与 journal 等语义。重构要把这些能力组合成 Node 与边缘都能调用的稳定公共合同，且 NextClaw 自身改用同一合同。它是 NextClaw 的通用能力，不包含 Bibo 数据模型；抽取以真实双宿主消费为依据，不为包数量或纯代码移动而拆层。
2. **宿主适配**只负责运行环境和持久化：Node 可保留本地 journal/文件适配；Bibo 使用每用户 DO 的 SQLite 存储会话事件、状态索引、提交序列以及常用小文件版本，较大文件版本交给 R2。小文件留在 DO 可减少普通工具调用中的跨服务读取，也能与引用在一个数据库事务里提交；阈值、数据库增长和备份代价要按文件分布实测，不凭空定一个上限。工具按能力选择执行位置，当前 Bibo 的创建、读取、修改与展示文件属于普通对话路径，必须搬到边缘存储接口；只有确实依赖 shell、进程或本地软件的工具才启动隔离容器。
3. **状态归属**以持久事件及版本为准。请求内写入采用单一序列号、幂等键和乐观版本检查；流式增量可以先发送，但只有持久提交后的完成状态才作为可续聊事实。小文件正文与引用可以在 DO 内同事务提交。DO 与 R2 没有跨存储原子事务：大文件先写不可变 R2 对象，再在 DO 事务中提交版本引用；失败对象异步回收，读取只看已提交引用。文件上传、重试和取消都用相同的提交规则。
4. **并发语义**读操作不占发送消息的排他锁；同一会话的写入按版本串行，并明确跨会话写入共享文件的冲突处理。不能把“用户容器正在运行”当作“上一条消息尚未完成”。
5. **发布**普通对话核心与 Worker 代码使用同一已验证产物发布；独立 OS 工具镜像只在工具代码或依赖变化时构建。记录构建、上传、切换和线上冒烟各阶段耗时。源代码分包不等于部署服务拆分，先保证一个公开对话合同和清晰的数据所有权。

对话核心在 Cloudflare 上仍有两种放置方式：**在 DO 内完成整次运行**，协调简单、状态本地但模型等待时间计入 DO 墙钟费用；或 **在普通 Worker 执行模型与工具循环，DO 只做短事务和版本仲裁**，可降低 DO 活跃时间，但多次往返可能增加首字延时，也提高取消、并发和故障恢复复杂度。两者消费同一 NextClaw 公共核心；先以完整纵向原型测量，再选放置位置，不能为了账单把会话状态拆成两个 owner。

## 迁移与回滚

迁移需同时覆盖旧 R2 home 快照内的文件、Kernel journal/SQLite 投影、DO 中的 UI 会话历史和空间结构化状态。先做只读导入器与一致性报告，按用户生成新事件、文件内容和版本索引；以会话消息数、最近消息、文件清单、校验和、压缩后上下文续聊结果比对。旧格式保持可读直至抽样及线上回滚窗口结束。

按用户或小流量分阶段切换读写 owner，切换点记录单调版本；不可在新链路写入后直接回滚到旧快照，否则会丢新数据。回滚需让旧链路读取新提交，或暂停写入并执行经过验证的反向导出。迁移脚本要可重入，重试不重复生成消息与文件版本。先完成迁移及回滚演练，再扩大流量。

## 用来裁决的纵向验证

在真实 Workers 环境搭建最小纵向场景，而非只看 bundle 成功：真实模型流、新旧长会话、跨请求上下文与压缩、Bibo 文件工具、搜索工具、取消/重试、重复请求、冷启动和并发读写。另以 NextClaw Node 宿主及独立最小消费者验证同一公共合同和现有扩展能力，避免只对 Bibo 用例调通。对常用小文件分别测 DO 内存储与 R2 存储，比较读取时延、写入量、存储增长、导出和回滚。记录首字各段 p50/p95/p99、DO 活跃秒数与内存、Worker CPU/内存、R2/DO 读写量、容器唤醒次数、模型和搜索费用、每百次消息与每月每活跃用户成本。用同一流量样本运行共享 Node 候选，比较总成本与尾延迟。

Workers 单 isolate 128 MB；Node 兼容层中的 `node:sqlite` 和 `node:child_process` 不能当作可用的持久 SQLite 或进程能力。若长会话压缩、依赖兼容、CPU 或尾延迟不能满足门槛，立即以共享 Node 宿主承载同一核心，保留 DO/R2 存储合同与文件版本方案。正式架构决定以这个实测为门槛。

## 粗略成本边界，非报价

以 **1,000 位月活用户、30 天**为同一基线。设三档活跃度：每人每月 300 条（每天两次、每次 5 条）、900 条（每天三次、每次 10 条）、1,800 条（每天四次、每次 15 条）。同一次使用内消息相隔不足 5 分钟；每条消息从进入对话运行到完成平均 20 秒，其中容器实际占用 1 vCPU 秒。峰值到达率设为月均的 10 倍；同一用户同一时刻只有一个 run。假设每人保留的小文件/状态 3 MB、较大文件 5 MB，1,000 人分别约 3 GB DO 与 5 GB R2；这仅用于比较，真实版本历史和分布未知。现网全局模型额度为每天 2,000 次调用、容器最多 20 实例，因此表中流量属于未来产品场景，现有配额不能直接承载。

容器方案 A 按当前 `basic` 型 1 GiB 内存、4 GB 磁盘、闲置 5 分钟休眠计算，**假定解除现有 20 实例上限**。A 的 DO 等待时间保守按每条 20 秒计；容器冷启、恢复、快照的额外 DO 活跃时间和 R2 写入费没有加入，故它是低估值。边缘方案 B 在表中按**整次运行位于 DO**、每条消息 DO 活跃 20 秒计；CPU、存储和请求超过包含额度的部分未加入。共享 Node 方案 C 假设每台规划成本 **$25/月**，每台承载 25–50 个并发流，并额外留一台冗余；DO 仅作短事务，不随 Node 的模型等待保持活跃。$25 接近当前 Hetzner 欧区 CPX22 的 $22.99 标价，但可用性、地域和承载数未验证，表中也未计负载均衡、运维、备份与独立数据库。三方案都计入一个 $5/月的 Cloudflare Workers Paid 起步费，且共用相同模型/搜索供应商。

复算方法：A 的每人月容器运行秒数为 `消息数 × 20 + 每日使用次数 × 30 × 300`；按已配置的 basic 实例分别计入预留内存、磁盘和实际 CPU，减去账户共享包含额度。B 的 DO 活跃量为 `千人 × 每人消息数 × 20 秒 × 128 MB`，扣除每月 400,000 GB·s 包含额度后按官方整百万计费。C 的服务器数为 `ceil(峰值并发 / 每台可承载并发) + 1`。DO、R2 和 Workers 的包含额度是账户共享的；若其它产品已经消耗额度，这张表会低估增量费用。容器散点使用更贵：以 900 条为例，若每条都隔开 5 分钟，容器每人运行约 80 小时/月，而表中集中使用为 12.5 小时/月。

运行时长敏感性：在 900 条/月、千人规模下，若 DO 每条实际活跃 **10/20/60 秒**，B 的估算平台费分别约 **$18/$30/$93 每月**。如果在 Worker 运行模型循环、DO 只参与短事务，应另测 Worker CPU、DO 请求数、跨服务时延和故障恢复；不能直接套用上表或假定一定更快。现有容器 20 实例上限低于三档假设下约 23/69/139 的同时运行消息数，未经扩容 A 在峰值性能上就不具备可比性。

E 的区间是两个**容量情景**，不是账单置信区间或已测得的弹性策略：下端假设分别相当于 1/2/3 台 basic 全天运行，可覆盖平均 CPU 需求；上端假设 5/14/28 台全天运行，可覆盖上述 10 倍峰值的 CPU 需求。每条实际消耗 1 vCPU 秒，按容器实际 CPU、预留的 1 GiB 内存和 4 GB 磁盘及账户包含额度计费；与 A/B 相同，用户状态 DO 在每条 20 秒运行期间按 128 MB 活跃计费，另加 Workers Paid 起步费。池的实例随负载升降时通常位于两种情景之间，但极端零碎的到达、额外休眠尾时长、并发内存压力、冷启和排队可使账单或体验超出该区间；所以它不是可靠的价格上限。E 尚未实施，容器自带 DO 的额外计费和路由请求没有实测，表中可能低估 E；容器池仍需真实并发/内存压测才能选型。Cloudflare 容器与 DO 都有账户共享包含额度，若已被别的产品用掉，四列平台增量成本会更高。

生产边缘无工具样本补充了表中保守的 20 秒假设：82 条成功运行的 DO 内 `run.finished` 墙钟累计约 **98.73 秒**，折算约 **120 秒/百条**，并对应 82 次模型调用。按这个简单聊天路径机械外推到 900 条/人、千人，DO 活跃量约 **135,000 GB·s/月**，落在每月 400,000 GB·s 包含额度内；若其它应用未占额度、每条仅一次 DO 请求，则平台费接近 **$5/月总额**。这不是实测 CPU、全品类流量、真实 Cloudflare 账单或长上下文/工具任务预测；A/B/E 的主表仍保留同一 20 秒负载以公平比较。模型与搜索费单列。

**100 位月活用户的按需共享池示例。** 仍假设每人每月 900 条、20 秒运行和 10 倍峰值，则约 7 条消息同时运行；模型与搜索另计。A 按一人一容器且 5 分钟休眠，平台费约 **$19/月**，但大量消息遇到冷启。E 的最低常驻数初始为 **0**，费用由实际运行及闲置尾时长决定：若一台 `basic` 容器在负载下几乎全天运行，平台费约 **$13/月**；两台几乎全天运行约 **$20/月**。这不是 E 的最低费用或固定账单。900 条 × 100 人意味着全月平均约 **29 秒一条消息**；若请求分布均匀，共享实例即使没有常驻保底，也可能很少出现连续 5 分钟闲置。basic 仅 1/4 vCPU，按每条消息 1 vCPU 秒的假设，峰值需要约 0.35 vCPU，**一台不足以稳定承载**；两台能否承载约 7 条同时运行的实际 Harness 内存仍须测试。B 在这些条件下约 **$5/月**，C 按两台规划服务器约 **$55/月**。E 在接近全天运行的两台示例中与 B 每月相差约 $15 的平台费，远小于同场景的模型预算；因此在早期不能仅凭这笔差额证明全面边缘重构值得做。E 的聊天代码仍走容器镜像发布，而现有 `max_instances = 20` 和按用户寻址必须调整。

**模型与搜索单列。** 当前 Bibo 使用 `deepseek-flash` 和 Exa。假设每条用户消息触发两次模型调用，每次 6,000 输入 token（均按高峰缓存未命中）和 600 输出 token；10% 的消息各触发一次标准搜索。按当前公开价格，每条用户消息约 `$0.00504` 模型费和 `$0.00070` 搜索费；900 条/月约 **$5.17/活跃用户**，显著高于上表三方案的平台费。真实上下文长度、缓存命中、工具轮次和搜索比例会改变这个数，尤其长会话可能更贵；用量日志必须记录每次用户请求展开的模型调用数、token、缓存及搜索次数。

换成一个人容易理解的同口径月费用：300/900/1,800 条时，模型加搜索约 **$1.72/$5.17/$10.33/人**；再加 B 的平台分摊约 **$0.018/$0.030/$0.068/人**，分别约 **$1.74/$5.20/$10.40/人**。900 条时 A 的对应合计约 **$5.34/人**，E 情景约 **$5.23–5.31/人**。因此选 B 的价值同时来自更快的首字、零容器及平台成本弹性，而非向用户承诺总账单随平台费同比例下降；模型 token、轮次与搜索频率才是总成本的主要敏感量。

**延时与费用同权验收。** 在上述三档流量及 10 倍峰值下，对新会话、长会话、闲置超过一小时的旧会话和带文件工具的消息分别测发出到首字 p50/p95/p99、错误率和上下文正确性，并标出模型前平台耗时与模型首字耗时。目标暂定整体 p95 < 5 秒、p99 < 10 秒，最终按真实模型基线校准。A 在上述集中使用条件下，首条消息占比依次为 20%、10%、6.7%，因此 p95 都会包含休眠后的冷启；实际冷启时长尚无分布数据。B 没有容器冷启，但可能有 DO/Worker 初始化、存储或压缩尾延迟；C 常热但可能受地域往返、峰值排队及容量不足影响；E 的冷启命中率随全体用户请求分布变化，需要单独测空池首条与已有运行实例两类请求。不能用价格表推断谁的首字更快，必须跑相同模型、相同地区、相同内容和峰值并发的纵向对照。

当前 `BiboModelBudget` 还把全局额度及逐用户计数存在同一个 DO 键里，模型调用会在这个全局 owner 上预留额度。规模化负载测试必须单独量它的排队、状态体积和写入耗时；否则即使对话运行位置改变，首字仍可能被入口处的全局瓶颈拖慢。额度实现属于 Bibo 宿主，不能为解决它改动 NextClaw 的通用会话语义。

按这些假设，B 的平台费最低，但这是**有条件的成本结论**。若 B 的完整 NextClaw 通用合同、长会话或首字达不到门槛，C 的额外平台费可能值得换取稳定体验；A 即使通过增量持久化降费，仍须证明冷启尾延迟能过线。正式选择以真实账单、负载测试、兼容性合同和迁移演练共同裁决，不能只按服务器标价选择。

## 自我审查与未决项

- B 的关键好处是从普通消息路径移除容器冷启动和整包快照，但目前没有端到端 Workers 原型；它是优先验证的目标，不是已证明可交付的最终选型。
- 最大架构风险是为了让 Bibo 跑在 Worker 而把 NextClaw 通用能力拆碎、复制语义或削弱 Node 扩展。新增的每个接口要能指出真实的第二消费者与变化点；兼容性回归不过，边缘方案就不能进入生产。
- 现有 runtime 的部分依赖引入 Node API；必须检查 Worker 实际加载和运行，不能根据模块名称推断兼容。
- 更快的运行平台不能掩盖模型本身的尾延迟；需要按阶段埋点，分别优化初始化、上下文、外部服务与流式传输。
- DO 的单用户顺序执行适合会话状态，但超长工具任务、CPU 密集压缩及大文件要验证资源和切分策略；常用小文件放 DO 还是 R2 的阈值，以及边缘和共享 Node 的成本交叉点，都未知。
- 紧急修复错误 `RUN_BUSY` 已独立通过维护性检查并部署，生产真实账号冒烟已通过；特定旧会话仍待直接复验。它不能替代持久化与运行架构迁移。

## 2026-09-29 可运行切片后的设计收敛

- 真实本地 workerd 已证明公共 NCP Agent runtime、会话状态管理器、模型流和一个 Bibo 工具轮次能运行；这只裁决**循环内核可移植**，不代表完整 NextClaw 对话语义或生产分位数过关。实际 `AgentRunModelInputBuilder` 直接导入 workerd 会经 Kernel/Core 根入口加载原生 `sharp` 并在启动时失败；动态 import 也被当前 Wrangler 打入启动 bundle。下一刀应给模型输入、压缩投影和预算提供真正窄的、宿主无关的公共入口，并让 Node Kernel 自身消费，避免在 Bibo 重写上下文语义。
- `NcpTool.parameters` 在 workerd 的执行验证会触发 Ajv 运行时编译而失败。Bibo 工具已抽为同一工厂：Node 保留原 schema 验证，Worker 在模型输入仍发送同一 schema、执行时使用公共 NCP `validateArgs` 扩展点做无 JIT 验证。后续应在通用合同中说明 schema 的“呈现”和“执行验证”可分别由宿主实现；不为 Bibo 增加第二套工具业务逻辑。
- Bibo 文件层已有独立 `BiboFileStorage` 接口切片：Node 原路径不变；DO 草稿以稳定文件 ID 存正文并随结构化元数据同事务提交。复核旧 Node 路径确认文件上限是 **1 MiB UTF-8 字节**，不是请求层允许的最多 100 万字符；DO 必须维持相同字节限制。此切片尚未接入生产；完整 Agent run 的文件变动必须延迟到最终会话提交，不能沿普通空间操作的每次 `save` 直接生效。
- 旧用户迁移不能靠 DO 当前 `sessions` UI 投影重建 Agent 上下文，因为其消息只保留约 100 条，而且独立于 R2 快照内的 NCP journal、压缩检查点及身份/记忆。应从旧容器经通用 NextClaw 会话读取合同导出完整 NCP 数据，与 R2 文件和 DO 元数据对账；若无法提前枚举旧用户，先使用 R2 快照中的 DO ID 清单，补充无快照但有 DO 会话的情况。首次旧用户聊天若需要当场启动容器导入，则 BE-01 和 BE-02 均不达标，不能以“惰性迁移”偷换目标。
- 旧 Node `BiboSpaceService` 的 Agent 送达收件箱还从本地 `inbox/deliveries.json` 桥接。边缘切换前必须导入此事实或给它一个通用的送达读取接口；不能简单忽略该路径而宣称体验不退化。
