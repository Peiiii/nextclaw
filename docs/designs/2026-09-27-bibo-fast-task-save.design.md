# Bibo 待办保存延迟优化

## 来源与目标

用户 2026-09-27：添加待办耗时很久，希望优化到 1 秒以内；随后授权实现、验证、提交、发布和部署。愿景依据：减少用户维持搭档和记录日常事项的等待负担，网页与 Agent 继续消费同一领域 owner。

线上测试账号基线：待办接口端到端 7.3 秒、44.4 秒，两个请求的 runtime ID 相同；聊天添加约 19 秒。44 秒没有分段证据，不能归因于冷启动或备份。源码确认：结构化写入等待容器与整个 home 快照，前端随后等待项目、任务、概览读取。

## 黄金使用链路

登录 app.bibo.bot → 打开待办页 → 输入标题并添加 → 服务端持久化完成 → 列表立即出现返回对象，输入可继续使用 → 刷新仍存在 → 连续添加、改状态、删除均能正确保存。服务端失败保留草稿；响应丢失后使用同一 requestId 重试不重复创建。聊天写入和网页写入不能互相覆盖。

以点击到已保存对象可见且输入解除等待的 P95 ≤ 1000ms 为性能目标，同时分别记录浏览器往返与服务端耗时。首次从已有快照装载数据需单独报告；不以乐观显示冒充持久化成功，也不从有限样本保证所有网络环境。聊天模型生成不是待办页保存链路；保留真实聊天写入验收，不承诺其生成时间 ≤1 秒。

## 主链路与 owner

- 保留 BiboSpaceService 作为动作校验、版本控制、引用与去重的唯一业务 owner。仅注入状态持久化读写端口，默认文件存储继续服务容器工作副本与本地测试。
- 现有 BiboUserContainer Durable Object 的分块状态成为个人空间结构化状态的权威持久副本。spaceState 记录块数量，spaceState:N 保存 JSON 字符串分块，事务同时提交全部块与快照指针，避免 SQLite KV 单值 2 MiB 限制；结构化数据上限 32 MiB。task/project/event 动作直接执行同一 BiboSpaceService，不启动容器，不创建 R2 快照。
- 文件、收件箱桥接和聊天继续在容器执行。执行前将权威状态同步到工作副本，成功时读取工作副本状态与文件快照一起提交到 DO；失败或取消停止容器，工作副本不成为权威。
- onStart 恢复文件快照后覆盖为当前 DO 状态，避免旧快照回滚已保存待办。首次访问已有空间从当前快照装载同一 schema，无平行写入和永久兼容分支；新空间直接使用空状态。
- 所有写入使用当前 DO 操作串行边界，聊天期间保留既有忙碌响应；不能以任务快路径绕开聊天暂存事务。迁移/同步失败明确返回失败，不回退为空状态。
- 待办前端使用服务器已提交对象立即更新当前筛选列表、结束保存；概览打开时刷新，避免占用下一次保存的容器队列。存在偏移分页时后台重新读取任务页。读取版本号使旧列表请求失效；账户切换不能接收前账户的异步写入结果。
- 部署后分段实测发现逐次外部身份校验仍有 840ms、3022ms 长尾。仅 `/api/space` 复用平台已验证身份，现有 Cache API 以凭据 SHA-256 为键，仅保存用户 ID 和绝对到期时间，最多 30 秒且不晚于原凭据到期；命中不续期。缓存异常继续实时校验，拒绝结果不缓存，退出登录删除缓存。账户与模型/余额检查始终实时。平台撤销凭据对空间操作最多有 30 秒生效延迟；未知凭据格式无缓存，不建立未验证声明信任或新增资源。

部署恢复边界：新待办权威状态不在旧 R2 快照中，不能直接回滚到只读取快照的历史 Worker；采用保留新状态 owner 的前向修复，或只回退静态 UI。容器镜像与 Worker 分别滚动，首次装载若命中旧镜像，应失败保留内容、等待镜像更新后重试，不能降级为空状态。

## 取舍与抽象审计

仅延长容器存活无法解决已热容器 44 秒样本，且增加运行成本；仅删除前端等待不能消除备份和冷启动。采用现有 DO 状态持久化，无新增付费资源、在线状态服务或模型调用。拒绝后台快照后提前报成功：容器磁盘不保证休眠后恢复。持久化端口隔离已有文件存储与 DO 存储的实际变化点，不新增任务 service/wrapper 或复制业务校验。

设计文件 required；单批实施，无独立执行 plan。方案 Review：已核对重启覆盖、聊天失败、文件保存、账户隔离、幂等及版本冲突，进入实现前无开放 finding。无 UI 偏好更改，不追加人工批准门。
