# 移动端发送后的草稿与接收确认

## 目标与证据

用户在手机聊天页发送消息后立刻切换会话，返回时已发送的文本不应回到输入框；失败时应能恢复，结果不明时不能以新消息重复发送。现有 UI 草稿按会话持久化，发送前清空，但 Lexical 在 IME 合成结束后仍可能回写旧节点；发送抛错后无条件恢复快照。NCP envelope 已有消息 ID 和可选幂等键，kernel 已按会话及幂等键查询已接收消息或队列；当前聊天入口未设置稳定幂等键。

## 用户链路与主方案

从手机聊天页输入并点击发送时，输入内容立刻转为该草稿分区的待确认发送记录，输入框清空。导航、返回和刷新都显示清空的输入框，旧编辑器节点不能回写。服务端返回接收 handle 后清除记录并显示消息或队列。明确拒绝时，若用户没有新输入则恢复原草稿；有新输入时保留它，并单独保留失败发送供恢复。网络中断或响应丢失时保留待确认记录与错误提示；返回页面先按预分配的会话 ID 和原消息 ID 查询，重试始终复用原 envelope 的消息 ID 与幂等键，由服务端去重。用户能从同一聊天页处理待确认发送。

UI draft store 是草稿与待确认发送的唯一持久 owner；NCP/kernel 是消息接收与幂等的唯一 owner。旧编辑器回写抑制只保护最近一次已提交的节点，不改变正常输入。子会话创建由服务端分配会话 ID，不能在没有确认 ID 时安全重发；此路径若发生结果不明，只展示待确认状态并要求先查子会话，不自动重发。

## 取舍

仅在发送成功后清空会留下切换期间的旧草稿；仅在异常后恢复会把已接收但响应丢失的消息误当草稿。待确认记录增加少量持久状态，但复用现有 envelope、会话查询和 kernel 幂等合同，且能覆盖刷新后的结果不明状态。

## 2026-09-26 发送反馈纠偏

用户指出正常发送也会在输入框内突然出现“正在确认消息是否已接收…”卡片，重复显示刚提交的内容并撑高输入区。该卡片来自上述草稿保护实现，持久化发送记录本身不要求将每次服务端确认过程展示为卡片。

修正边界：发送中的记录只在后台保留，输入区不渲染确认卡片；现有会话消息、发送按钮及真正的排队项承担正常反馈。只有明确拒绝或结果不明、需要用户恢复/核查时才显示恢复内容与动作。队列、草稿 owner、幂等与刷新恢复合同均不改变。

本次为单一组件内的 L1 展示修复，skip-design：不改变状态或恢复语义，无新增交互分叉，局部可逆；复用原设计并内联修正。plan: not-required。验收覆盖普通发送和运行中排队发送均无确认卡片及重复全文、结果不明仍可核查重试、失败恢复不覆盖新草稿。新增组件回归先在旧实现复现两项失败，再沿同一入口复验。

验证：发送反馈组件、原草稿 store 与控制器共 31 项定向回归通过；源码组件浏览器回放显示普通发送额外高度为 0px，排队发送仅保留一条 32px 队列行，结果不明仍显示查询重试入口。浏览器证据只证明渲染边界，不冒充真实模型回复；本次未修改传输和模型执行。可维护性检查无 findings，原移动草稿回填合同继续由既有回归保护。复盘更新原设计 owner，不新增常驻规则。
## 2026-09-26：HTTP 发送消息 ID 回归修复

用户从普通 HTTP 地址打开聊天页，输入消息或点击菜单预设消息，发送必须正常进入接收确认流程。`260eae4fb` 在生成 envelope 时新增了 `crypto.randomUUID()`；该 API 仅在安全上下文提供，异常发生在请求发送及其 try/catch 之前。`988f2bfb0` 曾修复编辑消息的同类问题，但其测试不覆盖此控制器。已通过禁用 `randomUUID`、保留 `getRandomValues` 的 controller 回放复现普通、steering、预设发送三条路径。

方案：在现有 `buildSubmissionEnvelope` 内使用 `crypto.getRandomValues(new Uint8Array(16))`，编码为 `user-` 前缀的 32 位十六进制 ID。所有新发送共享这一 producer；每次发送保留 128 位随机身份，幂等键仍直接取消息 ID，持久记录和重试继续复用原 envelope。`getRandomValues` 在普通 HTTP 上可用，不增加环境探测、fallback 或全局补丁。不采用 builder 默认的毫秒时间 ID，以避免同毫秒发送的幂等键冲突；不要求用户更换访问地址，也不触达旧消息或协议迁移。

风险 L2，bugfix；局部单 owner，无新增状态、跨包改动或兼容分支；无需另建计划。设计 Review：方案覆盖报错及三条共用发送入口，随机 ID 不要求 UUID 格式，已有重试合同保持不变，无未关闭 finding。

验收：同一毫秒连续发送产生不同 ID；禁用 `randomUUID` 时三条入口均到达 agent.send，接收确认使用相同 ID；已有首次发送、明确拒绝、结果不明重试测试保持通过。AI 执行 controller 边界回放、UI tsc 和定向 lint；普通 HTTP 浏览器核对实际 Web Crypto 能力与 ID 生成。用户当前 URL 和部署版本未知，现场请求接收及助手回复仍需区分验证范围。这是已有发送行为的恢复，公开故障说明同步至中英文 troubleshooting，发布记录用 UI patch changeset；当前无发布授权。

验证记录：修前新增三项测试均命中相同 TypeError；修后 controller 与历史编辑发送共 25 项测试、UI tsc、治理检查通过。定向 ESLint 无错误，既有队列 describe 超行数警告仍存在；diff-only maintainability 无错误，控制器临近文件预算提示已人工复核，本次仅增加三行生产逻辑。真实 Chromium 普通 HTTP 上 `isSecureContext=false`、`randomUUID=undefined`、`getRandomValues=function`，1000 个生成 ID 格式正确且互不重复。当前源码 Vite `http://127.0.0.1:5347` 代理既有 `55667` 后端，真实会话 `ncp-muiebv32-uesfoiv9` 已接收测试消息并从 `deepseek/deepseek-flash` 显示“发送正常”；该回环地址属于安全上下文，非安全上下文发送由 controller 回放及浏览器能力证据证明，未冒充用户现场复验。预览保留，无提交或发布。
