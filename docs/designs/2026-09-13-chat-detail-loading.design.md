# 聊天过程详情加载反馈

用户点击已完成消息的过程摘要后，应立即知道点击已生效、详情正在读取，且能随时收起。这提升长期协作中对系统状态的理解。仅影响 UI，不需要 CLI。

## 现状与选择

`ChatMessageList` 将宿主的详情状态和请求交给 `ChatMessage`，`useChatMessageToolPayload` 目前用 pendingProcessOpen 等到 ready 后才展开；消息组件仅在摘要拼接加载文字。截图中的无展开、无动效与该路径一致。

采用立即展开、加载区转圈和三行骨架；保留已有摘要文字。仅在摘要加转圈仍缺少展开反馈，因此不采用。请求和缓存仍由宿主负责，展开状态仍归原 hook；删除等待完成才展开的过程状态，避免完成时覆盖用户收起意图。失败展示原有错误文案和可点击重试，成功替换占位。工具组保留用户展开意图，仅在详情 ready 后展示；过程收起后仍保持收起，不通过 effect 修正用户展开状态。

复用开发专用 stress harness 增加固定 5 秒慢加载与失败演练；不在生产请求加延迟、不修改会话数据。演练只证明组件交互，真实请求链路另由宿主既有测试及实际页面核查。

## 验收与交付

1. 点击过程摘要立即展开，等待时显示转圈、骨架和加载文字；正文仍可读。固定等待 5 秒后显示详情。
2. 等待时收起，5 秒后仍保持收起；再次展开直接显示已加载内容。
3. 模拟失败后出现重试入口，再次请求成功；重复运行可复验。检查键盘、窄屏、明暗主题和减少动画设置。

定向组件测试覆盖展开/成功/收起竞态/失败重试，匹配包执行 tsc，浏览器验证真实组件渲染。交付运行中的本地演练入口与最短操作；不提交或发布。设计审查通过：复用原 owner，无协议、持久化或新生产配置；单批完成，无独立 plan。

## 实现与证据

- 用户验收纠偏：摘要始终只显示“已处理＋耗时”；加载、错误和重试提示仅在展开内容区域显示，不在摘要重复拼接。回归断言保护摘要稳定和加载文字只出现一次。开发演练不能代替完整产品页面，实际验收提供 `/chat` 下真实会话；固定慢加载只通过临时本地转发延迟真实详情请求，不修改真实数据或生产请求实现。

- flow=bugfix，L2；修前未另跑浏览器基线（skip-reproduction），原 hook 等待 ready 才展开和已有回归测试的 false 断言直接锁定问题；修后同入口断言立即为 true，保留收起意图。
- 过程区展示集中在 `process-details/chat-message-process.tsx`，原消息组件缩小；宿主请求仍沿 `use-ncp-session-message-history.ts` 的去重、loading、ready/error 链路。
- 定向组件覆盖过程与工具组的等待/收起意图，宿主会话 17 项测试通过；两个 UI 包 tsc 与定向 ESLint 通过。浏览器固定 5 秒演练确认骨架、实际 spin 动画、成功替换、收起保持、键盘展开、失败重试成功；466px 容器无横向溢出。卡片和平铺均查看。
- 源码前端 `http://127.0.0.1:5179/chat` 连接已有 18792 宿主，真实历史会话“衡水婚礼出行准备”的“已处理 51秒”展开显示思考和记忆工具详情。慢网络时序单独由开发演练覆盖，不声称原网络延迟已重现。
- 验收演练：`http://127.0.0.1:5179/__debug/chat-tool-call-stress`，点击“演练慢加载（5 秒）”再展开摘要；失败演练使用旁边按钮，5 秒后点击错误提示重试。数据仅在浏览器。
- 复盘：问题已沉淀到原展开状态 owner、回归测试和本设计；已有交互规范已要求即时加载反馈，不新增重复规则。审美待用户确认，暗色主题和系统减少动画设置未做浏览器切换核验，相关样式使用既有语义 token 和 motion-reduce。
