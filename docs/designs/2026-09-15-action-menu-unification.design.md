# 操作菜单统一修复

## 目标与证据

用户从消息底部更多按钮打开运行元数据/触发详情时，菜单应与会话顶部更多菜单保持一致，再选择条目进入详情，关闭后回到触发按钮。相邻项目、定时任务、供应商和服务授权入口应使用相同菜单密度与反馈。

现状：会话菜单消费 `ACTION_MENU_ITEM_CLASS` 与 `CONTEXT_MENU_SURFACE_CLASS`；消息菜单来自 agent-chat-ui 的独立 Popover，使用 rounded-2xl、text-sm、普通字重且缺图标。另有操作菜单未启用 menu variant。根因为跨包皮肤重复与调用方遗漏，按 bugfix/L2 处理。

## 实现与边界

- 在 agent-chat-ui 默认皮肤提取稳定菜单样式，从包根导出，NextClaw 现有反馈与菜单常量转用同一来源；不反向引用应用代码、不增加主题覆盖选择器。
- 默认聊天 Popover 增加 menu variant，消息菜单和输入附件操作页使用它；详情动作支持可选 ReactNode 图标，由产品 view model 提供。
- 将明确的操作菜单接入公共 variant 和条目样式。搜索、模型选择、目录浏览、表单浮层保留功能布局。
- 保留原操作、权限与弹窗流程。menu variant 只涉及组件 props 到 DOM，无持久化、传输或配置迁移；纯视觉修复不增加 CLI。
- 排除复制一套相同 class 的方案：未来会再次漂移。也不为视觉修复搬迁完整应用菜单状态机。

## 验收与交付

1. 真实聊天页面：更多 → 统一图标菜单 → 元数据/触发详情 → 关闭，验证内容与焦点；同视口对比会话菜单。
2. 相邻菜单展开，抽查明暗主题、hover、键盘焦点和窄视口；操作目标保持不变。
3. 两个 UI 包 tsc、消息详情回归、菜单组件回归、diff-only maintainability。

交付工作区修复和本地可用入口；不提交或发布。用户判断最终审美偏好，AI 负责渲染与行为验证。plan: not-required，单批实施。方案审查：原用户入口和跨包样式 owner 均覆盖，无额外状态 owner，design-review: passed。
