# 聊天内交互式成果展示设计

## 要解决的问题

NextClaw 已能把自包含 HTML 和 Panel App 放进聊天原位展示，但官网主要用静态截图说明“小工具可以边聊边用”。用户无法在首次了解产品时直接感到“结果会随着我的操作继续变化”，因此这项真实能力的传播强度低于同类公开演示。

用户任务：访问首页的人在不安装、不进入产品的情况下，拖动一个控制项，看到任务节奏、数据图和聊天里的产物同步更新，并理解这类成果可留在 NextClaw 会话中继续使用。

## 现状与约束

- 产品内的事实链路是：Agent 创建 self-contained HTML 或 Panel App → `nextclaw-inline` 声明 → 聊天内 renderer → 用户继续在同一会话中操作；本次不改动该协议。
- 首页的内容由 `apps/landing/src/shared/lib/landing-content/landing-home-sections.utils.ts` 编排；互动展示的纯渲染与 DOM 控制分别归 landing-content 模块内的 `utils/` 与 `controllers/`，页面入口只在 render 后调用 controller，样式由既有 `style.css` 承载。
- 对外内容只承诺已经存在的聊天内展示能力；演示数据是解释交互的样例，不宣称为真实运行截图或新增分析功能。

## 候选方案

1. 新增静态截图与文案：改动最小，但无法让访问者感到“可继续操作”，不采用。
2. 嵌入预录视频：可控且适合社媒，但不能建立亲手操作的证明，且制作与迭代依赖额外素材链路，不作为首页主入口。
3. 首页内的真实 DOM 互动演示：用一个 range 控件驱动图形、数字和聊天内成果预览；直接传达能力，复用现有 landing owner，能够键盘操作和响应窄屏。采用。

视频仍可在该演示稳定后由同一套交互录制，但不阻塞本次可见结果。

## 主链路与交互

页面首次进入显示一个“安排一天的工作节奏”的样例，默认值为 60。用户拖动滑块或用键盘调整后：

1. `input` 事件由 landing 页面的单一 binder 接收；
2. 以纯函数将 0–100 的值转换为连续的“资料、图表、行动项”三段占比与摘要文字；
3. 更新同一演示区域内的 SVG 路径、重点节点、时间标签、聊天气泡和可继续操作的结果卡；
4. `output` 与 `aria-live` 文案宣布当前选择，键盘和触控走同一条路径。

状态仅存在浏览器 DOM 中；刷新恢复默认值，没有 URL、持久化、网络请求或跨页面状态。

## 信息结构与边界

- 区块置于首页的“主工作台”之后，用“让成果继续响应你的操作”解释核心价值。
- 左侧是一个实际可拖动的时间轴/曲线，右侧是缩小版的会话内成果；两者是一个单一故事，不增加 dashboard、标签页或模拟设置页面。
- 结果卡明确用“聊天里的互动成果”描述，不使用内部协议、工具名或“新功能”等不准确表述。
- 非目标：不变更产品运行时、`nextclaw-inline` 合同、Panel App、数据分析能力、官网路由、SEO 元数据或截图资产；不把示例伪装成真实产品截图。

## 失败与降级边界

- 没有 JavaScript 时，静态初始布局仍呈现能力说明和默认图形；交互只是不更新。
- `prefers-reduced-motion` 时不做节点/路径过渡。
- 窄屏改为单列，滑块和当前值保持可见；不以横向滚动保留桌面布局。

## 验收标准

- 首页中可以通过鼠标、触摸或键盘改变滑块，图形、时间、总结和聊天结果同步变化。
- 默认、最小、最大值均有正确的可见文本、`output` 和无障碍语义。
- 演示在 390px 与 1512px 视口无横向溢出，焦点可见，减少动态效果偏好得到尊重。
- landing 类型检查与生产构建通过；用浏览器自动化读取交互后的 DOM 并生成实际页面截图进行目视检查。

## 实现边界

- `utils/interactive-artifact.utils.ts`：演示的静态 DOM 结构和可本地化文案。
- `controllers/interactive-artifact.controller.ts`：一次性事件绑定和 DOM 更新；`main.ts` 只调用该 controller，不新增 manager、store 或通用展示框架。
- `style.css`：局部、响应式视觉规则。

`design-document: required`。`plan: not-required`：单一现有页面 owner 内可在一批改动中闭环，且验证路径直接。
