# 应用包列表故障隔离设计

## 问题

Apps、面板应用和服务应用列表会读取所有已启用应用包。任一包的安装目录、完整性记录或组件 manifest 无法读取时，异常会穿透列表接口，导致整个页面返回 500；用户既看不到其它正常应用，也不知道哪个包需要处理。

## 用户结果

用户打开应用管理页时，正常应用继续可见、可使用。发生异常的应用包会显示为“不可用”，并给出可操作的本地诊断；其 Panel 与 Service 组件不会被加载或运行。

## 主链路

`AppPackageManager` 仍是已启用包完整性校验和组件投影的唯一 owner。它逐包校验，生成两类只读结果：可用组件源，以及不可用包诊断。Panel 和 Service manager 消费同一结果，分别投影自己的正常条目和诊断；Apps 页面消费应用包健康状态并禁用该包的运行入口。

列表操作只读取和报告状态，不会自动禁用、删除、修复或修改应用包。用户通过现有的更新、回滚或卸载操作恢复该包；一次成功的重新读取会自然清除诊断。

## 合同

- 每个不可用包包含稳定 `appId` 与面向用户的错误摘要。
- `/api/panel-apps` 与 `/api/service-apps` 始终返回其余可用条目，并附带不可用包诊断。
- `/api/app-packages` 的对应条目带有健康状态；不可用时 Apps 页面展示诊断、禁用启用/打开操作，并保留更新、回滚和卸载入口。
- 组件 manifest 在打包与安装时使用运行时相同的解析合同，避免“能打包、首次列举才失败”。

## 取舍

不在 HTTP controller 捕获并吞掉异常：那会让 Panel、Service 与 Apps 三个表面产生不同事实，且会隐藏坏包。

不在列表读取时写回 `enabled=false`：读取接口必须无副作用，且自动禁用会改变用户状态。健康状态由当前读取结果投影，不持久化。

## 范围与验证

本次覆盖已启用包的完整性失败和组件 manifest 失败；不尝试修复损坏文件，也不迁移历史包。定向测试将证明一个坏包和一个正常包并存时，三个列表返回 200、正常组件仍可见、坏包明确标记为不可用且不进入运行时。
