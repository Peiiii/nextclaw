# Bibo Personal Agent 实现前对齐

> 2026-09-25。状态：**首批工作区已上线，真实 Agent 文件、网页 CRUD 与冷恢复已有成功证据；整体验收仍开放**。当前结果、失败记录与剩余项以[验收合同](../work/2026-09-25-bibo-personal-agent/acceptance-contract.md)为准。本文是正式产品实现的对齐入口；[界面概念设计](./2026-09-25-bibo-personal-agent-interface-concepts.design.md)及 [Studio 演示](../../concept-demos/bibo-personal-agent/public/studio.html)提供交互细节和视觉参照。概念中的本地示例数据不构成后端协议或完成证明。

## 目标与避免返工的方法

Bibo 是面向个人的长期搭档。用户可以在对话中思考和推进事情，也可以在独立的概览、收件箱、日程、任务、笔记、文件页面中连续工作。概览负责判断当下要看什么；真实操作在对应模块完成。AI 的建议、待确认动作和已执行结果必须可区分、有来源、可回到原对象。

实现前先冻结**产品语义、数据 owner 和关键交互**；具体组件、接口字段与持久化方式在这些决定后设计。每个模块以一个真实用户链路验收，不用“页面有入口”替代“能力可用”。不能在开发中由原型的 `localStorage` 或模拟数据悄悄替用户决定。

**阶段前提（用户 2026-09-25 明确确认）**：Bibo 目前从 0 到 1，没有需要保留的真实用户数据。只要用户未明确改变这一前提，Bibo 实现不做旧托管会话迁移、旧数据兼容、双写或为假设客户准备发布矩阵；新能力直接采用目标模型。这不意味着放弃新数据的保存正确性、权限隔离和失败恢复，也不授权破坏仓库中其他已有 NextClaw 应用的数据。该前提的自动开发入口同步写在 [Bibo 局部规则](../../apps/bibo-hosted/AGENTS.md)。

## 已对齐的产品与界面约束

以下来自用户连续纠偏及最新 Studio 选择；改动这些属于产品方案变更，不能作为普通实现微调：

### 内容工作区密度修订（用户 2026-09-25 再次纠偏）

对话旁的产物工作区遵循相同约束：文件切换合入顶部选择器并显示当前文件名，移除常驻底部“最近文件”按钮带；关闭按钮保留。编辑/预览和保存继续复用文件编辑器，正文吃满余下空间。

任务详情以名称、说明和步骤为内容主体，项目/状态/优先级/日期在其后。详情标题和关闭同一紧凑行；字段区域独立滚动，保存/取消始终可见，不让长任务或子任务列表把保存挤到屏幕外。关闭详情保留草稿，取消明确丢弃当前草稿。

- 原始输入：用户指出“标题部分……占很高的高度”“主要的内容……只占很小的一块区域”，先点名文件/笔记，随后明确所有类似页面一起处理。此修订对应 BIBO-01/04/05/06/09/12，并覆盖后续同类重内容模块。
- 根因不是字体单独过大：共用外壳标题、模块标题、搜索行、圆角内框、标签、文件类型/文件名/路径、模式栏和底部动作层层叠加。原有卡片页面骨架不适合编辑器、收件箱和任务工作台。
- **共用约束**：每个工作模块只有一处可见模块标题；全局栏承担身份与导航，模块工具栏承载实际操作。正文/列表直接填满余下区域，不再套居中的展示卡片。概览维持摘要布局。反馈不长期占一整行挤压内容；状态、错误及重试仍可见、可访问。
- **文件/笔记**：移除模块大标题及外围留白/边框；搜索和新建归左侧资源栏；编辑区只保留标签和一条紧凑工具栏，路径可省略显示完整提示，编辑/预览、保存及更多操作同一行。移除永久底部删除/移动栏，动作按需展开；移动端把返回资源列表合入标签行。正文独立滚动并撑满高度。
- **任务/收件箱**：移除重复标题和围栏；任务搜索、项目和列表/看板切换与新建同一工具区域；列表、看板和详情各自使用余下高度，手机不把列表锁进 290px 小窗。收件箱直接列表/详情两栏，详情标题仅表示消息内容。
- **日程**：模块只保留年月/视图/导航/新建的一条操作区；月历/时间网格为主区域，选中日期安排或编辑作为相邻辅助区，桌面避免先滚完整个月历才能编辑；手机保留完整主视图，并以显式进入/返回查看当天或编辑。
- 参考理由：[VS Code 布局](https://code.visualstudio.com/docs/editing/getting-started/userinterface)采用资源树与编辑区，标签和路径用于定位；[Obsidian 工作区](https://obsidian.md/help/workspace)让中央内容与可折叠侧栏分工。借鉴内容占比和层级，不复制品牌色、装饰或不适用的代码功能。
- 验收：在 1440×900、1280×720 和 390×844 检查实际内容边界。文件正文在无弹出操作时从屏幕顶部约 150px 内开始，编辑区主体占去除系统导航后的大多数高度；桌面任务/收件箱列表填满可用区；页面无横向溢出、重复模块大标题或嵌套滚动陷阱。检查长内容、空态和正在编辑三种状态，保留已有 CRUD、键盘、草稿和标签恢复证据。
- design-review: passed：该修订落实用户现有“简约、高效、完整工作面”约束，主要变动是布局 owner 和工具位置；内容、版本及写入主链路保持单一。主观风格仍交用户判断，内容可见面积及交互由浏览器实测。

### 原有产品约束

1. **产品入口**：默认进入概览；对话是最重要的独立模块。一级导航使用「概览、对话、收件箱、日程、任务、笔记、文件」。名称是**任务**，不是待办。
2. **概览职责**：显示待回应消息、近期时间、在推进的项目与任务、最近笔记，以及 Bibo 的简短关联提示。它是可读摘要和入口，不内嵌对话输入框，不在每张卡片下重复放“打开”，不承担完整编辑操作。没有数据时展示可信的起步状态，不造一张虚假简报。
3. **视觉方向**：以当前 Studio 的双列概览、横向 Bibo 简报和暖白／低饱和绿为基准。吸收旧工作桌的信息关联与卡片层次，但不搬用三列＋独立右侧搭档栏、倾斜便签、刺眼黄橙和重纹理。全局侧栏桌面可收起；手机另有清晰导航。
4. **完整工作面**：每个模块都要有适合该工作的列表、详情、主操作、空态和失败态；不以小弹窗承载主流程，不在顶部浪费一块仅含标题与“返回概览”的区域。桌面与手机分别验收。
5. **对话与产物**：对话可并排打开可收起的右侧工作区，查看文件、图表、草稿或来源。右侧内容按需要出现；它和文件模块应引用**同一对象**，不能复制一份正文。关闭工作区不丢会话与草稿。
6. **笔记与文件**：笔记是独立的快速记录入口；文件是基于真实目录的完整空间。笔记也出现在文件树中，移动后仍能从笔记入口找到。文件模块左侧可独立折叠目录树，右侧以标签打开多个文件；目录树与全局侧栏各自管理状态。AI 产物、用户文件和笔记共用文件对象与稳定引用。
7. **任务系统**：任务有自身状态、详情、项目／清单、子任务、列表／看板与来源关联。概览只是任务投影；截止时间不会自动变成日历事件。详细行为沿用概念设计中的 `T01–T10`；文件树／标签行为沿用 `F01–F13`，但其“正式实现事项”仍需按批次排期。
8. **多会话与可扩展性（用户已确认）**：Bibo 正式产品必须有真实多会话；前端可以简约呈现，但不得因为首屏简约而裁剪 NextClaw 底层已有的会话能力。新建、切换和恢复会话是基本路径，来源与产物按稳定会话 ID 关联。当前托管网页的单会话包装需要升级，不能误称底层只支持单会话。
9. **容量方向（用户已确认）**：当前 10 MiB 是托管首发代码的快照阈值，**不是产品目标或长期上限**。正式文件空间应适当扩大容量，并有可扩展的存储与恢复设计；具体额度、费用及物理存储方式由实现方案验证后确定，不承诺无限容量。
10. **注意力收件箱（用户已确认）**：它收纳需要用户注意、阅读或决定的内容，不是邮箱的同义词。可包括 Bibo 主动送达、待确认操作、提醒及将来接入的邮件；每种来源有明确身份和处理状态，不把建议伪装成已执行。
11. **首版数据来源（用户已确认）**：Bibo 自己实现任务、日程、笔记和收件箱；目前不连接外部邮箱或日历账号。页面不能出现暗示已连接的假邮件或外部事件。未来集成不要求首版预先实现适配器。
12. **内核边界（用户已确认）**：NextClaw 保持通用 agent／会话／工具运行能力，不内建任务、日历、笔记等 Bibo 领域模型；这些能力采用轻量、可拆卸的应用层模块，数据基于 AI 易读的 Markdown／JSON 等文件格式。首版结构保持简单，遇到真实规模或功能瓶颈再升级。
13. **AI 操作边界（用户补充）**：文件格式是持久化与可读性选择，不是让模型直接手改任务或日程 JSON 的操作协议。结构化对象必须通过带 Schema、校验和明确结果的标准动作读写。Mini App／Service App 是待权衡的实现选项，不是指定技术路线。
14. **第一方默认可用（用户补充）**：Bibo 自带的个人能力无需用户安装、授权或逐项批准，Bibo Agent 默认能调用。这个决定只约束 Bibo 第一方能力，不改变 NextClaw 对第三方 Mini App 的权限规则。
15. **Agent 入口渐进加载（用户纠偏）**：领域动作可以很多，但不能把 `task_create`、`event_update` 等每个动作都直接列成模型工具。默认工具表保持很小；已知操作可直接调用。需要帮助时可按关键词／领域批量取得相关操作及用法，也能列出完整紧凑目录；不要求先取全量目录，更不要求每做一个操作先查一次 Schema。可评估统一工具、命令行或脚本调用，不预设必须采用逐动作工具注册。

**冲突裁定**：旧概念设计中早期的「待办」名称、三列概览和右侧常驻搭档栏均已被后来决定覆盖。以本文和旧文 `Studio：笔记与文件的双入口` 段落的最新修订为准；截图中的旧工作桌只作为信息组织灵感。

## 托管底座重新评估

当前托管服务是为快速跑通对话而建，**不把它当正式产品的架构约束**。现有账号认证、每账号容器与 NextClaw Harness 可继续利用，但以下三处需要在完整模块实现前调整：

| 当前做法 | 正式产品需要的改变 |
| --- | --- |
| Durable Object 只记一个 `sessionId` 和展示消息数组 | 会话目录、消息与来源按多个稳定会话 ID 查询和恢复；会话标题及最近活动可供简约侧栏使用。底层 NextClaw 多会话能力保留。 |
| 容器内文件只在成功对话后整体打包到 R2 | 账号级提交协调必须覆盖网页 CRUD、Agent 动作和对话；向用户报告成功前远端持久化已完成。容器磁盘是易失工作区，[Cloudflare 容器生命周期文档](https://developers.cloudflare.com/containers/concepts/architecture/)明确休眠后会换新磁盘。 |
| 每次提交整份 `home` 快照且拒绝大于 10 MiB | 提高容量前测量 20／50／100 MiB 等代表性空间的冷启动恢复、单对象保存延迟和 R2 传输量。小型文本空间可以先沿用整份快照，但若保存一个小笔记也要反复传输大量文件，就在文件模块成型前改用按文件持久化；不能只把阈值调大却把操作拖慢。 |

首版仍只要**一个账号写入协调者**：当前每账号 Container Durable Object 可负责同账号串行提交、版本号及快照指针，Bibo 领域服务负责对象规则，NextClaw Harness 只执行 Agent 会话。这样不同模块不各自发明持久化机制。文件物理存储的最终粒度由上述真实数据测量决定；无论整份快照还是按文件写 R2，用户看到的目录、稳定文件 ID 和 Markdown／JSON 内容合同相同。这里不预建多套存储 adapter，也不为当前演示数据造迁移层。

Harness 生命周期也重新测量，而不是沿用 demo 或立即改成常驻：当前每轮启动可让账号容器在空闲时释放资源；常驻可能改善连续对话但需要处理模型令牌更新、进程故障及容器休眠。它与 Service App 的选择是两个决策；即便改为常驻 Harness，第一方领域服务进程内调用仍比增加独立应用进程、安装和授权接线更直接，而 Service App 的隔离和运行时安装能力在首版用不到。

## 轻量、可拆卸的应用层方案

**首版决策：借鉴 Service Action 的合同，暂不运行 Service App；Agent 只注册一个 Bibo 统一工具。** 在 Bibo 托管宿主内放独立的个人空间领域模块，定义一份带 Schema、风险属性和结构化结果的动作目录。网页 API 和统一工具都委托同一个领域服务执行，服务校验并写入每账号文件空间。统一工具通过现有 Harness Contribution 注册；它的固定模型工具描述只说明“查询 Bibo 能力／调用已知动作”，不内嵌全部动作 Schema。无用户授权页面、独立应用进程或新的内核领域模型。这里的可插拔是 Bibo 宿主可以注册／移除独立能力模块，不宣称首版支持用户动态安装第三方插件。

这与完整 Service App 的取舍不是纯性能猜测：**当前 Bibo 每轮重建 Harness**，完整 Service App 会增加独立运行时、应用启用与授权接线；选择 MCP 还要在每轮重新建连。进程内 Contribution 可沿用当前会话启动方式，避免这些新增环节。进程内执行仍有磁盘读写与快照成本，且缺少 Service App 的进程隔离、运行时安装和统一作业日志。若以后确实需要第三方安装或独立故障隔离，再依据实测把该模块包装为 Service App；动作语义和文件模型应尽量可迁移，但不承诺零成本切换。

| 候选 | 开发与运行代价 | 结论 |
| --- | --- | --- |
| 直接把任务、日程加进 NextClaw 内核 | 调用路径短，但每次业务改动都会侵入通用 Agent 代码。 | 不采用。 |
| 直接复用现有 `nextclaw.personal-organizer` | 省去建包，但它的待办只是完成布尔值，笔记与文件空间分离；扩写会影响另一产品。 | 不采用；只参考存储方法。 |
| Bibo 专属 Service-only Mini App | 有现成安装／动作／授权机制和进程隔离；托管宿主还需补安装、默认可用、网页调用，当前每轮重建应用运行时。 | 首版不采用；需要动态安装或隔离时重新评估。 |
| Bibo 领域模块＋逐动作 Agent 工具 | 调用直观，但工具和 Schema 随功能数线性增长，每轮上下文都要承载。 | 不采用；违反渐进加载。 |
| Bibo 领域模块＋一个统一工具 | 无新增进程通信、应用授权与安装接线；帮助按需返回，已知动作可直达；需维护动作目录及网页 API 绑定。 | **首版采用**，保持一份领域服务与文件真源。 |

首版数据建议如下；这是**可验证的实施提案**，不是声称现有 Bibo 已经具备：

- `workspace/` 是用户可见文件树的内容 owner；普通文档、AI 产物和笔记正文都是真实文件。笔记以 Markdown 保存，笔记身份使用与文件关联的轻量元数据，移动目录后身份不变；文件路径不是跨模块主键。
- 应用数据目录中用 UTF-8 JSON 保存任务、日程及注意力条目的结构化记录；有大段可读正文时用 Markdown 文件，并以稳定 ID 引用。任务模型包括项目、状态、子任务和来源，不直接复用旧 `todos.json` 的完成布尔值。
- 收件箱是**注意力视图**：AI 送达、需要确认的动作、提醒各保留来源 ID、阅读／处理状态。首版不接外部账号，因此不生成虚构邮件；以后真实邮件可作为另一种来源接入，无需现在开发邮箱同步层。已有 NextClaw AI 送达链路可以作为来源，但是否能在托管 Harness 中直接使用还需验证。
- 用户界面和 Agent 工具通过同一 Bibo 领域动作读写；保存采用临时文件＋原子替换、版本检查和失败保留草稿。共享 JSON 文件的并发更新要序列化提交或锁定后检查版本，避免两个写入各自成功却覆盖对方。索引可以从文件重建，不另存第二份正文；当前 10 MiB 快照阈值需提高或调整存储方式，实施前核算实际文件规模和恢复成本。
- “可插拔”指 **Bibo 第一方领域模块可独立注册或移除，NextClaw 内核仍只提供通用工具接口**；首版不设计动态插件市场、数据库或多套 adapter。

### 第一方默认可用与开发效率

一个 Bibo 领域服务是唯一动作执行 owner。HTTP 路由只负责账号校验、请求／响应映射和调用服务；Harness Contribution 只注册**一个**统一 Agent 工具，按需查询动作目录或执行具体动作。状态、引用、版本和输入校验都在服务内，避免网页与 AI 各写一套 CRUD。首版不做 Mini App 包、授权流程、MCP 服务、插件注册表和新内核公共接口。模块可以随着 Bibo 发布，用户无需配置。

动作合同至少定义名称、输入 Schema、输出对象／错误码、读写属性。统一工具的帮助接受可选的关键词、领域或动作过滤，返回**匹配操作的批量用法**，包含调用名、用途、关键参数和示例；按领域可取完整字段与结果说明，不设过滤条件时可列出全部操作的紧凑目录。复杂细节允许继续查询某个动作，但正常使用不依赖逐动作查询。已知动作直接执行，未知动作或参数错误返回可恢复的提示。帮助内容按请求才进入模型上下文，不在每轮预先注入。写动作携带预期版本和幂等键，防止网页冲突覆盖或 Agent 重试时重复建任务。对话内工具可返回“本轮已应用、等待账号提交”；只有账号远端提交成功后网页才呈现已保存的最终结果。网页直接编辑也须等提交成功再回应。这样的合同以后可以映射到 Service App 或 CLI，但当前只维护这一份服务实现。

当前 Harness 每轮重建是既有成本；先在每次运行前注册 Contribution，不为 Service App 专门改成常驻 Harness。若正式产品的响应时间显示这段既有启动成本明显，再单独评估复用 Harness，并处理模型令牌配置与容器休眠。动手前测量至少冷启动对话、单次任务读取／写入和连续两轮对话的端到端耗时；以数据决定是否进一步优化，不以“进程内一定足够快”作保证。

### AI 如何感知和操作

1. **发现**：Bibo 动作目录内部声明任务、日程、笔记、注意力和文件操作，每项有用途、JSON Schema 输入和 `read`／`write` 等风险属性。Harness Contribution 只向 Bibo Agent 注册一个 `bibo` 工具。`bibo({operation:"help", query:"安排日程"})` 只取相关操作，`bibo({operation:"help", domain:"tasks"})` 批量取得任务操作及用法，`bibo({operation:"help"})` 才列出全部操作的紧凑目录。模型初始工具描述不列出所有 `task_create`、`event_update` 等动作。
2. **感知**：对话开始可从同一领域服务取得有大小上限的当下摘要，例如近期日程、进行中的任务数和待关注条目；需要细节再调用 `list`／`get`。不把完整个人文件和全部任务塞进每轮提示词。具体摘要是否自动注入，应以真实对话效果与成本验证；不能只靠模型“知道文件存在”假设它会主动发现。
3. **操作**：Agent 对已知操作可直接调用 `bibo({operation:"call", action:"task.create", input:{title:"…"}})`，无需每次先走帮助；领域服务校验状态、引用、时间和版本后原子写文件，返回稳定 ID、最新对象或可解释错误。网页创建同一任务也调用这个服务动作。禁止另设“AI 直接编辑 JSON、网页通过 API 编辑”的双写链路。
4. **反馈**：没有应用授权弹窗或逐项授权流程。领域服务仍要校验输入、账号边界和写入结果；Agent 只能根据动作返回结果声称成功。失败时保留输入，不把拟议动作显示为已执行。对象删除可在界面提供撤销，属于产品操作反馈，不是安装权限流程。

## 实现合同

以下是实现必须满足的关系；具体文件 schema 与 HTTP 路径在托管应用的小规模可行性验证后确定，不得通过新增第二个内容 owner 绕开：

- **身份与隔离**：正式模块使用服务端验证的同一账号；每项读取和写入都由服务端校验归属。浏览器本地仅可保存导航偏好与未提交草稿，不把 `localStorage` 当用户数据真源。
- **统一对象引用**：会话、文件、任务、日程、注意力条目各有稳定 ID；显示路径／标题可变，不做跨模块主键。概览、笔记入口、文件标签、对话工作区读取同一对象版本。对象被删除或无权访问时展示失效来源，不跳到相似对象。
- 收件箱的来源跳转先按稳定 ID 读取目标，确认存在后再切到对应模块；404 时留在当前消息详情并提示来源已删除或不可访问，其它读取失败保留当前位置和重试入口。等待期间禁用重复点击；若用户切走模块、换账号或选择了另一条消息，晚到的读取不能抢走当前页面。会话来源沿用已验证的独立会话 404 路径。
- **写入状态**：AI 提议、用户确认、执行中、已保存／已发送、失败分别可见。只有服务端提交成功才改变正式列表；失败保留输入和明确重试。文件编辑需冲突检测及恢复路径；跨端刷新不能以旧缓存覆盖新版本。
- **持久化提交**：当前 R2 快照只在对话结束后创建；新增 HTTP 编辑和 Agent 动作也需由账号容器统一串行协调写入及快照提交。容器文件写入成功但远端快照失败时不可向用户或 Agent 报告“已保存”，须保留可重试输入和明确失败状态；休眠恢复后核对相同数据版本。实际提交粒度和存储方式在容量验证时确定。
- **概览投影**：首屏只取有真实来源的摘要；卡片与来源模块状态一致。无数据、未连接、加载失败和权限受限分别呈现。点击卡片进入完整模块的相应对象，返回保持上下文。
- **独立导航状态**：全局侧栏、文件树、文件标签、对话右侧工作区各自收放；切模块和刷新时的保留策略明示。桌面、手机都能完成主任务，键盘焦点与触控操作可达。
- **清空与恢复**：沿用“个人空间”含义时明确删除范围并二次确认；新写入的文件、任务、日程和收件箱数据必须能正常恢复。无需为当前托管演示数据建兼容迁移。

## 最小真实链路与实施前验证

实现不围绕发布批次或旧数据兼容设计，但每条能力要能真实跑通；不把占位页报告成已完成：

1. **对话 → 产物 → 文件**：在独立会话中得到一份可识别的产物，右侧工作区打开并修改；文件树出现同一文件，刷新、切标签、重命名／移动后原会话引用仍有效。失败保存不会显示成功。
2. **笔记 ↔ 文件**：快速新建笔记、编辑保存，在文件树定位；从文件标签修改，再回笔记看到同一版本。目录树与全局侧栏分别收起，桌面与手机都不丢正文。
3. **概览 → 注意力 → 任务／日程**：首页摘要仅来自真实对象；Bibo 送达一项需要关注的内容，用户在收件箱查看来源、确认或延后，相关任务／日程显示同一状态。空账号、加载失败、刷新以及窄屏均能正常进入独立多会话对话。

任务还要验证「建任务 → 改状态／子任务 → 列表与看板一致 → 概览同源」；日程验证创建、修改、时间冲突提示和来源跳转。没有外部账号接入验收。每条链路核对用户文档、容量成本、账号隔离和对话回归。

**实施前只需验证三个技术事实**：① Bibo Contribution 只注册一个工具，已知动作可直达，相关操作、领域用法和完整目录都可按请求批量取回，HTTP 路由调用同一领域服务；检查模型初始工具清单、帮助输出体积及实际完成任务所需调用次数；② 每账号文件数据怎样与会话一起保存、扩容和恢复，避免 10 MiB 阈值；③ 已有 NextClaw AI 送达能否在托管环境作为 Bibo 注意力来源。若 ③ 不成立，Bibo 收件箱按同一文件合同自行送达。测量冷／热路径后再定性能优化；随后补可执行方案，写清 owner、文件 schema、API、页面状态和验收。当前文档仍是方案，不表示正式功能已经实现。

## 正式应用可执行设计（2026-09-25 补充）

本节落实[大型交付合同](../work/2026-09-25-bibo-personal-agent/acceptance-contract.md)；此前的选型论证仍有效。设计状态：待方案 Review，不把下述拟议路径写成已实现事实。

### 黄金验收使用链路

1. **每天开始与继续对话**：已登录用户进 `app.bibo.bot` 看真实概览；可点一个待关注对象进入收件箱详情，也可切换「对话」新建会话。输入后看到流式回答与保存阶段；服务端快照提交后成为正式消息。另建会话、切回上一会话、刷新和容器休眠恢复，历史仍在。对话引用一份文件时右侧工作区打开该文件，编辑后文件模块看到同一版本。若保存失败，原输入或草稿保留并显示失败，不出现已保存的假成功。
2. **整理一个项目**：从「任务」创建项目和任务、拆子任务，更新状态并在列表／看板切换；概览显示同一任务。打开「日程」安排时间，系统检查时间重叠并提示，创建后回概览可见。让 Bibo 通过统一工具查看相关任务并修改一个状态，刷新后网页仍一致。不存在外部账号时页面只显示自建事件，不填充演示邮件。
3. **记录与交付产物**：在「笔记」快速记录一篇 Markdown；「文件」左树定位目录和该笔记，右侧标签编辑。移动和重命名后切回笔记及原对话来源仍指向同一对象。桌面收起全局侧栏与文件树、手机用导航切换，均能继续编辑和保存。版本冲突时保留草稿并让用户决定重新载入或覆盖最新版本。

AI 自验包括账号隔离、请求失败、保存失败、刷新恢复、窄屏、键盘焦点及浏览器实际交互；用户只需判断布局、信息取舍和整体体验是否符合预期。用户已明确授权本任务合入主干、推送并部署上线；本地可运行产物不能冒称已上线，最终按远程黄金链路关闭验收。

### 状态与存储 owner

- Worker 验证平台账号，只按服务端身份命名账号 Container DO；不接受浏览器传来的 user ID。DO 是**唯一账号写入协调者**。运行中的 chat 和网页 mutation 串行；GET 可读提交后的对象。写请求进入容器领域模块，成功后 DO 取快照上传 R2，再回成功。失败时停止容器，使下次从最后提交快照恢复；客户端保留草稿。同步写入未确认前不能展示为最终状态。
- DO 存每个网页会话的稳定 `id`、标题、更新时间及消息记录；同一个 `id` 直接作为 Harness `sessionId`，避免额外映射。创建空会话不需要容器。Harness journal 仍随快照保存。会话元数据和快照指针由同一次 DO storage 更新提交。没有老 Bibo 会话迁移。
- 容器领域模块是结构化对象唯一 owner。`/data/bibo/state.json` 保存项目、任务、日程、注意力条目、文件元数据与版本；`/data/workspace/` 保存用户可见正文。`fileId` 是跨入口引用，`path` 可变。笔记是一种文件类型，不另存一份正文。元数据写入临时文件并原子改名；DO 串行写避免同账号竞争，版本字段防跨端过时覆盖。
- 快照继续覆盖 Harness journal、领域状态和 workspace，初始压缩阈值从 10 MiB 提高至 **32 MiB**。当前 Worker 以 `arrayBuffer()` 上传快照，直接提高到 100 MiB 可能逼近 Worker 内存预算，因此不能只凭磁盘压缩速度设上限。此值是首版受控容量而非永久产品上限。2026-09-25 本机 20/50/100 MiB 随机数据的 tar 压缩分别约 0.34/0.85/1.54 秒，解压约 0.02/0.05/0.07 秒；这**只**证明本机 CPU/磁盘，未测 Cloudflare R2 上传、冷启动和计费。正式验证必须以真实环境数据确认，若单次小编辑被全量上传拖慢，改按文件持久化；更换物理粒度不改变领域 API 或文件 ID。
- Agent 运行前注册 Bibo Contribution，只加 `bibo` 一个工具。它的 `help` 可返回紧凑目录或按关键词／领域批量用法，`call` 可直达动作。工具与 HTTP 路由调用同一个领域模块；面向模型返回结构化成功或错误，不由模型直接改领域 JSON。Agent 在本轮的写入最终随 run 快照提交；若提交失败，网页只见失败，后续从最后快照重建。
- 注意力条目第一方创建与处理使用 Bibo 领域模块。现有 NextClaw AI delivery 的托管可用性尚待独立核对；若其文件目录可在同一 home 中稳定读取，则桥接为来源；否则直接由 Bibo 统一工具的 `inbox.create` 送达。两种方式都不能变成平行写入真源。

| 注意力 | `id,kind,title,body,source,readAt,resolvedAt,createdAt,version`；空来源仍要明确 `bibo`，不能冒充邮件。 | 列表／详情／概览；`inbox.list/get/create/read/resolve`。 |

HTTP 采用同源 `/api/sessions`、`/api/space/*`，所有 mutation 返回最新对象及版本；条件版本不匹配返回 409，校验失败 400，找不到 404，忙碌 429，快照失败 503，容量超限 507。客户端只对成功响应更新正式对象；导航偏好和未提交草稿可放浏览器。列表在本阶段按有界页读，不能把全账号文件或消息无界加载到首页。账号删除操作明确包含所有对象和会话，强确认；普通对象删除可在界面撤销或二次确认。

前端业务状态归应用 store：一级页面保留 URL，概览只请求摘要；对话 session ID 入 URL；文件选中 ID 与标签入状态，左树折叠独立于全局侧栏；右侧工作区仅在需要时打开。页面按空／载入／失败／正常分别渲染。文件编辑时有未保存状态和离开提示；导航不把小弹窗当主要工作面。响应式布局桌面给双栏或三栏工作区，手机以单主面 + 显式切换，不缩成无法操作的窄三栏。

### 模型额度耗尽时的对话反馈（BIBO-07 / BIBO-09）

来源：用户要求前后端真实链路可用、失败状态明确；线上真实 Agent 验收中，模型代理连续返回 429，而聊天等待约一分钟后只显示通用 503。模型额度事实仍由现有全局 Budget Durable Object 持有，不在容器或前端复制计数。新对话首次发送前，客户端先通过鉴权后的只读可用性入口检查，避免额度已满时先创建空会话；已有会话无此额外往返。聊天入口收到非空消息后也向同一个 Budget 对象做只读检查，已耗尽直接返回明确的 429，不启动账号容器、不占用每小时对话次数。真正的模型请求仍在原代理里原子预留额度，避免预检查与预留间的竞争绕过上限。检查服务故障继续明确失败，不能假装额度可用。

黄金验收：额度已满的账号在桌面或手机首次发送新对话 → 立即看见“今日试用额度已用完”的可读反馈，输入保留 → 会话列表没有因此产生空白新会话；同账号文件等非模型操作保持可用。可用额度下，正常对话仍按原链路运行；并发接近上限时最终以代理预留结果为准。AI 验证使用 Budget 边界测试和线上已耗尽账号请求，不人为提高生产额度。不在本修订中重写模型客户端的通用重试策略。

design-review: passed（本局部修订）：只有 Budget 对象拥有额度状态，检查不预留、不新增第二计数 owner；最终预留仍是唯一写入口。已耗尽、正常、并发竞争及检查失败路径均有明确结果，旧存储结构不变。计划为单批现有文件修改。

### 右侧产物工作区恢复与失败状态（BIBO-02 / BIBO-10）

来源链接补充（L2 bugfix）：显式指定的会话不存在时，history 返回 404；未指定会话仍可返回默认会话或空历史。网页保留失效 URL、清空错误目标的展示并明确提示，不静默回退到最近会话。会话列表继续可用，选择有效会话或新建对话可恢复。复用现有 chat store、文案配置与历史路由，不新增来源路由或第二份会话状态。验收覆盖失效链接刷新、有效链接、空白新会话和删除后历史请求。design-review: passed（此失效引用修订）；原始依据为用户要求的稳定来源及本方案“删除或改名来源”合同，现有后端 200 空历史已由真实 Worker 类边界复现，网页 fallback 由 bootstrap 分支直接定位。

来源为用户要求的独立、灵活 artifact 区及本合同代表场景 1。保留 Studio 的并排编辑与手机单面板，不新增工作区 owner。选择文件、关闭面板是即时用户意图，归现有 space store；异步文件读取只填充同一份文件缓存，不在完成后重新打开面板或覆盖最新选择。失败在当前工作区显示，可重试，不能永久显示“正在打开”。

复用现有账号隔离的布局偏好保存工作区开关与所选稳定文件 ID；正文仍向正式服务读取，未保存内容不写入偏好。刷新打开的工作区恢复所选文件，关闭后刷新保持关闭，再打开恢复选择。文件不存在时明确报错并允许另选，不以同名文件代替。退出/换账号清空内存状态并读取对应账号的偏好。

黄金验收：选择产物 A→编辑→关闭再打开，草稿保留→保存→刷新，选择与正式正文恢复→切换两个会话，产物仍是同一对象；另以延迟 A/快速 B 和读取期间关闭验证用户意图不被晚响应覆盖，以 503/404 验证可见失败和重试。桌面及手机覆盖。复用文件 owner、布局工具及 Notice，无新协议、适配层或本地内容真源。

design-review: passed（仅上述恢复修订）。反例检查包括异步重开、账号切换、文件删除和未保存内容；正文必须真实读取，偏好不能证明保存成功。现有文件读取/错误状态可承载此范围，不增加并行文件存储。

### Markdown 阅读与产物预览专项（BIBO-02 / BIBO-10）

现状：聊天回复、文件预览和收件箱已经调用同一个 `Markdown` 组件，但完整排版样式只作用于聊天；代码块没有语言标记、高亮和局部复制，图片退化为替代文字，数学公式与图表未渲染。用户要求参考 NextClaw 与成熟产品，尤其保证产物可读、可取用。ChatGPT 把代码块作为独立的阅读和复制单元；NextClaw 的现有渲染器提供选定语言高亮、复制、公式和 Mermaid。这些是交互依据，不直接接入其依赖聊天业务上下文的私有组件。

比较三条路径：直接复用 NextClaw 整个 ChatMessageMarkdown 会带入聊天文案、文件资源和主题上下文；只补几个 CSS 会继续让文件/收件箱与聊天表现分叉；选择扩充当前品牌无关的 `personal-agent-ui` Markdown owner。保留 GFM 和默认跳过原始 HTML；同一内容在聊天、文件预览、收件箱得到一致排版与代码交互。文件正文仍是原 Markdown，预览不成为第二份真源。

- 标题、段落、列表、任务清单、引用、表格、行内代码在三处共用样式；表格/长代码横向滚动，不撑宽手机主布局。长正文由宿主容器滚动。
- 代码围栏显示可识别语言与复制按钮，复制原始代码而非高亮 HTML；复制成功/失败有可读反馈。已知语言用选定语言语法高亮，未知语言保留纯文本；没有代码围栏时不增加工具栏。
- `$…$`/`$$…$$` 公式采用项目已有的 KaTeX 路径；`mermaid` 围栏按需加载引擎，以 strict 安全级别绘制。解析失败显示源代码和错误提示，绝不吞掉原文；流式未完整图表期间避免反复高成本绘制。
- 外部图片仅加载安全的 HTTPS 地址，加载失败仍展示替代文字；链接只允许明确安全协议，外部链接新窗口带 `noopener noreferrer`。原始 HTML 不执行；相对文件链接在没有真实文件资源映射前只显示文字，不制造失效跳转。
- 文案通过公共组件可配置的标签参数提供默认值，宿主按产品语言注入；品牌名不进入组件/API。代码复制、图表预览和文件预览均需键盘可达、可见焦点及触控反馈。

验收：真实浏览器在桌面和 390/320 手机分别检查聊天、Markdown 文件、收件箱中的 GFM 表格与长代码；代码复制含行尾内容、重复点击反馈；公式和有效/无效 Mermaid；安全/不安全链接及图片回退；手机不横向撑破页面。公共包与宿主 tsc、客户端 smoke、人工截图复核。不同正文的业务持久化仍由原文件/消息服务验证，渲染专项不另加数据 owner。

design-review: passed（此 Markdown 修订）。反例检查包括流式不完整图表、错误图表丢失原文、长代码高亮阻塞、外链协议及图片失败；图表引擎按需加载，超过长度预算的代码保持纯文本和可复制，不改变文件或对话的写入合同。

保留：现有账号认证、每用户 Container DO、Harness 多会话、单个 Bibo 领域模块与统一工具、现有 Bibo UI 包。删除：DO 单 `sessionId`、单条消息全局状态、前端仅一页的状态假设。延后且不写空接口：动态第三方安装、多存储 adapter、外部账号集成、为 Bibo 旧用户造兼容。欠设计会造成 Agent/网页双写和丢数据；过度设计会在首版引入 Service App 进程、授权和同步层。当前单协调者＋单领域 owner 是平衡点。
