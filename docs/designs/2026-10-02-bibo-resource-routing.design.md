用户要求“现在这个笔记界面的加载速度非常之慢，需要优化优化”。contract-id: bibo-note-performance；parent-goal: 用户从现有笔记入口更快打开并编辑、保存同一正文；scope-revision: 1；授权沿用 Bibo 完整交付。风险 L3（共享 UI 公共入口与 R2 流读取边界）。

真实线上基线使用专用账号的两份约百字节短笔记、单用户、1440/390 宽度、全新 Chromium context、同一网络代理。首次导航到 contenteditable 可见：4247/4289 ms；热切换另一笔记：1304/800 ms。HTML TTFB 约 1 秒；file.get 871/895 ms；编辑器资源等正文返回后才开始，约再等 600 ms。增加同条件基线样本，交付后同样重复测量，报告全部样本的中位数与区间，不用最佳值。性能目标：两种设备合计冷打开中位数降低至少 15%，热切换降低至少 25%；目标依据是可移除的一段约 600 ms 编辑器下载与文件元数据往返，不承诺所有用户网络达到固定秒数。

采用已有 resource manager 发起限定详情的 preload，共享 UI 只公开现有 rich 模块加载函数；React.lazy 消费同一导入函数，浏览器拥有模块缓存，不建第二套加载状态。文件详情 owner 直接读取 R2 的 body+metadata 快照，复用该快照的版本；读取失败才查询是否为文件夹/缺失。普通小文件读完整，超过 1 MiB 只消费 64 KiB 并取消剩余流；保存写入仍走现有版本检查。创建/修改/移动详情继续复用同一解码 owner，下载保持完整流。拒绝全站 eager 编辑器和正文缓存：它们会增加其它入口负担或引入内容一致性 owner。此次没有必要改动代码高亮与聊天恢复：已测得的主要额外串行等待可在现有主链路内消除。

## 用户验收返工：笔记目录中的普通文档

2026-10-03 用户截图显示“Mermaid 图表示例”标题与“此文件不是笔记”空白页。代码链路确认目录菜单不限制 kind，`openFile` 却沿用当前 notes 路由，Workbench 再拒绝非 note；用户文件的实际服务端分类未读取，不能声称其元数据异常。

修复采用资源类型导航，不更改文件分类或内容。用户在笔记中展开目录并选择普通 Markdown，直接进入 files 编辑同一文件；从已有 `/notes/<普通文件>` 地址进入时，读取成功后由文件打开 owner 将 URL replace 为 files 地址，复用已读详情，刷新与返回仍指向正确对象。正常笔记保持 notes，files 中的笔记保持 files；聊天右侧工作区保持原位。读取失败保持原目标与重试，不根据扩展名推断领域 kind，迟到响应不得导航或夺取当前对象。

对比：过滤目录中的普通文件会让用户无法打开已经看到的文档；把 Markdown 全部转换为 note 会改变领域分类；只移除拒绝提示会留下错误模块/URL。采用已有 store 文件打开链路与 Router 的 replace，不新增状态 owner、分类迁移或导航层。

验收：桌面真实目录选择、手机错误文档直链（手机笔记当前隐藏面包屑）、已缓存 Tab、错误 notes 直链（新读/缓存）、刷新、历史回退、自动保存、缺失文件重试，以及晚到文档响应返回集合后不导航。交付沿用 Bibo 已授权的 Worker/UI 发布和真实账号复验。design-document: required（更新原 owner）；plan: not-required（单批闭环）。

修前真实浏览器已从笔记目录选择普通 Markdown，复现相同标题与“此文件不是笔记”的空白页。修后 1440/390 路由回归覆盖同一入口及错误直链、缓存零重复正文请求、replace 后回退、实际自动保存响应、刷新、迟到响应；完整交互冒烟与 170 项单测、三项 tsc、Vite 构建、定向 lint 和目录治理通过。资源请求 fixture 移至 `scripts/workspace/bibo-resource-routing.fixture.ts`，保留唯一响应 owner，回归入口继续承载用户操作断言；不为文件体积预算改动产品 owner。

## 目标与证据

用户反馈进入笔记模块先看到列表，随后自动显示某条笔记，要求统一排查文件等页面。此修复尊重用户的当前位置与选择，减少搭档工作空间的意外切换。

源码已接入 React Router；`load(notes/files)` 在读取列表后调用 `restoredFileTargets`，恢复 localStorage 的 activeFileId 并通过 `openFile/revealFile` 隐藏列表。`SpacePage` 还在列表 ready 后才打开详情引用。任务、日程、收件箱的点击与关闭没有一致维护资源 URL，资源 manager 会把详情直链改回模块根路径。

风险 L2；flow=bugfix。直接源码锁定违约边界，skip-reproduction：没有修前浏览器失败基线；修后用真实 Router、延迟 API、持久化布局与浏览器历史验证同一违约点。

## 用户链路与选择

1. 登录后点击笔记或文件模块，稳定停留在集合/目录。已有 Tab 与未保存草稿保留，但不自动读取或选择旧正文。点击目标后 URL 变成详情地址，立即显示目标加载态，随后正文；返回、前进与刷新指向同一对象。
2. 直接打开笔记/文件详情地址，只请求目标正文；侧栏所需列表可并行加载，列表慢或失败不能阻塞正文。加载中不能显示旧详情或闪现笔记集合。路径引用通过同一 resource owner 解析。
3. 任务、日程、收件箱点击、关闭、模块切换和历史回退均由 URL 决定选中对象。快速切换及账号更换后旧响应不得夺取选择。对话中的文件引用继续打开右侧工作区，工作区恢复只在对话中按需发生。

采用已有 Router + Zustand + WorkspaceResourceManager；修正路由到领域 owner 的同步边界，不引入第二个路由框架或把草稿搬进 Router loader。相比只禁止恢复旧笔记，此方案也关闭直链串行依赖与历史失配；相比全面重写数据层，保留现有写入、草稿与权限 owner。

## 唯一主链路与生命周期

- React Router 拥有 view/resourceId/filePath。增加 `/notes/:resourceId?`，复用已有动态参数与 Link，模块根路径表示集合。
- WorkspaceResourceManager 同步 location/account 到领域 store：清除无 URL 的选中状态，立即启动目标读取，列表读取独立。组件只连接路由变化，不等待 readStatus 后再次打开资源。
- 文件关闭、移动和删除后的 URL/工作区同步由同一 resource manager 编排；store 只执行文件数据与草稿变更。展开目录树只改变目录显隐，不返回集合或清除当前正文。
- 领域点击导航到资源 URL；路由同步使用显式标志调用已有读取方法，避免递归导航。无 Router 的 owner 单测保留直接动作入口。
- `load` 只更新列表，不恢复主页面旧正文。旧 Tab 和草稿仍保留；主页面 URL 优先于持久化 activeFileId。
- 开始详情读取就投影目标 ID/加载态；完成时校验当前 route/request/account。失败展示可重试反馈，保持目标 URL；关闭或删除当前文件将 URL 更新到明确邻居或集合。
- 从集合删除文件保持集合和空选中状态，不从旧 Tab 推导新的正文；嵌套正文先显示，再由既有目录 owner 独立补齐祖先导航。创建响应已携带正文时复用该快照，不再次读取同一新建对象。
- 笔记只读取笔记列表；各空间页面通过 lazy/Suspense 按需加载模块。编辑器现有按需依赖继续复用，组件类型和实体 key 保持模块级稳定。

## 用户验收返工：多级路径与编辑器加载

用户反馈 `/notes/笔记/功能演示 - 起步.md` 刷新进入“页面不存在”，编辑器有持续加载现象。线上已复现：请求把整个文件 ID 编成单段后，Cloudflare 返回 307，将 `%2F` 规范化为 `/`；重定向后的多级路径不匹配 `notes/:resourceId?`。线上文件 owner 的 ID 本身是完整路径，上一轮浏览器 fixtures 使用不含目录的伪 ID、真实线上验收使用根目录笔记，未覆盖这条合同。

修正方案：笔记、文件身份使用 splat；URL 生成按路径段编码，集中到现有 router owner。按路径查找使用 `/files?path=...`，保留客户端 `{path}` 输入合同，同时消除真实 `path/` 文件夹与原 `/files/path/` 路由的命名冲突。按真实原始 pathname 解码路径一次，防止 `%2F` 字面文件名被框架的参数还原规则误作目录。任务、日程、收件箱和会话的单段对象 ID 合同保持原样。

编辑器加载持续等待目前没有取得用户浏览器的网络证据，不能归因于解析或某一分块。已确认共享编辑器的 Suspense 只有等待文案，没有模块加载错误边界或过慢时的恢复入口。补充模块级稳定错误边界、12 秒后的慢加载提示及宿主重新加载回调；慢加载不丢弃仍在进行的请求，成功后自然进入编辑器，失败不会退到路由全局错误页。重新加载页面使用既有草稿持久化合同，不自动刷新、不覆盖正文。

验收必须覆盖：中文多级路径、空格和保留字符、字面 `%2F`，规范化与原编码地址的直达/刷新/返回；延迟与失败的 rich/source 分块、重新加载后的恢复和未保存草稿。复用原路由浏览器回归，新增专门的编辑器加载故障注入入口，并在线上创建专用多级笔记复验，清理仅限本次测试数据。方案自审确认没有第二套路由 matcher 或文档状态 owner；新增状态只属于加载反馈，数据继续归现有 store。

返工后的本地证据：162 项 Bibo 测试、Worker/网页/scripts 与共享 UI 的 tsc、Vite 构建通过；1440/390 路由回归和完整交互冒烟通过。正文与源码分别注入模块延迟/失败，八组桌面/触屏恢复检查通过，慢请求自然完成、重新加载恢复草稿且没有 `file.update`。真实线上编辑器验收也改用专用中文多级笔记和服务端返回的资源 URI；父目录、笔记和会话都只清理本次创建对象。
