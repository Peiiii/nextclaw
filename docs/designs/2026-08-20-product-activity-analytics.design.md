# NextClaw 产品活跃统计与隐私分流设计

## 问题定义

NextClaw 需要回答“有多少人在真正使用产品、使用是否持续、核心任务是否成功”，但当前没有远端产品活跃事实。现有 `DiagnosticRuntime` 只服务本地故障诊断，并明确禁止远端上传、用户身份和业务内容，因此不能把诊断日志改造成埋点平台。

活跃统计还存在三个容易混淆的问题：未登录用户没有账号身份；同一个人可能使用多个安装；开发者、测试人员、自动化和子 Agent 会污染真实用户指标。本设计建立一条独立、最小、默认关闭的产品活跃链路，在不采集会话内容和设备指纹的前提下统计匿名安装与已登录用户，并将外部用户、内部人员、QA、开发测试环境和发布通道分开。

## 成功标准

1. 管理端能查看外部生产稳定版的核心 DAU、WAU、MAU、成功活跃和 30 日趋势；
2. 未登录用户以随机匿名安装标识参与统计，登录后能与账号归并，且不承诺跨设备精确去重；
3. 人类直接或渠道发起的 Agent 请求计为核心意图，定时任务、子 Agent、系统续跑不计入核心活跃；
4. 内部、QA、开发、测试、非稳定发布通道保留独立维度，默认不进入外部用户指标；
5. 客户端不上传消息、提示词、回复、工具参数、会话/项目/文件路径、URL、IP、User-Agent、硬件指纹或诊断日志；
6. 采集失败不影响 Agent 主链路，禁用采集后不生成匿名标识、不发网络请求；
7. D1 迁移、Worker API、管理端页面和生产部署完成，并通过本地测试和部署后真实链路验证。

## 指标口径

“活跃”不是应用启动或页面打开，而是用户向 NextClaw 提交了一个可执行意图。

| 指标 | 口径 | 用途 |
| --- | --- | --- |
| 核心 DAU | 当日至少一次 `intent_accepted` 的去重主体 | 日常真实使用 |
| 核心 WAU | 最近 7 个自然日至少一次 `intent_accepted` 的去重主体 | 周留存与使用广度 |
| 核心 MAU | 最近 30 个自然日至少一次 `intent_accepted` 的去重主体 | 月度用户规模 |
| 成功活跃 | 周期内至少一次 `run_succeeded` 的去重主体 | 活跃是否产生结果 |
| 匿名安装 | 周期内活跃且尚未关联账号的安装数 | 未登录覆盖面 |
| 已识别用户 | 周期内活跃且已关联账号的账号数 | 登录用户覆盖面 |
| 识别率 | 已识别主体 / 全部去重主体 | 身份归并质量，不作为增长目标 |

自然日统一按 `Asia/Shanghai` 计算；WAU/MAU 使用包含当天在内的滚动 7/30 日，不使用自然周或自然月。默认管理视图固定为 `audience=external`、`environment=production`、`releaseChannel=stable`，内部与 QA 必须显式切换。

## 统一身份模型

### 匿名安装

Service 在用户明确启用产品活跃统计后生成随机 UUID，保存在 NextClaw 数据目录的产品分析状态文件中。它不来自 MAC、磁盘序列号、机器名或任何硬件特征，因此卸载清理数据、复制配置或多设备使用都会形成新的匿名安装；指标名称必须使用“匿名安装”，不得把它表述为精确“匿名用户”。

客户端只把原始随机 UUID 发送给 NextClaw 平台。Worker 使用服务端密钥和独立域前缀执行 HMAC，D1 只保存不可逆安装摘要，不保存原始 UUID。平台不以 IP 或 User-Agent 补充指纹。

### 登录归并

客户端只有在当前 `apiKey` 是有效平台会话令牌时才附加 `Authorization`。Worker 验证令牌后以账号 `user_id` 关联安装；查询时用 `user:<id>` 作为已登录主体，用 `install:<hash>` 作为未登录主体。同一账号的多个安装被归并为一个主体；安装后来登录后，历史活动通过当前关联关系一并归入账号。

这是一种“安装到账号”的单向归并，不做账号退出后的拆分，也不推断多账号属于同一个人。

## 人类活动判定

活动语义归 Kernel，因为只有 Kernel 能稳定区分用户意图、自动化与内部编排。Kernel 只向可选 `ProductActivitySink` 发送两个低基数信号：

- `intent_accepted`：人类请求进入真实 Agent run；
- `run_succeeded`：对应 run 正常结束。

以下请求进入核心统计：

- Chat/UI/CLI 的直接用户请求；
- QQ 等外部渠道转交的人类消息；
- 用户明确触发的继续或编辑后重跑。

以下请求排除：

- `metadata.session_origin === "cron"` 的定时任务；
- `metadata.session_materialization.kind === "child"` 的子 Agent 会话；
- 没有形成 Agent run 的启动、页面浏览、配置读取和后台心跳；
- 测试脚本直接构造的合成请求，除非部署验证显式标记为内部环境。

Kernel 不知道安装标识、账号、网络端点或分析开关。Service 拥有匿名安装状态、环境和传输；Worker 拥有 HMAC、身份归并、受众纠正和聚合；Admin 只读取聚合结果，不接触原始安装标识。

## 隐私、同意与测试分流

### 默认关闭与最小化

配置新增 `productAnalytics.enabled`，默认 `false`。关闭时不生成安装 UUID、不落分析状态、不发送请求。`productAnalytics.audience` 支持：

- `external`：真实外部用户，默认值；
- `internal`：团队成员和自用安装；
- `qa`：人工验收与测试设备。

开发者可把自己的生产安装设为 `internal`，测试人员设为 `qa`。开发、测试环境和 beta/nightly 通道还通过独立维度隔离，不能仅靠受众标签。

### 服务端纠正

客户端标签不是权限边界。登录账号在 `users.analytics_audience` 中保存服务端受众；管理员账号强制为 `internal`。已登录事件以服务端受众为准，避免客户端误配。匿名事件允许自报 `external/internal/qa`，这是用户自我排除机制，不用于权限和计费。

合成监控不复用真实客户端链路；部署验收发送 `internal` 事件，验证后只检查内部视图，永不进入外部指标。

### 数据边界与保留

允许字段仅包括：事件类型、服务端时间、安装 UUID、可选平台会话令牌、受众、运行环境、发布通道、操作系统类别、产品版本、入口类别。服务端落库前对安装 UUID 做 HMAC。

禁止字段包括：消息/提示词/回复、工具名和参数、会话/项目/空间/文件标识与路径、渠道账号、邮箱、手机号、IP、User-Agent、设备名、硬件标识、任意 URL、诊断事件和异常正文。

日聚合保留 180 天；安装映射在最后活动超过 180 天后随清理任务删除。首批以写入时的惰性清理实现，不建设原始事件流水表。

## 数据与接口

### D1 模型

`product_analytics_installations` 保存安装摘要、可选关联账号、当前受众和最后一次低基数客户端维度。`product_activity_daily` 以 `activity_date + installation_hash` 为主键，只保存当日是否接受意图、是否成功以及直接/渠道入口布尔值；重复上报使用幂等 `MAX` 合并，不保存原始事件列表和次数。

`users` 新增 `analytics_audience`。现有管理员迁移为 `internal`，其余账号默认为 `external`。

### 写入接口

`POST /platform/analytics/activity` 是公开、限字段的 best-effort 接口。请求体固定 schema；Worker：

1. 校验事件、UUID、时间偏差和枚举；
2. 可选验证平台会话令牌；
3. HMAC 安装标识并决定最终受众；
4. 更新安装映射；
5. 对当日日聚合执行幂等 upsert；
6. 惰性删除超过 180 天的数据；
7. 返回 `202`，不返回任何主体标识。

### 管理接口

`GET /platform/admin/analytics/activity` 仅管理员可用，支持 `audience`、`environment`、`releaseChannel` 和 `days` 白名单参数，返回：当前 DAU/WAU/MAU、对应成功活跃、匿名/已识别拆分、识别率和按日趋势。接口不返回安装摘要或主体明细。

管理员用户更新接口允许修改账号 `analyticsAudience`，以便把内部与 QA 账号从外部指标中长期排除。

## 客户端传输

Service 的 `ProductActivityReporter` 实现 Kernel sink：

- 每个活动信号构造固定 schema，不接收业务 payload；
- API 基址复用平台 `nextclaw.apiBase` 解析；
- 仅识别有效平台会话令牌形态，普通免费 provider key 不进入 Authorization；
- 网络请求设短超时并吞掉失败，绝不阻塞或改变 Agent run；
- 不做无限重试和后台常驻队列；服务端布尔 upsert 保证重复上报安全；
- `development`、`test` 和非稳定发布通道即使显式启用也进入独立维度。

## 管理端

平台管理首页新增“产品活跃”区：

- 外部 / 内部 / QA 受众切换；
- DAU、WAU、MAU、周成功活跃、匿名安装、已识别用户和识别率卡片；
- 最近 30 日核心活跃与成功活跃的轻量柱状趋势；
- 明示当前过滤条件和“匿名安装不等于精确人数”的口径说明。

测试人员在自己的 NextClaw 设置中选择 `QA`，团队自用安装选择“团队 / 自用”；管理首页只负责切换和读取三类聚合视图。账号受众也可由管理员更新接口长期纠正，不为这项能力迁移旧的用户管理 API 模块。

## 失败与恢复语义

- 客户端关闭：没有安装标识和远端活动，管理端不把缺失解释为零使用；
- 单次上报失败：Agent 正常运行，后续活动仍可上报；首批不保证离线补传；
- 重复上报：日布尔 upsert 幂等，不抬高 DAU/WAU/MAU；
- 登录令牌无效：接口拒绝带无效凭据的请求，客户端后续可在无凭据状态继续；
- 受众误配：管理员修正账号受众后，查询通过当前映射重新归类历史 180 日活动；
- 部署失败：Worker 和 Pages 分开部署；D1 迁移只新增列和表，旧 Worker 可继续工作，新页面必须等待新 Worker 可用；
- 回滚：回滚 Worker/Admin 代码即可停止新读写，新增 D1 表和列保留，不执行破坏性 down migration。

## 非目标

- 不统计页面 PV、停留时长、点击热图、消息内容或工具级行为；
- 不把匿名安装估算包装成精确用户数；
- 不引入 PostHog/Mixpanel SDK 或第三方数据处理方；
- 不上传本地诊断日志；
- 不在本批发布 NPM、Desktop 安装包或更新通道；平台部署完成后，客户端采集会随下一次经授权的产品发布进入用户安装。

## 验证与部署标准

1. Kernel 对直接、渠道、cron、child、成功和失败 run 的活动判定测试；
2. Service 对默认关闭、随机 UUID 持久化、字段白名单、令牌识别、超时和失败不阻塞测试；
3. Worker 对匿名写入、登录归并、管理员强制内部、幂等日聚合、指标窗口和隐私字段拒绝测试；
4. Admin API 类型检查、页面 smoke 和用户受众更新测试；
5. 所有触达 TypeScript package 执行匹配范围 `tsc`；
6. 运行本地 D1 迁移与集成测试，并执行 diff-only maintainability review；
7. 生产顺序为远端 D1 迁移、Worker 部署、内部验收事件、远端 D1 聚合核验、Admin Pages 部署、线上页面与 API 健康检查；
8. 不提交、不推送、不发布客户端产物，除非用户另行授权。
