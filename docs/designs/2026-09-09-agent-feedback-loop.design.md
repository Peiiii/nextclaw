# 用户反馈到修复发布的 Agent 闭环设计

日期：2026-09-09。状态：方案评审稿。已核实本地入口与官方调度合同，未启用自动化、未执行真实反馈或发布。

`design-document: required`：跨反馈、身份、开发执行和发布生命周期。
`plan: required`：实现需分批验证入口、自动修复和交付；本轮只形成整体设计。

## 1. 用户结果与固定约束

用户在 NextClaw 中让 AI 反馈问题，不需要登录 GitHub、Linear 或任何外部系统。没有 NextClaw 账号也能匿名提交并追踪；已经登录 NextClaw 时，系统可关联经过服务端核验的账号身份，无需重复登录。

维护侧 AI 分类、核实，在授权范围内修复与交付。发布结果回到原始反馈单；用户侧 AI 可查询、继续补充和复验。严重程度、身份和自动化权限分别判断，登录用户可以获得排队优先，但匿名用户不能因此失去反馈闭环。

对齐 [产品愿景](../VISION.md) 的统一入口、自感知、自治和自进化。推荐：**复用现有反馈门户作为反馈事实源，Codex 定时读取待办，单执行者在隔离 worktree 修复，调用现有发布流程，结果写回原反馈。GitHub 承载代码协作，可按需关联工程 issue，不是用户入口。**

轻量的尺度是新增多少必须长期维护的机制。首版不另建反馈后台、账号体系、队列平台、通用工作流引擎或多 Agent 集群。

### 问题池选型：用户入口和维护后台分别决定

用户无须登录外部系统是固定约束，GitHub 是否做后台不是固定约束。以下两个候选都可以做到用户匿名提交：

| 候选 | 用户如何提交 | 需要新增/维护的部分 | 当前判断 |
| --- | --- | --- | --- |
| 平台代投 GitHub，GitHub 为问题池 | NextClaw 接收报告，服务器用维护侧身份创建 issue | 仍需接收接口、防滥用、匿名回执、身份私密映射、GitHub 故障补偿；公开仓库还需脱敏或另选私有存储 | 可行；若已经高度依赖 GitHub 人工分诊且反馈可公开，它有优势 |
| 现有反馈服务为问题池 | NextClaw 直接调用自有反馈 API | 在已有存储中补回执、认证关联、私密隔离、领取/状态更新与维护查询 | 推荐；最贴合当前匿名/身份/私密跟踪需求，且已有代码基础 |

第三种“自有反馈池与 GitHub 全量双向同步”不采用：同一状态会出现两个 owner，增加冲突与恢复成本。Linear 等工具同样只有在已有团队流程带来明确收益时才选，不为了可能扩展预建工单 provider 抽象。

推荐方案允许反馈直接关联修复分支或 PR，不创建 GitHub issue；GitHub issue 仅用于确实需要公开协作的缺陷。当前仓库代码托管与发布使用 GitHub，不意味着反馈产品也必须以 GitHub 为基础。

选择依据是现有代码和本轮需求，不是已证明部署成本最低。实施第一步核实门户能否以 live 模式可靠运行；如其落地成本明显超过代投方案，就重新比较这两个具体候选，不同时实现两套后端。

## 3. 最小完整链路与 owner

~~~mermaid
flowchart TD
  U[用户或用户的 AI：匿名/已有 NextClaw 登录] --> F[现有反馈服务：持久化并返回回执]
  F --> P[待分类反馈]
  T[Codex 桌面定时唤醒] --> P
  P --> D[分类、身份优先、证据与授权检查]
  D --> Q[答疑/补充信息/维护者决策]
  Q --> F
  D --> W[单执行者：隔离 worktree 复现与修复]
  W --> V[验证与审查]
  V --> G[按需关联 GitHub issue/PR]
  G --> B[冻结已授权发布批次]
  B --> R[既有发布 workflow]
  R --> C[核实版本与渠道，回写结果]
  C --> F
  F --> U2[用户或 AI 查询回执、复验和补充]
~~~

| 职责 | 唯一 owner | 不承担的职责 |
| --- | --- | --- |
| 报告、报告人关联、对话、用户可见状态 | 现有反馈门户服务和数据库 | 不执行源码修复、不持有发布权限 |
| 已登录身份真实性 | 现有平台认证服务 | 不把昵称/客户端字段当认证 |
| 客户端报告整理与本地回执保存 | NextClaw kernel 的反馈能力，UI/AI/对象级 CLI 复用 | 不复制平台认证、不拥有云端处理状态 |
| 唤醒周期 | Codex scheduler | 不以聊天是否结束判定反馈是否完成 |
| 领取和阶段变更 | 反馈服务的受限维护端接口 | GitHub 标签与本地文件不再作为第二套业务状态 |
| 修复产物与运行证据 | 单个 Codex 执行者和隔离 worktree | 不自行扩大权限 |
| 发布事实 | 既有发布 workflow、registry 和 update channel | 不相信 AI 自述成功 |
| 用户环境复验 | 用户侧 AI/用户 | 未回复不等于复验成功 |

客户端入口建议为“反馈问题”和“查看反馈”；AI 与 CLI 通过同一对象级操作提交、查询和追加证据，具体命令名进入实现计划再冻结。新增 CLI 时同步中英文 commands、自管理用法与文档站，不能只提供后台 API 就称用户闭环成立。

必要时维护者机器人将可行动缺陷的脱敏摘要发布到 GitHub，关联 feedback ID、issue、PR、修复 SHA。多个重复反馈可关联同一个工程 issue。GitHub 不保留完整私密报告，也不反向主导原始反馈状态；不默认把每条匿名反馈都变成公开 issue。

## 4. 匿名、已登录与追踪能力

### 4.1 匿名首版即完整支持

提交最少需要问题描述；AI 能收集到版本、环境、复现就附带，不能因用户提供不了技术信息而拒绝接收。报告以私密维护反馈入池，公开展示另走明确脱敏后的投影。

持久化成功后返回 feedback ID 和高熵随机回执密钥。客户端在本地保存，凭密钥查询该单、读维护回复、追加信息；服务端只存密钥摘要。密钥不放公开 URL/query、日志、GitHub 或模型上下文，工具内部使用认证头传递，公开 ID 本身不提供私密读写权限。

匿名用户可以在原设备的“我的反馈”中回来查看，不要求注册。需跨设备时可导出回执；丢失回执且没有账号关联时无法证明归属，不能仅凭编号取回私密报告。可选联系方式不是必填项，也不能据此直接标记已登录。

客户端以一次提交生成的 request ID 做幂等。服务端将 request ID 与报告摘要、回执摘要一起原子保存；响应丢失后重试得到同一报告，不产生多个工单。回执密钥由客户端安全生成并保存，避免服务端只能回传一次导致重试无法取回；具体编码不扩成通用身份协议。

### 4.2 有登录态时自动关联，不增加登录步骤

“已登录”限定为有效的 NextClaw 平台账号；本地 UI 解锁、provider key、GitHub 登录和自填邮箱均不等价。

客户端通过现有凭据管理发送认证证明，反馈服务调用平台认证 owner 验证并只保存内部 user ID、认证来源和验证时间；不保存 access token、Cookie、密码，不向维护 AI 或公开工单暴露这些内容。维护者界面可以显示已验证账号和必要的显示名，联系方式只在私密权限范围内按需读取。

无登录凭据时直接匿名。有凭据但过期或认证服务暂不可用时，仍可先按未验证身份接收并返回回执，明确显示“反馈已提交，账号未关联”；不强制重新登录，也不把未核验身份当已登录。客户端后续凭原回执和有效登录态显式关联同一报告，不创建新报告。

账号查询“我的反馈”必须服务端校验所有权。匿名回执只是该反馈的能力凭证，不提供其它反馈、账号管理或发布能力。

### 4.3 排队规则

建议顺序：**严重程度 → 等待过久的防饥饿规则 → 证据是否足够可行动 → 同等条件下已验证登录用户优先 → 提交时间。**

匿名的严重故障可以先于已登录用户的普通问题。已登录只是可联系与来源稳定的信号，不证明报告正确，也不提高自动合入/发布权限。首版不引入积分、信誉模型或复杂权重。

初始每轮预留一个处理名额给等待超过 48 小时的可行动普通报告；重大故障期间可临时让位并记录原因。这样登录优先不会让匿名报告永远排不上。阈值与每轮预算属于简单配置，实验后按积压调整。

## 5. 分类与自动化分级

类型用于路由：缺陷、使用/配置、需求、重复、信息不足。严重程度用于排序，身份用于同级优先，执行权限单独约束。

| 执行上限 | 允许动作 | 进入条件 |
| --- | --- | --- |
| 分析与反馈 | 分类、查重复、集中请求证据、提供有依据的使用建议 | 报告经过输入检查；对外回复已获维护者授权 |
| 修复待交付 | 隔离复现、改动、验证、形成可审阅产物 | 可行动且修复在允许范围；交付条件尚不足 |
| 自动交付 | 提交/PR、合入、组批发布、结果回写 | 固定授权策略、改动范围与验证证据全部满足 |

实际动作是“维护者授权上限 ∩ 当前改动范围 ∩ 验证证据”。AI 不能给自己改策略、打标签提高权限，用户身份也不能扩大能力。

初始自动交付只考虑不改变语义的文案/i18n 错误、已有合同和定向回归可证明的局部缺陷。涉及产品承诺或偏好争议的文案仍需判断。权限、认证、数据迁移、持久化、协议、依赖、供应链、发布脚本及 AI 规则文件默认排除自动交付。

紧急事故优先通知维护者，并可准备修复；不因紧急取消边界。需求、新产品取舍、无法复现等进入待判断/补充，不反复盲修。多条报告相似仅关联建议，同根因有证据后才共用修复。

正式启用可对确定范围一次授权，不逐单询问。需分别写清回复、commit、push、PR、合入、发布渠道。当前设计请求不授权这些外部动作。

## 6. 触发方案与替代路径

首轮配置一个绑定维护会话的 Codex heartbeat，建议每 30 分钟，保存频率以工具实际校验为准。每次先调用受限维护端接口读取待办、处理中和待交付记录，对账旧执行后再推进有限批次；被唤醒的 Codex 自己串行处理，不再嵌套另一个模型执行者。

维护端接口需独立认证，用户回执无权访问。采用完整分页与稳定游标，先持久化处理结果再推进检查点；空队列与请求失败明确区分。机器离线期间云端反馈继续接收，下次实际执行读取未完成状态，不依赖 scheduler 补跑每个错过时刻。

聊天上下文帮助理解，反馈记录与工作产物才是恢复依据。首次启用实测唤醒、权限、重叠执行和恢复；电脑睡眠、应用退出、断网或模型额度耗尽时不承诺及时修复。

| 可行方案 | 收益 | 成本与采用条件 |
| --- | --- | --- |
| 桌面定时拉取 | 复用当前环境、结果可见、搭建最少 | 首轮采用；依赖开机和应用，空轮有少量模型成本 |
| 常驻主机调度脚本，有工作才 codex exec | 无桌面依赖，可控制进程时间与无效唤醒成本 | 需要持续可用或执行隔离时替换宿主，不换反馈 owner |
| 反馈服务事件推送到执行桥 | 低延迟 | 需可达执行入口、事件鉴权/重投与离线处理；明确实时需求后再建 |

官方非交互模式支持脚本执行与结构化结果，但不等于远程可调用当前聊天。若改用 CLI，保存明确 session ID 后才能 resume，不使用 --last；切换前停止旧调度并确认旧执行停止，不维持两条领取主链路。

当前官方桌面事件触发能力不足以承诺“收到任意 issue 即唤醒本地”；云端事件任务也不能直接操作本地工作目录。[官方调度说明](https://learn.chatgpt.com/docs/automations?surface=app)

## 7. 状态、领取和中断恢复

用户状态：已收到 → 待补充/待判断/处理中 → 待发布 → 已发布。答疑与重复可按对应原因结束。进度由反馈服务拥有，GitHub issue/PR 只是关联对象；不进行两套工单状态的双向同步。

首版单执行者，维护端通过数据库条件更新原子领取，返回 run ID/执行代次；每次阶段转换和受控外部动作须校验当前代次。已有记录增加最小执行字段即可，不建消息队列或分布式任务框架。本地记录只保留 worktree/进程/证据位置等运行信息，不另起业务状态。

中断记录先进入待恢复。单机确认旧进程已停止后才交接新的执行代次；不能仅因超时就让第二个执行者写同一工作区。若跨机无法确认旧执行是否还活着，则停止交付并请求维护者处理，首版不支持多机并发修复。

最小记录包含报告 ID、相关输入版本、当前状态、run ID/代次、产物/验证 SHA、GitHub 关联、发布身份/渠道/结果、已确认外部操作 ID、预算与失败原因。AI 运行输出不是发布完成证明。

| 情况 | 恢复行为 |
| --- | --- |
| 重复提交或扫描重叠 | 提交 request ID 幂等、领取条件更新只有一方成功 |
| 报告新增证据 | 递增相关输入版本，重新评估；旧结论不得覆盖新证据 |
| AI 自己回复 | 作者角色由服务端确定，不再次触发自身处理；GitHub 评论同时校验账号与 🤖[墨爪] 前缀 |
| 回复成功但响应丢失 | 服务端按稳定操作 ID 幂等；GitHub 侧先查作者与操作标记再重试 |
| API 限流、认证失效、额度耗尽 | 保留状态，有界退避/暂停；请求失败不当作无待办 |
| 修复中断 | 保留 worktree，确认旧运行终止后基于记录恢复 |
| 用户撤回或维护者暂停 | 下次副作用前复核，停止新领取/动作；保留已发生事实 |
| 发布部分成功 | 调用既有发布恢复入口，不用升新版本掩盖失败 |
| 本地运行信息丢失 | 按服务端记录和 GitHub/发布证据对账；无法确认时不重新发布 |

建议每轮最多深入分类 10 条变化报告、串行修复 1 个，同一输入最多两次修复尝试，初始修复时间预算 45 分钟。执行宿主不能硬限制 token 时如实用时间/次数限制，触顶通知一次。高流量积压先限流、归类和人工评估，不无限启动模型。

## 8. 发布批次与回评

先定义原 bug 可观察失败条件，再复现、修改、运行相关 tsc、测试和既有审查。无法复现或缺少目标平台验证时停在待验证，不能拿无关测试全绿替代真实证明。所有产品源码改动隔离 worktree，保护现有 WIP。

独立问题保留独立修复证据，同一根因可关联多条反馈。建议每天最多一个普通发布批次，无成熟修复不发布。冻结反馈 → issue/PR（可选）→ 修复 SHA → 发布 SHA → 版本/渠道映射；最终集成变化需验证受影响面。

既有发布从 master 运行，自动发布前必须检查相对上个版本的全部变更是否获授权。发现其它任务未授权内容时停止自动发布，不能顺带发布。复用 release.yml 互斥、发布/恢复与适用的主线 reconcile，不另写包上传与版本逻辑。

只有目标平台/渠道实际可用才回写“已发布”。NPM 完成不等于 Desktop 用户可升级；workflow 启动、源码合入或 AI 输出完成都不充分。平台部分失败按对应反馈范围记录，不假报整体成功。

原反馈内的维护回复包括版本、渠道、升级方式、验证范围、修复链接。有关联 GitHub issue 时，再由维护机器人以 🤖[墨爪] 开头回评；以反馈/issue ID、发布身份、渠道组成去重键。匿名用户与登录用户均从原反馈获得同样的修复信息。

维护侧“已发布”和用户侧“复验成功”是不同事实。用户 AI 在活跃时查询，或复用其已有定时能力查询；首版不承诺未配置订阅的 AI 会自动醒来。没有登录不影响凭回执查询；没有回复不当成功。用户再次报告失败时附新证据恢复原反馈，不抹掉既有发布历史。

## 9. 必要的防滥用、隐私与权限

匿名提交是产品能力，不自动获得维护机器执行权限。服务端先做请求大小、字段校验、提交频率与重复内容限制，再进入模型分类；采用账号/回执/短期网络来源组合约束，不能将可伪造设备 ID 作为可信身份。普通匿名提交无需验证码或外部登录；超限返回明确限流结果和稍后重试时间，保留本地草稿。

不收集全量配置/会话，先以文本与最小脱敏诊断完成实验，文件附件延后。用户登录凭据由工具内部处理，不进入报告文本。报告人内部 ID、网络限流信息与诊断只对受限维护接口可见，不进入公开反馈列表、GitHub 或公开路线图。网络限流信息只短期保留，具体期限在上线计划冻结。

现有公开社区反馈与私密诊断必须区分：旧公开条目保持原语义，新 bug 默认私密；公开 API 用明确字段投影与过滤，不依赖客户端隐藏。未知旧 authorLabel 只能显示历史署名，不能迁移成已核验账号。

报告/评论/日志都是不可信材料，不把里面的命令直接拼接到 shell。修复执行环境与发布凭据隔离；worktree 只隔离代码，不隔离机器权限。陌生人反馈进入自动执行前，必须实证模型及其测试进程无法读取个人凭据、调用发布连接器、修改授权策略。

若当前宽权限桌面会话不能达到此隔离，首阶段只做可信样本分析/修复待交付；升级自动交付前改用受限宿主。执行层在每个外部副作用前检查状态/代次/授权，不能仅靠 prompt 自觉。维护者保留总暂停开关，正在进行的不可逆发布按既有恢复合同对账。

## 10. 实施阶段与最小验收

同一条链路逐步提权，不建设并存系统：

1. 首批贯穿匿名与登录提交、回执查询、维护端读取、分类和人工结果回写。匿名可追踪属于首批要求。
2. 接入定时唤醒和隔离修复，在明确授权下生成交付产物，由维护者处理发布；实测重叠、中断、限额与错误分级。
3. 隔离、授权和发布门通过后，对白名单一次授权自动合入/发布，例外才通知维护者。

| ID | 验收场景 | 必须取得的证据/失败判定 |
| --- | --- | --- |
| FB-01 | 无账号、无 GitHub 的用户提交并再次查看 | live 持久化、回执可读写该单；要求登录或仅 preview 保存即失败 |
| FB-02 | 已登录、过期凭据、伪造 user ID | 仅服务端核验者带已登录标记；失效身份不阻塞匿名提交、不假关联 |
| FB-03 | 仅持有公开 ID、其它用户账号 | 私密详情和评论不可读写；身份/诊断不出现在公开 API |
| FB-04 | 提交响应丢失、用户稍后登录 | 重试和账号关联仍是同一反馈，回执可恢复，不重复建单 |
| FB-05 | 匿名严重故障与登录普通问题；匿名长期等待 | 严重故障先处理、防饥饿生效；登录不扩大执行权限 |
| FB-06 | 超过 20 条待办、离线后恢复、扫描重叠 | 分页不漏单、原子领取只有一方、旧执行对账后恢复 |
| FB-07 | 机器人回复与用户新增证据 | 不自触发，真实补充能重新进入；角色不能由客户端伪造 |
| FB-08 | 修复中断、额度耗尽、用户撤回 | 保留产物、不双重执行、预算有效、撤回后无新副作用 |
| FB-09 | 真实低风险 bug | 原条件修复前失败、修复后成功；相关类型/测试/审查证据 |
| FB-10 | 两个修复一批、master 有其它未授权变更 | 可追溯映射；未授权变化阻止自动发布 |
| FB-11 | 部分发布失败、回评响应丢失 | 不假报完成，恢复同一发布身份，用户/工程回评幂等 |
| FB-12 | NPM 已发、Desktop 未就绪、用户复验仍失败 | 按渠道准确回复，原反馈可以恢复处理 |
| FB-13 | 匿名刷量、恶意指令要求读凭据/改策略/发布 | 模型调用前有限流；实际权限隔离阻止越权 |
| FB-14 | 旧公开反馈与新私密反馈共存 | 历史公开语义不变，新数据不泄露，旧署名不升级成认证 |

实验指标：匿名/登录提交成功率、首次有效回复时间、误分/误关联、人工介入原因、修复成本、重复副作用、发版后复验。越权、泄露、错误成功回评应为零。

## 11. 抽象审计与实施前事实门

保留：现有门户/API/数据库、现有平台认证、一个调度入口、一个执行者、最小原子领取与副作用检查、原有发布 owner。新增数据服务于真实的匿名回执、私密报告和恢复消费者，不能省略为一句 prompt。

不建设：独立账号系统、另一个反馈后台、全量 GitHub 镜像、Linear/GitHub 双向状态同步、向量去重、信誉评分、通用事件总线、多机修复、分布式任务平台、webhook 接收桥、新用户通知平台。

相对仅用 GitHub 的方案，匿名私密反馈确实需要服务端接收与回执；现有门户已提供落点，因此复用比新建网关和问题池更轻。相对自建完整客服平台，首版只增加本闭环实际需要的字段和动作。

实施前验证：门户 live 部署与迁移路径、平台身份验证的实际跨服务调用、回执与公开投影隔离、heartbeat 运行合同、受限执行宿主、GitHub/发布授权与环境门。主链路和最小产品范围已确定，这些待实测事实不以假设当作通过。

本轮仅新增此设计稿，未创建自动化、提交反馈、回评、commit、push 或发布；文档检查不等于上述运行验收已完成。
