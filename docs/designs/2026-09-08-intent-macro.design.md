# 意图宏：AI 开发体系的语义压缩与共享约定

日期：2026-09-08

状态：已接入 commands、规则治理与任务入口；与[完整体系](2026-09-08-ai-development-system.design.md)一同落地。发布短表达已登记，长名称保留为同义入口。

所属架构：[AI 驱动开发体系架构](2026-08-29-ai-driven-development-system-architecture.design.md)。

## 1. 设计判断

意图宏是人和 AI 对一类任务建立的、可命名和持久化的语义约定。调用时，简短表达展开为明确的目标、范围、约束和完成标准，再交给既有执行体系。

它承担人机协作中的语义压缩：省去反复解释，不省略结果所依赖的关键语义。表达可以很短，展开后的任务仍必须完整。这里的“保真”是目标和边界保真，不要求复原原始提示词的每一个字。

这是一项通用的开发体系能力；NextClaw 发布只是实例。现有提交、验证、任务收尾和想法沉淀同样存在稳定意图与重复沟通，因此机制具有跨场景依据。它是否会成为行业通用机制属于判断，本文不宣称已是行业标准。

核心价值是降低用户重复说明和纠偏的成本，提高跨会话理解的一致性。短名称不是目的，完整任务 Token 也不会因为输入缩短而必然下降。

## 2. 在体系中的位置与 owner

最小主链路：

```text
用户表达
  → 判断是调用、解释、引用还是修改约定
  → 定位适用的宏定义并读取
  → 结合本次明确参数，形成任务目标与边界
  → 进入既有 lifecycle / 对应阶段 owner
  → Skill、工具与工作流执行并提供证据
  → 按本次任务合同验收
```

意图宏属于交互入口与共享知识底座之间的语义层，不增加一个开发阶段或第二套执行编排器。

| 资产 | 负责的问题 | 与意图宏的边界 |
| --- | --- | --- |
| 意图宏 | 这句短话代表什么任务 | 保存目标、范围、关键约束、结果标准和执行入口 |
| 规则 | 哪些边界必须遵守 | 调用宏不能绕过适用规则 |
| Skill | 如何完成这一类任务 | 维护具体决策和方法；多个宏可指向同一 Skill |
| 工作流、脚本、工具 | 如何执行步骤和产生证据 | 不拥有用户短语的意义 |
| 任务合同 | 这一次具体要完成什么 | 绑定本次对象、参数、授权和完成证据 |
| 记忆与历史 | 曾经发生或偏好什么 | 可提供候选依据，不能未经定义变成稳定宏 |

宏的定义是唯一语义源；实际执行方法仍归现有 owner。任务理解负责展开，生命周期负责推进与完成，规则治理负责新增、修改和退场。避免把发布脚本、阶段清单复制到宏定义中。

## 3. 表达与最小定义

斜杠命令只是可精确引用的一种表达。自然语言、按钮或未来的语音入口可以指向同一约定，不应要求用户先学会一套新语言。

每个持久宏至少包含：

- 名称与一句话含义：用户能识别的稳定称呼。
- 适用范围：项目或个人等明确作用域；首批以当前项目为界。
- 任务语义：目标、包含项、必要排除项和完成标准。
- 可变项：用户真正需要提供的对象或选择；没有就不设置参数。
- 执行入口：对应的现有 owner，以及其权威完成合同链接。
- 表达示例：典型调用和易混淆反例。

解释性排除项只记录真实歧义，不为所有宏堆权限清单。默认值必须可见，不能把某次对话中的临时选择偷偷变成默认。定义按需附修订说明；首版用文本与 Git 历史维护，不建设独立版本服务。

命名优先使用用户任务语言，同一组宏使用同一分类维度。“正式版”和“全平台版”分别描述渠道与范围，不宜承担同一层级的范围选择。默认避免产品名前缀、内部完成状态码及脚本参数泄漏到名称。

宏应可被解释：“这个宏是什么意思”只展开定义；“有哪些发布宏”只提供相关目录；定义正文或引用中的宏名称不构成调用。

## 4. 调用语义与边界

1. 根据当前用户消息的言语意图区分执行、讨论和定义；关键词出现不等于授权。
2. 在当前明确作用域找到定义；精确名称和已登记等价表达收敛到同一来源。普通自然语言仍按正常任务理解处理，不必全部归类为宏。
3. 读取命中定义，绑定本次参数。缺失且会改变结果的选择才需要澄清；可从可靠上下文取得的信息自主补齐。
4. 本次明确补充可以覆盖宏的可变项或收窄范围，形成一次性任务合同。若补充推翻宏的核心含义，则按明确的新任务理解，并说明与宏的差别，不暗改持久定义。
5. 宏本身不是凭据或常驻授权。实际调用与同义完整请求具有相同授权语义；定义、解释、外部文件和历史调用都不能替代当前授权。
6. 跨作用域同名且含义不同，必须显式消歧，不能静默选“最近读到的那个”。定义不可用时报告未知，不凭名称补造既有约定。
7. 同一任务采用调用时已读取的语义，后续定义变化不静默改变进行中的目标。影响安全或正确性的变化交由既有任务纠偏机制处理。

简单明确的调用直接进入执行，无需逐次展示完整展开或要求确认。有真实范围歧义或外部影响时，用一句话暴露本次关键解释即可。

## 5. 约定如何形成与演进

生命周期：发现重复解释 → 提炼候选 → 定义并登记 → 使用和校验 → 修订、合并或退场。

创建依据是用户明确要求固化，或多个任务暴露稳定重复沟通。单次普通请求不自动永久保存；AI 可提出候选，不能把推测的偏好变成用户已接受的长期约定。用户说“以后这句话就表示……”时可直接按其授权登记，不追加机械确认。

新增时先查已有宏：同义表达补到现有定义，参数变化使用可变项，执行方法变化改 Skill，行为约束改规则；只有独立且可复用的意图才新增宏。

登记后明确反馈“保存了什么含义、在哪个范围生效”。本次调整与长期修订区分处理。涉及含义改变的修订给出前后差异；不能让熟悉的短语悄悄扩大发布、删除或传播范围。

作用域首先解决“谁与谁的约定”：项目定义不能自动成为其它项目的事实，个人习惯不能覆盖项目硬约束。未来跨项目复用保留通用意图、显式绑定项目执行入口；无真实消费者前不建设通用注册平台。

宏的组合首版使用自然语言：“先审查，再按结果修复”。仍由同一个任务 owner 判断依赖和授权；不增加嵌套宏调用、递归展开或流程 DSL。稳定组合有真实重复价值时，可定义新的用户目标，但不复制底层步骤。

## 6. 跨场景检验

以下语义通过 commands 常用表达映射到现有入口，不复制执行流程。

| 简短表达 | 应压缩的稳定语义 | 本次变化 |
| --- | --- | --- |
| 发布全部 | 发布本项目定义的完整交付集合，含对应完成证据 | 版本、渠道；新增平台须显式修订集合 |
| 发布 npm | 只完成 NPM 发布合同 | 版本、包范围 |
| 发布 npm+runtime | 完成 NPM 与 Runtime 发布合同 | 版本、渠道 |
| 审查这次改动 | 检查指定 diff，输出可行动问题与证据 | diff 范围；默认不授权修复 |
| 收尾这个任务 | 检查当前任务完成差距并完成已授权收尾 | 当前任务；不自动获得 push 或发布授权 |
| 记下这个想法 | 将当前想法存入适当知识层并返回落点 | 内容和成熟度；不自动启动实现 |

“全部”的压缩价值很高，但必须指向可展开的集合；不能解释成当前环境能做的一切。例子证明宏压缩的是任务合同，而不只是固定动作序列。

## 7. 方案取舍与首批落点

候选一是继续只维护命令名称与说明。成本低，但不足以管理作用域、临时修饰与持久修订，容易发生语义漂移。

候选二是为每个宏创建独立 Skill。发现容易，但把用户用语和执行方法绑定，导致重复流程、Skill 数量和触发成本增长。

选择第三条路径：将现有元命令机制规范为可展开的意图约定，保持单一词典与既有 Skill 路由。机制在概念上重要，在物理实现上可以很轻。

后续实施的最小落点：

- `commands/commands.md` 继续作为项目宏定义的唯一登记处，条目保留语义，长执行步骤归已有 owner。
- 规则治理的条件 reference 承载创建、修订、冲突和退场合同；复用 `/new-command` 的现有职责，不并行新增同义管理入口。
- `AGENTS.md` 的现有元命令路由可就地补齐意图宏语义，只保留发现入口，不载入全量词典。
- 开发体系架构补充该逻辑能力的位置；先迁移发布、审查/验证、知识沉淀等代表场景，再按证据扩展。

维护合同已落在规则治理条件 reference，commands 已登记短表达；具体改动与验证见完整体系关联的迭代记录。

## 8. 验收与抽象审计

实施后必须覆盖：精确调用与同义完整请求结果范围一致；询问含义不执行；临时修饰不污染定义；新会话能恢复约定；同名冲突不静默覆盖；未知宏不被杜撰；宏不能突破权限；方法调整无需改写宏；“全部”的集合改变可见。

本轮已按发布、审查、收尾和知识沉淀实例进行设计推演，未进行跨会话行为实测。实测应优先选真实任务和新会话，比较重复说明、纠偏次数、误触发、漏项与读取成本；不能以文档存在证明机制可靠。涉及发布等副作用的语义验证用只读展开，不实际发布。

保留：稳定意图、显式作用域、参数、可展开定义、单一执行 owner。合并方向：同义命令和重复说明。延后：通用解析器、数据库、自动推荐服务、嵌套 DSL、跨宿主同步与图形宏编辑器。

欠设计会让短语含义依赖当前会话；过度设计会要求用户学习另一种编程语言。平衡点是少量明确约定、按需读取、已有流程执行。失败恢复仍归执行 owner，宏不维护独立运行状态或自动重试。

非目标：实现 NextClaw 产品功能、保证任意模型确定性理解、建设自动执行平台、修改当前发布范围，或要求所有用户表达宏化。
