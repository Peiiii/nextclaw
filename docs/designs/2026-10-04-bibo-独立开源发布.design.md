# Bibo 独立开源发布设计

用户明确要求完成 Bibo 开源和发布，并强调极低成本与真实沙箱能力。现有源码属于 NextClaw MIT 仓库，但独立部署仍依赖平台账号。任务风险 L4，使用 standard；不改变现有托管账号服务及执行架构。

## 单一路径

在原 Bibo auth owner 加入明确的 self-hosted 部署模式：部署者设置邮箱和强密码 Secret，服务端验证后签发有期限的 HMAC HttpOnly cookie；旋转密码立即使旧 cookie 失效。错误密码及缺失配置不能取得空间权限，登录尝试按来源在现有预算 DO 内限速。普通托管模式保持原平台认证。独立部署 UI 默认登录，不显示注册与试用余额。

模型沿现有 DeepSeek transport，使用部署者自己的 BIBO_DEEPSEEK_API_KEY；可选 Exa 密钥。首次开源不发明多供应商模型注册体系。保留现有调用上限、10 分钟任务上限和 5 分钟沙箱休眠；普通聊天/文件操作不获取沙箱，只有 OS 工具才获取沙箱。持久文件继续 R2，执行环境保持临时语义。

独立仓库由显式导出器生成：只包含 Bibo app、两个未发布的客户端/UI workspace 包、根构建配置和公开说明；其余公共 NextClaw 依赖锁定当前已在 NPM 发布的对应源码版本，保持公共入口。导出器只复制 Git 跟踪文件及本任务明确文件，不复制本地配置、私有文件、账号 ID、站点路由、构建产物或 NextClaw 内部治理资料。保留 MIT 归属，记录 source commit；两个代码库之间以单一源导出保持同步。不是 fork 全仓或另写一套 Harness。

## 黄金验收与失败矩阵

1. 新 checkout → frozen install → tsc/build → credential-free preview；构建产物和依赖完整，公开 README 可直接执行，CI 同样执行。
2. 自托管配置 → 错误密码被拒绝 → 正确登录 → 创建任务/文件 → 刷新读取同一内容 → 退出后访问被拒绝；cookie 篡改、过期、缺 Secret、跨站写入均失败，普通 hosted auth 测试继续通过。
3. 自托管真实 Cloudflare 测试部署 → 普通文件写读不获取沙箱 → 通过 Agent 运行 Linux 命令、挂载 R2 文件并生成产物 → 读回结果；验证任务后台/持久化已有合同，若第三方环境有阻塞如实记录。
4. Review 后精确提交、主线协调 → 独立公共仓库默认分支、CI、v0.1.0 GitHub Release/源码资产可访问；部署从冻结提交运行，记录产物身份。

## 取舍和审查

没有新存储 owner、运行时或传输路径。选择既有邮箱/密码登录 UI 而非强迫用户先接入 Cloudflare Access，独立版清晰说明单人部署范围；现有多账号官方服务保留。成本宣传只说明已实现的资源模型，不编造账单、用户量或免费承诺。成本验收检查普通路径零沙箱获取，沙箱按需路径真实执行和默认休眠。

plan: not-required（单批交付，由 current-state 恢复）。design-review: passed：已核对原始输入、公共包版本可用性、认证边界、沙箱条件分支与独立仓库构建路径；发布不是仅提供源码链接，包含可独立部署的入口和验证。所有必需项在对应验收合同登记。
