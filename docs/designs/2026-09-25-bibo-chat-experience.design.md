# Bibo 对话体验与真实流式交付设计

日期：2026-09-25。目标是让 `app.bibo.bot` 的一次对话从发送、等待、阅读到刷新继续都达到成熟聊天产品的基本体验。以 2026 年 10 月为近期目标，不把尚未实现的联网、邮件或后台任务包装成现有能力。继承[首发边界](2026-09-24-personal-agent-quickstart.design.md)：每个账号独立容器、NextClaw Harness 是 Agent owner、R2 快照保存成功后才算一次对话完成。

## 现状与用户链路

用户截图中的长会话让整个文档滚动，输入区掉到视口外。实测 1365×900 视口中 `document.scrollHeight=1167`，消息区域高度和自身内容高度均为 905，说明 `list.scrollTop` 不会控制用户实际看到的页面。网页当前等待 `/api/chat` 完整 JSON 才追加用户和 Bibo 消息；Harness 已提供 `onAssistantDelta`，只是 Bibo 容器、Durable Object 和网页没有传递它。回答中的 Markdown 原样显示。截图里的 Bibo 自称能搜网页、收件箱和定时任务，与托管首发的能力边界不符。

代表链路：已登录用户在桌面或手机输入并发送消息，自己的消息立即出现，Bibo 先给出真实运行反馈，再逐步显示 Harness 产生的文字；用户上滑阅读旧消息时不被拉回底部，可一键回到最新；回答保存后显示完成并可复制。刷新页面得到已保存的完整对话。如果模型、容器或快照失败，界面明确指出本次内容未保存，保留用户原输入供重试；重新加载以服务端历史为准。

## 技术栈与代码边界（用户追加约束）

- 网页：React 18、TypeScript、Vite；Zustand 是会话、草稿、请求阶段和账号展示状态的唯一前端 owner。React 组件只订阅状态、调用 action 并呈现结果。流式网络解析与提交判定在 store 调用的独立 manager 内，不把状态机塞进组件 effect。
- 组件体系：建立专用 `@nextclaw/bibo-ui` 包，统一视觉 token、按钮、消息展示与输入区等稳定公共组件；组件库不 import Bibo API、Zustand 或 Cloudflare 类型。Bibo app 将其组成页面，后续独立表面可复用。规范写在 Bibo 作用域的 `AGENTS.md`，不改变全项目约束。
- 服务端：Cloudflare Worker / Durable Object 与容器入口均维护 TypeScript 源码。容器在构建时编译成 Node 可运行的 JavaScript 产物，运行时不加载 TS 转译器。底层 Agent 继续调用 `@nextclaw/harness` 公共入口。
- 发布：Vite 构建静态产物供 Worker Assets 托管，维持单一 Worker、每账号一个容器和现有额度；组件包是构建期依赖，不引入额外在线服务。

## 必要体验与方案选择

1. **真实进度**：采用 `fetch` POST + `text/event-stream`。事件为 `accepted`、`delta`、`saving`、`committed`、`error`。`delta` 来自 Harness 的 `onAssistantDelta`，不做打字机动画。`committed` 只在容器快照写入 R2 且消息写入 Durable Object 后发出。旧网页请求的 JSON 响应仍由同一执行路径生成，以跨越 Cloudflare Worker 与容器分别滚动更新的窗口。
2. **唯一滚动面**：应用占用动态视口高度，消息列表是主滚动容器，输入区在其下方始终可见。新消息发送时定位到最新；仅当读者接近底部时跟随流式增长。读者离开底部时出现“回到最新”，点击后恢复跟随。手机侧栏遮罩、软键盘空间和安全区一并处理。
3. **清楚的消息状态与停止**：发送后立即显示临时用户消息和 Bibo 占位；等待、生成、保存、完成、失败各有可见反馈。生成阶段可用“停止生成”明确取消这一轮；停止后丢弃未保存的本轮容器状态，保留上次 R2 快照。保存开始后不再接受取消，避免已经提交却显示未保存。临时消息不冒充已经持久化的历史。失败时不吞掉用户输入，不把部分生成内容当成已保存结果。
4. **可读且可信**：放宽桌面阅读列，助手长回答不放在窄卡片内；安全地呈现段落、列表、代码和链接，禁止模型输出 HTML 注入，容器内相对文件路径不伪装成网页链接。为完成回答提供复制入口。系统身份说明与示例只承诺当前已验证的文字对话、隔离空间和会话继续；对外部操作按实际工具与执行结果回答。

候选比较：纯前端把完整回答逐字播放，改动少但等待时间和真实进度不变，会误导用户；直接透传模型流无法保证 NextClaw 的工具、会话和 R2 保存语义。选择 Harness delta 经 Bibo 容器与 Durable Object 流转，保留既有 Agent 和持久化 owner。滚动选择单一消息区而非整页滚动加粘性输入区，后者在移动软键盘与长消息下仍有双滚动冲突。

## 成本约束

流式展示复用现有一次模型调用、一个账号容器和同一个 Durable Object 请求；不增加轮询、WebSocket、队列、独立流状态服务或第二次模型生成。delta 只在内存中转发，网页按动画帧合并渲染；R2 每轮仍只写一次完整快照，提交后删除旧对象，避免版本化带来持续存储增长。继续使用 `basic` 容器、1 分钟空闲休眠、最多 5 个并发实例、单账号与全站模型额度。显式停止可缩短无用的模型与容器运行时间。费用的主要变量仍是 DeepSeek token 和容器运行时长；参考 [DeepSeek 官方价格](https://api-docs.deepseek.com/quick_start/pricing/)及 [Cloudflare Containers](https://developers.cloudflare.com/containers/platform/pricing/)、[Workers/R2 计费](https://developers.cloudflare.com/workers/platform/pricing/)。上线后用实际用量决定是否调整额度，而不为节省少量传输费牺牲即时反馈。

## 状态与失败合同

Durable Object 继续串行化同账号 run、执行每小时限额并拥有保存提交点；容器只运行 Harness 并发出临时 delta 与最终结果；网页只保存当前请求的展示状态。快照改为每轮独立 R2 对象：先写新对象，再由 Durable Object 一次写入 `snapshotKey`、session ID 和消息，最后尽力清理旧对象。恢复时优先读取已提交指针，没有指针的旧账号读取原有固定 key。这样 R2 写成功而会话提交失败时，旧快照仍是权威，不把临时内容带进下一轮。

`accepted` 携带本轮 ID，同账号且匹配本轮 ID 的取消请求只在执行阶段通过 Durable Object `destroy()` 停止容器，原快照仍是权威；执行转入保存阶段后返回已无法取消，并由客户端等待完成或重新读取历史。浏览器连接断开时也终止未完成的生成，避免继续付费且避免假定 Durable Object 在响应断开后可以无限期运行；Cloudflare 的断线后后台运行只有有限宽限期。刷新只读取权威历史，前端暂存本轮输入供重试，并明确显示中断未保存。保存已经开始时继续尝试提交，刷新通过历史判定结果。流内错误与流意外结束都不能显示“已保存”，应重新读取历史核对是否已提交。滚动更新不覆盖用户的主动阅读位置。旧消息和旧快照不要求批量迁移。

部署窗口中旧容器可能仍返回 JSON；新 Durable Object 识别该响应后按同一持久化步骤完成，只是这一次没有中途 delta。新容器对旧 JSON 调用方保留完整 JSON 响应。等不再有旧网页消费者时可移除此过渡，不能形成第二套对话状态 owner。

## 黄金验收

| ID | 用户可见结果与证据 | 必需 |
| --- | --- | --- |
| BX1 | 真实账号从 `app.bibo.bot` 发送消息；在答案完成前收到至少一个真实 delta，随后看到保存完成；刷新后内容一致 | 是 |
| BX2 | 长会话在桌面与手机只让消息区滚动，输入区留在视口内；上滑后流式内容不抢滚，回到最新可用 | 是 |
| BX3 | 流断开或保存失败时显示未保存、原输入可重试；浏览器离开时不继续无意义生成；刷新只显示服务端已提交消息 | 是 |
| BX4 | Markdown 列表、代码、外链可读且不能注入脚本；长回复可复制 | 是 |
| BX5 | Bibo 对尚未接入的联网、邮件、定时任务不作虚假承诺；现有账号、限额、隔离和冷恢复继续有效 | 是 |
| BX6 | 生成中可停止且本轮不进入历史；保存阶段不可误报取消；刷新后仍是上次完整快照 | 是 |

先用真实浏览器注入分块响应验证 UI 时序与滚动，再用真实账号在线检查从 Harness delta 到 R2 提交、刷新恢复。复杂交互由 AI 先完成桌面和手机验收；用户只需判断视觉与手感偏好。生产部署沿此前已授权的 Bibo 服务范围执行，不触碰本地 `nextclaw` CLI。

## 2026-09-25：首字延迟纠偏

用户反馈「流式输出像答案完成后才开始播放」。线上时序确认浏览器确实在保存前逐步收到文本，但 DeepSeek `deepseek-flash` 默认开启 thinking：模型约 1.9 秒开始发送 `reasoning_content`，约 5.5 秒才开始发送用户可见的 `content`；一次浏览器长回答约 9.6 秒才出现首字，之后文字在约 1.6 秒内增长完毕。此前 BX1 只要求“完成前有 delta”，会放过这种体验，应以用户可见首字和正文增长过程为判定。DeepSeek [官方 Thinking Mode 文档](https://api-docs.deepseek.com/guides/thinking_mode/)确认 thinking 默认开启，并可在 Chat Completions 请求中设 `thinking: { type: "disabled" }`。

本轮只在 Bibo 模型代理关闭默认 thinking，使普通对话直接生成可见正文；Harness、容器、Worker SSE 和浏览器继续逐增量传递，不合成打字机动画，也不增加第二次模型调用。保留未来显式“深度思考”模式的设计空间，但不能为修复当前首字延迟引入另一套会话状态或隐藏推理文本冒充回答。此选择可能降低复杂推理任务的质量；当前首发服务以即时日常协作为默认模式，复杂任务模式需要另行设计用户选择与质量验收。

修后黄金验收：同一真实账号在 `app.bibo.bot` 发送较长请求；模型代理的正式 `content` 在模型完成前持续到达，浏览器中的 Bibo 消息在“正在保存”之前多次增长；之后 R2 提交、刷新恢复和继续提问仍成立。记录首个正文增量、最后一个正文增量与完成时间；短回答或仅在完成前挤出一个 delta 不算充分证据。取消、限额与账号隔离沿用现有合同。

## 2026-09-25：本地前端开发与 Markdown 排版

用户指出 Markdown 的阅读层次不足，并要求前端有一条 `pnpm` 一键启动的本地调试链路。前端默认开发模式使用 Vite 和开发时内存 API：自动提供预览账号、覆盖标题/列表/引用/代码/表格的会话样本，并按 SSE 分块发送回答。它复用正式页面的 React 组件、Zustand 状态和事件解析路径，改动后可热更新，不调用 Cloudflare 或模型。真实 Worker 联调仍使用单独的代理模式；开发模拟不能代替线上保存与容器恢复验收。

消息组件库对生成中和已保存的助手内容使用同一个 Markdown renderer，renderer 类型和配置保持模块级稳定。排版层级、引用、代码和表格样式由 `@nextclaw/bibo-ui` 的主题统一负责；禁用原始 HTML，仅放行安全外链，不加载模型给出的远程图片。验收覆盖桌面与手机宽度、流式过程中部分 Markdown 的即时展示、保存后的语义结构和刷新恢复。
