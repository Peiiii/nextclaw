# v0.26.58 提供商模型目录发现与选择

## 迭代完成说明

- 支持目录发现的提供商设置页新增“获取模型列表”操作，用户可在保存前使用当前表单里的 API Base、API Key 与请求头获取模型；获取结果进入候选面板，不会自动同步，支持勾选若干模型“添加所选”，小目录也可“全部添加”。已知不提供目录接口的内建提供商不显示该操作，仍保留手工添加模型。
- 模型发现由 Core 统一负责协议与响应解析：OpenAI 兼容提供商读取 `/models`，Anthropic 读取并分页遍历 `/v1/models`，OpenCode Zen 按官方目录元数据排除已弃用和存在输入费用的模型，并进行五分钟进程内缓存。
- Core 在目录进入缓存和前端前统一筛选聊天 LLM：显式输出模态只接受纯文本输出，元数据缺失时按模型类型与稳定 ID 族排除图像、视频、语音、Embedding、Rerank 与 Moderation；图像输入、文本输出的视觉理解 LLM 不受影响。
- Server 只暴露一条 `POST /api/providers/:providerId/models/discover` 主链路；它复用连接测试的草稿配置解析，不持久化 API Key、API Base、请求头或获取结果。
- 前端保留本地模型的原有顺序和配置，仅追加远端新 ID 并去重。远端失败时展示可行动错误，用户仍可继续手动添加与保存。
- Kernel 启动后立即刷新已启用提供商的模型目录，此后每 12 小时刷新一次进程内快照；自动刷新只更新厂商事实，不会静默新增、删除、重排或切换用户模型。
- 聊天模型选择器收起时不显示提醒；只有展开且存在候选时，才显示低优先级入口。候选默认显示“全部”，同时按提供商分段并支持提供商筛选；“添加”只补全配置，不切换当前会话模型。
- 进入具体提供商详情页时会自动读取该提供商的后台目录快照；后台快照与显式获取复用同一选择面板，支持添加所选与全部添加。操作只进入表单草稿，用户点击“保存”后才持久化；未保存连接参数仍通过“获取模型列表”读取对应目录。
- 已配置模型新增按需展开的批量删除模式，支持全选、取消全选、删除所选与取消；删除只修改当前表单草稿，不绕过页面统一保存入口。
- 设计依据：模型列表属于提供商能力发现，而不是静态 UI 常量；协议差异由 Core owner 收敛，Server 负责草稿配置边界，前端只负责触发、合并与反馈，从而避免为每个厂商复制一套交互和请求逻辑。
- 合同边界：获取模型就是获取目录，不发送测试消息，也不声称目录中的每个模型都通过了实时调用验证；账号权限、限额与服务健康属于独立的调用链路。
- 自动刷新、聊天选择器与提供商详情页的 owner 和交互边界见 [Provider 模型目录自动刷新与选择器发现设计](../../designs/2026-08-07-provider-model-catalog-refresh.design.md)。

## 用户/产品视角的验收步骤

1. 打开“设置 → 提供商”，选择一个支持目录发现的已配置或正在编辑提供商；普通 DashScope 应只显示手工“添加模型”，不显示“获取模型列表”。
2. 可先修改 API Base、API Key 或自定义请求头，但不要保存。
3. 点击模型列表区域的“获取模型列表”，等待候选面板自动展开。
4. 确认获取后原有模型、保存按钮和后端配置都不变化；勾选若干候选后点击“添加所选”，或按需“全部添加”。
5. 确认只有明确添加的模型进入列表末尾，重复 ID 不会出现两次，并且“保存”按钮变为可用；刷新页面前，后端配置仍是旧值，只有主动点击“保存”才会持久化。
6. 将 API Base 临时改为不可达地址后再次获取，确认出现明确错误且仍可手动添加模型。
7. 在全新安装环境中无需填写 OpenCode API Key；启动完成后打开聊天模型选择器，确认收起时无提醒、展开后有“全部”和对应提供商筛选，长模型名不会覆盖“添加”按钮。
8. 添加任一候选，确认当前会话模型不变、选择器保持打开，候选在配置刷新后消失。
9. 进入“设置 → 提供商 → OpenCode Zen Free Trial”，确认页面自动提示对应候选；勾选部分后“添加所选”或“全部添加”，确认“保存”按钮变为可用，刷新页面前后端配置仍未被自动改写。

## 纠偏复盘与规则落地

- 纠偏来源：用户明确指出当前密钥不是 Coding Plan，并提出“不支持就不要提供操作”。此前把 Coding Plan `/models` 的 200 外推成密钥类型判断，属于跨操作、跨端点推断。
- 失误模式：把“同品牌、兼容 OpenAI、另一个端点成功”错误等同于“目标目录端点受支持”。现有代码调查规则要求走完整链路，但没有明确约束外部协议必须按具体操作逐项取证，因此没有及时拦住这类端点能力外推。
- 方法级修复：在 `code-investigation-workflow` skill 增加通用规则——端点 A、SDK 兼容声明或共享 Base URL 都不能证明端点 B；未证实能力不得生成 UI 操作，必须由 capability 合同控制。该规则会在今后研究外部源码、协议和厂商兼容性时自动触发，而不是只记住 DashScope 这一例。
- 产品与代码修复：`ProviderSpec.modelDiscovery=false` 成为 Core 的明确禁用合同；Kernel、自动刷新、Server 元数据和设置页统一消费该事实。测试从网络 owner、调度 owner、API 投影到 React 展示逐层覆盖。没有新增静态治理脚本，因为外部厂商能力会变化，静态扫描无法可靠判断；正确的自动约束是 capability 合同与回归测试。
