## 3. 最小循环

```text
读取目标 + 最佳版本 + 上轮结论 + 剩余预算
  → 观察真实页面
  → 更新问题队列，选择一个最高价值问题
  → 写出假设、成功/失败条件与最小实验范围
  → 检查预算，决定是否进入实现
  → 在隔离预览制作一个候选
  → 定向验证 + 与最佳版本对照
  → 保留 / 返工一次 / 放弃
  → 更新简短记录
  → 检查继续条件；继续或交付最佳结果
```

每轮围绕一个假设。实现可以同时涉及必要的文案、样式和交互，但不得夹带与假设无关的重构或美化。

同一个 Agent 依次承担观察、实现、验收视角。不得把这些视角包装成独立评委或真实用户反馈。

## 4. 各阶段的进入与退出条件

| 阶段 | 必须得到的结果 | 不满足时 |
| --- | --- | --- |
| 观察 | 具体画面或操作路径、可定位的问题证据 | 不凭“还不够高级”启动开发 |
| 选题 | 说明问题如何影响用户；判断收益是否值得验证成本 | 删除低价值问题或结束本批 |
| 假设 | 一句因果判断、最小改动范围、可观察成功/失败条件 | 不写代码；最多一次补充分析 |
| 实现 | 一个可运行候选和明确差异 | 超预算或持续扩大范围则保存状态并停止实验 |
| 验证 | 行为证据、前后对照、回归检查、主观判断及其不确定性 | 不晋升最佳版本 |
| 决策 | 保留、返工或放弃，附理由 | 无明确改善默认保留旧最佳版本 |

候选晋升必须同时满足：目标问题得到具体改善；没有损害已认可的优点；关键行为正常；新增复杂度与收益相称。不能靠提高自评分或降低原验收标准晋升。

主观审美由 Agent 给出有依据的暂定判断，最终偏好由用户 Review；功能、状态与资源正确性由 Agent 自验。无真实访客证据时，不声称转化率、理解率或用户喜爱程度提升。

## 5. Token 与成本约束

### 预算模式

1. 有可用硬预算执行器：使用其支持的计量单位与中止机制，并记录统计口径；不得承诺比工具能力更强的上限。
2. 仅有消耗统计：采用软预算，明确统计范围、延迟与可能超额；到检查点主动停止。
3. 无可靠计量：使用单轮校准或用户指定的轮数/时间边界，报告 Token 不可测，不估造精确账单。

账户周额度百分比不能直接换算成固定 Token。模型用量、缓存输入、输出及工具成本可能使用不同口径；额度、Token 和费用不得混称。

有绝对 Token 总预算 B 时，默认仅用 80% 探索，20% 留给验证、恢复和交付。普通轮次初始上限为 B 的 20%；这只是软分配策略，不能覆盖全局硬上限。任何候选开始前都要预留完成验证与安全恢复的余量，不能先耗尽预算再要求追加。

只在批次开始、进入候选实现前、轮末检查消耗；统计有明显延迟时保守处理。计量成本也计入预算，不为省 Token 建立高频统计流程。生图等独立费用在使用前另做价值判断，默认关闭，确有必要才使用。

### 抑制浪费的默认动作

- 单 Agent，不创建并行审查组。只有用户明确允许且预期总成本净节省时才考虑一个有边界的子 Agent；多 Agent 成本计入同一总预算，不能另开预算池。
- 已读且未变的规则、代码和材料不重复全文读取；按路径和差异定向搜索，限制输出大小。
- 每轮最多实现一个候选。路径明确时不机械生成多套方案。
- DOM/状态用于行为检查，截图用于视觉判断；按受影响布局选择代表性尺寸，稳定后统一检查必要回归。
- 优先本地预览，失败候选不反复云端发布；不引入与本轮无关的依赖、框架或基础设施。
- 使用事件或有界等待，禁止无变化的密集轮询；进度只说新发现和下一步。
- 同一假设最多返工一次。失败理由入记录，后续无新证据不得换个名称重试相同方案。
- 记录几行结论即可；不生成长篇自评、逐轮演示文稿或多份重复日志。

## 7. 继续、停止与交付

仅当存在有证据的高价值问题、存在未被否定的新假设、预算足够闭合一轮时继续。

出现任一条件即停止探索：用户叫停；达到约定上限；剩余预算不足以完成下一轮及验收；连续两轮无可保留改善；找不到值得验证的问题；遇到无法独立解决的外部阻塞；需要改变用户已认可的核心方向。

停止探索后，使用预留预算恢复稳定状态并交付。不得为了达到轮数制造改动，不以“永远还能更好”为理由持续运行。停止原因是预算或阻塞时，不宣称质量目标已经完成。

交付一次给齐：最佳版本入口、保留的关键差异、放弃的尝试与原因、实际验证范围、未解决问题、实测成本或计量缺口、停止原因。没有改善时直接交还原最佳版本。

实验验证与正式发布分开。达到交付条件后按本会话有效授权及仓库交付流程执行；不得把每轮实验直接覆盖线上。纯文档设计不涉及新产品行为，因此本次不新增产品验收 UI、CLI、changeset 或发布。

## 8. 对 Loop 机制的复盘

首批 Pilot 同时验证网站结果和 Loop 方法。批次结束时只回答以下问题，不另写长篇报告：

| 观察项 | 判定证据 |
| --- | --- |
| 质量收益 | 至少一个候选解决了预先记录的问题，并通过前后对照晋升；没有改善也如实成立 |
| 选择效率 | 实际实现的候选都来自有证据的问题，没有为凑轮数制造方案 |
| 成本控制 | 在约定检查点记录用量或计量缺口，没有因反复读取、重复验证或多 Agent 明显浪费 |
| 连续性 | 中断后能由本文件恢复基准、已耗预算、最近决策与下一步，没有重复实验 |
| 判断可信度 | 主观审美、功能事实和真实用户证据明确分开，没有把 Agent 偏好包装成用户结论 |
| 治理负担 | 记录足以恢复任务，但维护成本没有超过实验本身；若超过，下一版应删减字段或频率 |

复盘只允许基于本批真实记录调整全局 `.loop.md` 规则。单次感觉、未发生的风险或为了显得完备而增加的字段，不上升为通用机制。
