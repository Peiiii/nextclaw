# AI 驱动开发体系首批落地

## 迭代完成说明

本轮把“AI 自动寻找最小但完整结果、按实际不确定性分配思考投入、只在有效反馈后受控改进规则，并约束上下文与 Token 成本”的讨论落入现有开发生命周期。

具体完成：

- Task Understanding 条件形成最小完整结果、必要链路、上下边界和完成判定；
- Design 条件加载自适应方案思考，不固定要求多方案；
- lifecycle 完成门拒绝把仍可关闭的必要缺口包装成后续优化；
- Retrospective 把重复、系统性、高影响反馈路由到开发体系演进判断；
- 指令治理补充开发体系演进、规则资产生命周期、上下文与 Token 治理、模型能力补丁标识和 Skill 拓扑创建门；
- 形成可跨会话召回的架构设计与讨论来源文档。

实现没有新增第二套生命周期、独立平台或 Skill，也没有扩大 `AGENTS.md` 常驻上下文。首次尝试新增独立演进 Skill 时，渐进加载检查识别出依赖环和体积超限；随后把它下沉为现有规则治理 owner 的条件 Reference，并把只在正式沉淀或 Skill 拓扑变化时需要的内容移出入口。

## 用户/产品视角的验收步骤

1. 给出边界模糊的开发目标，Task Understanding 应先形成最小完整结果、必要链路和非目标，而不是按最窄字面任务开工。
2. 面对简单、可逆、惯例明确的方案应直接收敛；存在真实不确定性时，Design 应选择调查、实验、最强替代方案比较或失败预演中最匹配的一项。
3. 明确提出“优化 AI 驱动开发体系”时，应由指令治理入口加载开发体系演进闭环；只有涉及一级架构、职责边界或新机制时才继续读取架构文档。
4. 模型或 runtime 变化时，可搜索 `model-capability-patch` 标识并按代表性任务做移除复核，而不是让补丁永久累积。
