# Mini APP 发现、安装与管理体验修正计划

## 1. 背景与目标

本计划处理的是一条完整用户链路，而不是一次局部视觉换肤：

> 用户发现一个应用，判断它是否适合自己，发起安装后可以立即继续浏览或离开市场，并在任何相关界面看到真实进度；安装完成后可以打开、停用、切换版本和卸载，失败时知道发生了什么以及如何恢复。

当前实现已经打通了 Registry、组合包、Panel APP 和 Service APP 的技术主链，但产品体验仍处于可运行原型阶段。用户已经直接遇到图标破损、回滚无反馈、内置应用不能卸载、安装阻塞和公开站信息贫乏等问题，说明当前版本尚未达到面向普通用户的发布质量。

本轮目标：

1. 修复已证实的功能缺陷，避免错误结果和无反馈操作。
2. 把安装、更新、回滚和卸载变成可观察的后台操作。
3. 让本机应用市场与应用库形成连续、克制、信息优先的产品体验。
4. 让 `apps.nextclaw.io` 从开发者演示页变成用户可以发现和判断应用的公开目录。
5. 在真实桌面和移动视口中完成任务级、状态级和视觉级验证。

本轮不会执行公开部署、Registry 发布、NPM 发布、桌面发布、Git 提交或推送。代码与页面只做到本地可验证、可进入后续发布评审的状态。

## 2. 事实证据与问题分级

### 2.1 P0：会产生错误结果或破坏用户信任

| 问题 | 已确认的证据 | 根因 | 用户影响 |
| --- | --- | --- | --- |
| 组合包内四个 Panel APP 图标破损 | 用户截图显示待办、收藏、笔记、日历均为浏览器破图；manifest 实际使用 `✓ / ◇ / ✎ / □` 文本图标 | package 来源绕过统一图标解析，错误地把文本字符拼成资源 URL | 用户第一眼看到产品损坏，无法把它理解为可用应用 |
| 安装同步阻塞且可能出现“客户端失败、服务端仍继续” | UI 用单个 React Query mutation 等待完整下载、解包、校验、复制和注册；SDK 默认 15 秒超时 | HTTP 请求既承担启动命令，又承担完整作业生命周期 | 市场被占用；慢网络下可能超时，但后台安装仍完成，用户重试后产生不确定性 |
| “内置”应用没有卸载入口 | UI 明确以 `!builtIn` 隐藏卸载；底层卸载实际可执行 | 把“随 NextClaw 提供”错误地解释成“用户无权移除” | 用户不能管理自己的应用空间 |
| 直接开放卸载仍会在重启后复活 | built-in bootstrap 在每次新进程首次读取时补装缺失包 | 没有持久化“用户已移除内置应用”的意图 | 表面卸载成功，重启后被系统反向恢复 |
| 回滚操作没有可观察结果 | 菜单点击后仅等待同一 mutation；无进行中版本、完成提示或失败就地反馈 | 生命周期没有操作实体，UI 只能显示笼统“处理中” | 用户不知道是否点击成功、当前版本是否已切换，也不知道能否离开 |

### 2.2 P1：主任务可以完成，但体验明显不成熟

| 问题 | 现状 | 需要达到的结果 |
| --- | --- | --- |
| 应用没有稳定视觉身份 | 本机市场和应用库统一使用 `AppWindow`，公开站没有图标 | 优先显示真实应用图标；缺失时使用稳定、可辨识的字母/色彩回退，不出现破图 |
| 市场信息架构围绕卡片和标签，而非用户判断 | 大边框卡片、技术标签、外链详情和安装按钮彼此割裂 | 一眼看到名称、用途、发布者、版本、安装状态；详情在当前市场内完成判断 |
| 安装进度被困在弹窗 | 关闭市场后没有任何安装中的对象 | 市场卡片与应用库同时显示同一后台操作；离开市场后仍可观察 |
| 错误反馈位置不稳定 | 错误只出现在市场顶部或应用库顶部，滚动后可能不可见 | 失败归属到具体应用，保留重试动作，并以 toast 提供跨界面完成通知 |
| 应用库视觉层级像设置列表 | 渐变说明块、重边框卡片、组件小格子叠加，空间利用率低 | 内容优先、低装饰、清晰主操作、组件可直接打开，更多操作保持可发现 |
| 详情链路要求跳出 NextClaw | “查看详情”打开公开浏览器；安全提示又要求先看详情 | 市场内提供用途、组成、权限、发布者和版本；公开页作为可分享的延伸 |

### 2.3 P1：`apps.nextclaw.io` 公开内容不成立

1. 首屏标题解释“轻量、可分发、可本地运行的应用形态”，正文继续讲 `web coding / napp publish / runtime`。它回答了团队如何构建，而没有回答用户能得到什么。
2. 安装命令占据首屏最强视觉区域，普通用户尚未理解应用价值就先被要求进入命令行。
3. “官方精选”只有等权卡片，没有图标、截图、适用对象、信任信号或明确动作。
4. 中文页面混用大量英文摘要、标签和栏目名，语言不连续。
5. 目录筛选要求用户手输 tag，没有可发现的分类；加载、失败和空状态也不完整。
6. 详情页把 README 作为原始等宽文本展示，权限和版本以内部字段形式罗列，缺乏可读层级。
7. 发布者页只有 ID 与卡片列表，不足以建立可信发布者身份。
8. Registry 握手异常或请求悬挂时，目录和详情会长期停留在骨架屏；失败后也缺少原位重试。

### 2.4 P2：需要补齐但不阻断本轮主链

- 安装任务取消：下载阶段可安全取消，进入提交阶段后需要事务边界。本轮先保证不阻塞、可观察、可重试，不引入不完整取消语义。
- 跨进程恢复精确进度：本轮操作状态由 kernel owner 管理，进程重启时未完成操作标记为中断并允许重试；不尝试从任意文件复制步骤中间续传。
- 评分、评论、下载量和排行榜：当前没有可信数据源，不伪造社交证明。
- 网站一键唤起桌面并安装：尚无操作系统级 deep-link 合同，本轮保留复制命令与进入 NextClaw 应用市场的真实说明，不制造无效按钮。

## 3. 方案比较与选择

### 方案 A：只做视觉润色与 UI 乐观态

保留同步 API，在前端立即关闭弹窗、显示旋转图标，并调整颜色、圆角、阴影。

- 优点：改动小、见效快。
- 缺点：15 秒超时和服务端继续执行的问题仍存在；刷新或离开后状态丢失；回滚与卸载仍没有统一语义。
- 结论：不采用。它只能掩盖结构问题。

### 方案 B：长连接流式安装

用一个 SSE 或流式 HTTP 请求承载安装阶段与下载进度。

- 优点：进度实时，服务端改动相对集中。
- 缺点：请求断开、页面刷新和跨界面观察都需要额外恢复协议；“连接”容易再次成为操作状态 owner。
- 结论：不作为第一版 owner。未来可把 SSE 作为操作状态的传输优化。

### 方案 C：kernel 拥有后台操作实体，客户端轮询状态

写操作先创建 operation 并立即返回；kernel 在后台串行执行真实生命周期，记录阶段、目标、时间、结果与错误；市场和应用库读取同一 operation 列表。

- 优点：命令与执行解耦；离开弹窗仍可观察；安装、更新、回滚和卸载共享同一模型；轮询简单可靠。
- 缺点：需要新增 API 合同、状态模型和并发约束。
- 结论：采用。第一版以短轮询作为传输，后续可以不改变 owner 地升级为事件推送。

## 4. 用户链路与信息架构

### 4.1 本机应用市场

列表页：

- 标题改为“添加应用”，副标题说明应用会进入当前 NextClaw，并可以随时停用或卸载。
- 搜索是主筛选；精选、个人、效率等分类仅在真实数据存在时出现。
- 应用行显示真实图标、名称、本地化用途、已验证发布者、版本和当前状态。
- 点击应用主体进入同一弹窗内的详情，不跳出当前任务。
- 安装按钮只启动 operation，立即进入“准备中 / 下载中 / 校验中 / 安装中”状态，市场仍可滚动、搜索和关闭。

详情页：

- 返回按钮、图标、名称、用途、发布者与版本。
- “它会添加什么”：按 Panel 与 Service 数量说明，不暴露 component path。
- “需要访问什么”：把文档目录、网络域、本机服务能力转成用户可读文案。
- 主按钮显示安装状态；失败后显示原因摘要和“重试”。
- 公开详情页作为次级可分享链接。

### 4.2 本机应用库

- 顶部保留应用/Panel APP/Service APP 三个现有视图，但应用库自身不再增加大面积装饰性说明块。
- 正在安装且尚未进入 registry 的应用，以临时应用行出现。
- 已安装应用显示图标、启用状态、活动版本、是否随 NextClaw 提供、是否包含本地服务。
- 主操作为“启用 / 停用”；组件入口保持可直接打开。
- 更新、版本切换和卸载位于统一更多菜单。
- 版本切换时卡片显示“正在切换到 vX”；成功后版本号更新并出现一次完成通知；失败则在卡片内保留重试入口。
- 所有应用均可卸载。随 NextClaw 提供的应用卸载后记录用户意图，重启不再自动补装；从市场显式重装会清除该记录。
- 卸载默认保留个人数据，并在确认文案中明确说明。

### 4.3 公开 Apps 网站

首页：

1. 顶部导航：Apps、开发者文档、GitHub；不设置无内容导航。
2. 首屏价值：说明用户可以给自己的 NextClaw 添加新的空间和服务；主动作是浏览应用，开发者入口为次级。
3. 精选应用：突出一个主推荐和若干紧凑应用卡片；安装命令不再占据首屏。
4. 信任说明：本机安装、安装前查看访问范围、可停用与卸载。只陈述真实能力。
5. 完整目录入口。

目录页：

- 搜索、可点击分类、结果数量、加载/失败/空状态。
- 卡片显示图标、本地化摘要、发布者、版本和少量有意义标签。
- 卡片主体进入详情；复制安装命令是次级动作。

详情页：

- 应用视觉身份、用途、版本、发布者、更新日期。
- 主动作复制安装命令，并明确也可以在 NextClaw 内的“应用 → 添加应用”中搜索名称。
- 以用户语言解释权限、数据位置和本地服务。
- README 使用 Markdown 排版，不再原样显示源码文本。
- 版本记录和开发者链接退到次要区域。

## 5. 后台操作状态模型

### 5.1 操作类型

`install | update | rollback | uninstall`

`enable / disable` 保持短请求，因为它们不包含下载、解包和长事务；但仍提供即时 pending、success 和 error 反馈。

### 5.2 公共状态

| 状态 | 含义 | UI |
| --- | --- | --- |
| `queued` | 已接受，等待同一应用的前序操作完成 | 准备中 |
| `resolving` | 解析来源与目标版本 | 正在检查应用 |
| `downloading` | 拉取远端 bundle | 正在下载 |
| `verifying` | 校验摘要、manifest、兼容性与冲突 | 正在校验 |
| `installing` | 解包、构建、复制或切换活动版本 | 正在安装 / 正在切换 |
| `finalizing` | 更新 registry、运行时与查询投影 | 即将完成 |
| `succeeded` | 操作完成 | 短暂完成态，然后进入正常应用状态 |
| `failed` | 操作未完成或已回滚 | 错误摘要、重试 |
| `interrupted` | 进程退出时操作未到终态 | 安装被中断、重试 |

### 5.3 并发与幂等

- 同一 appId 同时只允许一个写操作。
- 对同一来源重复点击安装时返回已有 active operation，不创建第二个任务。
- 不同应用允许有限并发；文件 registry 的写入仍由既有原子 mutation queue 串行化。
- 终态操作保留有限数量和时间，供 UI 完成通知与问题诊断，不无限增长。

### 5.4 失败恢复

- 下载或校验失败：不写 registry，删除临时目录，可直接重试。
- 安装复制完成但 registry 写入失败：沿用现有 immutable install 回滚清理。
- 更新或回滚兼容性检查失败：恢复前一活动版本，并把恢复结果写入 operation error。
- 卸载失败：沿用 staged rename 恢复；built-in suppression 在执行前写入，失败时同步撤销，避免进程中断后应用被意外补装。
- 进程启动：把未到终态的 operation 标记为 `interrupted`；以 registry 为准恢复仍被引用的 `.uninstalling-*` 目录，并清除无主 `.staging-*` 与 `.uninstalling-*` 目录。
- UI 请求超时不再代表安装失败，因为启动 operation 的请求只创建任务并立即返回。

## 6. 数据与 owner

```text
Marketplace UI / App Library
          │ start + poll
          ▼
AppPackagesRoutesController
          │
          ▼
AppPackageManager ── owns operation state, concurrency, built-in semantics
          │
          ▼
AppInstallationService ── owns download/extract/install/registry transaction
          │
          ├── AppRegistryService: installed versions + built-in suppression
          └── Runtime hooks: panel/service deactivate, validate, cleanup
```

约束：

- operation 只描述产品级生命周期，不复制安装逻辑。
- AppInstallationService 通过进度回调暴露事实阶段，不依赖 UI 文案。
- built-in suppression 是持久化用户意图，必须和 installed app record 分开；卸载后 record 消失，意图仍保留。
- 网站只消费公开 Registry 数据，不拥有安装状态。

## 8. 验收标准

### 功能

- 四个内置 Panel APP 在列表、应用卡片和打开后均不出现破图。
- 点击安装请求被接受后立即出现操作状态，市场仍可搜索、滚动、查看其他应用和关闭。
- 关闭市场后，应用库仍显示同一安装进度；完成后无需手动刷新即可出现应用。
- 重复点击同一应用不会创建重复安装。
- 点击切换版本后立即显示目标版本；成功后活动版本与 Panel/Service 投影一致，失败后保持原版本并可重试。
- 内置应用存在卸载入口；卸载后重建 kernel 仍不会自动恢复；显式重装后恢复正常 bootstrap 语义。
- 安装、回滚和卸载失败均归属到具体应用，不只显示全局错误。

### 交互与可访问性

- 所有动作使用 button，公开详情与开发者链接使用真实 link。
- icon-only 按钮有可访问名称和 tooltip/title；键盘可以完成搜索、查看详情、安装、更多菜单和确认卸载。
- hover、focus、pending、disabled、success、error 和 empty 状态可区分，不只靠颜色或灰度。
- 弹窗只有一个主滚动区；窄屏不横向溢出，主任务在首屏可见。

### 视觉与内容

- 本机市场不再由大边框卡片和重复标签占据主要空间，应用身份和主动作优先。
- 公开站首屏不出现安装命令作为主视觉，不再用构建术语解释用户价值。
- 中文界面不混入可本地化的英文摘要和状态；技术字段只出现在确有需要的详情中。
- 公开首页、目录和详情页均使用真实 Registry 数据完成截图，不用空态或 mock 冒充成品。
- Registry 不可用时在有限时间内进入可理解的失败态，并可原位重试；成功态另用固定边界数据验证，避免外部网络波动掩盖 UI 回归。

### 工程

- kernel、app-runtime、server、client-sdk、UI、apps web 和 marketplace worker 的相关测试通过。
- 所有触达包的 `tsc` 和定向 lint 通过。
- 未修改、覆盖或提交工作区中与本任务无关的既有改动。

## 9. 发布门槛

本地验证通过只代表“具备发布候选质量”，不代表已经获得公开发布授权。进入任何公开部署或发布前，必须单独确认：

1. 公开 Registry 条目和应用资产是否应该继续可见。
2. worker API 与网站是否一起部署，避免 `iconUrl` 等合同半更新。
3. 桌面/服务端最低兼容版本和迁移行为。
4. 面向用户的版本说明、回滚方案和真实安装冒烟。

## 10. 产品级视觉验收补充

用户补充了更高的完成门槛：不能把“功能可用”当作体验完成，应用市场必须建立独立视觉身份与可重复执行的质量评估。本节覆盖在第 8 节之上；任一硬门失败，都不得声称达到发布候选质量。

### 10.1 现状基线

上一轮实现的主要问题不是故障，而是成品感不足：公开目录只有 `iconUrl`，没有封面或展示图；本机市场以紧凑文本行承载发现任务；公开卡片把安装命令、标签和详情入口并列，视觉上更像包管理器；`Hello Notes` 与 `Workspace Glance` 甚至使用同一图标。按以下量表，其基线为 **62/100**，属于“可靠可用”，不属于高品质应用市场。

### 10.2 对标原则

- Apple：应用身份跨尺寸一致，核心概念简单、可辨识；内容加载尽快出现可理解占位，耗时任务不阻断其它操作。
- ChatGPT：名称、用途与开始方式在进入前清楚可见；默认界面降低选择与操作负担。
- Claude：层级克制，正文与说明保持可读，不用装饰性容器淹没内容。

这不是复制三者的皮肤。验收只采用能从 NextClaw 真实页面观察的原则：视觉身份、层级、反馈、可预期性、响应式和内容可信度。

### 10.3 视觉资产合同

每个面向用户发布的应用至少包含：

1. 一个可在 44–80px 保持辨识的矢量图标；禁止多个应用复用同一图形。
2. 一张 16:10 封面，建议 1440×900 WebP/AVIF，单文件不超过 512 KiB；不得包含生成错误文字、水印、第三方品牌或假 UI。
3. 一个六位十六进制主题色，只用于封面降级、焦点和轻量身份提示，不接管产品主题。
4. 封面通过 `marketplace.json.visuals` 声明，由 Registry 作为独立文件分发；`.napp` 安装包必须排除 `marketplace-assets`，避免展示素材增加安装体积。

首批艺术方向为“安静的个人数字花园”：暖象牙背景、低饱和点色、纸张/陶瓷/磨砂玻璃等触感材质、单一清晰主体。个人空间表现四类上下文围绕中央花园；Hello Notes 表现单一授权文件夹及受控概览；Workspace Glance 表现有明确边界的工作空间与局部扫描。

### 10.4 100 分体验量表

| 维度 | 分值 | 可观察标准 |
| --- | ---: | --- |
| 视觉身份与内容资产 | 20 | 所有产品应用有独立图标和封面；缩略图、详情与本机市场身份一致；失败时降级仍稳定 |
| 信息层级与发现效率 | 20 | 3 秒内可识别应用名称、用途、发布者和主动作；封面优先，技术字段不抢占首屏 |
| 操作与状态反馈 | 20 | 安装、更新、回退、卸载均有即时反馈、后台进度、成功/失败归属和恢复动作 |
| 一致性与精细度 | 15 | 间距、圆角、按钮、图标、动效和文案遵循同一系统，无假按钮、重复入口或混杂语言 |
| 响应式与可访问性 | 15 | 桌面/窄屏/390px 无溢出；键盘、焦点、语义、对比度、减少动效和图片替代文本成立 |
| 信任与性能 | 10 | 权限/发布者/版本清楚；封面懒加载、体积受控、不进入安装包；加载与离线不会无限等待 |

通过规则：总分至少 **90/100**，且六个维度均不得低于该维度分值的 80%；另有七项硬门：无破图、无阻塞安装、无无效操作、无不可恢复错误、无移动端横向溢出、无控制台运行时错误、所有产品应用均有独立图标与封面。视觉偏好仍需用户最终确认，但 AI 必须先完成上述客观验收，不能把主观确认当作工程正确性的替代。

### 10.5 本轮实现选择

比较三种做法：

- 网页按 slug 内置图片映射：改动最小，但第三方应用无法复用，网站成为第二个元数据 owner；不采用。
- 把封面放进 manifest/assets 并随安装包下载：链路简单，但增加每次安装和更新体积，混淆运行时资产与市场展示资产；不采用。
- `marketplace.json` 声明视觉，发布时独立上传、Registry 投影 URL：数据 owner 唯一，本机市场和官网共享合同，安装包保持轻量；采用。

四个公开目录应用的生成素材由内置生图能力生成并人工检查构图、文字伪影、系列一致性与小尺寸辨识；最终素材落在各应用的 `marketplace-assets/cover.webp`。这次仍不发布线上 Registry，部署与重发应用需单独授权。

### 10.6 结构与尺寸契约

用户在真实使用中补充发现：一级应用类型切换时 tab 宽度会变化；添加应用弹窗高度和单个应用媒体比例也缺乏稳定规则。代码调查确认这不是单个 CSS 数值问题，而是 owner 错位：三个条件渲染的子面板各自接收并渲染同一份 `headerContent`，但页头分别采用横向、纵向和可滚动布局；市场弹窗只有 `max-height`，目录卡片与详情共用一个 8:5 封面比例。

本轮冻结以下结构：

1. `AppsPanel` 是一级导航唯一 owner；tablist 在三类内容切换时保持同一 DOM。子面板只拥有等高二级工具栏和业务内容，不再接收一级 `headerContent`。
2. 一级 tablist 宽度为 `min(100%, 390px)`，三列等分；触发器允许文本截断，不以标签长度改变整体宽度。
3. 共享 Tabs 使用 `tablist / tab / aria-selected` 语义，并支持左右方向键、Home 和 End。
4. 桌面市场使用 `min(920px, 100vw - 48px)` × `min(680px, 100dvh - 64px)` 的稳定窗口，header、唯一滚动区和 trust footer 分离；列表与详情切换不改变外框。
5. 目录封面与详情封面统一为 16:9。目录在宽桌面显示三列、普通桌面两列、移动端单列；卡片主体进入详情，卡片底部只保留一个安装/更新主动作，不重复提供“查看详情”按钮。
6. 小于 `sm` 时市场明确切换为 `100vw × 100dvh` 的全屏应用页，取消圆角和外边框，并使用 `env(safe-area-inset-top/bottom)` 保护系统安全区，不维持“接近全屏的弹窗”中间态。
7. 详情首屏在桌面采用 16:9 媒体与应用身份卡并排，在移动端上下排列；媒体不再为了与身份卡等高而改变裁切比例。
8. 市场目录展示拆入 `AppMarketplaceCatalog`，弹窗只拥有搜索、分类、选中应用和列表/详情路由；操作查找归 `app-marketplace-operation` 唯一 owner。

### 10.7 实测验收记录

2026-08-12 在当前本机源码热更新实例完成只读验证，未重启宿主、未安装/卸载应用、未发布 Registry：

- 1280×720：三类页面下一级 tablist 均为 `387×32px`，三个 tab 均为约 `127.66×28px`，位置完全一致。
- 1280×720：市场列表与详情外框均为 `920×656px`，外框 `scrollWidth === clientWidth`；目录封面为 `280×157.5px`，严格 16:9。
- 390×844：市场外框为 `390×844px` 全屏页，页面与弹窗均无横向溢出；目录封面为 `356×200.25px`，详情封面为 `350×196.875px`，均为 16:9。
- 每张目录卡片只剩两个可操作目标：可点击的卡片主体和单一安装/更新 CTA；详情按钮不再重复。
- UI 定向测试覆盖 tab DOM 稳定和方向键切换；最终相关 14 个组件测试、UI TypeScript 检查、定向 ESLint 与 Apps 官网生产构建通过。
- 可维护性守卫先后发现弹窗文件增长过快、Worker 应用基础设施目录越过硬预算：前者拆出 catalog，后者把 3 个同域测试归入 `__tests__`。最终守卫为 0 error；共享 UI 等历史目录仍只有既有预算例外，本轮未继续恶化。
- 本机 `opencode/big-pickle` 通过真实 NCP 会话完成独立评审。采纳了“统一媒体比例、删除卡片重复 CTA、移动端明确全屏语义”三项；其“720p 必然裁切”和“关闭市场后状态失联”判断分别与真实像素测量、应用库共享 operation / toast / 失败重试代码证据矛盾，因此不采纳。
- 当前线上 Registry 尚未重发本轮 cover，所以本机真实宿主使用同尺寸 fallback；真实 WebP 已在本地网站预览与素材检查中验证。没有获得发布授权前不得用线上缺图掩盖为“已发布完成”。
- 隔离的真实素材网站预览在 1280×720 与 390×844 下均无横向溢出；详情封面分别为 `1180×737.5px` 与 `362×226.25px`，图片自然尺寸 `1440×900`，全部加载成功且无运行时控制台错误。
- 最终资产审计补齐了非精选但仍公开展示的 Starter Card：四个公开应用现在均有独立图标、`1440×900` WebP 封面和主题色，封面体积为 48–80KB；安装包仍排除 `marketplace-assets`。

### 10.8 真实数据源缺图复盘与预览边界

用户在本机市场继续验证时发现卡片仍显示“无封面”占位。端到端取证确认：2026-08-12 的公开 Registry 列表与详情均未返回 `coverUrl`，四个应用的公开文件清单也只有 `marketplace.json`；直接请求预期 cover blob 均为 404。此前“图片加载成功”的证据来自隔离 mock Registry，只证明了新合同和网站消费端，没有证明当前公开 Registry 已拥有素材，因此原验收结论越界。

在没有获得重新发布应用的授权前，本轮不修改线上数据。为支持本机打磨，UI 开发服务器新增显式的 `serve`-only 素材路由 `/__app-marketplace-preview/:slug.webp`：它只映射四个已知 NextClaw 官方应用，直接读取各应用 canonical `marketplace-assets/cover.webp`；生产构建不注册该路由，Registry `coverUrl` 一旦存在始终优先，第三方应用永不猜测映射。查询 key 升级为 `v2`，避免热更新后的旧缓存继续保留无封面对象；无封面降级也改为应用字母标识，不再使用容易被误解为破图的图片图标。

修复后在当前 `http://localhost:5174` 真实界面验证：个人空间、Hello Notes、Workspace Glance 三张可见封面均从 `__app-marketplace-preview` 返回 `200 image/webp`，浏览器自然尺寸均为 `1440×900`，fallback 数为 0，控制台错误为 0。Starter Card 当前被本机产品过滤，但对应开发素材端点同样返回 `200 image/webp`。这只是本机预览闭环，不可表述为线上 Registry 已修复；线上闭环的退出条件仍是用户确认视觉后授权重发四个应用并复验公开 API 与 blob。

根据 10.4 量表的当前自评为 **92/100**：视觉身份 19/20、信息架构 19/20、状态交互 19/20、一致性 14/15、响应式与可访问性 13/15、信任与性能 8/10。剩余扣分主要是尚未在公开 Registry 完成真实线上素材回放、移动设备安全区只能由 CSS/视口证据覆盖而未在实体设备检查，以及视觉审美仍需用户最终确认；这些不授权擅自发布。

## 11. 规模化目录补充与当前发布边界

本计划原先解决了应用发现、视觉资产和后台安装体验，但旧市场仍以 `pageSize=100` 拉取目录、客户端筛选，并在 Worker 使用 `COUNT + OFFSET + LIKE`。当应用数量增长后，这会静默遗漏第 101 个之后的应用，也会让数据库读取成本随页深和搜索数据量增长。规模化目录的 owner、API、索引、缓存、资产合同和验证结果已进一步冻结在 [可规模化应用市场方案设计](../designs/2026-08-13-scalable-app-marketplace.design.md)。

当前源码完成度：v2 cursor/FTS/标签读模型、Edge/ETag、内容寻址资产、官网与本机分页消费、持久化异步安装/回退/卸载均已本地验证。当前生产完成度：v2 Registry 尚未部署，官网与客户端尚未发布；本机只通过“v2 明确不受支持时回退 v1”的兼容边界恢复可用。下一发布批次必须先上线远端 migration 和 Worker，生产探测通过后再发布消费者，禁止再次让新版消费者先于提供者生效。
