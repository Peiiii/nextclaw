## 1. 目的

NextClaw 的项目治理能力不应限定在软件开发，但“通用”不能只依靠抽象名词证明。本文先把候选场景的广度拉开，再使用统一维度逐项评估，形成一组可以反复检验数据模型、页面结构和使用体验的代表性场景。

这组场景的角色是**设计与验收基准**，不是产品能力白名单：

- 一个模型只有在多个差异显著的真实链路中仍然自然，才能被视为通用。
- 场景可以有自己的类型、状态、阶段和领域词汇，但不能把专用名词写入通用治理模型。
- 代表场景既要覆盖高频高价值任务，也要覆盖会暴露模型缺陷的边界任务。
- 不因为某个场景进入候选池，就在首版实现完整行业软件。

通用治理模型暂以六个对象为基准：Project、Work Item、Run、Artifact、Attention 与 Policy。这里讨论的是用户可感知的项目治理产品，不是 Agent 内核设计。场景评估的任务是检验这六个对象及其关系是否够用，而不是提前证明它们一定正确。

## 2. 评估方法

### 2.1 先评价单个场景，再选择场景组合

本文保留两种不同结论：

1. **单场景优先级**：回答“这个场景本身有多重要”。
2. **组合覆盖价值**：回答“它加入代表场景套件后，能否带来已有场景没有覆盖的新约束”。

不能只按总分机械选择前八名。两个高分场景可能都在检验相似的软件开发链路，而一个分数略低的移动端现实世界项目，反而可能暴露完全不同的产品问题。

### 2.2 评分维度

每个维度按 1–5 分评估，5 分最高。加权总分满分为 100。

| 维度 | 权重 | 判断问题 |
| --- | ---: | --- |
| 需求强度（D） | 20% | 用户是否经常遇到，完成后是否有明确价值？ |
| AI 增益（A） | 15% | AI 是否能承担大量真实工作，而不只是记录信息？ |
| 治理必要性（G） | 20% | 用户是否需要目标、进度、证据、风险和人工介入视角？ |
| 模型压力（M） | 15% | 是否能检验分支、回退、多执行、多产物、长期运行等结构？ |
| 战略契合（S） | 15% | 是否符合 NextClaw 作为 AI 时代个人操作层的方向？ |
| 首版可验证性（F） | 10% | 能否以可观察、可演示的链路验证，而不是依赖庞大外部系统？ |
| 跨域代表性（R） | 5% | 是否能代表一类广泛任务，而不是罕见特例？ |

计算方式：

```text
总分 = D×4 + A×3 + G×4 + M×3 + S×3 + F×2 + R×1
```

分数用于统一讨论尺度，不假装是精确市场数据。后续获得真实用户研究、行为数据或可用性验证后，应更新评分依据。

### 4.2 对评分的解释

- S01 得分最高，是因为它同时具备高频、高 AI 增益、完整治理链路和首版可验证性；这不意味着通用模型应采用开发术语。
- S04 与 S05 用于检验探索式工作：工作开始时只有问题，不一定有明确路径，也可能以“不建设”或“暂不采纳”结束。
- S20 是长期 AI 项目治理不可缺少的场景。没有它，项目主页容易退化为一次性任务列表。
- S10 的单场景价值不仅在视觉创作，而在于它强迫模型支持多个候选、衍生版本、人的方向选择和非文本预览。
- S15 把项目带到移动端和现实世界，能够检验动态变化、外部交易以及“计划不等于实际执行”。
- S18、S17 的治理压力很高，但首版验证成本和风险也高，因此适合作为边界压力测试，不适合成为首批完整交付场景。

### 5.2 B 级：模型压力测试

这些场景暂不要求首版形成完整行业体验，但设计不能堵死它们：

- S02 缺陷与线上事件处理：紧急性、回滚和假设竞争。
- S06 数据分析与经营判断：数据口径、敏感数据和可重复证据。
- S11 视频与多媒体制作：复杂多模态依赖和长耗时 Run。
- S14 活动组织：现实世界依赖、截止时间和多人协作。
- S18 行政、合同与合规办理：强 Policy、材料完整性和专业复核。
- S19 客户问题闭环：外部沟通、时效和知识沉淀。

### 5.3 C 级：后续扩展观察

这些场景与前两级存在较多能力重叠，或需要未来专项能力后才能显著改善体验：

- S03 代码库持续维护
- S07 学术与文献研究
- S08 采购与方案选型
- S13 持续内容栏目运营
- S16 个人学习与能力提升

## 6. A 级场景的端到端体验假设

这里先给出足以指导后续设计的链路骨架。下一阶段再为每个场景补充界面逐步稿和异常分支。

### S01 软件功能开发

- **进入**：用户从项目主页创建“新工作”，或将一段会话沉淀为 Work Item。
- **默认详情**：目标与描述、当前阶段、最近 Run、开放 Attention、最新设计/代码/验证产物。
- **关键介入**：范围选择、高风险实现授权、验证结果确认、是否交付。
- **完成定义**：目标达到、必要验证闭合、交付动作得到授权；仅“代码已生成”不等于完成。
- **体验检验**：流程图要能表达跳过、回退和阶段产物，但不能把开发阶段写死为通用字段。

### S04 产品发现与需求定义

- **进入**：用户提交一个模糊想法、用户问题或机会信号。
- **默认详情**：问题陈述、现有证据、当前探索方向、待确认假设和研究产物。
- **关键介入**：选择研究方向、确认目标用户、决定继续原型还是停止。
- **完成定义**：形成明确决定及依据；“不建设”同样可以是成功结果。
- **体验检验**：状态不能只表达执行进度，还要表达探索、等待证据和决策终止。

### S05 开放式研究与决策

- **进入**：用户提出需要形成判断的问题，并可附带范围与判断标准。
- **默认详情**：研究问题、来源覆盖、当前结论置信度、相互冲突的证据和下一步研究建议。
- **关键介入**：缩小/扩大范围、选择深挖方向、采纳或搁置结论。
- **完成定义**：形成可追溯结论和明确决策状态，不要求产生外部执行结果。
- **体验检验**：Artifact 必须区分来源、分析和结论；活动历史应保留结论如何变化。

### S09 文章与内容发布

- **进入**：用户创建内容目标，或从产品交付结果派生发布工作。
- **默认详情**：受众与目标、当前稿件、事实核验状态、品牌规则、待选标题/配图。
- **关键介入**：选择叙事方向、审阅事实和语气、最终发布授权。
- **完成定义**：内容完成与渠道发布分开表达；可能完成稿件但暂不发布。
- **体验检验**：同一 Artifact 的版本演进要清晰，外部动作必须与内容生成解耦。

### S10 视觉设计与方案选择

- **进入**：用户提交 Brief、参考资料和必须遵守的视觉 Policy。
- **默认详情**：当前候选组、选中方向、反馈记录、最近一次生成 Run 和预览。
- **关键介入**：从候选中选择、组合方向、给出反馈、确认最终稿。
- **完成定义**：选定成果及适用规格已经形成；未选候选保留来源但退出主视线。
- **体验检验**：产物不是单一附件列表，需要候选、选中、废弃、衍生等轻量关系。

### S12 产品发布整合项目

- **进入**：从一个已经接近交付的版本或明确发布日期创建整合工作。
- **默认详情**：发布范围、子工作状态、依赖、各 Agent 当前 Run、统一阻塞项和待审批动作。
- **关键介入**：调整范围、处理跨工作依赖、批准多渠道发布或回退。
- **完成定义**：适用渠道完成发布并闭合关键验证；单个子工作完成不代表整体完成。
- **体验检验**：Project、父子 Work Item 与多次推进之间必须有清楚、稳定的关系，不能让用户靠零散页面自行拼接。

### S15 旅行规划与执行

- **进入**：用户给出时间、预算、偏好和同行约束。
- **默认详情**：候选行程、待决定事项、已确认预订、实时变化和重要凭证。
- **关键介入**：选择路线、授权预订或付款、在行程变化时确认替代方案。
- **完成定义**：计划形成、必要外部动作完成，并在执行过程中持续可用；不是生成一份攻略就结束。
- **体验检验**：手机必须能快速看到“现在做什么”和“需要我处理什么”，不能依赖桌面宽表或 hover。

### S20 持续监测与例外处理

- **进入**：用户为项目选择监测目标、频率、阈值和允许的自动动作。
- **默认详情**：总体状态、最近有效 Run、趋势、开放异常和自动处置结果；正常日志默认折叠。
- **关键介入**：调整 Policy、处理异常、批准高影响修复、把异常升级为 Work Item。
- **完成定义**：它通常没有一次性完成状态，而是运行中、暂停、退役或需要关注。
- **体验检验**：系统必须能承受大量历史 Run，并把异常信号提升为 Attention，而不是把每次运行变成一个工作项。

## 8. 对通用模型的初步约束

从二十个场景中已经可以得到一批比“支持非开发项目”更具体的约束：

1. **Work Item 统一目标与治理关系，不统一工作方法。** 类型、来源状态和阶段由来源工作流定义。
2. **流程是可选能力。** 简单工作可以没有显式阶段；探索型、循环型和持续型工作不能被迫伪装成线性流程。
3. **Run 不等于一次聊天。** 它可能来自 Agent、自动化、人或外部系统，并支持并行、周期和长耗时执行。
4. **Artifact 不等于文件。** 它还可能是外部结果、结构化数据、决定、发布记录或现实世界凭证。
5. **Artifact 需要轻量关系。** 至少要能表达候选、选中、废弃、衍生和作为证据，但首版不建设通用图数据库。
6. **Attention 是 AI 治理核心。** 它需要覆盖补充信息、方向选择、反馈、复核、审批、授权与异常，不只表达“阻塞”。
7. **完成语义由场景定义。** 代码生成、稿件完成、内容发布、结论采纳、旅行执行和持续监测不是同一种完成。
8. **外部动作与内容生成分离。** AI 可以完成草稿或建议，但发布、购买、提交和高风险修改需要明确 Policy 与授权。
9. **项目主页默认呈现异常和下一步。** 大量正常 Run、历史版本和详细证据按需下钻，不占用主要注意力。
10. **桌面与手机拥有同一治理事实，但入口和布局不同。** 现实世界任务尤其不能依赖 hover、宽表和永久双栏。

## 9. 场景驱动的设计裁决规则

后续设计通用字段、对象关系或页面组件时，采用以下规则：

- 一个通用必填字段必须能在全部 A 级场景中自然成立。
- 只服务一个领域的字段默认保留为来源属性，不进入通用治理合同。
- 一个新的通用关系至少应解决两个差异明显的 A/B 级场景问题。
- 一个默认页面模块至少应在多数 A 级场景中提供直接价值；否则按需展开或由项目配置投影。
- 每次修改 Work Item、Run、Artifact、Attention、Policy 或工作流合同，都要重新过一遍 A 级覆盖矩阵。
- 如果场景为了适配模型而必须使用不自然的命名或伪造阶段，应优先怀疑模型，而不是解释场景。
- 如果为了覆盖边界场景导致首版出现复杂配置器，应先保留扩展点和来源属性，不提前实现平台化编辑能力。

## 10. 从场景提取基础能力的方法

### 10.1 为什么先做能力提取

从场景进入能力，再从能力进入产品需求，优于直接列功能清单：

- 场景能够证明一项能力为什么存在，以及缺失时用户会在哪里失败。
- 跨场景重复出现的能力更有资格进入通用底座。
- 只在少数场景出现的能力可以留给来源系统、Plugin、Skill 或专项应用，不必膨胀项目治理模型。
- 高频不是唯一标准。授权、安全、隐私等能力即使只被少数场景强依赖，也可能因为风险而成为基础合同。
- 场景链路能同时检验数据模型、执行链路和用户体验，避免“后端能表达，但用户无法掌控”。

### 10.2 三种需求层级

每个场景对能力的需求应区分：

- **基础必需**：没有它，场景无法形成可信的端到端闭环。
- **体验增强**：没有它仍能完成，但会明显增加用户负担或降低治理质量。
- **领域专项**：只服务特定行业或工具，应通过来源属性、Plugin、Skill 或专用视图扩展。

本轮先提取“基础必需”，避免把理想功能全部算成平台基础。后续设计具体体验时再补充增强能力。

### 10.3 能力进入通用底座的判断

一项能力不能只看场景出现次数，还要同时判断四个因素：

1. **覆盖率**：多少个场景缺少它就不能闭环。
2. **不可替代性**：是否能由现有产品能力自然组合，而无需增加新的通用概念。
3. **风险临界性**：缺少它是否会导致越权、误发布、隐私或不可逆后果。
4. **愿景贡献**：是否增强统一入口、意图到执行、自感知、自治、自进化或生态扩展。

因此，最终基础能力不是二十个场景需求的简单并集，也不是只保留多数票，而是“高覆盖通用能力 + 低频高风险合同 + 可扩展专项入口”。

| C02 | 工作组织与关系 | 创建、拆分、关联 Work Item，表达父子、依赖、阻塞、派生和重复工作，而不绑定某种任务管理方法 | 治理领域 |

### 13.2 不能只按覆盖率裁决

- C07 虽不是 100%，但它保护外部发布、付款、招聘、合同和系统修改，属于低频也不能缺失的风险合同。
- C08 直接体现 NextClaw 的个人操作层定位。没有真实外部接入，项目主页只会成为另一个信息看板。
- C10 是 S20 持续自治的核心，也是 NextClaw 与普通任务管理平台的重要差异，不能因为只覆盖一半场景就被降为无关扩展。
- C12 对桌面研究任务可能只是增强，但对旅行、活动、异常和客户响应是链路连续性的前提。
- C13 不能被简化为“写一篇复盘文档”；它必须支持把经验转化为可追溯的知识、Policy、偏好或 Skill，服务长期自进化。

### 13.3 四层产品能力结构

十三项能力可以按照用户从宏观到细节的使用顺序分为四层：

1. **理解项目**：目标、范围、总体状态、最近变化和下一步。
2. **治理工作**：工作项、流程、关系、执行进展和需要人介入的事项。
3. **检查依据**：描述、产物、来源、规则、决定和活动历史。
4. **保持连续**：搜索筛选、大数据量浏览、自动化、通知、多设备与经验沉淀。

项目主页不需要同时把四层全部铺开。首屏优先“理解项目”和“需要人处理”，工作详情承载治理与依据，连续性能力在数据量或使用阶段达到需要时再出现。

### 13.4 对六个对象的阶段性检验

能力盘点暂未证明需要立即增加第七个通用治理对象，但暴露了几类产品必须能够表达的关系：

- Work Item 需要可选的父子、依赖、派生和阻塞关系，但不必升级为完整图项目管理。
- Artifact 需要版本、候选、选中、废弃、衍生、证据和外部结果关系。
- Attention 必须关联触发它的状态、Run、Artifact、Policy 或外部动作，并记录解除条件。
- Run 需要表达触发来源、执行者类型、结果和用户可理解的状态；Runtime、Session 与工具调用只在有助于用户判断时下钻展示。
- Automation、通知、上下文记忆和 Skill 不是新的治理对象，而是项目主页中的持续运行、抵达和治理能力。
- 如果后续场景无法自然表达“决定”或“项目知识”，再评估 Decision/Knowledge 是否应成为独立对象；本轮先分别投影为 Artifact、Activity、Policy 或项目知识，不提前扩张治理模型。

## 14. 跨场景的通用产品能力设计

### 14.1 “通用能力”在本轮的含义

本轮要回答的不是“底层应该抽象哪些技术模块”，而是：**NextClaw 希望给用户提供哪些稳定、可组合、跨场景成立的项目治理能力。**

判断一项能力是否通用，主要看三个问题：

1. 不同项目中的用户是否都在完成相似任务，例如理解进度、找到产物、处理异常或作出决定。
2. 场景差异是否可以通过名称、类型、流程、关系和展示层级表达，而不必重新制作一套页面。
3. 用户能否直接感知并使用这项能力，而不是只能从内部架构上证明它“很通用”。

因此，六个对象是帮助我们组织产品语义的工具，不是产品设计的终点。真正交付给用户的是项目主页中的概览、列表、流程、详情、产物、待处理事项、活动和操作体验。

### 14.2 十三项通用产品能力

| 能力 | 用户要解决的问题 | 产品应提供的通用体验 | 出现方式 |
| --- | --- | --- | --- |
| C01 项目上下文与意图 | 这个项目为什么存在，现在关注什么？ | 项目名称、描述、目标、范围、当前摘要和关键入口 | 所有项目基础能力 |
| C02 工作组织与关系 | 有哪些事情要完成，它们如何关联？ | 工作项标题、描述、类型、状态，以及可选的父子、依赖、阻塞和派生关系 | 基础列表精简展示，关系按需下钻 |
| C03 流程与状态 | 当前在哪一步，如何到这里，下一步是什么？ | 可选流程图、当前节点、历史流转、分支、跳过、不适用和可执行的下一步 | 简单项目可隐藏，流程型项目展开 |
| C04 推进者与执行进展 | 谁或什么正在推进，最近发生了什么？ | 人、Agent、自动化或外部系统的执行摘要、时间、结果和继续入口 | 工作详情中的“执行”层 |
| C05 产物与证据 | 产生了什么，哪个版本有效，依据在哪里？ | 产物角色、状态、版本、关联工作项和执行；长内容在抽屉或来源页查看 | 摘要列表 + 按需详情 |
| C06 人工介入与决定 | 现在有什么必须由我处理？ | 待确认、反馈、选择、审批、授权、异常和验收；说明原因、影响和建议动作 | 概览主动浮出，详情保留上下文 |
| C07 规则、风险与权限 | 这个项目有哪些边界，哪些动作不能自动完成？ | 规则和 Skills 概览、适用范围、风险提示与授权状态 | 默认弱化，相关时出现 |
| C08 来源与外部动作 | 信息来自哪里，下一步要去哪里完成？ | 明确来源、更新时间、打开来源和可用动作，不把外部结果伪装成本地内容 | 详情中的来源与动作 |
| C09 活动与追溯 | 状态为什么变化，谁做了决定？ | 按时间排列的状态、执行、产物和人工决定记录 | 详情的次级“活动”层 |
| C10 自动化与持续运行 | 哪些事情会持续发生，异常时怎么办？ | 自动化计划、最近结果、下次运行和异常升级 | 项目级入口，普通项目可不出现 |
| C11 视图、检索与规模 | 历史很多时如何快速找到重点？ | 聚焦视图、表格视图、搜索、筛选、排序、分页和 Attention 优先 | 所有大数据量页面的基础体验 |
| C12 多设备与通知 | 离开桌面后还能否理解和处理关键事项？ | 手机单层导航、可追溯通知、状态连续和明确返回路径 | 跨设备体验合同 |
| C13 反馈、知识与能力沉淀 | 这次经验如何让下一次更好？ | 反馈结果、项目知识、规则或 Skill 的来源与演进记录 | 后续渐进能力，不占首屏 |

这十三项不是十三个页签。项目主页应根据用户任务重新组合它们：概览集中 C01、C06 和关键 C10；工作页面集中 C02、C03、C04、C05、C09、C11；产物、文件、Skills 和自动化提供稳定的专项下钻。

### 14.3 通用性的产品机制

产品要适配多种场景，主要依靠以下机制，而不是依靠一个无限配置的“元平台”：

- **稳定骨架**：所有项目共享项目主页、工作项详情、产物详情、Attention 和活动追溯的基本结构。
- **可替换词汇**：通用语义保持稳定，来源可以显示自己的类型和状态名称，例如 Story、研究问题、稿件或设计任务。
- **可选流程**：流程不是每个项目的必填项；需要时可以表达分支、循环、跳过和不适用，不需要时只显示状态。
- **可选关系**：简单任务不展示依赖图；复杂项目才逐步显示父子、阻塞和派生关系。
- **统一详情**：聚焦视图右侧与表格抽屉使用同一份内容，必要信息不因视图变化而缺失。
- **渐进披露**：首屏只回答状态、下一步和需要人处理的事项；描述、流程、产物正文、更多属性和历史继续下钻。
- **场景组合**：软件、研究、内容或旅行通过组合通用能力形成不同体验，不创建互相孤立的专用治理产品。

### 14.4 用代表场景检验产品链路

| 场景 | 项目主页首先回答 | 主要工作链路 | 最关键的通用能力 |
| --- | --- | --- | --- |
| 软件功能开发 | 哪项功能正在推进，哪里阻塞？ | 需求 → 设计 → 实现 → 验证 → 交付 | 流程、执行、代码/文档产物、Review Attention |
| 开放式研究 | 当前问题、证据和结论是否清楚？ | 提问 → 搜集 → 比较 → 形成结论 → 人采纳 | 多轮执行、来源证据、候选结论、人工决定 |
| 文章与内容发布 | 哪些内容待写、待审或待发布？ | 选题 → 提纲 → 草稿 → 审核 → 发布 | 工作状态、稿件版本、反馈、发布授权 |
| 视觉设计 | 当前 Brief、候选方案和选择结果是什么？ | Brief → 探索 → 候选 → 反馈 → 定稿 | 视觉产物、候选关系、抽屉预览、方向选择 |
| 产品发布整合 | 多条工作线是否已经汇合？ | 准备 → 联调 → 审核 → 上线 → 复盘 | 依赖、跨类型产物、授权、完成条件 |
| 旅行规划与执行 | 下一步行程和需要确认的事项是什么？ | 需求 → 候选 → 预订 → 行中调整 | 手机体验、外部结果、选择、付款授权 |
| 持续监测 | 系统是否正常，哪些例外需要处理？ | 持续运行 → 发现异常 → 升级 → 处理 → 恢复 | 自动化摘要、异常 Attention、活动追溯 |
| 个人知识整理 | 什么值得保留，如何归类和复用？ | 收集 → 提炼 → 归类 → 复核 → 沉淀 | 产物关系、人工复核、知识与规则演进 |

检验标准不是所有场景使用完全相同的字段，而是用户始终能够用相同心智完成五件事：理解项目、找到工作、看懂推进、检查产物、处理介入。

### 14.5 产品范围控制

通用产品设计不意味着重做 Linear、Notion、GitHub、文档编辑器和自动化平台的全集。当前明确不做：

- 不提供复杂排期、工时、资源容量、甘特图和团队绩效。
- 不要求所有工作项都有复杂流程、依赖和自动化。
- 不把所有元数据平铺到一张巨型详情页。
- 不为每种行业建立独立导航和专用对象体系。
- 不在首版提供任意字段、任意页面和任意流程的搭建器。
- 不把“有 AI”作为项目主页和治理能力成立的前提。

NextClaw 的重点是让用户在有限注意力下治理由人、AI 和外部系统共同推进的项目，而不是成为最重的传统项目管理软件。

### 14.6 产品阶段建议

#### P0：只读项目治理主页

- 项目概览：目标摘要、最近推进、关键产物和待你处理。
- 工作视图：聚焦 / 表格两种视图，支持搜索、筛选、排序和分页。
- 统一工作详情：标题、描述、类型、状态、流程、执行、产物和活动。
- 流程查看：显示当前阶段、历史、跳过 / 不适用和人工检查点。
- 产物查看：摘要列表、角色与状态；长内容进入抽屉或来源。
- Attention：把需要确认、反馈、审批和异常主动浮出。
- 文件、Skills 与自动化：项目级只读概览和下钻。
- 桌面与手机：不依赖 hover，保持清楚的进入和返回链路。

#### P1：最小治理操作

- 创建和编辑工作项的标题、描述、类型与必要关系。
- 记录人工决定、反馈和 Attention 处理结果。
- 执行来源允许时，提供明确的状态流转与继续动作。
- 将文件或外部结果标记为工作产物。
- 保存常用筛选和项目视图，但不做复杂权限与协作系统。

#### P2：可配置方法与持续项目

- 项目可选择或定义轻量流程、阶段交付物和人工检查点。
- 提供少量代表性项目模板，但模板仍由同一组通用能力组成。
- 加强自动化、持续监测、通知与跨设备处理体验。
- 逐步提供项目知识、规则和 Skills 的演进视角。

## 15. 下一步

1. 以十三项产品能力为候选池，逐一标注八个 A 级场景的“必需 / 增强 / 不需要”。
2. 为八个 A 级场景补完整的界面旅程，检验用户能否用相同心智完成理解、推进、查看产物和人工介入。
3. 根据覆盖结果收敛 P0 的页面内容合同，删除首版不必要的能力，而不是继续增加抽象对象。
4. 用 P0 内容合同更新 HTML 原型，重点检查信息层级、详情下钻、流程、产物和 Attention 是否符合直觉。
5. 技术架构、数据归属和 Agent 如何感知项目治理信息另行讨论，不混入当前产品能力梳理。
