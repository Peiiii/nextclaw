# Bibo 官方托管长期搭档产品讨论

> 状态：产品讨论稿。本文沉淀围绕 `bibo.bot`、官方托管和单一长期搭档形态的当前讨论，不代表已经冻结的产品设计、PRD、商业承诺或实施计划。

## 背景

NextClaw 已将“做好用户的长期搭档”确立为根本使命，并在[从任务型 Agent 到个人数字家园](./2026-08-11-personal-digital-home-positioning.thought.md)中进一步讨论了个人上下文、搭档判断、行动能力和用户主权之间的关系。

当前新的讨论是：在保留 NextClaw 开源、自托管和本地运行能力的同时，是否通过已经持有并托管在 Cloudflare 的 `bibo.bot`，提供一个由官方负责运行和维护的云端产品。用户无需先安装 NextClaw、准备服务器或理解部署细节，即可获得一个持续在线、能够长期了解自己并完成实际工作的个人 AI 搭档。

这一方向受 Grok Bot 等持久云端 Agent 产品启发，但讨论目标不是复刻其多 Bot 产品结构。Grok Bot 官方公开形态包括持久云端电脑、浏览器和终端、网站登录状态、定时任务、用户接管以及多个 Bot 的协作。Bibo 更值得探索的是：能否用更低的用户心智负担，把这些执行能力收敛到一个长期存在、统一负责的个人搭档中。

## 当前讨论形成的核心判断

### Bibo 不应只是“部署在云端的 NextClaw”

把现有 NextClaw 部署到服务器，再增加注册、登录和聊天页面，可以降低安装门槛，但不足以形成清晰的产品价值。用户真正需要的不是一台由官方代为维护的服务器，而是能够放心交付长期职责的搭档。

Bibo 当前可以围绕下面的产品命题继续收敛：

> Bibo 是一个由官方托管、持续在线的个人 AI 搭档。它长期理解用户，拥有可以工作的数字环境，能够在用户离开后继续推进，并从每次合作中学会更好地帮助用户。

这个命题包含四项必须共同成立的能力：

1. **持续在线**：用户关闭网页或设备后，Bibo 仍能等待事件、继续任务和履行定时职责。
2. **长期理解**：理解用户的目标、项目、偏好、关系和当前状态，而不只是保留聊天记录。
3. **完成工作**：能够进入经过授权的服务和工作环境，交付可以检查的真实结果。
4. **持续改进**：从用户纠正、执行结果和重复工作中形成更适合该用户的做法。

云端计算、浏览器和持久工作空间是支撑这些体验的基础设施，不应单独成为产品定义。

### 一个用户只需要一个 Bibo

当前讨论已经明确倾向：首发产品不需要创建或宣传多个 Agent。用户不应承担“创建什么 Agent、任务交给谁、Agent 之间如何交接、谁拥有什么上下文”等内部编排成本。

推荐原则是：

> 一个用户，一个 Bibo；多个对话、任务、职责和工作空间，但始终是同一个搭档。

产品身份和内部执行需要分开：

- 对用户负责的产品身份只有 Bibo。它拥有连续的关系、统一的表达和长期理解，并对最终结果负责。
- 内部可以按任务调用不同模型、工具、浏览器会话、代码执行器或临时 Worker，也可以并行完成多个步骤。
- 内部执行单元默认是临时、可替换和无独立长期人格的，不要求用户理解或管理。
- 所有执行结果回到 Bibo，由 Bibo 结合用户背景解释、检查并交付。

这不是简单减少首发功能，而可能成为长期产品原则。Bibo 的差异不在于让用户管理一支 AI 员工团队，而在于让用户拥有一个逐渐熟悉自己、可以独立调度能力的长期搭档。

## 产品关系模型

“一个 Bibo”不等于“一个无限延长且混合所有内容的聊天”。产品上保持统一身份，系统内部仍需清晰区分不同范围的上下文和权限。

当前可使用下面的对象帮助后续讨论：

| 对象 | 当前含义 | 是否需要首发直接暴露 |
| --- | --- | --- |
| Bibo | 用户长期面对的统一搭档身份和最终责任方 | 是 |
| Understanding | 对用户、目标、偏好、项目和当前状态的持续理解 | 部分暴露，并允许查看和纠正 |
| Conversation | 用户与同一个 Bibo 围绕某个主题进行的交流 | 是 |
| Task | 一次有目标、进度、结果和结束条件的具体工作 | 是 |
| Responsibility | Bibo 长期承担的关注、跟进或执行职责 | 是，但名称和交互待定 |
| Workspace | 文件、浏览器、终端、应用和执行结果所在的持久环境 | 部分暴露 |
| Connection | 邮件、日历、GitHub、云盘或网站登录等授权能力 | 是 |
| Worker | Bibo 内部为完成工作临时启用的执行单元 | 默认不暴露 |

其中值得重点探索的是 `Responsibility`。任务回答“这一次要完成什么”，职责回答“以后哪件事情由 Bibo 持续关注或负责”。例如：

- “分析这份竞品报告”是一次任务；
- “持续关注这些竞品，只有出现会影响我产品方向的变化时再告诉我”是一项长期职责。

长期职责可能是 Bibo 将一次成功协作转化为长期关系的关键产品对象，也比单纯增加定时任务更贴近用户意图。

## 用户可感知的产品结构

Bibo 的核心界面不宜只是一组聊天记录。用户需要同时理解 Bibo 在想什么、正在做什么、已经承担什么，以及它目前怎样理解自己。

可以继续探索以下入口，但当前不视为已经确定的信息架构：

| 入口 | 回答的用户问题 |
| --- | --- |
| 对话 | 我和 Bibo 正在讨论什么？ |
| 任务 | Bibo 当前正在替我完成什么，进展如何？ |
| 职责 | 哪些事情已经长期交给 Bibo？ |
| 理解 / 记忆 | Bibo 目前怎样理解我，哪些地方需要纠正？ |
| 工作空间 | Bibo 保存了哪些文件、网页和工作成果？ |
| 连接 | Bibo 可以访问哪些服务，权限范围是什么？ |
| 活动记录 | Bibo 做过什么、依据是什么、结果如何？ |

这些入口不是不同 Agent，而是同一个 Bibo 的不同观察面。

## 建议探索的首次使用闭环

首发体验不应从“创建第一个 Agent”开始，而应让用户直接见到自己的 Bibo。

### 1. 建立最小的相互理解

Bibo 通过简短交流了解用户目前主要在做什么、最希望获得什么帮助、哪些行为必须先询问，以及用户希望它多主动。这里不要求用户一次完成详细档案，后续应能通过正常协作逐步补全和纠正。

### 2. 完成一件真实、可检查的工作

用户连接一种服务，或者提供一个网页、文件或项目。Bibo 在较短时间内返回有证据、可检查的结果。首个任务需要证明它不只会回答，而是能够进入真实工作环境并完成事情。

### 3. 用户离开后仍能继续

任务不依赖网页持续打开。用户离开后，Bibo 可以继续工作，并在完成、失败或需要决定时通知用户。用户回来后能够看到结果和必要的过程依据。

### 4. 将成功做法转成长期职责

完成一次任务后，Bibo 可以提出具体且克制的延续建议，例如每周检查一次同类变化，并只在出现真正影响用户目标的内容时通知。是否建立职责由用户决定。

### 5. 在下一次合作中证明自己学会了

Bibo 在后续任务中使用已经确认的判断标准、偏好和背景，并让用户能够理解这些信息如何影响了结果。用户应该实际感受到“它更懂我了”，而不是只看到系统声称保存了记忆。

这一闭环可以概括为：

```text
认识用户
  -> 完成一件真实工作
  -> 用户离开后继续推进
  -> 交付可核验结果
  -> 经用户同意承担长期职责
  -> 下一次使用已有理解做得更好
```

## 云端运行形态的方案空间

### 方向一：每位用户拥有长期运行的完整虚拟机

优点是产品隐喻直观，浏览器、桌面、文件和登录状态容易持续保留，用户也可以随时接管。主要问题是固定成本高，升级、隔离、安全和容量管理责任较重，不适合未经验证就作为所有用户的唯一资源模型。

### 方向二：每次任务启动隔离执行环境

优点是弹性好、成本更容易控制，任务之间也容易隔离。问题是浏览器登录、桌面状态和长时间监听的连续性更难维护，用户可能感觉每次任务都从陌生环境重新开始。

### 方向三：逻辑持续在线，计算资源按需唤醒

当前更推荐继续研究这一方向：

- Bibo 的身份、理解、职责、事件订阅和任务队列持续存在；
- 文件、必要浏览器状态和工作成果使用持久存储；
- 新消息、定时任务或外部事件到来时唤醒合适的执行环境；
- 需要完整浏览器或桌面时启动较重环境；
- API、检索和轻量推理任务使用成本更低的执行器；
- 用户感受到的是同一个 Bibo 一直存在，不需要理解资源何时休眠或切换。

这里需要继续验证浏览器身份保存、安全隔离、唤醒时延、并发任务、用户接管和成本模型，当前不视为已完成架构设计。

## 执行能力不应只依赖浏览器自动化

真实浏览器可以覆盖缺少 API 的网站，但也会遇到验证码、风控、页面变化、登录失效、速度和执行正确性等问题。Bibo 更适合采用分层执行策略：

1. 有稳定 API 或官方连接器时，优先使用结构化接口；
2. 有 MCP、插件或 Skill 时，使用稳定能力合同；
3. 没有接口或必须使用用户现有登录态时，再使用云端浏览器；
4. 遇到验证码、敏感信息或高风险操作时，交给用户临时接管或确认；
5. 需要用户本地文件、设备或私有环境时，可以通过本地 NextClaw 节点协作。

官方托管不必等同于所有工作都发生在官方云端。长期方向可以是由 Bibo 统一调度官方云、用户设备、用户服务器和外部专业执行服务，而用户仍只与同一个 Bibo 协作。

## 一个 Bibo 仍然需要上下文与权限边界

统一人格不能演变成无差别共享全部上下文和权限。内部至少需要区分：

- 用户层的稳定背景、偏好、目标和协作原则；
- 项目层只在相关项目中使用的资料和历史决定；
- 任务层的执行材料、临时推理和运行状态；
- 连接层的账号、权限、授权期限和可执行动作；
- 敏感信息的可见范围、使用条件和审计记录。

Bibo 在开始任务时应选择相关上下文，而不是把所有历史记录都放入一次执行。任务结束后，也只将经过判断、具有长期价值的信息带回持续理解。

“一个 Bibo”需要对应一个明确的责任 owner，而不是一份无限增长的上下文。

## 信任与控制

用户是否愿意长期把事情交给 Bibo，取决于它能否建立稳定的信任合同：

- Bibo 能说明自己理解的目标、使用的背景和判断依据；
- 用户能看到任务状态，不需要一直盯着执行过程；
- 只有真正需要用户决定时才打扰；
- 发消息、付款、删除数据和修改生产环境等高风险动作具有明确审批边界；
- 失败时能解释失败位置、当前影响和可恢复路径；
- 行动、结果和权限使用可追踪；
- 用户能够纠正、遗忘、导出或迁移长期积累。

长期理解和强行动能力会同时扩大价值与风险，因此审批机制、权限范围和用户主权不是后续企业功能，而是个人产品成立的前提。

## Bibo 与 NextClaw 的关系

当前存在三个方案：

### Bibo 作为 NextClaw 的云服务名称

能够直接继承 NextClaw 的开源技术和社区认知，但普通用户需要同时理解两个品牌。

### Bibo 作为面向用户的官方托管产品，NextClaw 作为开源底座

这是当前更值得继续讨论的倾向：

- 普通用户直接认识并使用 Bibo；
- 自托管用户、开发者和贡献者继续认识 NextClaw；
- Bibo 复用 NextClaw 的 kernel、运行时、Skill、插件、渠道和本地节点能力；
- Bibo 增加账号、托管运行、租户隔离、计费、安全审查和服务保障；
- 两者共享稳定的核心合同，但不要求用户先理解技术关系。

### 将整个产品和开源项目统一更名为 Bibo

品牌最统一，但会带来现有包、文档、社区资产和兼容关系的大规模迁移。在托管产品尚未验证前，没有足够依据承担这项成本。

以上只是方案空间。当前确认的是计划使用 `bibo.bot` 探索官方托管产品，品牌关系尚未冻结。

## 能力扩展的表达

如果坚持单一 Bibo，未来能力扩展也不应默认表现为创建新 Agent。更自然的产品表达包括：

- 为 Bibo 安装一项 Skill；
- 连接一个新的服务；
- 教会 Bibo 一套工作方法；
- 让 Bibo 承担一项新的长期职责；
- 为某个项目建立独立工作空间和权限范围。

市场或生态可以提供 Skill、连接器、职责模板、工作模板和专业知识包。用户感受到的是自己的 Bibo 学会了新能力，而不是需要管理越来越多的智能角色。

## 商业与成本约束

官方托管的持续成本不仅包括模型调用，还包括浏览器、计算、内存、持久存储、网络、日志、安全审查、失败重试和人工支持。产品定义需要与资源模型同时演进。

当前可以继续探索的定价原则是：

- 基础订阅对应拥有一个持续在线的 Bibo；
- 套餐包含一定的工作量，而不是宣传不可控的无限使用；
- 高成本执行在开始前提供可理解的预计消耗；
- 完整云端桌面、长时间构建和媒体处理等资源密集任务可以单独计量；
- 低成本事件监听、职责判断和通知不应长期占用完整计算环境；
- 用户购买的是 Bibo 持续承担职责的能力，而不是难以理解的 Token 数字。

具体计费单位、套餐和价格仍需结合目标用户、基础设施测试和真实使用分布决定。

## 最小产品闭环候选

首个版本不需要同时实现多 Agent、团队协作、工作流编辑器、市场、移动端、录制教学和大量连接器。更值得先证明的是：

> 用户注册 Bibo，建立最小理解，连接一种真实工作环境，交付一项任务；用户离开后 Bibo 仍继续推进，回来时得到可核验结果；成功做法可以经用户同意转成长期职责，下一次执行能够使用已有理解做得更好。

围绕这个闭环，候选首发能力包括：

- 一个持续存在的 Bibo 身份；
- Web 对话入口；
- 可查看和纠正的用户理解；
- 后台任务及明确状态；
- 持久文件和必要的执行环境；
- 浏览器、终端和文件能力；
- 少量与首批场景匹配的连接器；
- 长期职责或定时运行；
- 高风险动作审批；
- 执行证据和最终结果；
- 清晰的用量、成本和失败反馈。

这仍然是候选范围，不代表进入开发。

## 当前共识、推荐倾向与未定事项

### 当前共识

- `bibo.bot` 用于探索官方托管产品。
- Bibo 的目标不是依赖用户自行安装和维护服务。
- 面向用户只需要一个 Bibo，不以创建和宣传多个 Agent 为核心。
- 同一个 Bibo 可以处理多个对话、任务和长期职责。
- 内部可以有多个执行单元，但不把编排责任交给用户。

### 推荐倾向

- Bibo 定位为持续在线的个人长期搭档，而不只是云端任务 Agent。
- 以长期职责连接一次任务和长期关系。
- 逻辑持续在线、计算按需唤醒，作为优先研究的资源模型。
- Bibo 面向普通用户，NextClaw 保留为开源底座和自托管产品。
- 能力扩展优先表达为 Skill、连接、工作方法和职责，而不是新的 Agent。

### 未定事项

- 首批目标用户是独立开发者和创业者，还是更广泛的个人用户；
- 首个最有说服力的真实任务是什么；
- Bibo 应表现出多强的人格感，以及用户如何设定或修正这种关系；
- 长期职责在界面和语言中应使用什么名称；
- 用户理解、项目上下文、任务状态和连接权限的具体数据边界；
- 浏览器状态如何持久化，何时允许用户接管；
- 官方云与本地 NextClaw 如何建立统一身份、授权和任务路由；
- 免费试用、订阅、用量和高成本执行如何计费；
- `bibo.bot` 当前网站需要保留、替换还是逐步迁移；
- Bibo 与 NextClaw 的品牌关系如何向普通用户和开发者分别表达。

## 非目标

- 不在本讨论稿中冻结技术架构、数据库结构或云服务供应商；
- 不把多个 Agent 的数量和协作过程当作产品卖点；
- 不把云端虚拟机本身当作用户价值；
- 不假设所有任务都必须通过浏览器模拟操作；
- 不因官方托管而放弃本地、自托管、开放能力和用户迁移权；
- 不将候选首发范围直接写入路线图或发布承诺；
- 不在产品需求尚未验证时启动 NextClaw 全面品牌迁移。

## 升级条件
