# 个人信息 Mini App 试水思路

> 状态：探索性思路。本文只记录试水范围和判断，不视为正式功能设计或实施计划。

## 背景

NextClaw 正在探索从任务型 Agent 工作台向个人操作系统发展。当前不准备一次性把待办、笔记、日历和收藏深度嵌入主产品，也不预设它们最终一定成为原生一级模块。

更合适的方式是先利用现有 Panel App 与 Service App 能力，把四项功能做成内置 Mini Apps，在真实使用中观察应用形态、数据边界和 AI 介入方式，再决定是否需要全屏化、原生化或进入主导航。

本思路延续[从任务型 Agent 到个人数字家园](./2026-08-11-personal-digital-home-positioning.thought.md)中的个人上下文方向，但将试验范围严格限制在四类用户会主动维护的对象。

## 已确认范围

| 功能 | 当前产品形态 |
| --- | --- |
| 待办 | 独立管理功能 |
| 笔记 | 独立管理功能，基于 Markdown 文件并保持轻量 |
| 日历 | 独立视图，优先连接用户已有日历 |
| 收藏 | 轻量收藏页或筛选视图，暂不建设复杂管理系统 |

其它上下文类型不在本轮范围内。不新增历史事件管理器、人物关系管理器、记忆管理器或大型个人知识图谱。

## 核心判断

第一阶段将四项能力作为内置 Mini Apps 试水，而不是主 UI 原生模块：

- 界面优先使用 Panel App；
- 持久化、查询和外部同步能力由 Service App 承载；
- 从 Apps 入口打开，可以收藏或固定，但暂不进入主导航；
- 数据优先保存在用户控制的本地环境中；
- 先验证实际使用效果，再决定更深度的产品嵌入。

当前倾向是四个独立 Panel App 消费一个共享的个人信息 Service App，避免待办、笔记、日历和收藏各自形成数据孤岛。这个共享边界仍需通过第一个应用验证，不在 thought 阶段冻结完整数据模型。

## 建议试验顺序

### 1. 待办 Mini App

先验证 Panel App 日常交互、Service App 写入、本地持久化、授权体验和轻量 AI 辅助。第一版只覆盖列表、新建、编辑、完成、归档、截止时间和自然语言生成草稿。

### 2. 笔记 Mini App

以 Markdown 文件为事实源，覆盖列表、创建、编辑、搜索和最近打开。不建设块编辑器、复杂知识图谱或第二套私有笔记数据库。

### 3. 收藏 Mini App

覆盖标题、资源引用、备注、收藏时间和简单分类。先验证统一收藏入口的真实使用意愿，再判断是否需要快照、摘要和复杂整理。

### 4. 日历 Mini App

优先连接一个真实日历来源，先做只读议程或日历视图，稳定后再考虑创建和修改。用户日历与 NextClaw Cron 保持不同语义。

## AI 介入边界

试水阶段先让 AI 在 Mini App 内提供轻量辅助，例如解析自然语言待办、整理 Markdown 草稿、提取收藏信息和生成日程草稿。涉及写入时由用户确认。

普通聊天中的 Agent 是否可以直接读取和修改这些数据，属于后续的能力投影、授权与主产品集成问题，不为了第一轮试水提前做重。

## 观察重点

- 用户是否会反复打开这些 Mini Apps；
- Panel App 是否像 NextClaw 的自然组成部分，还是有明显割裂感；
- 右侧面板是否足够，是否需要全屏或独立主入口；
- Service Action 的授权是否影响高频操作；
- 四类数据是否真的需要共享关联；
- 用户是否希望在普通聊天中直接操作；
- 哪一项值得进一步原生化或进入主导航。

## 非目标

- 不一次性建设完整个人信息管理套件；
- 不把所有用户上下文都产品化为独立管理功能；
- 不在第一轮实现复杂跨 App 关系模型；
- 不先做大型数字花园或可视化；
- 不在本文冻结 Mini App 市场、分发包和依赖规范；
- 不承诺四项功能最终都进入主产品一级导航。

## 升级条件

当待办 Mini App 完成真实试用并获得以下证据后，再升级为正式功能设计：

1. Panel App + Service App 能支撑稳定的日常增删改查；
2. 本地数据、升级和卸载边界清楚；
3. 授权交互不会让高频操作不可用；
4. 能判断 Mini App 形态是否足够，还是需要更深度嵌入；
5. 能判断共享 Service App 是否比独立 Service Apps 更合适。
