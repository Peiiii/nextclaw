# Bibo 托管服务代码规范

本文件只约束 `apps/bibo-hosted`，遵循仓库根目录 `AGENTS.md`。2026 年 9 月 25 日的前端重建以此为交付规范。

## Bibo 当前阶段

- Bibo 仍处于从 0 到 1 的产品阶段；在用户明确告知已有必须保留的真实用户或数据之前，不为现有托管演示状态设计兼容层、双写、旧会话迁移或客户影响流程。直接建立目标模型，必要时重建测试数据；这不放宽新数据的正确性、账号隔离和保存失败恢复。
- 当前托管系统是为快速验证做出的 demo 架构，并未固化。后续产品和实现方案必须根据目标能力、开发效率、运行成本和真实链路重新审视现有进程生命周期、数据存储与接口边界；有更合适的方案可以直接替换，不得把当前代码形态当成不可更改的前提。具体取舍记录在对应设计中。
- 任务、日程、笔记和注意力收件箱属于 Bibo 产品能力，优先用文件存储的轻量独立模块实现，不把这些领域语义塞进 NextClaw agent 内核。已有 NextClaw 应用的真实用户不属于上述 Bibo 阶段假设；修改其行为需单独判断。产品决议见[实现前对齐](../../docs/designs/2026-09-25-bibo-personal-agent-implementation-alignment.design.md)。
- Bibo 的领域动作可以有许多，但不得把每个动作无差别注册为 Agent 模型工具。Agent 入口保持少量且渐进加载：已知操作直接调用；需要帮助时可按关键词／领域获取相关操作及用法，也可一次列出全部操作的紧凑目录；不强制获取全量目录或逐动作查询 Schema。网页与 Agent 复用动作 owner，不复制读写实现。

## 技术栈与 owner

- 用户网页只维护 React + TypeScript 源码，使用 Vite 构建。`dist/` 是产物，禁止手改；不再增加原生 JS 页面控制器。
- 会话历史、草稿、请求阶段、账号展示状态统一由 Zustand store 拥有。`@nextclaw/bibo-client` 负责同站点请求、响应类型和 SSE 解析；store 只在服务端提交后更新正式历史，组件不得直接 `fetch`、解析 SSE 或持有第二份对话状态。
- 产品界面从 `@nextclaw/personal-agent-ui` 包根入口导入可复用组件。命名遵循根规则，优先职责与业务语义，品牌强相关边界允许保留品牌名；品牌名称、标记、文案和具体配色由应用传入或覆盖主题。组件包不依赖本 app、Zustand、Cloudflare 或用户凭据。
- 当前对话执行与持久化分布在 Worker/Durable Object、容器和 NextClaw Harness；正式产品可按上面的架构审视重新划分 owner。服务端维护 TypeScript 源码，容器构建时编译为 Node 可运行产物。
- `nextclaw` CLI 只管理本地实例；托管运维不得加入该 CLI。

## 组件封装

- 抽组件的依据是重复交互、稳定视觉语义或独立可验证行为。不要因页面变长就把每个标签拆成组件，也不在组件库里复制业务编排。
- 所有同级操作使用组件库的 `Button` 变体，表单、分段切换、列表行、空状态和反馈使用同一套公共控件；颜色、间距、圆角和焦点反馈来自 token。新增视觉状态先扩展组件库合同，再在页面消费，禁止局部魔法颜色覆盖。
- 链接用真实 `<a>`，动作用 `<button>`；图标按钮有可访问名称与 title；键盘、鼠标和触控完成同一主任务。状态文案来自 `bibo-copy.config.ts`。
- 流式内容只在服务端 `committed` 后成为正式历史；组件只区分临时与已保存状态，不能从文字显示推断持久化成功。

## 验证门槛

- 每次相关修改运行 Bibo Worker、网页、容器三个 TypeScript 检查，Vite 构建，以及真实浏览器桌面/手机的发送、滚动、保存、刷新、失败恢复链路。
- 组件库改动运行自身 `tsc`，并抽查默认、悬停、焦点、禁用、窄屏与长回复。可交互状态由浏览器证据证明，不以静态截图或类名代替。
- 用量约束是单次模型调用、无轮询、无额外在线状态服务；增加后端付费资源前先记录成本与用户收益。
