# Bibo hosted companion

Independent Cloudflare Worker and Container service at `https://app.bibo.bot/`. The existing `bibo-bot` Worker keeps handling `bibo.bot/*`; the previous `bibo.bot/app/*` route redirects to this service. No NextClaw service, account database, or existing Bibo concept-site route is changed.

The React app consumes the hosted API through the private `@nextclaw/bibo-client` package. That package owns same-origin HTTP and incremental SSE decoding; the Zustand store owns pending and saved conversation state. See the package README for its contract and tests.

Operation feedback follows the result: visible updates do not also produce success toasts. Write failures belong to their form, row, inbox action, or individual file draft; read failures retain a page/workspace retry. Saved tasks outside the active filter offer an inline details link, and saved events reveal their date. Undo, clipboard confirmation, saving state, and version-conflict recovery remain available. Screen readers receive committed-state announcements. Run `pnpm -C apps/bibo-hosted smoke:feedback` for desktop/mobile failure-and-retry, filtered saves, edits during saves, conflicts, projects, events, and inbox actions.

Both sides of a chat, inbox bodies and file previews use personal-agent-ui's Markdown host backed by NextClaw's shared parser and preview components. This includes explicit nested list markers, task checkboxes, all four math delimiters, scoped footnotes, Mermaid expansion and zoom, syntax highlighting, and image previews. The host retains its copy controls and HTTPS-only image policy. Run `pnpm -C apps/bibo-hosted smoke:markdown` to verify desktop and narrow-screen reading, clipboard feedback, streamed message identity, and refresh. Set `BIBO_SMOKE_BASE=https://app.bibo.bot` when running `scripts/bibo-markdown-chat.smoke.ts` to exercise deployed assets with mocked API fixtures; this does not replace the authenticated `smoke:live` model and persistence checks.

Markdown file links use the existing resource manager: object URIs, personal-space relative/absolute paths and local `file:` URIs resolve to the same file route. The server alone validates account ownership, saved-file registration and the workspace root. Use `pnpm -C apps/bibo-hosted smoke:resources` to cover file links, previews, refresh, unsafe URI rejection and failure feedback at desktop/mobile widths.

## Local frontend development

From the repository root, run `pnpm dev:bibo:ui` and open `http://127.0.0.1:5188/`. This starts the real React/TypeScript app with Vite hot updates, including source changes in `@nextclaw/personal-agent-ui`. A development-only local API supplies a signed-in preview account, a Markdown conversation, and delayed SSE chunks. Send a message to inspect incomplete Markdown while it arrives, the saving state, and the committed result. Reset clears the in-memory conversation; restarting Vite restores the example. This mode makes no Cloudflare or model requests and needs no credentials.

For integration against a separately running local Worker, start `pnpm -C apps/bibo-hosted dev:worker` and `pnpm -C apps/bibo-hosted dev:proxy` in separate terminals. The proxy mode forwards `/api` to port 8787. The default `dev` command in this package uses the credential-free frontend preview.

## Runtime

- The Worker serves static assets and proxies registration/login to the existing NextClaw account API. It stores the platform session in an HttpOnly cookie. Workspace actions reuse only a platform-verified user ID for at most 30 seconds, bounded by the credential expiry and keyed by its SHA-256 digest in the existing Cache API. Cache failures fall back to fresh verification; logout removes that entry. Account and model/balance checks remain fresh. Revocation can take up to 30 seconds to affect workspace actions; cache hits never extend this interval.
- A named Durable Object and Container are selected from the verified account ID. One container runs one account's `@nextclaw/harness` with a private `NEXTCLAW_HOME`.
- Tasks, projects and events execute directly through `BiboSpaceService` in the account Durable Object, without starting a Container or uploading a home snapshot. Structured state is stored atomically in bounded KV chunks; the structured JSON limit is 32 MiB. Saved task responses update the current UI immediately; overview is reloaded when opened.
- Chat, inbox deliveries and files use the Container as a working copy. Before an operation it receives the latest structured state. After a successful write, its structured state and R2 snapshot pointer commit together. Startup restores the filesystem snapshot, then applies the current durable structured state. First access to an existing account imports its current snapshot once. Failed operations stop the working copy and do not report success.
- Compressed home snapshots exclude configuration, logs, caches, and derived session message projections. Canonical journals and consistent SQLite backups are retained; NextClaw replays journals and rebuilds missing projections after restore.
- The account Durable Object serializes workspace API requests, including concurrent list reads from one page. Container response bodies must be consumed: the Containers SDK releases its activity counter when the response stream finishes. Restore and session deletion consume their internal responses before returning, so idle containers can stop.
- The low-cost first release uses `deepseek-flash` through a Bibo-only model proxy. The proxy explicitly disables DeepSeek's default thinking mode so visible answer tokens start streaming as they are generated; no text replay is used. Tool requests can require multiple model calls, all counted against the same budget. The DeepSeek key stays in a Worker Secret. A separate Durable Object caps model calls at 250 per account and 2,000 across the service per UTC day, with 2,048 output tokens per call. Context budgeting and automatic compaction belong to NextClaw Harness/Kernel; the proxy does not impose the former 128 KiB context cap. A bounded streaming reader stops anomalous transport bodies above 16 MiB, independently of token budgeting. Chat is additionally limited to 100 runs per hour per account, up to five active containers, and a one-minute idle sleep.
- Web search reuses the kernel `web_search` Exa adapter with `type: auto` and relevant highlights. The runner stores only the account token and `https://app.bibo.bot/api/search/exa`; `BIBO_EXA_API_KEY` stays in a Worker Secret. The proxy authenticates the token, fixes upstream options, and reserves a separate atomic search budget in the existing global budget Durable Object: 100 searches per account per UTC day, 1,000 per day across the service, and 10,000 per UTC month, including failed upstream attempts. Each search returns up to 10 results. Query text goes to Exa; the full conversation does not. Search tasks usually use a model call before and after the tool. Built-in identities gain source-citation instructions; customized identities remain intact.
- Clearing the Bibo workspace stops the container and deletes the R2 snapshot and Durable Object conversation state. It does not delete the shared NextClaw platform account.

## Build and deploy

File display follows the existing kernel `show_file` → `uiShowContent` event. The existing Bibo space contribution captures the native file target; the runner forwards it and the Worker releases `show-content` only after storage commits. `@nextclaw/bibo-client` owns event validation and exact `readFile({ path })` reads. The chat store connects this to the existing workspace resource manager and file preview. Bibo adds no separate display bus or preview service; only registered personal-space files can be read. Run `pnpm -C apps/bibo-hosted smoke:display` for desktop/mobile auto-open, source view, close/reopen, failed-save and refresh behavior. `smoke:live` also creates and displays an artifact through the normal browser composer using a real model, then checks desktop/mobile preview and refresh. Use `BIBO_SMOKE_SCOPE=display pnpm -C apps/bibo-hosted smoke:live` for the display chain alone, skipping the independent model and search probes.

1. Use a Cloudflare account on the Workers Paid plan. Ensure the `bibo-user-snapshots` R2 bucket exists and `BIBO_DEEPSEEK_API_KEY` is configured as a Wrangler Secret. Configure `BIBO_EXA_API_KEY` with `pnpm -C apps/bibo-hosted exec wrangler secret put BIBO_EXA_API_KEY`. Keep credentials outside the repository, in the coding tool’s secret store or an owner-only local environment file; never print or commit them. Without the Exa secret, hosted search remains disabled.
2. Run `pnpm -C apps/bibo-hosted tsc`, `pnpm -C apps/bibo-hosted test`, and `pnpm -C apps/bibo-hosted smoke:client`. These cover the Worker, React client, runner, streaming parser, a live SQLite WAL snapshot, and desktop/mobile chat behavior without a deployment.
3. From a clean checkout of the frozen remote `master`, run `pnpm -C apps/bibo-hosted run deploy`. Docker must be running. This command uses Wrangler 4.138.0, which deploys the current Container configuration; the workspace's older Wrangler 4.67.0 fails its observability validation. Wrangler builds and pushes the Docker image.

For frontend or Worker-only changes that leave the runner and Container contract unchanged, use `pnpm -C apps/bibo-hosted run deploy:client` from the same clean, frozen remote checkout. Both deploy commands refuse a dirty checkout or a HEAD that differs from the current remote `master`, checking before the build and again immediately before upload; merge and push the intended release first. The client command builds the client and deploys Worker/static assets with `--containers-rollout none`, preserving the deployed Container metadata without building, pushing or rolling out an image. It requires an already deployed service and must not be used for runner, container configuration or Worker-to-Container protocol changes. See [Cloudflare's deployment guide](https://developers.cloudflare.com/containers/guides/deploy/). Compare the deployed Container image before and after, then verify the assets and inbox layout with `BIBO_SMOKE_BASE=https://app.bibo.bot pnpm -C apps/bibo-hosted exec tsx scripts/inbox/bibo-inbox-layout.smoke.ts`; this uses API fixtures and does not change real inbox messages.

4. After a full deployment, wait for Container provisioning, then run `pnpm -C apps/bibo-hosted smoke:live`. The command reads a dedicated test account from `~/.config/bibo-hosted/smoke-account.json` (or `BIBO_SMOKE_ACCOUNT_FILE`), logs in afresh, verifies its user ID, and keeps the session token only in memory. Create the account once through the normal Bibo email registration flow; store `{"origin":"https://app.bibo.bot","email":"...","password":"...","userId":"..."}` in that local file with directory permissions `0700` and file permissions `0600`. Never commit or print the credentials. The smoke checks model streaming and authenticated Exa highlights, then runs a real search turn with source links and an Agent turn that creates and displays an artifact through first-party file operations. It verifies the R2 commit, refreshed history, parallel workspace reads, and the same artifact in desktop/mobile Files. Tool use can require several model calls within that one turn, each counted against the UTC daily budget. The smoke removes only its own artifact and conversation. Separately verify registration, account isolation, and `https://bibo.bot/` when those paths change.

Run `pnpm -C apps/bibo-hosted smoke:tasks` after provisioning to measure 20 real saves on each desktop/mobile viewport, verify refresh persistence, and remove only marked test tasks. Reports include click-to-saved UI time and `Server-Timing` for authentication and structured persistence. This uses the same protected account file and keeps credentials in memory.

After deploying durable structured state, recover with a forward fix that retains this state owner. Do not roll back to a Worker that only reads R2 snapshots: it cannot see newer task saves. UI-only rollback can retain the current Worker and Container. Retain snapshots and durable state until a data handling decision is explicit.

## Diagnose a failed run

Use the historical query command without opening a browser:

```bash
pnpm -C apps/bibo-hosted logs -- --session SESSION_ID --since 24h
pnpm -C apps/bibo-hosted logs -- --run RUN_ID --since 1h --json
pnpm -C apps/bibo-hosted logs -- --since 2026-09-28T07:09:00Z --until 2026-09-28T07:11:00Z --json
```

Set `CLOUDFLARE_API_TOKEN` in the process environment with Cloudflare permissions for Workers Observability queries and Container application discovery; never pass tokens in arguments. The command can reuse Wrangler's existing OAuth file in memory, but OAuth scopes may not permit historical telemetry queries. A 403 is an authentication/permission failure, not an empty log result. The connected Cloudflare API tool is another browser-free entry to the same `workers/observability/telemetry/query` endpoint.

The command queries both `cloudflare-workers` and `containers`, applies session/run filters at the API when supplied, follows pagination and returns an explicit error if it cannot finish the query. Cloudflare may mark even a short query as sampled; the command returns the available events with `samplingLevel` and `complete: false` in JSON rather than hiding them. Omit session/run filters for older logs, which cannot be retroactively correlated. Retention and previously sampled/missing records cannot be recovered by increasing the query window. No matches do not prove no failures.

New records use `bibo.diagnostic/v1`: `runId` and `sessionId` correlate the Worker, Durable Object, runner and model gateway. Look for `model.rejected/response`, `context.compaction`, `run.failed`, `snapshot.committed`, `run.rollback` and `run.finished.persisted`. A model response records response headers, not stream completion; a streamed HTTP 200 alone does not mean the run succeeded. A run is saved only when the Worker records the commit. `errorCode`, safe error type/code locations, stage, duration and request sizes explain failures without recording prompts, answers, tool payloads, cookies or credentials. Token deltas are not logged. Worker sampling is configured at 100%; Container logs remain enabled. Platform retention still applies.

Run `pnpm -C apps/bibo-hosted test:diagnostics` for transport, error propagation, redaction, snapshot and rollback regressions. Both Worker and Container must be deployed for cross-layer diagnostics to become available; a frontend-only release is insufficient.

For a live reproduction, `wrangler tail bibo-hosted --format json` also streams the new diagnostic events. Check the Container application version with `wrangler containers instances <application-id>` after a deploy; the Worker and Container roll out separately. Reproduce storage failures with the local snapshot test before building another image.
