# 功能设计关

适用于用户可用能力：界面、CLI、SDK、后台自动化、外部集成及跨入口工作流。目标是先让用户判断“这是否是我要的使用方式”，再设计协议与代码。纯内部重构且调用方行为不变时说明不适用，不制造用户界面或旅程文档。

## 1. 冻结用户任务

用一句话写清：谁从哪里进入，为了完成什么，看到什么结果，如何确认成功。区分部署者、日常使用者与接入开发者，仅展开当前有真实任务的角色；“增加字段/API/组件”不是用户任务。

先列现状证据和约束。拟新增入口、身份/权限、存储或工作流时，核查任务涉及的用户与管理角色已有能力，记录实际入口、owner、证据和复用或不复用理由。未检索不能写成不存在；只有局部代码或单张截图时，不声称完整链路已确认。缺少会改变设计选择的证据就返回调查，不以新建实现填补未知。

## 2. 先走通用户链路

在方案技术细节之前，以一个具体故事逐步写出“起点 → 首次可用 → 日常往返 → 结果 → 继续/退出”。每一步交代用户动作、系统响应、用户可见反馈与下一步；系统调用链、功能清单、默认行为表不能替代用户链路。局部改动可用短段落，不强制表格、图或固定步骤数。

多角色或多入口只展开有行为差异的分支，明确交接时谁做什么、在哪看到结果；SDK 接入者和后台任务使用者也有开始与反馈入口。按风险补充必要分支：

| 分支 | 必须回答的问题 |
| --- | --- |
| 首次使用 | 前提由谁准备、从哪个真实入口开始、何时算配置成功、怎样完成第一次任务？ |
| 连续使用 | 用户补充、系统追问、角色交接后从哪里继续，是否保留此前上下文？ |
| 等待与反馈 | 用户如何区分等待、运行、完成、安静处理和失败；离线时能知道什么？ |
| 取消与恢复 | 用户从哪里暂停/退出，失败后回到哪里，何时确实需要用户介入？ |
| 已有用户 | 升级后原入口和数据如何继续，是否需要重新配置或迁移？ |

首次使用链路不能被最终验收脚本替代；必要登录或业务选择归用户，AI 应执行的安装、测试、等待和排障不能被伪装成必需人工步骤。无法自动完成时写明真实环境或授权原因。

## 3. 按链路设计入口与状态

- 每条链路对应到真实或拟新增入口、状态 owner 和验收证据；拟议命令/界面明确未实现，入口缺失要设计，不能让用户猜步骤。
- 有界面时明确默认/空/加载/错误态、浏览与搜索范围、分组、选择、返回；数据规模或设备改变行为时再补分页、键盘与移动端，不机械套完整页面模板。
- CLI 说明用户意图对应的操作和可读反馈；SDK 说明接入者提供什么、启动与关闭什么、从哪里取结果；后台能力说明如何启用、观察和恢复。
- 新增同类资源时指出它只需注册还是必须修改多个消费者，后者证明耦合合理；同一输入应产生可解释的结果。

## 4. 比较真实候选

存在设计空间时比较 2–4 个能成立的方案，至少评价：用户可理解性、完整场景覆盖、owner/耦合、规模化、失败恢复、实现与验证成本。不能把“当前写法加标题/加字段”当作默认最优。

推荐方案必须同时说明：为何最佳、牺牲了什么、何时应改选其它方案。不同选择会实质改变产品语义且证据不足时再请用户决定。

## 5. 设计完成条件

只有以下条件同时满足才进入协议和实现：

1. 至少一条代表故事可从起点走到结果；多角色/多入口的必要分支明确，没有让读者自行补全的操作。
2. 本次相关的默认、动作、等待、返回和关键异常反馈明确；没有无关页面清单或强制人工步骤。
3. producer、状态 owner、consumer 与扩展点唯一。
4. 验收标准从既有产品入口、真实角色身份一路证明到最终用户结果及数据/运行时结果；新增入口必须有必要性依据。AI 代办任务从用户表达意图开始，覆盖工具执行和结果返回原渠道，不能用人工表单、直接调接口、临时页面或专用凭据替代产品主链路。
5. 非目标明确，且不会把本次缺口伪装成非目标。
6. 交付方式与验收标准一起冻结：提供什么可用产物、用户在哪个实际入口做哪些必要判断、看到什么结果，以及环境、授权和耗时前提。长任务可用可追溯的真实完成记录减少现场等待，但预制状态或演练不能证明真实完成；临时页面或专用凭据只证明局部机制。局部成果不能替代整体完成条件。

实现中新现象若改变用户链路，先修设计；只偏离既定行为时直接修实现。
