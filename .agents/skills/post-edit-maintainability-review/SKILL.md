# Post Edit Maintainability Review

## 何时使用

满足任一条件才加载本 skill：

- 自动 guard 有需要主观判断的阻塞或警告；
- 新增、删除或重塑抽象、owner、状态归属、文件/目录边界；
- 改动跨模块、规模较大或可能把复杂度转移到别处；
- 显式启用了 --non-feature 零增长治理合同；
- 用户明确要求可维护性 Review。

普通局部修复、纯视觉调整、测试更新或 guard 无发现的小改动不使用。

## 复核问题

只回答与触发原因有关的问题：

1. 是否还有能直接删除或复用的重复路径？
2. 新增抽象是否减少了真实复杂度，还是只增加名字和跳转？
3. owner、状态、生命周期和文件边界是否更清楚？
4. 复杂度是否被移动到 helper、wrapper、兼容层或统计范围之外？
5. 剩余增长是否是实现目标所需的最小清晰形态？

必要的清晰代码增长可以通过。只有显式零增长治理合同才要求非测试净增 <= 0；不得把这一指标推广到普通 bugfix 或局部重构，也不得为了过线损害可读性、类型或协议安全。

## 结论

使用 findings-first 的短格式：

- 结论：通过 / 需继续修改 / 经说明保留债务；
- 触发原因；
- 发现与更小修正方向；
- 仅在影响判断时报告代码增减或后续观察点。

没有问题时写“无可维护性发现”，并用一句话说明为何不需要继续扩大 Review。

## 反模式

- 复述 guard 的所有数字和未命中项；
- 每次小改都做完整主观 Review；
- 只因代码净增长就扩大到无关模块找删除；
- 用压行数、弱化命名或移除 contract 信号伪造改善；
- 没有触发风险却为了流程完整而继续审查。
