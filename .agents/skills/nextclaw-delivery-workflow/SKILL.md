# NextClaw 标准开发与交付流程

## 定位

本 skill 只编排开发阶段和条件路由，不重复专项规则。目标是用最少但足够的调查、实现与验证完成可信交付。

核心原则：

- 正确性底线不能省；不能排除新风险的重复步骤必须省。
- 专项 skill 按真实触达面加载，不组成默认全家桶，也不因阶段切换重复读取未变化内容。
- 低风险任务保持短路径，高风险任务才逐级增加设计、复现、边界测试和真实冒烟。

## 1. 目标与风险分级

开始前只需明确：

- 一个可观察结果；
- 当前改动的最近 owner 和影响面；
- 最小可信验证；
- 风险等级。

风险等级：

- L0：文档、措辞、元信息。
- L1：局部、低风险、合同清晰的代码或纯视觉调整。
- L2：交互、状态、局部业务行为或明确 bugfix。
- L3：跨 owner/transport、持久化、兼容、运行链路或高回归影响。
- L4：发布、迁移、生产变更或不可逆操作。

复杂 debug 才用 long-chain-debugging；跨轮或易漂移才用 iteration-work-notes / goal-progress-anchor；不要为短任务预建过程文档。

## 2. 调查与设计

- L0-L1：直接调查最近链路，不写设计文档。
- L2：确认 producer、owner、consumer 和成功条件；根因不确定时冻结一份修前证据。
- L3-L4：使用 nextclaw-solution-design；涉及架构、交互、目录、fallback 等再加载对应专项 skill。

任何新增调查都必须回答一个会改变实现或验证决策的问题。已经确认且未变化的长文件、skill、日志和命令输出不得无理由重读。

## 3. 实现

源码修改前使用 nextclaw-clean-implementation，但只回答与当前改动有关的问题：

- 能否删除、复用或收敛已有路径；
- owner 是否正确；
- 是否新增不必要的分支、fallback、wrapper 或第二入口；
- 文件落点是否变化。

清晰、安全、最小的必要代码增长允许存在。禁止为了抵消行数扩大到无关模块、削弱类型/协议保护或制造额外重构。

只有新增、重命名、移动文件，或改变角色/目录边界时，才运行 planned-path governance preflight。局部修改现有文件不为仪式重复跑空检查。

## 4. 验证

使用 nextclaw-validation-workflow 选择验证等级：

- 迭代中只跑最快、最贴近当前失败面的定向证据；
- 实现稳定后统一做一次收尾验证；
- 同一风险已有权威证据后，不再叠加等价测试、浏览器路径或截图；
- 每增加一项验证，都要说明它新排除了什么风险。

纯视觉与主观审美由 AI 证明页面正常渲染，用户做最终偏好确认；交互、状态、数据、协议和持久化正确性仍由 AI 验证。

## 5. 可维护性收口

源码、脚本、测试或运行链路配置改动完成后，运行一次 post-edit-maintainability-guard。

只有以下情况才继续加载 post-edit-maintainability-review：

- guard 出现阻塞或值得判断的告警；
- 新增/调整抽象、owner、文件或目录边界；
- 改动跨模块、规模较大或维护风险明显；
- 用户明确要求主观复核。

普通局部修复不再默认执行“自动 guard + 主观 review + 强制行数抵消”三重收口。

## 6. 流程反思

收尾前内部回答四个问题：

1. 是否读取了与当前决策无关或未变化的长上下文？
2. 是否有工具调用、验证或 Review 只是重复证明同一件事？
3. 是否有强制步骤对当前风险没有新增信息，可以改成条件触发？
4. 下次能否用更短路径保持同等可信度？

只有发现可复用、反复出现且影响明显的问题时，才用 learning-from-failures 和 nextclaw-agent-instructions-governance 更新规则、skill 或自动化。没有机制缺口时只结束任务，不为完成复盘新增文字或文件。

## 7. 留痕、提交与发布

- 只有提交/发布、跨模块或长链路批次、重要根因修复、红区触达、大规模治理重构才使用 nextclaw-iteration-log-governance。
- 只有用户可感知且需要发布的变化才使用 release notes / changeset 流程。
- 用户未要求时，不提交、不推送、不发布。

## 最终汇报

只报告与当前风险和结果有关的内容：

- 结果；
- 关键验证及结果；
- 未验证或需要用户主观确认的部分；
- 触发时的可维护性、流程改进、迭代或发布状态。

不要罗列对结论没有帮助的命令历史、所有跳过项或仪式性“不适用”。

## 反模式

- 小改动自动加载所有专项 skill。
- 每次修改后重复跑完整验证。
- 用组件测试、浏览器操作和截图重复证明同一风险。
- 为满足行数指标扩大无关改动。
- 每个 bugfix 都新建迭代日志或修改治理规则。
- 为优化流程再新增一套平行流程。
