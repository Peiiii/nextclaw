# 验收契约方法

## 建立整体契约

先基于已确认的用户目标与事实写最小整体契约；未知项明确标记，不用猜测补齐。

1. **最终结果**：一句话描述用户最终能完成什么，而不是列实现组件。
2. **必须成立**：只保留缺失后用户会认为“没有交付完整”的结果、关键链路与产品能力。
3. **必须不发生**：只记录本任务真实高风险的退化、漂移、数据损坏、安全越界或错误兼容。
4. **架构不变量**：只约束 owner、数据/事件归属、公共 contract 或单一路径等长期意图；不锁定可替换的临时实现。
5. **代表性场景**：用少量真实用户任务覆盖主要机制、数据状态、失败边界和适用生命周期；不按 API 数量机械穷举。
6. **交付边界**：区分本地可交付、安装/升级、发布/部署和需要授权的外部动作。
7. **真实边界**：只记录用户明确排除、与最终结果无关、需要新增授权或受外部条件阻塞的内容；AI 不得为了让任务有限而自行制造“本轮非目标”。

### 完成边界、阶段切片与授权边界

大型任务必须分开维护三件事，禁止相互替代：

- **最终完成边界**来自用户想得到的结果和 AI 被委托负责的产品方向。用户把一个方面交给 AI 时，默认包含当前能够独立完成的产品、架构、实现、体验、生命周期、文档、打包与验证闭环，而不是只包含最先出现的任务清单。
- **阶段切片**只决定先后顺序和当前工作量。阶段完成只能表述为“该阶段完成”，不得据此把整体目标改称完成，也不得把后续仍可实施的工作放入“未来”后结束任务。
- **授权或外部边界**只暂停相应动作。commit、发布、部署等需要授权时，先完成其余可做工作并把产物准备到可执行状态；不得把“尚未获准执行外部动作”扩张成整个产品方向的缩减。

`MVP`、`本轮`、`非目标` 或 `后续再做` 不能由 AI 单方面用来降低用户结果。只有以下情况才能排除一项工作：

1. 用户明确排除或限定；
2. 证据表明它与最终用户结果无关；
3. 它需要尚未获得的外部授权、凭据、硬件或第三方状态；
4. 新事实证明继续建设没有产品价值，并形成明确的停止或缩小决策。

当用户表达“你负责这个方面”“能做的都做掉”或同等委托时，每次阶段收尾必须追问：**在不需要用户新增输入和授权的前提下，我现在还能继续闭合什么？** 只要答案非空，就只能报告阶段进展，不能报告整体完成。

验收标准定义“什么必须被证明”，Validation 决定“用什么证据证明”。不要复制测试命令或阶段 owner 的通用清单。

## 标准质量过滤

每条候选标准必须同时通过：

- 如果它不成立，用户是否会合理地认为任务未完成？
- 它是否对应当前任务真实可能出现的失败，而不是泛化想象？
- 它是否可通过行为、状态、产物或边界证据判断？
- 它是否保留合理实现空间，没有把临时方案写成永久合同？

再做删除测试：**删掉这条后，哪个现实中的坏结果会被错误放行？** 无法回答就删除。仓库常驻规则、一般 AI 不会遗漏的常识和与当前任务无关的最佳实践不要重复写入。

## 分阶段与即时阶段门

大型任务先画粗粒度阶段图，不在第一天设计完所有阶段细节。每个阶段交付一个可独立判断的纵向结果，力度足以让 AI 高效工作，但不混合两个彼此独立的重大未知。

每个阶段开始时，基于最新证据即时写阶段门：

- 本阶段结束时新增的可观察结果；
- 必须保持的整体契约和架构不变量；
- 覆盖该结果的代表性成功、状态恢复或失败场景；
- 本阶段暂不处理但仍属于整体目标的内容；
- 进入下一阶段前必须关闭的缺口。

阶段结束时只更新受新事实影响的后续阶段，不重写已经稳定的整体契约，也不把“写完代码”当作阶段完成。阶段门中的“暂不处理”不能进入最终完成声明的排除项。

## 学习与漂移控制

实现中出现新发现时必须归类：

- 当前验收必需：加入当前阶段并说明遗漏原因；
- 原标准被事实证明错误：修改契约，记录证据、影响与理由；
- 有价值且属于最终结果：放入后续阶段并保持为未关闭；
- 有价值但与当前委托无关：只有通过真实边界条件时才排除；
- 与目标无关：丢弃，不因已经发现就扩张范围。

不得静默改变最终结果、架构不变量、代表性场景或交付边界。设计学习可以改变实现，不能悄悄改变用户得到的结果。

兼容、fallback、重试或 legacy 保留只有在同时写明当前消费者、为何不应显式失败、可观察方式和退出条件时才能进入契约；否则优先单一路径和明确失败。

## 一次契约 Review

整体契约和每个阶段门各做一次针对性 Review：

- 是否可能所有条目都通过，用户仍明显只拿到 80% 的结果？
- 是否由 AI 自己选择了 `MVP`、单平台或单链路，然后把其它仍可完成的产品工作写成非目标？
- 当前还有哪些无需用户新增输入或授权就能继续完成的工作？若存在，整体状态必须保持未完成。
- 是否漏掉与当前产品真实相关的数据、权限、恢复、安装、升级、卸载、失败或 Agent 调用链路？
- 是否有条目只是重复项目规则、与任务无关或几乎不可能出错？
- 是否把临时实现、未来平台愿景或主观偏好误写成硬约束？
- 是否引入没有当前消费者的兼容层、兜底或扩展点？

只修正能改变完成判断的问题，不进行无上限自我辩论或反复改写。

```markdown
# 最终结果

## 整体验收契约
- 必须成立：
- 必须不发生：
- 架构不变量：
- 代表性场景：
- 交付边界：
- 真实边界：

## 阶段图
| 阶段 | 可验收结果 | 进入下一阶段的门 | 状态 |

## 当前阶段门
- 结果：
- 保持项：
- 场景：
- 本阶段不做：
- 待关闭缺口：

## 新发现与契约变更
- 事实 / 影响 / 决定 / 理由：

## 尚未关闭
- 仍可实施的缺口、未验证边界、真实外部阻塞或待授权动作：
```

契约形成后明确说明被删除的主要噪声标准及原因。契约足以支持下一阶段做明确决策后退出。
