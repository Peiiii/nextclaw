# 开发体系演进闭环

本参考把有效反馈转化为最小、可验证、可回退的体系改进，不是第二套开发生命周期。实际修改规则、Skill、脚本、文档或代码时，仍走标准开发流程。

涉及一级架构、职责边界或新增机制时，读取[AI 驱动开发体系架构](../../../../docs/designs/2026-08-29-ai-driven-development-system-architecture.design.md)；局部规则修正不为此加载整份设计。

产品交付优先。当前产品任务尚未达到最小完整结果时，先把缺口返回对应阶段；不能用“体系已经学到经验”替代未完成的用户结果。

## 有效触发

- 用户明确要求优化或落地 AI 驱动开发体系；
- 用户纠偏揭示重复、系统性或高影响的机制问题；
- 有证据的规则漂移、错误路由、交付不完整、无效消耗或模型能力补丁失效；
- 模型、工具或运行时变化使既有规则可能已经多余或有害。

一次性偏好、没有证据的设想、普遍正确但不可执行的口号，或普通实现偏差，不触发长期改进。

## 闭环

1. 记录用户反馈、任务结果、失败证据和可用 telemetry，不重放无关上下文。
2. 区分纠错、补充约束、新需求、偏好变化和长期原则。
3. 判断缺口属于产品实现、测试/脚本、阶段合同、规则路由、上下文组织，还是一次性执行偏差。
4. 写清根因、当前 owner 为什么未阻止、最小改动、触发条件、反例、质量收益、Token/延迟成本、副作用和回退方式。
5. 可确定行为优先测试或脚本；规则资产留在自然 owner；项目知识按知识治理分流。
6. 证明候选能阻止目标失误且不扩大无关任务成本；不能证明净收益时收窄、回退或不落盘。
7. 最终选择保留、提升、下沉、合并、自动化、收窄、回退或删除，不能默认永久累积。

输出有效反馈与证据、结构根因、最小候选、单一落点、验证/回退方式和生命周期决定。不创建独立平台、数据库、仪表盘或平行编排器。
