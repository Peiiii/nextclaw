# 上下文与 Token 治理

目标是在不降低结果可信度的前提下，让规则、证据和工具输出只在能改变当前决策时进入上下文。

## 分层加载

判断 skill 数量、description、路径或发现预算前，先读取 Wiki 的[Codex Skill 发现机制](../../../wiki/knowledge/codex/codex-skill-discovery.md)，区分官方事实、仓库代理指标和当前会话观测。

- `AGENTS.md` 只保留每轮必需的内核规则；
- 顶层 Skill 只保留必须参与初始发现的 workflow root、阶段或独立任务入口；
- 单 owner Reference 和跨入口下级 Wiki Skill 都必须有具体加载条件，不能作为默认全家桶；
- Wiki knowledge 只按当前问题检索事实，不因命中而获得指令或授权；
- 测试、脚本和 CI 承担可确定检查，避免每轮让模型重新推理；
- Docs 保存背景与历史，入口没有明确链接时不自动加载。

同一判断只保留一个当前 owner 和一个直接下游。已经完整读取且未变化的文件不重读；阶段尚未进入时不预读未来阶段。

## 运行时节流

- 每次读取、搜索、实验或多方案比较前，先说明它会改变哪个决策；无法回答就不执行；
- 优先结构化状态、定向片段和失败附近的最小日志，不读取成功全量日志；
- 复用仍有效的证据，只在事实源变化、证据冲突或当前决策需要更高证明等级时重验；
- 长期工作把稳定事实、决定、未决风险和精确链接压缩到工作记录，不复制大段原文；
- 并行只有在等待或独立取证的净收益高于协调、重复上下文和合并成本时才采用。

## 规则正则化

新增规则前先尝试删除、合并、收窄、下沉或自动化现有内容。评估净价值时同时检查：

- 质量：是否降低目标失误、方案偏差或交付缺口；
- 覆盖：是否能覆盖一类相邻场景，而非单个案例；
- 成本：常驻字节、命中频率、额外读取、工具调用、延迟和维护负担；
- 副作用：误触发、过度设计、保守兜底、重复 owner 或路径漂移；
- 可退场性：能否定位、测试、下沉或删除。

只增加文本而不减少失误，或收益无法覆盖上下文与执行成本时，不保留该规则。治理检查同时衡量名称、description、路径组成的 discovery 代理和入口正文体积；不能只压缩 description、放宽数量上限或凭主观感觉宣称节省 Token。
