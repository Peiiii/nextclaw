# 从失败中学习

## 目标

把反复、可复用、高影响的失败转成能自动触发的机制改进；一次性细节只修当前任务，不制造新规则。

## 判断门槛

同时回答：

1. 这是重复问题、系统性缺口或高影响单次事故吗？
2. 现有 owner 本应阻止它却没有阻止吗？
3. 改进能覆盖一类问题，而不只是用户这句话或某个文件吗？
4. 新机制的触发成本和误报是否低于问题损失？

任一答案不足时，记录当前修正即可，不进入治理修改。

## 分层复盘

- 表层症状：用户看到了什么。
- 直接触发：哪一步判断或执行出错。
- 结构根因：owner、路由、合同或验证为何允许它发生。
- 机制缺口：现有规则是缺失、重复、触发过宽、触发不到还是不可执行。

## 落点

- 每轮必须知道的安全硬约束：AGENTS。
- 特定场景流程：已有 skill；没有稳定 owner 时才考虑新 skill。
- 条件细节和长例子：reference。
- 高信号、低误报的确定性问题：扩展已有通用脚本，避免窄脚本。
- 人类背景或一次性复盘：docs/logs 或对应知识文档。

修改规则系统时再加载 `nextclaw-agent-instructions-governance`。规则更新应优先删、并、收窄触发，不用追加新层掩盖旧 owner 问题。

## 输出

说明重复模式、证据、现有 owner 为什么失效、选择的持久化层和验证方式。没有达到机制门槛时明确“不新增规则”。
