# 发布机制的版本演进门

仅维护 workflow、打包、恢复链路或修复发布失败时读取。目标是下一次正常版本演进仍能自动闭环，而不只是把当前版本补到通过。

- 配置、预算与产物身份消费现有 owner 的结构化接口；不依赖源码文本、声明位置、日志措辞或某个版本字符串来重写发布输入。历史迁移只有在仍有受支持消费者、明确边界、测试和退出条件时保留，不能积累永久补丁。
- owner、文件或配置迁移时，核对 build、verify、publish、recovery 的实际消费者，同步删除失效适配；不能只改生产代码，却把旧假设留在 workflow。
- 不可变产品 target 与可后补内容分别绑定明确来源。新控制流程可恢复旧产物，但不能移动既有 tag、混入新产品源码或重复 publish 掩盖来源错误。
- 验证覆盖当前失败及对应的真实演进场景：配置迁移后消费者仍使用同一 owner、内容晚于产品提交、旧产物由当前入口恢复。无需为无关场景扩大矩阵；仅断言某段补丁文本存在或当前版本通过，不足以证明机制稳定。
- workflow 先过静态检查，再跑最窄真实合同；确定性错误明确失败，瞬态故障才按既有有界恢复合同处理。禁止无限重试、放宽验证或把人工拼步骤伪装成自动化。
- 每次 owner 外介入都修回 owning entry 并记录回归证据，保留已成功 checkpoint。只有 artifact、公开投影、升级验证和 Git 闭环全部成立，才报告自动发布完成。

反例：平台确实不支持某种产物时应明确拒绝，不为“抗脆弱”新增猜测路径；仍受支持的历史产物需要显式迁移合同，不按新目录假设强行读取。

若后来接口和测试已完整覆盖某条判断，收窄或删除对应文字；不为单次事故新增常驻规则、独立治理脚本或第二套发布器。
