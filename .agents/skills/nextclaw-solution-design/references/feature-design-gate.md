# 功能设计关

适用于用户可见功能、信息架构、入口、浏览/搜索、选择、反馈或跨页面工作流。目标是先证明功能闭环，再设计协议与代码。

## 1. 冻结用户任务

用一句话写清：谁从哪里进入，为了完成什么，看到什么结果，如何确认成功。区分用户目标与实现手段；“增加字段/API/组件”不是用户任务。

先列现状证据和约束。只有局部代码或单张截图时，不声称完整链路已确认。

## 2. 建立功能地图

按当前功能相关性覆盖以下场景，不机械扩写无关项：

| 场景 | 用户看到什么 | 可执行动作 | 状态/数据 owner | 失败或返回路径 | 验证证据 |
| --- | --- | --- | --- | --- | --- |
| 首次进入 / 默认态 | | | | | |
| 浏览 / 分组 / 层级 | | | | | |
| 搜索 / 筛选 / 排序 | | | | | |
| 选择 / 提交 / 反馈 | | | | | |
| 空、加载、错误、无权限 | | | | | |
| 返回、取消、重进、刷新 | | | | | |

数据量、多类型或扩展注册会改变体验时，再补：大数据分页/限流、类型间公平性、重复项、过期对象、键盘与移动端路径。

## 3. 先设计信息架构

- 默认态用于发现和导航，搜索态用于定位；不要让大量结果淹没入口。
- 用户心智中的类别、层级和名称必须可见；不能只在后端存在类型、前端却混排。
- 明确全局搜索与组内搜索、进入与返回、动作项与导航项的语义。
- 新增同类资源时，指出它只需注册还是必须修改多个消费者；后者需要证明耦合合理。
- 检查同一输入是否产生可解释的同一结果，避免不可见上下文或隐式副作用。

## 4. 比较真实候选

存在设计空间时比较 2–4 个能成立的方案，至少评价：用户可理解性、完整场景覆盖、owner/耦合、规模化、失败恢复、实现与验证成本。不能把“当前写法加标题/加字段”当作默认最优。

推荐方案必须同时说明：为何最佳、牺牲了什么、何时应改选其它方案。不同选择会实质改变产品语义且证据不足时再请用户决定。

## 5. 设计完成条件

只有以下条件同时满足才进入协议和实现：

1. 功能地图没有依赖“以后再补”的主路径缺口。
2. 默认、搜索、导航、动作、返回和关键异常的可见行为明确。
3. producer、状态 owner、consumer 与扩展点唯一。
4. 验收标准能从用户表面一路证明到数据/运行时结果。
5. 非目标明确，且不会把本次缺口伪装成非目标。

实现中新现象若改变功能地图，先修设计；只偏离既定行为时直接修实现。
